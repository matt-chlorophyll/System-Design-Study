第 3 周 · 分布式与异步 · 复习

消息会重、会乱,节点会假死——
这一周教系统把这些都变「无害」。

前两周的系统基本还是同步、单库的:请求来了当场算完返回。可一旦要解耦、要削峰、要跨服务、要多节点,就必须异步。异步立刻换来弹性,也立刻欠下三笔账:消息会重复(at-least-once)、会乱序、多节点会假死双跑。第三周就是逐一驯服这些——而那块把所有「重来」变无害的地基,是一个词:幂等。先看清把这 7 天缝起来的贯穿线,再逐天回看。

🟡 线 1 · 黄金线:幂等——把每一次「重来」变无害的地基

D15D16D17D18D19D20D21

这是整周连得最多的一根线。文档原话:幂等不是某一天的知识点,是整个分布式异步周的底座。它的精确定义——同一操作执行 N 次,对系统状态的最终效果 == 执行 1 次;它保护的是副作用(写 / 扣款 / 出账),不是计算(纯函数算几遍无所谓)。

出现在这一天它兜的是哪一段「重」
Day 5(伏笔)幂等第一次出场:HTTP 方法的幂等性(GET/PUT/DELETE 幂等、POST 不幂等)。
Day 15队列 at-least-once 投递 → consumer 必须幂等;「来一条处理一条」崩了重投会重复。
Day 16Kafka 重复消费 / offset 重置 / replay 都靠幂等消费兜底;Kafka 自带「幂等 producer」(PID+seq 去重)。
Day 17夜间重定价崩溃重跑 = 幂等(upsert 覆盖写)+ checkpoint;「安全重跑」缺一不可。
Day 18主菜:收束成一条防线,点破 exactly-once = at-least-once + 幂等 = effectively-once;两种实现 upsert / 去重表。
Day 19Raft 状态机重放同一条日志必须幂等才不会越加越多;选主挡不住假死双跑,幂等兜那段窗口。
Day 20重试风暴是雪崩头号放大器 → 退避+jitter+重试上限;熔断从根上掐断 retry storm。
这根线的总纲(对你的 pricing engine)
  • QuoteFlow 里有三处副作用各需一道幂等闸:实时报价 API(POST,前端可能重试)、夜间重定价(崩溃重跑)、billing 扣款(消息重投)。记牢两种实现的分水岭——副作用可不可覆盖:可覆盖(改保单字段)→ upsert,连去重表都不要;不可覆盖(追加一笔扣款)→ 去重表 + idempotency key(且登记 key 与副作用必须同一事务)。一句话:batch 重算 → upsert;扣款 / 发消息 → 去重表 + key。

🔴 线 2 · 不可能定理的收口:别在「投递 / 选主」层求绝对,去「处理 / 资源」层兜底

D18D19

这是本周最深的一层认知,也是线 1 的理论根基——为什么我们必须用幂等,而不是想办法把消息「只发一次」。

  • Day 18 · 两将军困境:在会丢消息的信道上,不存在能在有限步内保证双方达成一致的协议(对「最短协议」反证:最后一条消息没人确认 → 删了它仍成立 → 一路砍到 0 条,矛盾)。结论不是「没救」,而是 别在投递层求确定性——改成 at-least-once 投递 + 幂等消费,把不确定性挪到能驯服的处理层。
  • Day 19 · 逻辑唯一 ≠ 物理唯一:选主只保证「同一刻多数派认一个 leader」,管不住一个假死的旧 leader 在租约过期前物理上还在写。重复的根源不是「重试」,是假死双跑。同样要去资源层兜底:幂等(让重叠写无害)+ fencing token(令牌单调递增,资源直接拒掉旧写)。

两天是同一句话的两种形状:分布式系统给不了「绝对只发生一次」这种保证,工程的智慧是承认它、然后在能控制的那一端(处理 / 资源)把重复变无害。Kafka EOS 里的 producer epoch、Raft 的 term,都是 fencing token 的同一思路。

🟢 线 3 · append-only 日志:第二周的金线,这周长成了主武器

D16D17D18D19

第二周「不可变 / append-only」那根金线没断,这周它从「建模选择」升级成系统的核心数据结构:一串只追加、可重放的日志。

在append-only 日志在这里干什么
Day 16Kafka 就是一串磁盘上的 append-only segment 文件;event sourcing 把日志当唯一真相源——审计与行为同源、构造上不可能各说各话。物理上「日志」不是比喻,是真在往文件尾巴写。
Day 17ELT 留底原始数据(先 Load 再 Transform)= 呼应 replay 精神:改口径只需改 SQL 重算、可回溯到最原始输入。Kappa 架构干脆用一条日志重放替代批层。
Day 18Kafka EOS 的原子性全靠「offset 提交也是一次 Kafka 写」——能跟输出绑进同一个事务,正因为输出也写进同一串日志。
Day 19Raft 的核心就是把同一条 append-only 日志在多节点上复制、按多数派提交;状态机重放日志必须幂等才不越加越多。

对你这行最值钱的兑现:把 policy-events 当 event log + 钉住 rate_table_version → 多年后监管问「这张保单当时为什么是这个价」,答案是「把那条事件配上当时钉住的费率版本重放、确定性地算回来」,而不是「翻日志大概是这个原因」。这就是 reproducibility 与单纯 traceability 的分界(见易混区)。

🟠 线 4 · 「全局一致快照」的退化与赎回:乱序、版本、保序

D15D16D17D19

同步单库时,「某一刻全系统看到同一份一致数据」是免费的。一旦异步 + 多节点,这个性质开始退化,你得逐处赎回——这是第二周「逐路径一致性预算」在异步世界的续集。

  • Day 15 / 16 · 乱序:消息乱序处理 = 因果违例(取消先于生效),用状态机看就是「非法转移」。赎回:按实体 id(policy_id)做 partition key 路到同一分区(分区内天然 FIFO)。⚠️ 但 Day 16 提醒:partition 数一改,hash%N 翻盘 → 单 key 有序被劈成两半 → 容量决策要趁早拍对(一开始就多开)。
  • Day 17 · batch vs stream:batch 的杀手锏是「整批钉死同一假设版本 + 原子切版本」=全局原子一致;切 stream 后保单一条条在不同时刻重估 → 库里新旧版本混杂 → 退化成逐条最终一致。这是性质变化、不是成本(钱买不回来),对 reserving / 监管披露是真问题。还要处理 event time vs processing time 的归期错误(window + watermark)。
  • Day 19 · 配置指针:「当前生效 rate_table_version」放 etcd 而非「又快又熟」的关系库 read replica——因为 etcd 给 linearizable(全集群同一瞬间切换),而 replica 有 lag 会读到旧版。强一致是 auditability 的前提:没有「当时全集群用同一版」,可追溯就是假的。

🔵 线 5 · 异步换来什么:解耦时间与空间(以及它的账单)

D15D16D17

退一步看「为什么要异步」。同步 = 调用方必须等被调方当场算完才能走;异步 = 把「收请求」和「处理请求」在时间和空间上解耦,立刻回 202,后台慢慢做。

异步红利怎么来的 / 账单是什么
解耦Day 15 队列让任务不必一起完成;Day 16 事件驱动把它推到极致——发布者不关心谁听,加下游零改动。账单:没有显式的完整流程逻辑、调试难、最终一致。
削峰 / 缓冲夜间 cron 一瞬间吐百万条,worker 按自己速率慢慢啃,队列把 burst 吸收。账单:积压(consumer lag) → 队列越堆越长,推高延迟(接线 6 护栏)。
弹性 / 重试某 worker 挂了,消息靠队列重投、先处理别的;反复失败进 DLQ 集中处理。账单:重投 = 重复 → 必须幂等(接线 1)。
攒 vs 来Day 17:延迟容忍高 → batch(攒一批、吞吐高、成本低);要近实时 → stream(来一条、延迟低、运维贵)。账单见线 4 的一致性退化。

一句话:异步不创造容量,它重新分配时间——把「现在必须做完」改成「迟点做完也行」,用这个时间差换解耦、削峰、弹性;代价是放弃了同步的简单(强一致、有序、调试直观)。

🟣 线 6 · 过载护栏:容量终会被打穿,那一刻要「优雅地少做」而不是「一起死」

D15D17D20

前面几周都在「把容量做大」(缓存 / 复制 / 分片);Day 20 第一次正面回答「容量被打穿那一刻怎么办」。四件工具,按方向记:

工具挡哪个方向 / 心法
rate limiting 限流防「入」:给单位时间进来的请求设上限(token bucket 允许短 burst);per-key 防单个 broker 失控、全局防加总打爆后端,两者叠着上。
circuit breaker 熔断防「出」:下游坏了就 fail fast、别再调(CLOSED 工作 / OPEN 跳闸 / HALF-OPEN 试探)。⚠️ 命名反直觉,你栽过。
backpressure 背压异步管道里下游忙不过来 → 沿链路反推「慢一点」,让生产者按最慢环节降速。有界队列是它的载体(无界队列 = 把过载推迟成 OOM)。
bulkhead 舱壁给每个服务独立资源池,一个出问题不拖垮全局。最关键一层:夜批与实时报价彻底隔到不同资源池,别让夜里的百万 job 吃光白天报价容量。

核心取舍一句话:实时报价怕延迟 → 宁可丢、不愿等(限流 / 熔断 shed);夜间批量怕打满 → 宁可慢、不愿丢(背压)。同一个熔断器两边配置还相反:实时配紧 timeout + 激进阈值(快进快出),批量配松 timeout + 宽容阈值(可慢、可重跑)。

幂等保护「副作用」  vs  它不负责跳过「计算」⚠ 你栽过(连两天)· Day 18
幂等 · 保护副作用 · 正确性
让有副作用的操作(写库 / 扣款 / 出账)执行 N 次效果 == 1 次。防的是副作用翻倍。
跳过计算 · 省算力 · 效率
把算好的结果存下来不再重算,省 CPU——那是 checkpoint / 缓存的活,跟正确性无关。
你怎么混的:你以为「幂等键就是为了跳过那层 premium 计算」。其实算 premium 是纯函数(输入钉死版本),重算第二遍是同一个数、零副作用、只费一遍 CPU——危险从来只在「写库 / 扣款」那一步。去重表实现「顺手」跳过了计算,但那只是副产品。在受监管场景,「崩了重跑能算出一模一样的数」反而是 reproducibility 的优点。记牢:幂等防副作用翻倍;跳过重算是效率问题,不归幂等管。
逻辑唯一(选主)  vs  物理唯一(谁在干活)⚠ 你栽过 · Day 19
逻辑唯一 · 谁说了算
leader election 保证同一刻多数派只「认」一个 leader(带最高 term 的那个)。
物理唯一 · 谁在写
真实世界里同一份活只有一个进程在跑——选主给不了这个。
你怎么混的:你把重复的来源说成「重试」,真正更要命的是「假死双跑」:旧 coordinator 网络抖一下被孤立,它自己还以为是 leader、还在跑批,而 etcd 已把新 coordinator 选出来 → 租约过期前两个物理上同时在写。选主挡不住,得靠幂等(让重叠写覆盖成同一个值、无害)+ fencing token(每次抢租约 token+1,资源拒掉旧持有者的低 token 写)。一个让它无害、一个根本不让它落地,生产里常两个都上。
phantom read(幻读)  vs  out-of-order(乱序 / 因果违例)⚠ 你栽过 · Day 15
幻读 · 隔离级别现象(Day 14)
同一事务内两次范围查询,因别的事务 INSERT 了匹配新行 → 第二次多读到「幻影行」。提高隔离级别解。
乱序 · 投递 / 分区顺序问题
消息不按真实发生序被处理(取消先于生效)→ 违反 happens-before。用 partition key 保序解。
你怎么混的:你把「保单取消先于生效被处理」叫成 phantom read——八竿子打不着。用状态机讲,乱序 = 试图在还没 issued 的状态上执行 cancel 这条非法转移,跟「并发 INSERT 搅乱范围读」的幻读毫无关系。一个是单事务内的隔离现象,一个是跨消息的处理顺序问题。
全局原子一致(batch)  vs  逐条最终一致(stream)⚠ 你栽过 · Day 17
batch · 整批同一版本、原子切
夜间重定价全量在同一假设快照下算、原子切版本 → 任意时点要么全新要么全旧,绝不会有人拿新价有人拿旧价。
stream · 一条条在不同时刻重估
切实时后保单逐条被重估 → 任意时点库里新旧版本混杂,破坏「全局某一时刻的一致快照」。
你怎么混的:你把切 stream 后一致性 / 可审计性的新麻烦都归成「更像成本」——这是误判。成本是多花钱能解决的;而「全局原子一致退化成逐条最终一致」是正确性 / 性质变化,钱买不回来。对 reserving(准备金按统一假设汇总)、对账、监管披露(「截至 X 时点按版本 V 的总准备金」)都是真问题。这正是受监管寿险系统「批往往是默认」的根本原因。
event log 即真相源(一份)  vs  状态表 + audit log(两份)⚠ 你栽过 · Day 16
event sourcing · 一个真相源
日志就是系统实际依据运行的那份,当前状态是它派生(derived)出来的;审计与行为同源。
state + audit · 两个真相源
状态表是真相、audit log 是旁路记录,靠应用层纪律保持同步——会漂移。
你怎么混的:你答「设计够好两者等价」——反了。event sourcing 的价值正是不需要你设计得足够好:一份真相源构造上不可能各说各话;两份只要有代码路径改了状态却漏写 audit、或 audit insert 在事务外失败,审计轨迹就残缺且你察觉不到。受监管寿险要的就是这个性质从架构来、不靠自觉。现实折中:dual-write 可以,但 audit 必须和状态变更进同一事务 + append-only。
CLOSED(熔断器闭合)  vs  OPEN(熔断器断开)⚠ 你栽过 · Day 20
CLOSED · 正常放行 · 工作中
电路闭合、电流通过——请求照常发往下游,同时统计失败率。
OPEN · 跳闸 fail fast · 已停发
电路断开、电流截断——调用立即失败、根本不发往下游,给它喘息。
你怎么混的:你写「失败率高过 threshold 时暂时关闭服务」——对应的状态其实是 OPEN,不是 CLOSED。别被中文「关闭」带偏:闭合(closed)= 通路 = 工作,断开(open)= 断路 = 熔断。中间还有 HALF-OPEN:冷却后放少量探针,成功回 CLOSED、失败退回 OPEN。

顺手再分清四对(核心概念 / 没栽过但常混)

对子一句话区别
exactly-once delivery vs effectively-once把 exactly-once 当「网络只传一次」是头号误解(被两将军判死刑);能落地的是 effectively-once = at-least-once 投递 + 幂等消费。Kafka EOS 也是「效果」,且仅在「Kafka→处理→Kafka」闭环内成立,跨出去调支付仍需自己放 key。
dedup table vs upsert⚠ Day 18幂等的两种合法实现,分水岭是副作用可不可覆盖:可覆盖(改保单字段)→ upsert 覆盖写、连去重表都不要;不可覆盖(追加扣款)→ 去重表 + key(查表与执行要原子)。「查到做过就跳过」只是 dedup 那一种,不是幂等的定义。
idempotency vs fencing token都防「假死旧节点的迟到写」,层次相反:幂等被动——重复来了当 no-op、让它无害;fencing 主动——压根不让低 token 的旧写落地。一个「来了也不出错」,一个「根本不让它进来」,生产里常两个都上。
rate limiting vs backpressure都控流入速率,手法相反:限流=丢弃式(门口一刀切、超了 429,适合同步请求——宁可丢不愿排队加延迟);背压=反馈式(让生产者按最慢环节降速,适合异步管道——宁可慢不愿堆爆内存 OOM)。

这几题要连着好几天才答得出

不是单日知识点,而是跨天综合——能答出来,说明这张网真的连上了。

Q1为什么说「幂等是整个第三周的底座」?它在 Day 15/16/17/18/19/20 各兜住哪一段「重」?
因为只要系统里存在「重试 / 重投 / 重跑」,就需要幂等让这些「重」变无害——而异步周里到处是「重」。Day 15——队列 at-least-once,崩了重投会重复;Day 16——Kafka replay / offset 重置 / 重复消费靠幂等消费兜底;Day 17——夜间重定价崩溃重跑 = upsert + checkpoint;Day 18——收束成防线,点破 effectively-once = at-least-once + 幂等;Day 19——Raft 状态机重放同一条日志必须幂等才不越加越多,且选主挡不住假死双跑、幂等兜窗口;Day 20——重试风暴是雪崩放大器,熔断从根上掐断。一句话:幂等保护的是副作用(写/扣款),不是计算(纯函数算几遍无所谓);它不是某一天的知识点,是把所有异步设计真正立住的地基。
Q2「exactly-once delivery 不可能」——两将军证明了什么、没证明什么?这怎么导出工程上的两条出路(effectively-once + 选主的逻辑/物理唯一区别)?
两将军证明的是:在会丢消息的信道上,不存在能在有限步内「保证(概率 1)」达成一致的确定性协议(对最短协议反证:最后一条没人确认 → 删了它仍成立 → 一路砍到 0 条,矛盾)。它没杀掉的是「概率无限趋近 1」——多发几轮可把出错概率压到任意小,只是永远 ≠ 0。两条工程出路都从这来:① Day 18——别在投递层求确定性,改 at-least-once 投递 + 幂等消费 = effectively-once,把不确定性挪到能驯服的处理层;② Day 19——选主同理只给「逻辑唯一」(多数派认一个 leader),给不了「物理唯一」(假死旧 leader 仍在写),所以还要去资源层兜底:幂等让重叠写无害、fencing token 拒掉旧写。同一句智慧:承认绝对保证不可能,在能控制的那一端把重复变无害。(Kafka EOS 的 producer epoch、Raft 的 term 都是 fencing 的同一思路;同族还有 FLP 不可能 → Raft/Paxos。)
Q3夜间批量重定价跑到一半、worker 崩了一半、窗口又快到点——怎么设计才能安全从断点续跑、不重复收费?(Day 21 思考题①)
这是三周零件的一次合奏,要答三层 + 一个约束:① 谁接管崩掉的活(Day 15)——靠队列的租约 / visibility timeout:没在租约内 ack 的消息自动重新可见、被别的 worker 接走(这才是「断点续跑」在队列层的真机制);② 重叠那段不翻倍(Day 17/18)——checkpoint 记「算到第 60 万张了」从断点续(效率),幂等 upsert / UNIQUE(policy_id, run_date) 让崩溃点附近被算第二遍也不重复出账(正确性),两者互补缺一不可;③ 防假死旧 worker 迟到写(Day 19)——fencing token(单调令牌,保单库拒掉低 token 的旧写)+ 调度器自己崩了靠 leader 选举顶上。约束:「窗口快到点」——续跑也可能跑不完,按优先级先跑今天必须完成的(billing 到期),其余延到明天(延到明天安全也正因为幂等)。全程钉死同一组 rate_table_version + run_id/attempt 留痕,保证可复现可审计。
Q4把「夜间批量」改成「保单一变更就实时重估」的流,QuoteFlow 得到什么、付出什么?为什么受监管寿险「批往往是默认」?
得到两个:① 新鲜度——用户/内部分析时刻拿到最新结果;② 平滑负载——批是「攒一晚一次性砸下来」(为峰值配 ~16 worker、只用几小时),流是来一条算一条、负载摊平到全天,没有夜间大尖峰。付出的(关键在这):① 一致性退化(性质变化,不是成本)——batch 的杀手锏是「整批共享一份不可变快照、原子切版本」=全局原子一致;切流后保单逐条在不同时刻算、费率中途换版 → 同一逻辑批次里新旧版本混杂 → 退化成逐条最终一致,对 reserving / 对账 / 监管披露是真问题;② 可审计性变难——从「一个批次=一个版本+一份完整台账」变成「事件溯源」,复现「某时刻这张为什么这个价」要 replay 到精确状态;③ 还要处理 event time vs processing time 乱序、window/watermark、状态管理,运维更贵。所以「批是默认」:受监管、要 reproducibility 的场景,「全局原子一致 + 批次台账可复现」恰恰是批的天然优势——而且费率换版/假设变更这种全局变更,仍必须批量重算所有受影响保单,batch 场景不会消失。
