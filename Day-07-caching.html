1缓存买到了什么

把贵的事,只做一次

缓存的全部思想就一句话:把“算一次/取一次很贵”的结果,先存在离使用者更近、更快的地方,下次直接拿。QuoteFlow 的费率表(rate table)一天里被读上百万次、却几乎不变——每次报价都去数据库重新拉一遍同一张表,纯属浪费。把它放进内存里的缓存,第二次起就省下了那一整趟数据库往返。

这趟“省下的往返”值多少?回忆 Day 3 的关键延迟数字——不同存储介质的速度差着好几个数量级。缓存的价值,本质就是把请求从“慢介质”挪到“快介质”:

这一步去哪里取数据量级(数量级感觉)
本机内存(进程内缓存)~100 纳秒(ns)
同机房一次 Redis 往返~0.5–1 毫秒(ms)
一次数据库查询~几 ms 到几十 ms
跨区 / 调用外部 API~几十到几百 ms

▲ 缓存命中,常常意味着把一次请求从“几十毫秒”压到“亚毫秒”——快上一两个数量级。差距越大,缓存越值。

而且缓存买到的不只是快。它同时给下游减负:命中的请求根本不打到数据库,于是数据库的负载、连接数、成本都降下来,同样的库能扛更多流量——这直接呼应 Day 2 的 throughput 和 Day 6 的扩展。一层好缓存,常常比加几台数据库副本还划算。

命脉指标:hit rate(命中率)

缓存的价值几乎全押在一个数字上:命中率 = 命中次数 / 总请求次数。命中(hit)= 要的东西缓存里有,直接返回;未命中(miss)= 缓存里没有,只能回去查源头、再顺手把结果回填进缓存。命中率 95% 的缓存,意味着 95% 的请求都走了那条亚毫秒的快路。

但这里有个反直觉的坑:miss 不是“白跑一趟”,而是“比没有缓存还慢一点”——因为它先查了一次缓存(扑空),才又去查源头。所以如果一份数据访问很分散、几乎不重复(命中率极低),加缓存反而是净亏:每个请求都多付了一次查缓存的开销,却很少命中。缓存只对“读多、且会重复读同一批热数据”的场景划算——QuoteFlow 的费率表、核保规则正是教科书级的好候选。

2缓存住在哪

一条请求路上,有好几层缓存

“缓存”不是一个东西,而是一连串关卡。从用户的浏览器到最深处的数据库,请求路上每一层都可能拦下它、直接给答案。越靠近用户的缓存越快、越省(连网络都不用走),但你越管不动它(数据已经发出去了,想改也改不回来)。理解这条链,才知道一份数据该缓在哪一层。

逐层看一眼

浏览器缓存:最靠近用户。靠 Day 4 提过的 HTTP 头(Cache-Control、ETag)决定一份资源能在用户本地存多久。QuoteFlow 官网的 logo、JS、CSS 第二次访问直接读本地,连请求都不发。

CDN(内容分发网络):把内容复制到地理上离用户近的边缘节点。悉尼的用户从悉尼节点拿官网静态资源,不用千里迢迢回源站。CDN 主要缓静态内容,也能缓“对所有人都一样”的动态响应。

应用进程内缓存(local / in-process):数据就放在那台应用服务器自己的内存里,读取是纳秒级、最快。但它有 Day 6 的老问题——每台机器一份、各存各的:10 台服务器就有 10 份可能不一致的副本,且每台容量有限。适合存“极少变、且不一致也无所谓”的小东西。

分布式缓存(Redis / Memcached):一个所有应用服务器共享的独立缓存集群。比进程内多走一次网络(亚毫秒),但换来全局一份、一致、容量大。这正是 Day 6 说的“状态下沉到共享存储”里那层共享缓存——让应用层可以无状态、随意加减机器。QuoteFlow 的费率表、报价进度都适合放这。

进程内本地缓存分布式缓存(Redis)
数据放哪那台应用机器自己的内存独立的共享缓存集群
速度纳秒级,最快(不走网络)亚毫秒,多一次网络往返
一致性每台一份,容易互相不一致全局一份,天然一致
容量受单机内存限制可独立扩容,大得多
适合存极少变、不一致也无妨的小数据需共享/一致的热数据、会话状态

▲ 不是二选一:高级玩法是两层叠用——进程内缓存兜最热的一小撮(扛住 hot key),分布式缓存做全局主力。第 5 节会看到这招怎么救命。

3读写策略

缓存和数据库,谁先谁后

有了缓存,就要决定一件事:读和写的时候,缓存与数据库怎么配合?这几种“缓存模式”是面试高频,差别在于谁负责回填、写的时候先写谁。

读:cache-aside —— 最常用的那个

Cache-aside(旁路缓存,又叫 lazy loading)是默认选择,逻辑由应用代码掌控:先问缓存,有就返回(hit);没有就回数据库查,再把结果写回缓存,下次就有了(miss + 回填)。“懒”在于——只有被真正请求过的数据才会进缓存。

rate_cache.py · cache-aside 读取费率表(示意)
def get_rate_table(version):
    key = f"rate:{version}"          # 版本化 key,见第 4 节

    cached = cache.get(key)
    if cached is not None:
        return cached              # ① 命中 → 亚毫秒返回

    # ② 未命中:回数据库取源头
    table = db.load_rate_table(version)

    # ③ 回填缓存,下次就命中(费率表按版本不可变 → 可设很长 TTL)
    cache.set(key, table, ttl=86400)
    return table

注意:cache-aside 下,缓存里没有的数据不会自动出现——只有读过一次才进缓存。优点是简单、只缓真正用到的东西、缓存挂了系统也只是变慢(不会错);缺点是每个 key 第一次读总是 miss,且失效逻辑要应用自己管(下一节的雷区)。

写:三种姿势

写数据时,缓存和数据库的先后顺序,决定了“快”和“别读到旧数据”之间的取舍:

策略写的时候做什么取舍
Write-through
写穿透		同时写缓存 + 数据库,都成功才算成功缓存总是最新、读永远命中新值;写更慢(两处都写)
Write-back
写回 / write-behind		先只写缓存、立刻返回,稍后异步刷回数据库写极快、吞吐高;但缓存一挂、还没刷回的数据就丢了(受监管写路径慎用)
Write-around
绕写		只写数据库,不动缓存(让它下次读时 miss 再回填)避免“写进去却没人读”的数据占缓存;但刚写的数据第一次读必然 miss

▲ 一个常被忽略的细节:写的时候,与其“更新缓存里的旧值”,不如直接删掉(invalidate)那个 key,让下次读自然 miss 回填——这样能避开一类“并发更新把旧值写回缓存”的竞态。删除比更新更安全,是个反复出现的实战经验。

4失效与一致性

缓存最难的事,是让它适时“忘掉”

计算机界有句广为流传的玩笑:“真正难的只有两件事——缓存失效,和给变量起名。”失效(invalidation)之所以难,是因为缓存的本质是一份副本:源头一变,副本就过时(stale)了。系统该怎么知道、又该多快让副本跟上?这就是缓存的核心张力——性能 vs 一致性:你缓得越久越快、却越可能读到旧数据;追求时时最新,缓存的意义又被削弱。三种主流办法,从“凑合”到“干净”:

① TTL —— 给每条缓存设个保质期

TTL(time to live):写入时设一个存活时间,到点自动失效、下次读重新回源。最简单、最常用,本质是用“可容忍的过时窗口”换简单。设 TTL=60s,就等于声明“这份数据最多旧 60 秒,我能接受”。问题是:在窗口内,读到的就是旧值——对官网的营销文案无所谓,对一条刚刚改了的费率,可能就是大事。

② 显式失效 —— 数据一变就主动删缓存

写数据库的同时,主动把相关 key 从缓存删掉(或更新)。准、即时,但难做对:容易漏删某个 key、容易在分布式下出现“删缓存”和“别的请求回填旧值”的竞态、一份数据散在多层多个 key 时更难一网打尽。强一致需求会用它,但它是 bug 的高发区。

③ 版本化 key —— 最干净的一招(对 QuoteFlow 尤其重要)

把版本号写进 key 本身:不存 rate_table,而存 rate:2026-06、rate:2026-07。每个版本的内容不可变(immutable)——一旦生成就永不修改。于是“失效”这个难题直接消失了:费率表要更新?不是去改 rate:2026-06,而是生成一个全新的 rate:2026-07,让应用改读新 key。旧 key 自然没人读、慢慢被淘汰,新 key 第一次读 miss 回填。没有“同一个 key 内容变了”的时刻,也就没有 stale 的窗口。

为什么版本化对受监管定价是“正解”
  • QuoteFlow 的费率表 / 核保规则 / 定价模型本来就该是版本化、不可变的(Day 1 的 auditability)。把这套版本号顺手用作缓存 key,就一箭双雕:既拿到缓存的速度,又永远不会因为缓存读到“半新半旧”的费率而算出不可复现的报价。一条报价钉住了 rate_table_version(还记得 Day 1 那份契约吗?),无论命中缓存还是回源,拿到的都是那个版本——这正是 reproducibility 的根。

顺带分清:expiration(过期)≠ eviction(逐出)

两个常被混的词。过期是“到 TTL 了,这条数据该失效”——按时间。逐出是“缓存内存满了,得腾地方,踢掉某些数据”——按容量,跟它过没过期无关。缓存满时踢谁,由逐出策略决定,最常见的是 LRU(Least Recently Used,踢最久没被用的),还有 LFU(Least Frequently Used,踢用得最少的) 和 FIFO。LRU 的直觉很对:最近没人碰的,大概率接下来也用不上。

5缓存陷阱

四个经典的“缓存反而把你拖垮”

缓存平时是救星,出事时却能反过来放大故障——因为大家都指望它挡在数据库前面,它一旦失灵,所有压力瞬间砸向后面那个本来扛不住全量的数据库。认全这四个经典陷阱,是“会用缓存”和“被缓存坑过”的分水岭:

陷阱怎么发生的怎么防
Stampede
惊群 / 缓存击穿		一个热 key 刚好过期,瞬间一大批请求同时 miss、齐刷刷砸向数据库重算同一个值加锁 / single-flight(只放一个去重算,其余等结果);TTL 加随机抖动;热点提前异步刷新
Penetration
穿透		反复查一个根本不存在的 key,缓存永远 miss,每次都白穿到数据库(常是恶意扫描)把“查无此项”也缓存成空值(设短 TTL);用 bloom filter 先挡掉绝不存在的
Avalanche
雪崩		大批 key 同一时刻集体过期,或整个缓存集群挂掉,流量整片涌向数据库把它压垮TTL 打散(别用同一个固定值);缓存做高可用 + 多副本;前面加限流 / 熔断(Day 20)
Hot key
热点 key		某一个 key 太火(如爆款产品费率),所有流量集中打到存它的那一个缓存节点,把单节点打爆在应用进程内再缓一层兜住它;把热 key 复制到多个节点分摊

▲ 共同点:平时被缓存挡住的洪水,在某个瞬间一起决堤砸向数据库。所以缓存层的设计,要顺带想清楚“它失灵那一刻,后面扛不扛得住”。

用伪代码看 stampede 的解法最直观——核心是“同一个热 key,同一时刻只让一个请求去重算,其余的等它”:

stampede.py · 用单飞锁挡住惊群(示意)
def get_with_lock(key):
    val = cache.get(key)
    if val is not None:
        return val                      # 命中,正常返回

    # miss:抢一把短锁,只有抢到的那个去查源头
    if cache.set_nx(key + ":lock", ttl=5):
        val = db.load(key)            # ← 同一时刻只有一个请求走到这
        cache.set(key, val, ttl=jitter(3600))  # TTL 加随机,防雪崩
        cache.delete(key + ":lock")
        return val
    else:
        sleep(0.05)                  # 没抢到锁的:稍等一下
        return get_with_lock(key)      # 再读,这时大概率已被回填

这段同时用上了两招:set_nx 的单飞锁挡住惊群(stampede),jitter() 给 TTL 加随机量打散过期时间(防雪崩 avalanche)。两个陷阱、一段代码。

QuoteFlow 的缓存地图

把今天的零件落到 QuoteFlow 上,每一层缓什么、用什么策略,一张表就清楚——关键是:读多变少的用缓存,版本化的当 key,绝不能错的别图快。

缓在哪一层QuoteFlow 缓什么策略
CDN官网 / App 的静态资源(JS、CSS、图片、产品介绍页)长 TTL + 文件名带哈希,改了换名即换缓存
分布式缓存 Redis费率表 / 核保规则 / 定价模型(读多、极少变)版本化 key(rate:2026-06),不可变 → 永不 stale
分布式缓存 Redis多步投保流程里的“报价进度”会话状态cache-aside + 短 TTL;应用因此可无状态(Day 6)

Case · QuoteFlow

缓存怎么同时服务“快”和“可审计”

报价路径上,真正贵的是反复拉同一套费率表 / 核保规则。把它们按版本号缓进 Redis,报价服务命中时亚毫秒拿到、不打数据库——latency 和 throughput 一起改善。而因为 key 是版本化、内容不可变的,无论哪台无状态服务、命中还是回源,拿到的都是同一份 rate:2026-06。这就接上了 Day 1 那份契约里钉死的 rate_table_version:缓存在这里不仅没破坏可复现性,反而是它的帮手。

哪条线不能图快

反过来,签发保单、扣款、写 audit log 这些写路径,绝不能用 write-back“先写缓存、稍后刷库”——缓存一挂,还没落库的那笔就凭空消失,在受监管场景里等于审计链断裂。这类写以数据库为权威源,缓存只在读侧帮忙。判断一份数据该不该缓、能缓多久,本质就是问一句:“它旧一点会怎样?丢一份会怎样?”——这正是 Day 2 一致性取舍在缓存层的具体落地。

★关键要点

今天带走这四句

1

缓存 = 把贵的结果存近一点、下次直接拿,买到低延迟 + 给下游减负。价值全押在 hit rate;读少又分散的数据缓了反而更慢。

2

一条请求路上有多层缓存:浏览器 → CDN → 应用本地 → 分布式 Redis。越近越快越管不动;cache-aside 是默认读法。

3

最难的是失效与一致性:TTL 简单但有 stale 窗口、显式失效准但易错、版本化不可变 key 最干净——对受监管定价是正解。

4

缓存失灵会反向放大故障:stampede / penetration / avalanche / hot key。设计时要想清“它一挂,后面的库扛不扛得住”。

?今日小测 + 思考题

读完自测一下

Q1某份数据几乎每次请求的 key 都不一样(命中率极低)。给它加缓存,大概率是赚还是亏?为什么?
大概率亏。缓存只对“读多、且重复读同一批热数据”划算。命中率极低时,几乎每个请求都先查一次缓存(扑空)、再回源——等于每次都比没缓存多付一次查缓存的开销,却很少命中。缓存的价值全押在 hit rate 上。
Q2费率表要更新。用“TTL 到点失效”还是“版本化不可变 key”更适合 QuoteFlow?为什么?
版本化 key 更适合。TTL 方案在“费率刚改、旧缓存还没到期”的那段窗口里,会读到旧费率,在受监管定价里可能算出不可复现的报价。版本化把版本号写进 key(rate:2026-07),内容不可变、改版本就是换 key——根本不存在“同一个 key 内容变了”的 stale 时刻,天然对齐契约里钉死的 rate_table_version。
Q3什么是 cache stampede(惊群)?和 cache avalanche(雪崩)有什么区别?各怎么缓解?
Stampede:单个热 key 刚过期,瞬间大量请求同时 miss、一起去重算同一个值砸向数据库——用单飞锁(只放一个去算、其余等)缓解。Avalanche:大批 key 同时过期(或缓存整体挂)导致流量整片涌向数据库——用 TTL 加随机抖动打散过期时间 + 缓存高可用 + 限流熔断缓解。一个是“一个点决堤”,一个是“整片决堤”。

A→Z术语表

今日术语

Cache Hit / Miss
命中=要的数据缓存里有,直接返回;未命中=缓存没有,回源查再回填(还比无缓存多一跳)。
Hit Rate
命中率=命中数/总请求数;缓存价值的命脉指标,越高越值。
CDN
内容分发网络:把内容缓存到地理就近的边缘节点,主要服务静态资源。
Cache-Aside
旁路缓存/lazy loading:应用先查缓存,miss 则查源头并回填;最常用的读策略。
Write-through / Write-back
写穿透=同写缓存+库(慢但不丢);写回=先写缓存稍后刷库(快但可能丢数据)。
TTL
缓存条目的存活时间,到点自动失效;用“可容忍的过时窗口”换简单。
Eviction (LRU/LFU)
缓存满时按策略踢数据腾空间:LRU 踢最久没用的、LFU 踢用得最少的。≠ 过期(按时间)。
Cache Stampede
惊群/击穿:热 key 一过期,海量请求同时 miss 砸向源头;用单飞锁+TTL 抖动缓解。
