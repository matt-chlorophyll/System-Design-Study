1为什么需要可观测性

从「它挂没挂」到「它为什么慢」

单体时代,出了问题你登上那台机器,看一眼日志、top 一下 CPU,基本就定位了。微服务一拆,一次报价请求要穿过网关、报价服务、核保服务、费率服务、数据库——任何一环慢一点、错一点,客户端看到的都是同一个「报价超时」。问题不在「哪台机器挂了」,而在「这一笔请求,究竟卡在了链路的哪一跳」。

这里有个常被混用、但值得分清的区别:

Monitoring(监控):盯着你预先想到要盯的东西。CPU 超 80% 报警、错误率超 1% 报警——回答的是「已知问题发生了没有」(known-unknowns)。

Observability(可观测性):系统对外暴露了足够丰富的信号,让你能事后问出当初没预设过的问题——「为什么只有用 broker 渠道、且保额超过 100 万、且命中了某条新核保规则的报价会慢?」这类 unknown-unknowns,靠的不是更多 dashboard,而是数据维度够细、且能下钻。

一句话区分:监控告诉你「系统坏了」;可观测性让你回答「它为什么坏、坏在哪」。前者是后者的一个子集。对 QuoteFlow 这种受监管系统,还有第三层——你不仅要能定位故障,还要能解释清楚某一笔具体报价当时经历了什么,这是 audit 的硬要求。

2三大支柱

Logs / Metrics / Traces:别只用一种

可观测性的数据有三种基本形态,各自回答不同的问题,谁也替代不了谁。新手常犯的错是「只打日志」,然后在日志里硬算指标、硬拼链路——又贵又拼不全。

Metrics(指标)—— 便宜、聚合、适合告警

随时间变化的数值:QPS、p99 latency、错误率、队列深度。它是预先聚合的(按时间窗口、按标签),所以存储极省、查询极快,是 dashboard 和告警的主力。代价:它告诉你「p99 涨到 800ms」,但答不出「是哪些请求慢了、为什么慢」——维度一多,基数爆炸(high cardinality)就扛不住。

Logs(日志)—— 离散事件,细节最全

一条条带时间戳的事件记录。信息最丰富,适合事后翻查某笔请求的具体经过。务必用 structured logging(JSON 而非纯文本),并在每条日志里带上 trace_id,否则海量日志里你根本捞不出「这一笔」。代价:量大、贵,全量存日志成本会失控,通常要采样或分级保留。

Traces(链路追踪)—— 一次请求的完整旅程

把一次请求穿过所有服务的路径和每一跳的耗时,拼成一条带层级的时间线。它专治微服务的「到底卡在哪一跳」。代价:要全链路埋点 + context 透传,且高流量下必须采样(只留一小部分 trace)。

MetricsLogsTraces
数据形态聚合数值时间序列离散事件记录跨服务的请求树(span)
擅长回答整体「多少 / 多快 / 多错」某笔请求「具体发生了什么」一次请求「卡在哪一跳」
成本最低高(量大)中(通常采样)
主要用途dashboard · 告警事后排查 · audit定位延迟 / 故障跨度
QuoteFlow 例子报价 p99、夜间批量吞吐某 quote_id 命中了哪些规则这笔报价 47ms 花在了费率服务还是核保

▲ 三支柱互补:metrics 发现「有问题」,traces 定位「在哪一跳」,logs 揭示「那一跳到底发生了什么」。三者用 trace_id 串起来,才是完整闭环。

3链路追踪

trace_id + span:把一次请求拼回来

昨天网关注入的那个 trace_id,现在登场了。一次完整的请求是一个 trace,它由若干 span 组成——每个 span 是「在某个服务里做的一段工作」,带有开始/结束时间、所属服务、以及指向父 span 的指针。只要每一跳都把 trace_id 和当前 span_id 通过 header 传给下游(这就是 context propagation),事后就能按父子关系把整棵树拼回来,看出每一跳各花了多久。

这正是昨天那笔伏笔的兑现:没有透传的 trace_id,你只有一堆各服务孤立的日志,拼不出这张图。对 QuoteFlow,这条 trace 还有第二层价值——它本身就是一份「这笔报价当时经过了哪些服务、命中了哪个版本的规则」的可审计记录。

4SLI / SLO / SLA

把「够好」变成一个能算账的数

有了信号,下一个问题是:多快、多稳才算「够好」?光说「要快要稳」没法落地。这三个层层递进的概念,把它变成可度量、可承诺、可决策的东西:

是什么对谁QuoteFlow 例子
SLI一个实际测量的指标(Indicator)工程内部报价请求中 p99 latency < 300ms 的比例
SLO给 SLI 定的内部目标(Objective)团队自己「99.9% 的报价请求 < 300ms」
SLA对外部的合同承诺(Agreement),违约有赔偿客户 / broker 合同「月可用率 ≥ 99.5%,否则退费」

▲ 记忆线:SLI 是测量、SLO 是目标、SLA 是承诺。SLO 一般要订得比 SLA 严(留缓冲),这样在违反对外合同之前,内部就先报警了。

Error budget:稳定与迭代之间的「预算」

SLO 最妙的副产品是 error budget(错误预算)。如果 SLO 是「99.9% 可用」,那剩下的 0.1% 就是你被允许「不可用」的额度——一个月约 43 分钟。这把一场没完没了的争吵(「要稳定」vs「要快上线」)变成了一笔可算的账:

error budget 怎么用
  • 预算还有富余 → 大胆发新版核保规则、做实验、上灰度,允许冒一点险。
  • 预算快烧光 → 本月冻结一切高风险变更,集中力气稳住系统,直到下个周期预算重置。

它的高明之处:把「该不该上这个变更」从拍脑袋的辩论,变成一个看预算余额的客观决定。100% 可用不是目标——那意味着你太保守、迭代太慢;目标是「正好花完预算」。

5告警

对症状告警,而不是对原因

有了 SLO,告警就有了锚:告警应该绑在「用户感受到的症状」上,而不是「某个内部原因」上。"CPU 80%" 不该半夜叫醒人——CPU 高但报价依然又快又对,那不是事故;反过来,CPU 正常但报价 p99 飙到 2 秒,才是真问题。好的告警问的是:「用户的 SLO 正在被违反吗?」

这背后是个很实际的痛点:alert fatigue(告警疲劳)。如果什么都报警、且大半是噪音,工程师会开始忽略告警——于是真正的事故也被淹没。少而准的告警,远胜多而吵的告警。一个常用分层:

级别含义响应
Page(电话/呼叫)SLO 正在被违反,用户已受影响立刻有人起来处理
Ticket(工单)趋势不妙,但还没伤到用户(如预算消耗偏快)工作时间内跟进
Info(仅记录)留痕供事后分析,不打扰任何人不告警,进 dashboard

下面把这套思路落到 QuoteFlow 的一条 structured log + 一段告警规则上,体会三支柱怎么靠 trace_id 串起来:

QuoteFlow · structured log + SLO 告警(示意)
// ── 一条结构化日志:带 trace_id,可被 audit 也可被排查 ──
{
  "ts": "2026-06-24T08:00:12Z",
  "level": "INFO",
  "service": "underwriting",
  "trace_id": "q_8f3a...",        // ← 把日志/指标/追踪缝在一起的那根针
  "quote_id": "q_8f3a...",
  "rate_table_version": "2026-06",    // 可审计:用的是哪版费率
  "rules_applied": ["base_rate", "high_sum_loading"],
  "latency_ms": 25,
  "msg": "underwriting decision computed"
}

// ── 告警规则:绑在“症状/SLO”上,而不是 CPU ──
alert: QuoteLatencySLOBurn
expr:  histogram_quantile(0.99, quote_latency_ms) > 300
        for: 5m            // 持续 5 分钟才报,过滤瞬时抖动
severity: page              // 直接违反用户 SLO → 立刻呼叫
summary:  "报价 p99 > 300ms,SLO 正在被违反"

注意这条日志同时服务两个目的:排查(顺着 trace_id 看这笔卡在哪)和 审计(留下「这笔报价用了哪版费率、命中哪些规则」的痕迹)。在受监管定价里,可观测性和 auditability 常常是同一套基础设施的两张脸。

?今日小测 + 思考题

读完自测一下

Q1报价 p99 突然涨到 800ms。你想知道「慢在链路哪一跳」,该先看三支柱里的哪一个?
Traces。metrics 只告诉你「整体慢了」,trace 才能把这一笔请求按 span 拆开,指出是费率服务、核保还是 DB 这一跳吃掉了时间;定位到跳之后再用该跳的 logs 看细节。
Q2「99.9% 的报价请求在 300ms 内返回」——这是 SLI、SLO 还是 SLA?
SLO(内部目标)。其中「p99 latency < 300ms 的请求占比」这个被测量的量是 SLI;如果把类似承诺写进对 broker 的合同、违约要赔,那才升级成 SLA。
Q3为什么「CPU > 80% 就半夜呼叫工程师」通常是个坏告警?
因为它对的是原因,不是症状。CPU 高但报价依然又快又对,用户毫无感知,不该叫醒人;这类噪音告警多了会造成 alert fatigue,真事故反被淹没。应该对「报价 p99 / 错误率」这种直接反映 SLO 的症状告警。
带着这两个问题回来讨论

① QuoteFlow 的「实时报价」和「夜间批量重定价」NFR 截然不同——你会分别给它们定哪几个 SLI?批量任务的「latency」还有意义吗,该换成什么?
② 全量存 trace/log 太贵,必须采样。但 audit 又要求「每一笔报价都可追溯」。这两个诉求冲突吗?你会怎么设计,既控成本又不丢审计?

今日术语

Observability
系统暴露足够信号,使人能事后回答没预设过的问题(unknown-unknowns)的能力。
Monitoring
对预先设定的已知指标做持续观测与告警(known-unknowns)。
Metrics
随时间变化的聚合数值(QPS、p99、错误率),便宜、适合 dashboard 与告警。
Structured Logging
以结构化格式(如 JSON、带字段)输出的日志,便于检索、过滤与关联。
Distributed Tracing
用 trace_id + span 把一次跨服务请求拼成带层级的时间线。
Span
trace 中的一段工作单元,记录某服务内的起止时间及父子关系。

实测指标 / 内部目标 / 对外可赔付的合同承诺,三层递进。
