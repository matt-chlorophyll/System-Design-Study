1问题从哪来

同步调用把命运绑在了一起

先看一个 QuoteFlow 里很自然、却很危险的写法。客户提交投保申请,submit_application 这个接口在一次 HTTP 请求里把所有事都做了:写申请、跑核保、发欢迎邮件、给再保系统推送、刷新分析看板。代码读起来很顺,但它有一个致命结构——这五件事被「同步」串成了一条命运共同体。

同步(synchronous)的意思是:调用方发出请求后必须原地等着,直到对方处理完、回了结果,才能继续。于是:

① 延迟叠加。客户要等的不是「写申请」那几毫秒,而是这五步耗时之和——核保慢、邮件网关卡一下,客户就在转圈。② 故障传染。邮件服务挂了,整个投保接口跟着报错,连「申请已收到」都没能存下来。一个边角功能的抖动,拖垮了核心流程。③ 强耦合。每加一个下游(比如新接个反洗钱筛查),就要改这个接口、重新部署、重新测——发送方必须知道每一个接收方的存在。

核心洞察:很多下游工作,客户其实并不需要等。「申请已收到」这件事一旦落库,核保、邮件、再保推送完全可以稍后再做。把「接收」和「处理」在时间上拆开——这就是异步,而承载它的基础设施,就是消息队列。

2队列做了什么

在发送方和接收方之间,插一个缓冲

消息队列(message queue)是一个独立的中间件。发送方(producer)把一条消息丢进队列就立刻返回,不等任何人处理;接收方(consumer)按自己的节奏从队列里取消息来处理。两边不再直接通话,而是通过队列这个「信箱」间接交流。这一层间接,带来四件实打实的好处:

① 解耦(decoupling):producer 只管「写一条消息」,根本不知道、也不关心有几个 consumer、它们是谁、在不在线。加一个新下游?让它来订阅队列就行,producer 一行代码都不用改。

② 削峰填谷(load leveling):早高峰投保请求暴涨,队列把瞬时洪峰暂存起来,consumer 仍按自己稳定的处理能力慢慢消化。系统按「平均负载」而非「峰值负载」来配置,省钱又稳。

③ 弹性缓冲(buffering):核保 worker 临时挂了 5 分钟?消息安全地堆在队列里,worker 恢复后继续消费,一条不丢。下游的短暂不可用,不再等于数据丢失。

④ 容错与重试:某条消息处理失败,可以重新投递、稍后重试;反复失败的「毒消息」被移进死信队列(DLQ)单独排查,不阻塞后面的正常消息。(重试与 DLQ 是 Day 18 的主题,今天先建立印象。)

3两种投递模型

一条消息「一个人吃」还是「人手一份」

用队列前要先想清一件事:这条消息是一份待办任务(只能有一个人处理),还是一个已发生的事实(谁关心谁都该收到)?这对应两种根本不同的模型。

点对点 / 工作队列(point-to-point / work queue)

一条消息只被一个 consumer 成功处理一次。多个 worker 同时盯着同一个队列抢活,谁抢到谁干——这天然就是负载均衡 + 横向扩展:积压多了,多起几个 worker 就行。适合「任务分发」:一条「重算这张保单」的指令,只该被算一次。

发布订阅(publish-subscribe / pub-sub)

一条消息被每一个订阅者各收到一份。producer 发布一个「事实」,所有订阅了这个 topic 的下游各自拿到独立副本、各做各的。适合「事件广播」:一条「保单已签发」事件,计费要建账、邮件要发保单、分析要入仓、再保要上报——四个下游互不知情,各收一份。

点对点队列发布订阅
一条消息被谁消费恰好一个 consumer每个订阅者各一份
语义一份待办任务一个已发生的事实
多 consumer 的作用分担负载、横向扩展各自独立的下游反应
QuoteFlow 例子「重算 pol_8f3a」交给某个 worker「保单已签发」广播给计费/邮件/分析/再保
典型产品RabbitMQ、SQS、Redis listKafka、SNS、RabbitMQ topic exchange

▲ 选错模型是常见 bug 来源:把「任务」当「事件」广播,会被重复执行;把「事件」塞进独占队列,下游就抢不全。明天(Day 16)会专门展开 pub/sub 与 Kafka 这类日志型系统。

4天下没有免费的异步

队列换来的代价:三个必须正视的真相

异步不是银弹。把同步改成异步,你其实是用一组新问题换掉了旧问题。不认清这些代价,队列会从「解药」变成「新的故障源」。

真相一:最终一致 + 乱序。消息「丢进去就返回」,意味着客户拿到「申请已收到」时,核保还没跑。系统进入eventual consistency:状态会对,但不是此刻就对。UI 得诚实地显示「核保中…」,而不能假装已完成。更麻烦的是顺序:多 consumer 并行消费时,消息处理完成的顺序不保证等于发送顺序。如果「保单生效」和「保单取消」两条消息乱序处理,结果可能完全错。需要保序时,得靠分区键把同一保单的消息路由到同一个 consumer(Day 13 的分片思想在这里复用)。

真相二:重复投递,至少一次。绝大多数主流队列给的是 at-least-once(至少一次) 保证——网络抖动、consumer 还没确认(ack)就崩了,同一条消息会被再投一次。所以 consumer 必须幂等(idempotent):同一条消息处理两次,效果要和处理一次完全一样。对 QuoteFlow 这种受监管系统尤其要命:一条「计提首期保费」的消息被重复消费,就可能给客户重复扣费——这是合规事故。所谓「exactly-once」大多是「at-least-once + 幂等」拼出来的错觉(Day 18 会拆穿)。

真相三:积压与背压。队列能缓冲洪峰,但缓冲不是无限的。如果 consumer 长期比 producer 慢,队列会越积越长——延迟飙升、内存/磁盘吃紧,最后崩溃。这叫积压(backlog)。健康的系统要监控「队列深度」和「消息年龄」,并有背压(backpressure)机制:让上游慢下来或拒绝新请求,而不是把下游压垮(Day 20 专门讲限流、熔断、背压)。还有个软成本:调试更难——一个请求的因果链断成了「发消息」和「处理消息」两段,跨进程追踪一次业务,需要靠 correlation id 把它们重新缝起来(Day 24 可观测性)。

什么时候不该用队列
  • 调用方必须立刻拿到结果才能继续(如实时报价:客户在前端等那个保费数字,这条路径就该是同步、低延迟的)。
  • 两步之间需要强一致、即时可见,且业务无法接受「稍后才对」。
  • 规则很简单:客户要等的、要立刻看到的 → 同步;客户不必等的、可以稍后发生的 → 异步丢队列。
5贯穿案例

给 QuoteFlow 的投保流程「异步化」

把第 1 节那个「同步五件事」的投保接口重构掉。原则:核心写入同步落库 → 立刻回客户 → 其余下游全部异步。

Case · QuoteFlow

同步只做一件事

接口收到申请,只在事务里写入 applications 表(状态 = RECEIVED),然后发布一条 application.submitted 事件,立刻返回「已收到」。客户的等待从「五步之和」降到「一次写库」。

下游各自异步消费

核保 worker 收到事件 → 跑规则 + 风险评分 → 写回结果并发出 underwriting.completed;签发流程再据此推进。邮件、再保推送、分析入仓各自订阅、各做各的、互不阻塞。这正是 Day 14 那条 saga 链的载体——每一步靠消息触发下一步。

下面是核保 consumer 的伪代码,重点演示幂等和审计留痕——在寿险里这两点不是加分项,是底线。

underwriting_consumer.py · 幂等 + 留痕的 consumer
def handle(msg):
    app_id = msg["application_id"]
    msg_id = msg["message_id"]      # 生产者给每条消息的稳定唯一 id

    # ① 幂等闸门:at-least-once 下同一条可能来两次
    if processed_log.exists(msg_id):
        ack(msg)                     # 见过了 → 直接确认,绝不重复核保
        return

    try:
        result = underwrite(app_id)   # 跑规则 + 风险评分

        with db.transaction():     # 业务写 + 去重记录,同一事务里原子提交
            apps.set_status(app_id, result.status)
            audit.append(app_id, result, rules=result.rules_applied)  # 可追溯
            processed_log.add(msg_id)

        publish("underwriting.completed", app_id)  # 触发 saga 下一步
        ack(msg)                     # 确认后,队列才删除这条消息

    except TransientError:        # 临时故障 → 不 ack,稍后自动重投
        nack(msg, requeue=True)
    except PoisonError:           # 反复失败的毒消息 → 进死信队列,别堵住后面
        send_to_dlq(msg)
        ack(msg)

三处设计值得记住:先查 processed_log 再处理(幂等闸门)、业务写与去重记录放进同一个事务(避免「处理了但没记上去重」的半成品)、处理成功才 ack(ack 之前崩了就重投,保证不丢)。而 audit.append 提醒我们:异步链路里,每一步的「为什么这么判」依然要留痕——队列没有豁免合规。

★关键要点

今天带走这四句

1

同步把调用双方绑成命运共同体(延迟叠加、故障传染、强耦合);队列在中间插一层缓冲,把「接收」和「处理」在时间上拆开。

2

队列的四大红利:解耦、削峰、弹性缓冲、容错重试。判断法则:客户要等/要立刻看到 → 同步;客户不必等 → 异步。

3

先分清模型:一份任务用点对点队列(只被消费一次、可横向扩展);一个事实用 pub/sub(每个订阅者各一份)。选错就是 bug。

4

异步的代价要正视:最终一致 + 乱序、at-least-once 重复投递、积压与背压。consumer 必须幂等——对受监管的扣费/核保尤其是底线。

读完自测一下

Q1QuoteFlow 的「实时报价」接口,适合改成异步丢队列吗?为什么?
不适合。客户在前端等着那个保费数字才能继续,这是必须立刻返回结果的同步路径。异步只适合客户「不必等」的下游(发邮件、再保推送、入仓)。判断标准是「调用方需不需要原地等结果」。
Q2「保单已签发」要通知计费、邮件、分析、再保四个系统,该用点对点队列还是 pub/sub?
pub/sub(发布订阅)。这是一个「已发生的事实」,四个下游都该各收到一份独立副本、各做各的。若用独占的点对点队列,一条消息只会被其中一个抢走,其余三个收不到。
Q3大多数队列只保证 at-least-once,这对 consumer 提出了什么硬性要求?在寿险里不满足会怎样?
consumer 必须幂等:同一条消息处理两次,效果要等于处理一次。否则一条「计提首期保费」被重投,就会重复扣费——在受监管的寿险里属于合规事故。常见做法:用稳定的 message_id 做去重闸门,并把业务写与去重记录放进同一事务。

① QuoteFlow 夜间要批量重算百万级 in-force 保单。如果把「重算每张保单」做成消息丢进点对点队列、起一批 worker 来消费——这个设计有什么好处?又会遇到哪些昨天/今天提到的坑(顺序、幂等、积压)?

A→Z术语表

今日术语

Message Queue
位于发送方与接收方之间的中间件,缓存消息、让两端异步、解耦地通信。
Synchronous / Asynchronous
同步:调用方原地等结果;异步:发出后即返回,处理稍后发生。
Producer / Consumer
生产者把消息写入队列;消费者从队列取出并处理。
Point-to-Point (Work Queue)
一条消息恰好被一个 consumer 处理一次,适合任务分发与横向扩展。
Publish-Subscribe
一条消息被每个订阅者各收到一份,适合广播「已发生的事件」。
Load Leveling (削峰填谷)
用队列暂存瞬时洪峰,让下游按稳定速率消费。
At-least-once
消息保证至少投递一次,可能重复;要求 consumer 幂等。
Idempotency (幂等)
同一操作执行多次与执行一次效果相同。
Backlog / Backpressure
积压:消费跟不上导致队列变长;背压:让上游减速以免压垮下游。
Dead Letter Queue (DLQ)
专门收纳反复处理失败的「毒消息」,便于单独排查、不阻塞主流程。
