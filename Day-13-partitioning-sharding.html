1为什么要切开

复制解决“挂了”,分区解决“装不下”

先把两个经常被混为一谈的词钉死。Replication(复制):每台机器都有完整的一份数据,挂一台还有别台——解决的是可用性和读扩展。Partitioning(分区,在数据库语境常叫 sharding / 分片):把数据切成多份,每台只放一部分——解决的是容量和写扩展。一个是抄作业,一个是分工。

什么时候非切不可?三个信号:① 数据量——QuoteFlow 的报价历史和 audit log 是只增不删的(合规要求留存多年),千万级、亿级行之后,单机磁盘和内存里的索引(Day 9)都开始吃力;② 写吞吐——Day 12 说过所有写只走一个 leader,单 leader 的写入能力就是全系统的天花板,复制再多 follower 也救不了写;③ 并行处理——夜间批量重算百万保单,如果数据切成 16 个分区,就能 16 路并行,各算各的互不干扰。

切开之后,理想图景是:N 台机器,各扛 1/N 的数据和 1/N 的负载。而今天全部的难点,都来自现实对这个理想的偏离:切不均匀(skew)、找不到数据在哪(routing)、机器数变了要重切(rebalancing)、一个查询要跨好几刀(scatter-gather)。

还要先说清一件事:分区和复制不是二选一,而是相乘。真实系统里,每个分区自己又是一套 leader-follower——比如 12 个分区 × 每分区 3 副本 = 36 个数据库实例。昨天的全部内容,在每个分区内部原样上演。

2怎么切

Key-range vs hash:顺序与均匀的对赌

切分永远围绕一个 partition key(分区键)进行:拿记录的某个字段,决定它落在哪个分区。两大流派:

Key-range partitioning(按键范围切)

像图书馆按书名首字母分书架:policy_id 000001–250000 → P1,250001–500000 → P2……好处是保序:相邻的 key 物理上也相邻,范围查询(“2026 年 5 月的全部报价”)只扫一两个分区。代价是容易产生热点:如果 key 本身有时间倾向——比如报价记录按 created_at 切——那么今天所有的写入都砸在“最新”那个分区上,其余分区在睡觉。N 台机器,写吞吐还是 1 台的水平,白切了。

Hash partitioning(按键哈希切)

先对 key 求哈希,再按哈希值分配分区。好的哈希函数会把哪怕高度相似的 key 也打散到天南地北——均匀是它的天赋。代价同样直接:顺序没了。相邻的 key 散落各处,范围查询退化成“问遍所有分区再合并”。所以 Cassandra 等系统玩了个折中:compound key——(customer_id, created_at),第一段哈希定分区,第二段在分区内保序:同一客户的报价记录聚在一起、按时间排好,“查某客户最近的报价”既均匀又高效。

Key-rangeHashDirectory(查表)
分配方式按 key 的连续区间按 hash(key) 落桶一张“key → 分区”映射表,人为指定
范围查询高效(顺序保留)差(scatter-gather)取决于映射设计
负载均匀度易倾斜,需主动拆热分区天然均匀(除非单 key 过热)可手动调,但靠人勤快
热点风险时间型 key 必产生“最新分区”热点低;但同一 key 的流量无法再切映射服务本身可能成瓶颈/单点
代表系统HBase、早期 BigtableCassandra、DynamoDB很多自研分库分表中间件
QuoteFlow 落点audit log(按月切,顺带满足留存策略)保单库、报价历史(均匀第一)(不引入:多养一个关键服务不值)

▲ 没有全能选手:要顺序就赌得过热点,要均匀就放弃范围查询。先想清楚你最高频的查询长什么样(Day 11 的老话),再选切法。

最后是 skew(倾斜)的另一种形态:哪怕 hash 切得再均匀,如果某一个 key 本身就承载了不成比例的流量——比如 QuoteFlow 某个聚合渠道的 broker 账号,一家就发来 30% 的报价请求——它的所有记录仍然落在同一个分区。哈希对“单 key 过热”无解,只能在应用层把这种 key 再拆细(如 broker_42#01、broker_42#02),代价是读它时要自己再合并。

3机器数会变

Rebalancing 与 consistent hashing

分区方案定了,新问题接踵而来:机器数不是常量。业务涨了要加节点,机器坏了要摘节点。这时数据要重新分布(rebalancing),而 rebalancing 的黄金标准只有一条:搬的数据越少越好——搬家期间网络、磁盘都在烧钱,搬错了还影响正确性。

最朴素的方案 partition = hash(key) mod N 在这里翻车:N 从 4 变成 5,几乎所有 key 的 mod 结果都变了——意味着集群里约 80% 的数据要搬家。加一台机器,全网大迁徙,这显然荒谬。

Consistent hashing 的解法优雅得多:把哈希值空间首尾相接,想象成一个环。节点和 key 都哈希到环上;每个 key 归属沿顺时针方向遇到的第一个节点。增加一个节点,它只“接管”环上紧邻的一段弧——只有这段弧上的 key 需要搬家,约占总量的 1/N,其余 key 纹丝不动。摘掉一个节点同理:它的弧由顺时针的下一个节点接手。

还有最后一块拼图。只把每个节点哈希到环上一个点,会有两个毛病:节点少时弧段长短悬殊(不均匀);节点下线时,它的全部负载砸给顺时针的下一个邻居(雪上加霜)。解法是 virtual nodes(虚拟节点):每个物理节点在环上放几十到几百个分身。弧被切得细碎均匀,某台物理机下线时,它的负载被所有幸存节点分摊,而不是压垮一个邻居。Cassandra、DynamoDB 的环都这么做。

consistent_hashing.py · 带 virtual nodes 的环(伪代码)
# 环 = 一个有序 map:position → 物理节点
class HashRing:
    def add_node(self, node, vnodes=200):
        for i in range(vnodes):              # 每台物理机 200 个分身
            pos = hash(f"{node}#{i}")        # 分身散布全环 → 均匀
            self.ring[pos] = node

    def get_node(self, key):
        pos = hash(key)
        return self.ring.ceiling(pos)         # 顺时针第一个节点(到尾则绕回头)

# 加节点:只有新分身“接管的弧段”上的 key 需要迁移 ≈ 1/N
# 对比 mod N:hash(key) mod 4 → mod 5,约 80% 的 key 换家 ✗

ring.add_node("db-shard-04")
ring.get_node("policy:P-2026-08831")      # → "db-shard-02",路由完成

顺带校准一个工程直觉:很多托管数据库(如 DynamoDB)把这一切藏在幕后,你只管选好 partition key;而自建分库分表时,rebalancing 是最容易出事故的运维操作之一——所以常见策略是一开始就切多(比如 1 台机器先扛 64 个逻辑分区),扩容时整分区搬走,不重切数据。

4隐性账单

二级索引与跨分区查询

按 partition key 查,一跳直达,很美好。但现实查询不会只按一个键来。QuoteFlow 保单库按 policy_id 哈希分区,那么“查客户 C-1024 的全部保单”怎么办?这就是分区世界里的二级索引(secondary index)问题,两种流派:

① Local index(本地索引,document-partitioned):每个分区只给自己那部分数据建索引。写入快——索引和数据在同一分区,一次写完。但按二级键查询时,任何分区都可能藏着匹配行,只能scatter-gather:把查询广播到所有分区、各自查完再合并。分区越多,尾延迟越糟(p99 由最慢的那个分区决定——Day 2 的 tail latency 又见面了)。

② Global index(全局索引,term-partitioned):索引本身也按被索引的值切分,比如 customer_id 的索引集中放在确定的分区。读高效——查一个客户只打一两个分区。代价转嫁给写:写一张保单,要同时更新另一个分区上的索引,跨分区写要么慢(分布式事务,明天的主题),要么异步(索引短暂滞后——又是 Day 12 的 lag)。

工程结论很朴素:选 partition key 的真正标准,是让你最高频、延迟最敏感的查询“单分区可达”,把 scatter-gather 留给低频的分析类查询。选错分区键的痛苦,往往要到数据搬不动时才显现——这也是为什么它值得在设计期多想一天。

请求怎么找到分区:routing

最后一个实务问题:客户端发来 GET policy P-8831,谁知道它在哪个分区?三种做法:① 随便问一台,节点不持有就转发(Cassandra 的 gossip 风格);② 中间加一层路由层,由它持有“分区 → 节点”映射(很多分库分表中间件);③ 客户端自己聪明,直接持有映射表。无论哪种,“当前谁负责哪个分区”这份元数据必须强一致地维护——通常交给 ZooKeeper / etcd 这类协调服务,这正是 Day 19(共识与协调)的伏笔。

5贯穿案例

QuoteFlow:给每张表选分区键

把今天的工具箱用在 QuoteFlow 的三类数据上。注意每个选择背后,都是“最高频查询长什么样 + 监管要求什么”这两个问题在做主:

Case · QuoteFlow

保单库:hash on policy_id —— 均匀第一,分区键终身不变

保单的高频访问是按单号点查(客服、理赔、客户自助),hash 分区一跳直达且天然均匀。特意不用 customer_id 当分区键:客户持有保单数差异巨大(个人 1 张 vs 团体渠道数千张),会倾斜;且分区键一旦选定,这条记录就“住死”在那个分区——选一个 immutable 的键(policy_id 永不变)能避免记录搬家。“按客户查保单”交给一个异步维护的 global index:索引晚几秒无妨,保单本体的写入路径不被拖慢。

报价历史:hash on compound key (quote_id),夜间重算按分区并行

报价记录量最大(大部分报价不会成交,但合规要求照样留痕)。hash 分区摊平写入;夜间批量重定价天然变成 per-partition 并行:16 个分区 16 个 worker,各自扫自己的分区,吞吐随分区数横向扩展——Day 2 的 high throughput 需求在这里兑现。每个 worker 的输出连同 rate_table_version 留痕,重算结果可复现。

Audit log:key-range on 时间(按月分区)—— 一个“好热点”

审计日志几乎只有两种访问:追加写“现在”,和按时间段审查“过去”(监管问询:“给我 3 月 1 日到 31 日所有费率变更记录”)。按月 range 分区让审查查询只扫一两个分区;留存策略也顺手——超过法定年限的旧分区整段归档/下线,不用逐行删除。写热点确实集中在“本月”分区,但 audit 写入是顺序追加、量可控,热点在容量预算之内——规则是死的:热点不是绝对禁忌,算得过来账就行。

受监管定价的提醒
  • 分区切开的是数据,切不开的是合规义务:监管报表、reserving、再保上报都是天然的跨分区聚合。设计时要预留一条“全量扫描/导出”的离线路径(Day 17 的批处理管道),而不是指望在线库的 scatter-gather 临时凑数。另外,“哪条记录此刻在哪个分区、何时迁移过”本身也值得留痕——审计师重建历史查询时,rebalancing 不能成为数据“凭空消失”的借口。
★关键要点

今天带走这四句

1

复制是拷贝,分区是切开:前者买可用性和读扩展,后者买容量和写扩展。真实系统二者相乘:每个分区内部自带一套 leader-follower。

2

Partition key 决定一切:range 保顺序但赌热点,hash 保均匀但失顺序。标准只有一条——让最高频的查询单分区可达,并选 immutable 的键。

3

Consistent hashing + virtual nodes:把节点和 key 都放到哈希环上,增减节点只迁移 ≈1/N 的数据;mod N 则几乎全量搬家。

4

分区的隐性账单是跨分区操作:二级索引要么 scatter-gather(读贵)要么 global index(写贵);跨分区的“原子写”更难——那是明天分布式事务的主题。

?今日小测 + 思考题

读完自测一下

Q1报价历史表按 created_at 做 key-range 分区,会发生什么?
写热点。所有新报价都写入“最新”那个分区,其余分区闲置——N 台机器只有 1 台在干活,写吞吐没有任何扩展。修法:hash 分区摊平写入;若需要时间范围查询,用 compound key 或把时间维度留给离线分析管道。(对比:audit log 按月 range 分区是有意识地接受这个热点,因为追加写量可控、且按时间段审查和整月归档的收益更大。)
Q2为什么 hash(key) mod N 不适合做分区分配?Consistent hashing 好在哪?
因为 N 会变。N 从 4 变 5 时,几乎所有 key 的 mod 结果都变了,≈80% 的数据要迁移。Consistent hashing 把节点和 key 都映射到首尾相接的环上,key 归顺时针第一个节点——新增节点只接管一段弧,只迁移约 1/N 的数据;配合 virtual nodes,负载在增减节点时还能均匀分摊到所有幸存节点。
Q3保单库按 policy_id 分区后,“查客户 C-1024 的全部保单”有哪两种支持方式?各贵在哪?
Local index:每个分区索引自己的数据,写入快,但查询要 scatter-gather 广播所有分区,读贵、p99 被最慢分区拖累。Global index:按 customer_id 集中存索引,读只打一两个分区,但每次写保单要跨分区更新索引——要么慢(分布式事务)要么异步滞后(lag)。QuoteFlow 选了异步 global index:保单写入路径不拖慢,索引晚几秒可接受。
带着这两个问题回来讨论

① QuoteFlow 的保单库,如果当初选了 customer_id 而不是 policy_id 当分区键,哪些查询会变好、哪些会变糟、哪些运营场景会埋雷?(提示:团体保单渠道、客户改信息、夜间重算。)
② 夜间批量重算按分区并行后,某一个分区的 worker 失败了。重跑整晚还是只重跑那个分区?这个选择对“重算结果可审计、可复现”提出了什么要求?(这题是给 Day 17/18 埋的伏笔。)

A→Z术语表

今日术语

Partitioning / Sharding
把数据集切成多份,每个节点只持有一部分,以扩展容量与写吞吐。
Partition Key
决定一条记录落在哪个分区的字段;应选 immutable、且让高频查询单分区可达。
Hot Spot / Skew
负载或数据在分区间分布不均,少数分区扛走大部分流量,扩展失效。
Key-range Partitioning
按键的连续区间切分;保顺序、利范围查询,但时间型键易产生热点。
Hash Partitioning
按 hash(key) 分配分区;天然均匀,但丢失顺序,范围查询退化。
Consistent Hashing
把节点与 key 映射到哈希环,key 归顺时针首个节点;增减节点仅迁移约 1/N 数据。
Virtual Node (vnode)
每个物理节点在环上的多个分身;使弧段细碎均匀,故障负载由全员分摊。
Scatter-Gather
把一个查询广播到所有分区、再合并结果;二级索引查询的常见代价,p99 受最慢分区支配。
