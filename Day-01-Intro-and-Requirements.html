1系统设计在解决什么

“算得对”只是及格线

QuoteFlow 要做的核心事情之一,是算出正确的保费:给定投保人信息、费率表、再保参数,输出一个数字——这是 correctness(正确性)。这部分逻辑本身,往往是有标准答案的。

System design 处理的是另一类问题。当成千上万用户同时请求报价;当依赖的费率服务突然挂了;当历史保单长到一条 SQL 要跑好几秒;当你要在不停机的情况下换一套定价算法——系统还能不能正确、快速、稳定、可追溯地继续服务?

一个比喻会很贴切:写一个定价模型,像设计一道菜的配方;系统设计,像设计整个餐厅的后厨——要同时出 200 桌、食材会断货、厨师会请假、高峰会排队,而且明年还要能开第二家分店。配方再完美,后厨垮了,客人一样吃不上饭。

这里有一个贯穿这 30 天的核心张力:几乎没有“最好”的设计,只有“在给定约束下的合理取舍(trade-offs)”。你真正要练的,是识别约束、并在冲突的目标之间做出有依据的权衡。

2需求拆解:第一刀

先问“做什么 + 做多好”,再画图

新手做系统设计最常见的错误,是一上来就画框图、选数据库。真正的第一步是把需求问清楚:这个系统到底要做什么,又要做到什么程度。把需求切成两类,整张图立刻清晰:

Functional requirements(功能需求)

系统“做什么”。每一条都能用一个具体的输入 → 输出来描述。例:给定投保人的年龄/性别/吸烟状态/保额 → 返回一个保费报价。它定义了系统“算什么”。

Non-functional requirements(非功能需求 / 质量属性)

系统“做得多好”。它不改变系统算的是什么,却决定它好不好用、扛不扛得住、能不能上线。例:报价要在 200ms 内返回(latency);99.9% 的时间可用(availability);每一条报价可审计、可复现(auditability)。

关键认知:难点几乎总是在 non-functional 这一侧。“算得对”通常有标准答案;“又快又稳又可审计又能扩展”才是工程上真正花力气的地方。

3质量维度速览

Non-functional 的常见“多好”

明天(Day 2)会把这些维度逐个量化并讲透取舍,今天先建立词汇表,看到名字能对上号:

维度一句话对 QuoteFlow 意味着
Latency单次请求多快返回客户在前端等报价的体感
Throughput单位时间能处理多少夜间批量重算百万保单的吞吐
Availability有多大比例时间可用承保渠道随时能拿到报价
Scalability量涨了能不能跟上新产品上线、流量翻倍仍稳
Consistency各处读到的数据一不一致费率表更新后,不能新旧混用
Auditability每个结果能否复现/解释受监管定价的一等公民:每条报价为什么是这个数,要留痕、可回溯、合规
受监管定价的提醒
  • 对大多数互联网系统,latency / availability 是主角。但对寿险定价这类受监管系统(QuoteFlow 正是),auditability、traceability、regulatory compliance 是同等甚至更高优先级的 non-functional 需求。设计里要把它当一等公民,而不是事后补丁。

5贯穿案例

拆解 QuoteFlow 的需求

把第 2 步学的“两类需求”用在 QuoteFlow 上。先别想架构,只列需求:

Case · QuoteFlow

Functional —— 它要做什么

接收报价请求 → 校验输入 → 拉取费率表 / 核保规则 / 再保参数 → 计算保费 → 返回报价并留痕。每一项都是一个明确的输入输出动作。

Non-functional —— 它要做到多好

单笔实时报价 p99 < 300ms;夜间批量重算百万级保单要在维护窗口内跑完;规则变更要能灰度发布、可回滚;每条报价可审计、可复现;PII 加密合规。

注意一件重要的事:列 non-functional 时,取舍已经浮现了。“单笔 300ms 实时报价”和“夜间百万保单批量重算”是两条性质完全不同的路径——一条要低延迟、一条要高吞吐,硬塞进同一套设计往往两头都不讨好。(第 17 天“批处理 vs 流处理”会专门回到这个判断。)

下面把 functional 需求落成一个具体的接口契约草图。看不懂语法没关系,重点是感受:需求是怎么变成系统对外的“合同”的。

POST /v1/quotes · QuoteFlow 接口契约(示意)
// ── 请求:functional 需求“算什么”的具体形态 ──
POST /v1/quotes
{
  "applicant": { "age": 42, "sex": "F", "smoker": false },
  "product":   "TERM_LIFE_20Y",
  "sum_insured": 500000,
  "rate_table_version": "2026-06"   // ← 钉住版本 = consistency + auditability
}

// ── 响应:注意它同时承载了 non-functional 的痕迹 ──
200 OK
{
  "quote_id": "q_8f3a...",        // 可追溯:每条报价有稳定 id
  "monthly_premium": 38.20,
  "currency": "AUD",
  "rate_table_version": "2026-06",
  "rules_applied": ["base_rate", "non_smoker_disc"],  // 可解释 / 审计
  "computed_at": "2026-06-01T08:00:12Z",
  "latency_ms": 47                  // 把 SLA 变成可观测的数字
}

看这份契约:age/sex/smoker → premium 是 functional;而 rate_table_version(一致性)、rules_applied(可审计)、latency_ms(延迟可观测)这些字段,是把 non-functional 需求“焊进”接口的方式。好的设计,从契约这一层就开始为质量属性留位置。

★关键要点

今天带走这四句

1

系统设计先问“做什么 + 做多好”,再画图、再选技术。顺序错了,后面全是返工。

2

Functional = 算什么;Non-functional = 算得多好/多稳。后者通常才是真正的难点。

3

没有“最优解”,只有约束下的取舍。识别约束、做有依据的权衡,是这门手艺的核心。

4

在受监管的定价系统里(如寿险),auditability 与 compliance 是一等公民的 non-functional 需求,要从契约层就设计进去。

?今日小测 + 思考题

读完自测一下

Q1“报价接口必须在 200ms 内返回” —— 属于哪类需求?
Non-functional(具体维度是 latency)。它没改变系统“算什么”,只约束“算得多快”。
Q2“系统要能根据年龄、性别、吸烟状态计算保费” —— 属于哪类?
Functional。这是一个明确的输入 → 输出动作,定义了系统“算什么”。
Q3如果 functional 全对,但 non-functional 不达标,系统能上线吗?
通常不能。慢到没人愿意用、动不动就挂、或报价无法审计——在受监管的定价场景里,最后一点可能直接意味着违规。“算得对”是必要条件,不是充分条件。
带着这两个问题回来讨论

① 给 QuoteFlow 做设计时,最容易被低估的 non-functional 需求会是哪个?
② 把“实时单笔报价”和“夜间批量重算”拆成两条独立路径,会带来什么好处、又要付出什么代价?

A→Z术语表

今日术语

System Design
在真实约束下,把组件组织成能持续、可靠服务的系统的设计活动。
Functional Requirement
系统“做什么”,可用具体的输入→输出描述。
Non-functional Requirement
系统“做得多好”,一个可度量的质量指标或约束。
Latency
单次请求从发出到返回所花的时间。
Throughput
单位时间内系统能处理的请求/数据量。
Availability
系统在一段时间内可正常服务的比例(如 99.9%)。
Trade-off
在相互冲突的目标间做出的有依据的取舍。
Auditability
每个结果能否被复现、解释、追溯到其依据。
