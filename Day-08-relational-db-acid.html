数据库凭什么
当“权威源”

第一周我们反复把数据库当成 source of truth 在用——缓存可以丢、可以旧,但“以库为准”。今天正式走进数据层,在你已有的 SQL 基础上往深里挖:它凭什么配当那个“准”——答案是 transaction 和 ACID。

昨日回顾 · Day 7

1事务:一个原子单元

“要么全做,要么全不做”

你已经写过无数 INSERT / UPDATE。今天换个角度看它们:很多业务动作不是一条语句,而是好几条必须捆在一起的语句。捆不住,系统就会留下“半成品”。

QuoteFlow 签发一张保单,数据库里至少要发生三件事:写入保单主记录(policies)、建立首期账单(billing)、写一条审计日志(audit_log,合规要求:谁、何时、依据哪个 rate_table_version 签发)。现在设想:第一条写成功了,服务器在写第二条时崩了。结果是——一张有保单、没账单、没留痕的孤儿记录。在受监管的寿险里,这不是 bug,是事故。

事务(transaction)就是为这个而生的:把这几条语句声明成一个不可分割的单元。BEGIN 开启,中间随便写多少条,最后 COMMIT 让它们一起生效;只要中途任何一步出错,ROLLBACK 让它们一起当作没发生过。没有“写了一半”的中间态对外可见。

这就是数据库“配当权威源”的第一块基石。下面把这套保证拆成四个字母——ACID。

2ACID 逐字拆解

四个字母,各防一种灾难

ACID 不是一个抽象口号,而是四条互相独立的保证,每一条都在堵住一类具体的事故。用 QuoteFlow 签发保单这一笔事务挨个对照:

A — Atomicity(原子性)

事务里的所有操作,要么全部生效,要么全部不生效,没有中间态。上面那个“有保单没账单”的孤儿记录,正是原子性在防的灾难。它的实现机制(概念级)是 write-ahead log(WAL):改动先写进一份日志,崩溃重启时按日志把没 commit 的事务回滚干净。

C — Consistency(一致性)

这里的 consistency 容易和 Day 2 讲的“分布式一致性”混。ACID 的 C 指的是:事务结束后,数据库仍满足所有既定规则——主键唯一、外键有效、CHECK 约束、以及你自定义的业务不变量(如“保额必须 > 0”“in-force 保单必须有对应 billing”)。事务把数据库从一个合法状态搬到另一个合法状态,不会停在违规状态。(注意:这个 C 和 CAP 里的 C 是两码事,Day 12 会专门厘清。)

I — Isolation(隔离性)

多个事务并发跑时,彼此不应该互相看到对方“写了一半”的脏数据;理想情况下,并发执行的结果应当等价于某种串行执行。这是 ACID 里最微妙、代价最高、也最常被调档的一条——下一节单独展开。

D — Durability(持久性)

一旦 COMMIT 返回成功,数据就真的落到了非易失存储(磁盘 / SSD),哪怕下一秒断电、进程崩溃,重启后它依然在。这正是昨天 Day 7 那句“write-back 缓存可能丢数据”的反面:审计日志、保单、扣款这类记录,必须落到有 durability 保证的库里,不能停在易失的内存缓存上。

给受监管定价的一句话
  • 对 QuoteFlow 这种系统,A + D 直接撑起了 auditability:原子性保证“签发”和“留痕”同生同灭(不会有签了却没记的保单),持久性保证留痕一旦写下就不会丢。监管要的“每笔都可追溯”,技术底座就在这两个字母上。
3Isolation 深入

并发的三种异常,与四档隔离级别

Isolation 难,是因为它有档位——隔离越强越安全,但锁越多、并发越低。要选对档,先得认识它在防的三种经典并发异常(都假设事务 T1、T2 同时在跑):

① Dirty read(脏读):T1 读到了 T2 还没 commit 的修改;万一 T2 随后 rollback,T1 就基于一个“从未存在过”的值做了决定。
② Non-repeatable read(不可重复读):T1 在同一事务里读同一行两次,中间 T2 改了它并 commit,于是两次读到不同的值。
③ Phantom read(幻读):T1 用同一个条件查一组行两次(如“所有 product=TERM_LIFE_20Y 的报价”),中间 T2 插入/删除了符合条件的行,于是两次查到的行数/集合变了——凭空多出或少掉“幻影”行。

SQL 标准用四档隔离级别,逐级把这些异常关掉:

隔离级别脏读不可重复读幻读代价 / 谁在用
Read Uncommitted可能可能可能几乎不防,极少使用
Read Committed挡住可能可能开销小;PostgreSQL / Oracle / SQL Server 默认
Repeatable Read挡住挡住可能*更多锁/快照;MySQL InnoDB 默认
Serializable挡住挡住挡住最强最贵,可能更多锁冲突/重试

▲ 越往下越安全,但并发吞吐越低。*按 SQL 标准 Repeatable Read 仍可能幻读;MySQL InnoDB 靠 MVCC + gap lock 实际上也挡住了大部分幻读——“标准定义”和“某数据库的实现”常常对不齐,这是个高频坑。

怎么用得起“强隔离又不太慢”?现代数据库的答案多是 MVCC(multi-version concurrency control,多版本并发控制):每个事务看到的是一份数据在它开始那一刻的快照,读不加锁、读写不互相阻塞——读多的报价场景因此能既一致又快。这也是为什么 PostgreSQL 默认的 Read Committed 在实践中体感很好。

对 QuoteFlow 的取舍直觉:报价(读多)路径通常 Read Committed 足够;但涉及钱、额度、状态翻转的写(签发、扣款、调整保额)往往需要更强隔离,否则会撞上经典的 lost update(两笔并发更新,后写覆盖前写,丢了一次)。判断标准还是 Day 2 那句:这份数据“读到旧一点 / 看到别人写一半”会不会出事?

4落到代码与边界

事务长什么样,以及它的代价

把第 1 节那笔签发写成事务,ACID 就具体了:

issue_policy.sql · QuoteFlow 签发一张保单(示意)
BEGIN;                                  -- 从这里到 COMMIT 是一个原子单元

  -- ① 写保单主记录
  INSERT INTO policies (policy_id, applicant_id, product, sum_insured, status)
  VALUES ('p_77a2', 'a_1043', 'TERM_LIFE_20Y', 500000, 'IN_FORCE');

  -- ② 建首期账单
  INSERT INTO billing (policy_id, amount, due_date)
  VALUES ('p_77a2', 38.20, '2026-07-01');

  -- ③ 写审计日志:谁、何时、依据哪个版本签发(合规一等公民)
  INSERT INTO audit_log (entity, entity_id, action, rate_table_version, actor, at)
  VALUES ('policy', 'p_77a2', 'ISSUE', '2026-06', 'underwriting-svc', now());

COMMIT;                                 -- 三步一起生效;任一步报错 → ROLLBACK,一起作废

注意 rate_table_version='2026-06' 又出现了——它从 Day 1 的接口契约、Day 7 的版本化缓存 key,一路贯穿到这里的 audit_log。同一个版本号在报价、缓存、落库三处对齐,就是 reproducibility 的实现方式:任何一笔报价/保单,日后都能复现出“当时用的是哪套费率”。

但 ACID 不是免费的,用之前要知道它的边界:

代价 / 限制含义与后果
锁与争用 (contention)强隔离靠加锁;事务持锁越久,别的事务等得越久,吞吐下降。事务要短、别在事务里调外部 API 或等用户输入。
死锁 (deadlock)两个事务互等对方的锁。数据库会检测并 kill 掉一个让它重试——应用要能容忍重试。
单机为主经典 ACID 在一台数据库上最自然。一旦数据跨多台机器/多服务,要凑齐 ACID 就极难——这就引出了 Day 12(复制/CAP)和 Day 14(分布式事务 / saga)。
不是万能存储它擅长强一致的事务型写(OLTP),不擅长海量松散写或灵活 schema——那是后面 NoSQL(Day 11)的地盘。
Case · QuoteFlow

事务边界画在哪

QuoteFlow 里值得用一个事务包起来的,是那些“必须同生共死”的写:签发(policy + billing + audit)、扣款(扣 billing + 记 ledger + 写 audit)、保额调整(改 policy + 记 audit)。它们一旦只做一半,就会产生对账对不平、审计链断裂的灾难。

哪里不该硬塞进一个大事务

反过来,夜间给百万保单批量重定价就不该用“一个超大事务包住全部”——那会把锁持有几个小时、一处失败整批回滚、还可能撑爆日志。更合理的是每张保单(或每小批)一个小事务,各自原子、独立 commit、失败的单独重试。这正是“原子性该多原子”的边界判断,Day 17(批处理 vs 流处理)会把这条夜间链路完整展开。

★关键要点

今天带走这四句

1

Transaction = 把多条语句捆成一个原子单元:COMMIT 全生效、ROLLBACK 全作废,外界看不到“写一半”。这是数据库配当权威源的根基。

2

ACID 四字各防一灾:A 不留半成品、C 不违反规则、I 并发不互相污染、D 提交后不丢。受监管定价的 auditability 主要落在 A + D。

3

Isolation 有档位:脏读 / 不可重复读 / 幻读逐级被关掉,越强越慢。多数库默认 Read Committed,靠 MVCC 做到读不加锁。

4

ACID 有代价(锁、争用、死锁)且单机最自然。事务要短;边界按“是否必须同生共死”画;跨机器的 ACID 是后面 Day 12/14 的硬骨头。

?今日小测 + 思考题

读完自测一下

Q1签发保单要写 policies / billing / audit_log 三张表,写到 billing 时进程崩了。ACID 哪个字母保证不会留下“有保单、没账单”的孤儿记录?靠什么机制?
Atomicity(原子性)。三条 INSERT 在一个事务里,崩溃时未 commit 的改动会被整体 ROLLBACK(机制概念上是 write-ahead log:改动先写日志,重启按日志回滚未提交事务),于是“要么三条都在、要么一条都没有”,绝不留半成品。
Q2PostgreSQL 默认是 Read Committed。在它下面,一个事务里两次 SELECT 同一行,可能读到不同的值吗?这叫什么异常?想避免该升到哪一档?
可能,这叫 non-repeatable read(不可重复读)——两次读之间有别的事务改了那行并 commit。Read Committed 只挡脏读,不挡这个。要让同一事务里重复读保持一致,升到 Repeatable Read(它对同一行给你一份稳定快照)。
Q3把昨天 Day 7 的“write-back 缓存可能丢数据”和今天的 Durability 联系起来——它们是什么关系?对 QuoteFlow 的写路径意味着什么?
Durability 正是 write-back 风险的反面。write-back 先写易失内存、稍后才刷库,缓存一挂,没刷的就凭空消失;而 durability 保证 COMMIT 一返回数据就已落到非易失存储。所以 QuoteFlow 的审计、保单、扣款这类写必须落进有 durability 保证的数据库事务里,缓存只在读侧帮忙——这就是“写路径别图快”的技术理由。
带着这两个问题回来讨论

① QuoteFlow 夜间给百万保单批量重定价,事务边界该画在“每张保单一个小事务”还是“整批一个大事务”?各有什么取舍(想想锁持有时间、失败回滚范围、日志大小)?
② 同一个 QuoteFlow,为什么报价(读)路径和签发/扣款(写)路径可以选不同强度的隔离级别?你会怎么给这两条路径各定一档,理由是什么?

A→Z术语表

今日术语

Transaction
一组要么全部生效、要么全部回退的数据库操作单元(BEGIN…COMMIT/ROLLBACK)。
ACID
事务的四条保证:Atomicity / Consistency / Isolation / Durability。
Atomicity
原子性:事务内操作全成或全不成,不留中间态;靠回滚实现。
Durability
持久性:COMMIT 成功后数据落到非易失存储,崩溃/断电也不丢。
Isolation Level
并发事务彼此可见程度的档位:Read Uncommitted / Committed / Repeatable Read / Serializable。
Dirty / Non-repeatable / Phantom Read
三种并发异常:读到未提交值 / 同一行两次读不一致 / 同一查询两次行集变化。
MVCC
多版本并发控制:每个事务读它开始时的快照,读不加锁、读写不互阻。
WAL (Write-Ahead Log)
预写日志:改动先写日志再改数据,支撑原子性与崩溃恢复。
