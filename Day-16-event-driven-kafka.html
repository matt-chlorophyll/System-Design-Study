1翻转控制权

从「叫人做事」到「广播发生了什么」

先把三个常被混用的词钉死。Command(命令)是「请你去做某事」——有明确的接收者、期待一个结果,比如 重算保单 pol_8f3a。Event(事件)是「某件事已经发生了」——用过去式陈述一个事实,发布者不关心谁会听、也不期待回应,比如 PolicyIssued(pol_8f3a)。Message(消息)是最中性的词:承载 command 或 event 的那个信封。命令是祈使句,事件是陈述句——这一字之差,决定了整个架构的耦合方向。

传统的「命令式」系统里,签发服务做完会主动去调用计费、邮件、再保——它必须知道每一个下游的存在,下游一变它就得改。事件驱动(event-driven)把箭头反过来:签发服务只往外喊一句「保单已签发」,然后不管了;谁关心这件事,谁自己来订阅、自己决定怎么反应。发布者对订阅者一无所知——这就是控制权的翻转。

好处很直接:加一个新下游(比如「保单签发后触发一次反洗钱复查」),核心服务一行都不用改、不用重新部署,新服务订阅那条事件就行。系统从一张「谁调用谁」的硬接线网,变成一块「事实广播 + 自由订阅」的公告板。代价我们第 4 节再算账。

2队列 vs 日志

Kafka 新在哪:消息读完不删

昨天的队列(RabbitMQ、SQS 这类)有个隐含动作:消息被成功消费、ack 之后,就从队列里删掉了。队列像信箱,信取走就没了;它关心的是「这件待办有没有人处理掉」。

Kafka 这类日志型(log-based)系统换了个根本模型:消息被追加到一个只增不改的有序日志(append-only log)末尾,读取并不删除它。每条消息有一个单调递增的序号——offset。消费者不是「取走」消息,而是记住自己读到了第几号(committed offset),下次从那儿往后接着读。消息留多久,由 retention(保留策略)决定——按时间(如 7 天)或按容量,而不是「读完即焚」。

这一个改动,解锁了队列做不到的几件事:

① 多个独立消费者互不干扰。计费、分析、再保各自维护自己的 offset,在同一份日志上各读各的进度——这就是 pub/sub,但天然内建,无需把消息复制多份。② 可重放(replay)。分析系统改了算法、想重算过去 30 天?把自己的 offset 拨回去,从头再读一遍即可,源头日志原封不动。这对受监管系统是杀手级特性。③ 日志本身成了「事实的唯一真相源」。系统状态可以看作「把这串事件从头放一遍」的结果——这正是 event sourcing 的内核。

传统队列(RabbitMQ/SQS)日志型(Kafka)
消费后消息被删除消息保留,只移动 offset
消费进度由谁记broker(队列删了就没了)consumer 自己记 offset
能否重放历史不能,读完即逝能,把 offset 拨回去重读
多下游各取一份要复制成多个队列天然支持,各维护各的 offset
心智模型信箱:取走即空账本:只追加、可回看
最擅长任务分发、命令、即用即弃事件流、审计、重放、流处理

▲ 不是谁取代谁:命令式「待办任务」用队列更顺手;「已发生的事实流」用日志更强。很多系统两者并用。

3核心零件

Topic、Partition、Offset、Consumer Group

Kafka 的扩展能力,全靠 partition(分区)这一招。一个 topic(比如 policy-events)在物理上被切成若干 partition,每个 partition 是一条独立的、自带 offset 的有序日志。消息按 partition key(比如 policy_id)做哈希,决定落到哪个 partition。这带来一条必须记牢的保证:

Kafka 只保证「同一个 partition 内」严格有序,不保证跨 partition 的全局顺序。所以只要把同一张保单的所有事件用同一个 key 路由到同一个 partition,它们就一定按发生顺序被读到——这正好解决了昨天思考题里「保单生效 / 取消乱序」的隐患(Day 13 分片的分区键思想在这里复用)。

最后两个零件:consumer group(消费组)把 pub/sub 和负载均衡合二为一。同一个 group 内,每个 partition 只会分给一个 worker——组内是「分担负载」(点对点的效果),所以一个 group 的并行度上限就是 partition 数。而不同 group 之间互不影响、各读全量——这是「广播」(pub/sub 的效果)。于是「计费组」「分析组」各自拿到完整事件流,组内部又能多起 worker 分摊。一套机制,同时给了你昨天讲的两种模型。

4没有免费的事件

事件驱动的代价:认清再上车

事件驱动很优雅,但它把复杂度从「代码里显式的调用链」转移到了「散落各处的隐式反应」。不正视这些,系统会变成谁也说不清的「事件意大利面」。

① 没有人「拥有」整个流程。命令式代码里,一个函数从头到尾写明了业务流程,读代码就懂。事件驱动里,「投保 → 核保 → 签发 → 计费」这条链被拆成 N 个互不知情的订阅者,整条流程不写在任何一个地方。要搞懂全貌,得把所有订阅关系拼起来。好处是松耦合,代价是「全局意图」变隐形。

② 最终一致,且更难追踪。事件异步流动,各下游状态在不同时刻才追上(eventual consistency,昨天讲过)。更棘手的是调试:一笔业务横跨多个服务、由一串事件串起,要靠 correlation_id 把碎片缝回一条链(Day 24 可观测性会专门讲分布式追踪)。

③ Schema 演进是真问题。事件一旦发布、还会被长期保留和重放,它的格式就成了服务之间的长期契约。今天加个字段、明天删个字段,可能让一年前的老消费者在重放时崩掉。需要 schema registry 和「向前/向后兼容」的纪律(回看 Day 5 API 版本化——这里是同一道题的事件版)。还有老朋友:at-least-once 依然成立,consumer 仍要幂等。

什么时候该选事件驱动 / 日志
  • 该用:一个事实有多个互不相关的下游反应;需要重放历史(回填、改算法重算、灾后重建);需要不可篡改的事件留痕做审计;要做流处理(Day 17)。
  • 别硬上:只是「A 调一下 B、要立即拿结果」的简单同步请求(直接 API 调用更清楚);团队还没有可观测性与 schema 治理能力时,事件驱动的隐式复杂度会反噬。

Case · QuoteFlow

一条事件,各方自取

签发服务发布 PolicyIssued;计费 group 建立首期账单、邮件 group 发保单文件、分析 group 入数仓、再保 group 生成上报——四个组互不知情、各记各的 offset。新增一个「合规归档」下游?它订阅同一 topic 即可,签发服务零改动。

日志 = 天生的 audit trail

这是寿险定价最受用的一点:policy-events 这本只追加、不可改、有序、可重放的日志,本身就是一份完整的审计轨迹——每张保单「为什么在某时刻变成这样」,顺着事件从头放一遍就能精确复现。reproducibility / traceability 不再是事后补的日志表,而是架构的副产品。

下面是一个事件的 schema 与计费 consumer 的骨架,重点看版本化字段(schema 演进)、按 offset 消费与幂等:

policy_events.py · 事件 schema + 日志型 consumer
# ── 一条事件:过去式命名,陈述「已发生的事实」 ──
event = {
    "event_type": "PolicyIssued",
    "schema_version": 2,            # ← 事件会被长期保留+重放,版本化是底线
    "event_id": "evt_5c1a...",        # 稳定唯一 id → 幂等去重用
    "policy_id": "pol_8f3a",         # ← partition key:同一保单进同一 partition → 有序
    "rate_table_version": "2026-06",   # 复现定价所需:钉住版本
    "occurred_at": "2026-06-16T08:00:12Z",
    "correlation_id": "req_7b2..."     # 跨服务把因果链缝回去
}

def consume_billing(partition, offset, event):
    # 同一组内,这个 partition 只分给我一个 worker → 分区内严格有序
    if processed.exists(event["event_id"]):   # at-least-once → 仍需幂等
        commit_offset(partition, offset)            return

    with db.transaction():
        billing.open_invoice(event["policy_id"])
        processed.add(event["event_id"])
        commit_offset(partition, offset)            # 记进度,不删消息 → 别人/将来可重放

# 想重算过去 30 天的账?把分析组 offset 拨回去,从头重读即可,
# 源头日志原封不动 —— 这就是 replay,受监管系统的杀手锏。

对比昨天的队列 consumer:核心差别是「commit offset」取代了「ack 删除」——消息留在日志里,所以才有了重放与多组独立消费。而 schema_version、rate_table_version、correlation_id 这几个字段,是把可演进、可复现、可追踪这三件 non-functional 需求焊进事件本身。

★关键要点

今天带走这四句

1

Command是「请去做」(有接收者、期待结果),event是「已发生」(陈述事实、不管谁听)。事件驱动把箭头反过来:发布者对订阅者一无所知,加下游不改核心。

2

队列「消费即删」,日志(Kafka)「读完不删、只移 offset」。后者解锁多消费者独立读、可重放、日志即真相源三件大事。

3

Kafka 靠 partition 扩展:只保证分区内有序,用 partition key(如 policy_id)把同一实体路由到同一分区即可保序。consumer group 一招同时给你负载均衡 + 广播。

4

代价:没人拥有整条流程、最终一致更难调、schema 演进是长期契约;幂等依旧是底线。但对寿险,事件日志天生就是 audit trail——审计与复现成了架构副产品。

Q2Kafka 与传统队列最根本的区别是什么?它因此多了哪个杀手级能力?

A→Z术语表

今日术语

Event-Driven Architecture
组件通过发布/订阅「已发生的事实」来协作,发布者不知道订阅者是谁。
Command vs Event
命令=请去做某事(有接收者、期待结果);事件=某事已发生(陈述事实、不管谁听)。
Log-based / Append-only Log
消息只追加到有序日志末尾,读取不删除,按 retention 保留。
Offset
日志中每条消息的单调递增序号;consumer 记住自己读到第几号。
Topic / Partition
topic 是事件的逻辑分类;partition 是把它切成的若干条独立有序日志,扩展与有序的基本单位。
Consumer Group
组内分担负载(每 partition 只给一个 worker),组间各读全量(广播)。
Replay
把 offset 拨回历史位置重新消费,源头日志不变;用于回填、重算、复现。
Event Sourcing
把「事件日志」当作系统状态的唯一真相源,状态=从头重放事件的结果。
Schema Registry
集中管理事件格式与版本,保证向前/向后兼容,支撑事件长期保留与重放。
Retention
日志保留策略,按时间或容量决定消息留多久,而非读完即删。
