1为什么会有 NoSQL

关系库的三个“天花板”

2000 年代末,Google、Amazon 这批公司把关系库逼到了三个极限,NoSQL 就是从这三个缝里长出来的:

① Scale-out(横向扩展)。关系库的传统扩展路线是 scale-up——买更大的机器,但机器有上限、价格指数级上涨(Day 6 讲过这条曲线)。而 JOIN 和跨行事务让关系库很难简单地拆到几十台机器上:一旦数据分散,一条 JOIN 可能要跨网络拼,事务要跨节点协调。NoSQL 的思路是反过来:先放弃 JOIN 和跨行事务,换来随便加机器的自由。

② 灵活 schema。关系库写入前要先定义表结构(schema-on-write),改结构要 ALTER TABLE。当数据形状多变(不同产品的问卷字段完全不同),“一张表装所有形状”会变成几十个 NULL 列。文档库允许每条记录自带形状(schema-on-read)。

③ 访问模式专精。关系库是“通才”:什么查询都能跑,但都不是最快。如果你的访问模式极其固定——比如 99% 的请求是“按 key 取一个值”——一个专门为此设计的存储可以快一个数量级、便宜一个数量级。

所以记住今天最重要的一句话:NoSQL 不是“更先进的数据库”,而是“为特定访问模式牺牲了通用性的数据库”。NoSQL 的本意也是 “Not Only SQL”,不是 “No SQL”。选型的第一个问题永远不是“我的数据长什么样”,而是“我的查询长什么样”(query-driven design)。代价也要先说清楚:大多数 NoSQL 放弃了 JOIN、放弃了跨行 ACID 事务、放弃或弱化了强一致性——最后这条的确切含义,明天(Day 12)会用 CAP / PACELC 讲透。

2四大家族

每个家族为一种访问模式而生

Key-Value:最简单,也最快

数据模型就是一张巨大的哈希表:key → value,value 对存储来说是不透明的一坨字节。能做的操作基本只有 GET / PUT / DELETE——但正因为简单,它可以做到亚毫秒延迟、轻松横向分片。Day 7 你已经用过它了:Redis 缓存就是 KV 店的典型用法。QuoteFlow 里的落点:报价结果缓存(quote_id → 报价 JSON)、用户 session、API 限流计数器、feature flag。局限同样明显:只能按 key 找。“查出所有吸烟者的报价”这种问题,KV 店无能为力。

Document:按“聚合”整存整取

文档库(MongoDB、CouchDB,以及关系库里的 JSONB 列)存的是自描述的 JSON 文档。核心直觉:把一起读、一起写的数据放进同一个文档(领域驱动设计里叫 aggregate),一次 IO 整存整取,不用 JOIN。每个文档可以有不同的形状——对“不同产品问卷差异巨大”的场景特别友好。QuoteFlow 的落点:投保申请的问卷 payload(term life 问 40 题、TPD 问 60 题,字段集合完全不同)、Day 10 讲过的报价输入快照。

但 schema 灵活不是免费的:schema-on-read 只是把校验责任从数据库挪到了应用层。三年后这个集合里躺着五代不同形状的文档,每个读它的程序都要兼容全部历史形状。在受监管场景,这意味着你需要显式的 schema version 字段 + 应用层校验,否则 auditability 会被悄悄腐蚀。一个务实的中间路线:核心字段照常建列,多变部分放进 Postgres 的 JSONB——同一张表里同时拿到 ACID 和灵活性,很多时候这就够了,不必引入一个新数据库。

Wide-column:为海量写入设计

宽列店(Cassandra、HBase、Bigtable)的模型可以理解为“两级 key”:partition key 决定数据落在哪台机器,clustering key 决定分区内怎么排序。它建表时就要求你按查询来设计 key——“为查询建模”被写进了语法。底层用 LSM-tree(写优先的结构,和 Day 9 的 B+tree 相反:B+tree 读快写慢,LSM 写快读稍慢),所以写吞吐极高,天然适合 append-only 的事件和时序数据。QuoteFlow 的落点:audit 事件流——每条报价、每次核保规则评估、每次费率表发布都产生事件,写入量是保单数的百倍,而读取模式恰好固定:“给我这张保单的全部事件,按时间倒序”。

Graph:当“关系本身”是主角

图库(Neo4j、Amazon Neptune)把节点和边都当一等公民,擅长“沿关系走 N 跳”的查询。关系库做这件事要自 JOIN N 次,每多一跳成本翻倍;图库的遍历成本只和走过的边数成正比。QuoteFlow 的落点:欺诈检测——“这个新申请人的电话号码,是否和三个月内两次被拒保的申请人共享同一个地址和受益人?”这是典型的 3 跳遍历,SQL 写出来是噩梦,图查询是三行。多数系统不需要专门的图库;但当你的核心问题长成“网络”的形状时,它是无可替代的。

4看两个具体形状

文档怎么长,宽列怎么建

抽象说完,看两段具体的“形状”。第一段是投保申请的文档形态——注意 schema_version 字段和嵌套结构;第二段是 audit 事件的宽列建表——注意 key 的设计就是查询的设计:

application 文档(Document)+ audit_events 表(Wide-column,CQL 示意)
// ── ① 投保申请:一个自描述的文档,整存整取 ──
{
  "app_id": "app_7c21...",
  "schema_version": 3,            // ← 显式版本:合规场景的保命字段
  "product": "TERM_LIFE_20Y",
  "questionnaire": {                // 不同产品形状不同,无需几十个 NULL 列
    "smoker": false,
    "occupation": { "code": "2211", "hazardous": false },
    "medical": [ { "condition": "asthma", "severity": "mild" } ]
  }
}

-- ── ② audit 事件:key 的设计 = 查询的设计 ──
CREATE TABLE audit_events (
  policy_id   text,        -- partition key:同一保单的事件落在同一分区
  event_time  timestamp,   -- clustering key:分区内按时间排好
  event_type  text,
  actor       text,
  payload     text,
  PRIMARY KEY ((policy_id), event_time)
) WITH CLUSTERING ORDER BY (event_time DESC);

-- “这张保单最近 50 条事件” = 找到分区 + 顺序读前 50 行,毫秒级
SELECT * FROM audit_events WHERE policy_id = 'pol_91d4' LIMIT 50;

对照感受一下:文档库的灵活是写入侧的自由(每条记录自带形状);宽列库的快是读取侧的预谋(建表时就把查询路径焊死)。反过来问“宽列表怎么查任意字段”“文档库怎么保证五代文档都合规”,就立刻碰到各自放弃的东西。

5贯穿案例

给 QuoteFlow 的数据“分家”

真实系统几乎从不“全家搬去 NoSQL”,而是 polyglot persistence:每类数据按访问模式各归其家,同时清醒地接受“家越多,运维和一致性的负担越重”。给 QuoteFlow 分一次家:

Case · QuoteFlow

核心记录留关系库 —— 这是合规上的“保守正确”

Policy / Coverage / 财务流水 / 客户主数据 → PostgreSQL。理由不是惯性:这些数据需要跨表事务(签发保单 = 同时写保单、保障、账务,Day 8 的 ACID)、需要外键约束守住数据质量、需要成熟的备份/恢复/审计工具链——监管审查时,“我们用了 30 年工业级验证的关系库”本身就是答案的一部分。

报价缓存、session、限流 → Redis(KV):丢了也能重算,适合放最“随便”的家。问卷 payload → Postgres JSONB:形状多变但量不大,JSONB 拿到灵活性又不离开 ACID 的屋檐——够用就不引入新数据库。audit 事件流 → 宽列(或 Day 16 会讲的日志型系统):写入量百倍于保单数、append-only、读取模式固定。欺诈关系网络 → 图库:只在这个问题真的成为业务重点时才引入。

注意天平的另一端:每多一个存储,就多一套备份策略、监控、故障模式和“两边数据对不上”的可能。能用一个库解决,就不用两个——polyglot 是被访问模式逼出来的,不是技术品味。

最后把 audit log 多看一眼,因为它是 NFR 驱动选型的好例子:它要的是不可变(append-only)、完整(不丢事件)、可重放(按实体+时间顺序读)。宽列店天然契合前两条的写入模式,但“不可变”最终靠的是权限设计(应用账号只有 INSERT 权限、没有 UPDATE/DELETE)+ 流程,数据库自己不会替你拒绝删改。这是 Day 1 那句“把 non-functional 焊进设计”的又一次落地。

★关键要点

今天带走这四句

1

选存储先问“查询长什么样”,再问数据长什么样。NoSQL 是为特定访问模式牺牲通用性,不是“更先进”。

2

四家各有专长:KV 按键取值、文档按聚合整存整取、宽列海量写+分区扫、图沿关系遍历。专长都是用放弃换的。

3

共同账单:大多数 NoSQL 放弃了 JOIN、跨行事务和(默认的)强一致性。schema 灵活也只是把校验责任挪给了应用层。

4

Polyglot persistence 按需分家,但每多一个库就多一份运维与一致性负担。受监管的核心记录留关系库,常是合规上的保守正确。

?今日小测 + 思考题

读完自测一下

Q1报价缓存只有一种访问方式:按 quote_id 取整份报价结果。哪个家族最合适,为什么?
Key-Value(如 Redis)。访问模式是纯按 key 取值,KV 店在这件事上延迟最低、扩展最容易;并且缓存丢了可以重算,不需要持久化保证。用文档库或关系库做这件事,是为用不到的查询能力付费。
Q2为什么 audit 事件流适合宽列店,而不是直接塞进 PostgreSQL 主库?
访问模式契合 + 保护主库。事件量是保单数的百倍且 append-only,宽列的 LSM 写路径吞吐极高;读取模式固定为“按 (policy_id, 时间) 顺序读”,正好是 partition + clustering key 的形状。塞进主库则会让海量写入和实时报价的事务争抢同一套资源。注意:“不可变”要靠权限(只授 INSERT)+ 流程兜底,不是数据库自动给的。
Q3文档库“schema 灵活”的代价是什么?在受监管场景要加什么护栏?
校验责任从数据库挪到应用层。schema-on-read 意味着多代形状的文档长期共存,每个读取方都要兼容历史形状,数据质量问题发现得更晚。护栏:文档里放显式 schema_version、写入口做应用层校验、保留各版本 schema 定义供审计——否则 auditability 会被悄悄腐蚀。

A→Z术语表

今日术语

NoSQL
“Not Only SQL”:为特定访问模式放弃部分通用能力(JOIN/事务/强一致)的一类数据库的统称。
Key-Value Store
以 key → value 哈希表为模型的存储,只支持按 key 存取,延迟极低、易分片。
Document Database
以自描述 JSON 文档为单位存取的数据库,每条记录可有不同形状。
Wide-column Store
用 partition key 分布数据、clustering key 排序的存储,写吞吐高,查询需预先设计。
Graph Database
把节点和边当一等公民、为多跳关系遍历优化的数据库。
Aggregate
一起读、一起写的一组数据;文档建模的基本单位(整存整取)。
Schema-on-Read
写入时不强制结构、读取时再解释形状;灵活,但把校验责任挪到应用层。
Polyglot Persistence
一个系统按访问模式混用多种存储,各类数据各归其家。
