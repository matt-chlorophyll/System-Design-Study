1. 给 QuoteFlow 列一列：哪些数据**适合缓存**、哪些**绝不该缓**？你判断的标准是什么（提示：它旧一点会怎样？丢一份会怎样？）
   
   - 我的想法：对这个问题我有一点疑问。因为按照对文档中内容我的理解，没有什么数据是绝对不能缓存的，只是说有些数据，比如说费率表，核保规则，定价算法模型这些会直接影响报价的consistency和reproducibility的数据，缓存的内容必须和数据库里的最新数据内容完全一致，来避免请求命中缓存中的旧数据导致的返回结果不一致的情况。要满足这一点最好的解决办法就是用版本化key将数据和它对应的版本号作为key同时存进缓存，然后让应用改读新key。再就是有些情况下缓存反而成本更高，比如hit rate特别低的系统，这种情况也不应该缓存，否则过多miss缓存反而增加处理时间。还有一些适合缓存的数据就是网页CSS, Logo这些不会很快过时，过时也不会造成太大影响的数据。但我不知道是否有绝不该缓的数据。

   - **Claude 点评：** 「没有绝对不能缓的数据，只是后果不同」这个直觉很高级，比死记一张「这几类不能缓」的清单要深。但你只沿**一个轴**答完了——题目提示其实藏了**两个轴**：① 「旧一点会怎样?」= **staleness**（你答透了：费率表/规则旧 → 不可复现报价 → 版本化 key 解决）；② 「丢一份会怎样?」= **loss**——而**「绝不该缓」就住在这条轴上**，你基本没碰。所以你那个疑问的答案是：**「绝不该缓」不是某类数据沾不得缓存，而是别在权威写路径（签发保单 / 扣款 / audit log）上用 write-back**——缓存先收下、还没刷库就崩 → 那笔凭空消失 → 审计链断。你完全可以从缓存「读」一份保单；不能做的是让缓存当写**落地**的地方。一个精度修正：你说「缓存内容必须和最新数据完全一致」其实是**显式失效**的思路（难、易竞态）；版本化 key 更干净恰恰因为它**扔掉了「时刻一致」这个要求**——key 不可变，「更新」= 新建 key + 改指针，stale 窗口直接消失。**不是「让副本追上源头」，而是「让副本永不变，于是无需追」。**

2. 假设有人偷懒，用 `TTL=5 分钟` 缓存费率表。在「费率表刚更新」后的那 5 分钟里，系统会发生什么？这对**审计 / 合规**意味着什么？你会怎么改？
   
   - 我的想法：系统对于需要调用费率表的请求，由于命中缓存且缓存中还可能仍旧储存未被更新的旧费率表，会导致一些请求使用缓存里的旧费率表处理报价请求，从而导致报价没有应用新的费率，这个是对审计和合规的violation。改动也就是上一问我提过的，用版本化key的方法，把版本号作为key也存进缓存，然后费率表更新通过让服务端应用新费率表版本号来让报价请求都定位到新的费率表。这样既能保证不会出现请求使用旧费率表的情况，也能把历史费率表都保存下来，这样才能满足reproducibility的合规审计要求。

   - **Claude 点评：** 主线全对（stale 窗口 → 旧费率 → 违规 → 版本化 key + 历史留存）。补两点升级：① **最狠的不是「读到旧数据」，是审计日志会撒谎**——若代码按配置盖章 `rate_table_version=2026-07`，但缓存按没版本号的 key 仍返回 06 的数字，**盖的章和用的数对不上**；事后复现 → 价格不一致 → reproducibility 破功。版本化 key 的根治点：**盖章的版本号 = 取数的 key，不可能对不上**。② 那 5 分钟里，同一投保人先后两次报价可能拿**两个价**，纯看请求那一刻的缓存状态（不可见、不可审）——**这种不确定性本身就是违规**，轮不到讨论「哪个价才对」。③ TTL 本身不是坏东西（logo / 营销文案就该用），教训是**失效策略要匹配数据的赌注大小**——这其实就是第 1 题判断标准的应用，**两题是同一枚硬币**。

## 提问 & 解答

> 讨论时冒出来的问题记这。每条：先记自己的问题，再记讨论后的结论（用自己能看懂的话）。

### Q1. 版本化 key，缓存里到底存 key 还是 key+value？

**问：** 缓存是只存版本化 key、再拿它去数据库拉数据，还是把 key→value（整张费率表）成对存？如果是前者还得回库，那缓存真能变快吗？

**答：** 存**整对** `key→value`，value 就是费率表内容本身。Redis 是 key-value store：key 是「按什么找」，value 是「找到的那坨东西」。**命中时整张表已在内存、直接返回、根本不碰数据库**——这才是「快」的来源（若只存 key 还回库，确实白搭，所以不那么设计）。回库只在**第一次** miss 时发生一次，之后成千上万次读全命中。「版本化」管的是 key 怎么命名 / 怎么失效，跟「存不存 value」是两码事，别搅在一起。

### Q2. 单飞锁里 `set_nx` 是什么？以及那个并发 race

**问：** stampede 防护代码里 `set_nx()` 干嘛的？请求 B sleep 完回去读还可能 miss 吗？同一个 key、value 被存两次会出问题吗？

**答：** `set_nx` = **SET if Not eXists**：key 不存在才设上、返回 true（抢到）；已存在则什么都不做、返回 false（没抢到）。它是**原子**的 → 一群 miss 的请求里**恰好一个**抢到锁去查库、回填，其余等它填好再读 = **single-flight（单飞）**。`ttl=5` 是防死锁（赢家中途崩了，锁会自动过期，不会永远卡住）。**B 确实可能 sleep 完还 miss**（查库慢 >50ms）：若锁还在 → B 继续等（正确）；若锁刚放开 → B 可能多查一遍（**无害浪费**）。**存两次不会出错**：key-value 是覆盖写、一个 key 一个槽，不会变两条；何况版本化 key 不可变，两次写进去的 value 逐字节相同。想省掉那次浪费 → 抢锁后再读一次缓存（**double-checked locking**）。

### Q3. Redis 要不要像 LB 那样主备防 SPOF？

**问：** 分布式缓存 Redis 需不需要也搞主副本来防单点？

**答：** 要，机制和 Day 6 的 LB 一样（**冗余 + 故障切换**）：primary-replica 复制，primary 挂了把 replica 提升；「谁发现挂了、谁来提升」靠 **Redis Sentinel**（哨兵间选举 = leader election，Day 19）或 **Redis Cluster**，云托管把这套外包。**但「为什么要冗余」和 LB 不同**：缓存只是副本、数据库才是 source of truth，所以一个节点死，系统仍**正确**、只是**变慢**；做冗余主要是**防 avalanche**——缓存整片消失 → 全量流量砸向数据库 → 把库压垮。妙处：缓存敢用**异步复制**（replica 慢半拍丢几条 → 只是 miss 回库重算，无害），而数据库用异步复制丢写 = 真·数据丢失。

### Q4. LLM 的 KV Cache 和今天的缓存是一回事吗？为什么 hit 能省 token？

**问：** 学 LLM 时的 KV Cache（缓 K/V matrix 计算）和今天一个道理吗？为什么命中能降低 token 消耗？

**答：** **是两个东西，我之前把它们混了。** ① **KV Cache**：自回归生成时，新 token 要 attend 前面所有 token 的 K、V；缓存住已算的 K、V，每步只算新 token 的 → 省的是**算力 / 延迟**（避免 O(n²) 重算），是模型推理内部的自动优化，**不直接省 token 账单**。② **Prompt Caching**（真正省钱那个）：把一段 prefix 的 KV 状态**跨 API 请求**存住，命中时那段 token 按 **~0.1×（一折）** 计费；写入有 **1.25×(5min) / 2×(1h)** 溢价、默认 TTL 5 分钟。它是 KV Cache 思想的**跨请求放大版**，且完美映射今天：hit/miss、prefix **精确匹配**（一字节变即全段失效 = 版本化 key / 不可变）、TTL、以及「写有溢价 → 不复用就净亏」= 我 Q1 那条「读少别缓」。实战：把 system prompt、长文档这种**每次都一样的大块**放前面缓住，时间戳 / ID 这种易变的放最后（否则静默失效）。

### Q5. 缓存到底怎么「命中」的？

**问：** 命中是怎么判断的？是逐条对比吗？

**答：** 不是逐条扫（O(n) 太慢），是**按 key 哈希直接定位**（O(1)）：把 key 跑 hash → 跳到对应桶 → 桶里做一次**精确相等比较** → 在 = hit、不在 = miss。是**精确相等**，不是模糊 / 相似匹配（语义缓存 semantic cache 用相似度，那是特制的另一套）。不同层「key」不同：Redis = 应用给的 string（`rate:2026-06`）、浏览器 / CDN = URL、prompt caching = 整段 token prefix 的 hash（所以一字节变 → hash 全变 → 全段失效）。这跟我熟的 **hash index** 同思想（Day 9 索引）；分布式里「key 落在哪台节点」靠 **consistent hashing**（Day 13）。

### Q6. 哪种系统命中率极低、加缓存反而净亏？举例。

**问：** 什么样的系统访问太分散、加缓存反而是净亏？

**答：** 缓存赌的是「同一个 key 会被反复要」，没有重复就只剩开销。例子：① **QuoteFlow 缓「每条报价的最终结果」**（按完整投保人输入当 key）——组合是天文数字，两请求几乎不重复 → 几乎全 miss。**精妙对比**：它**读的费率表**被几百万次重复读（该缓！），但它**产出的报价结果**几乎不重复（别缓）——**该缓的是「被反复读的块」，不是「贵的结果」**。② ad-hoc 分析查询（每次 slice 都不同）。③ 按唯一 ID 的一次性点查（审计调查）。更深一层：这些一次性条目还会在 LRU 下**把热数据（费率表）挤出去** = **cache pollution**，连累本该高命中的数据。判断口诀：**「这个 key 待会儿还有人要吗?」几乎不会 → 别缓。**

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 缓存是为了不重复做”贵“的事情，来减少处理请求的latency，缓存命中率越高，意味着时间成本节省的越多。缓存可以发生在一个请求路上的很多地方，但是要特别注意一致性的问题，通过安全合理的方式对缓存进行读写和”失效“，同时也要对一些常见的缓存陷阱给出针对性的解决办法。
