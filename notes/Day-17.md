## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01–12 那样）。

1. 夜间重定价跑到一半挂了（比如第 60 万张保单时崩溃），你希望它具备什么性质才能**安全地重跑**、而不会把已经算过的保单算两遍？（提示：这正好是**明天** idempotency 的核心。）
   
   - 我的想法：保单重算的任务要有幂等键，使重算的重试可以幂等，i.e.当重跑时，已经算过的保单识别幂等键之后不再执行重算，直接返回结果。

   **点评（Claude）：** 方向对，抓住了 idempotency，也接住了明天 Day 18。补三点精度：① **漏了一个词：checkpoint。**「安全重跑」是**两件事的组合**——checkpoint（记录"跑到第 60 万张了"，重跑从断点**续跑**、不必从头重扫）+ idempotency（断点附近若有重叠、被算第二遍也不产生重复副作用）。图 1「合规要点」那句"失败可从 checkpoint 重跑且结果一致(幂等)"正是这个。② 你对幂等的描述（识别幂等键 → 发现做过 → 跳过、直接返回）其实是它的**一种实现（去重表 dedup）**，不是定义本身。幂等的精确定义是「**同一操作执行 N 次，对系统状态的最终效果 == 执行 1 次**」；另一种实现是 **upsert**（用幂等键覆盖写，算几遍结果都一样，根本不判断"做过没"）。而「先查'已处理'表、没做过才做」里**查表与执行不是原子的**（记录写成功但主操作崩、或反过来）——这恰是明天 Day 18 exactly-once「为什么很难」的核心，你提前撞上了。③ 为什么"算两遍"是灾难：副作用不只是算个数，是**写库、改保费、触发 billing 出账**——算两遍 = 客户被扣两次、准备金加两遍。幂等防的是**副作用**，不是计算本身。

2. 如果监管要求把「夜间重定价」从「T+1 出结果」改成「保单一变更就近实时重估」，你会从 batch 切到 stream 吗？这一改，会给一致性、成本、可审计性各带来什么新麻烦？
   
   - 我的想法：我会从batch切到stream，因为这个新的要求意味着对延迟的容忍几乎没有（实时重估），这适合流处理而非批处理（批处理要等）。这样改的话，首先成本增加，因为需要实时重估latency要很低，并且要考虑同一时间有多个保单变更需要重估的情况，因此要留足余量避免消息积压。对于可审计性和一致性，这个我不是很确定，我猜想的新麻烦会是为了保证一致性和可审计性，对于一条一条保单的重算任务/消息都要去满足幂等，存audit log等性质，这样会导致需要更多的存储空间去满足这些要求，不过我觉得这还是更像成本。所以听听你的回答。

   **点评（Claude）：** 切 stream 的判断方向对（延迟要求驱动 batch→stream，呼应第 5 节「回到 Day 2 的延迟要求」），**成本 + 背压/积压**那段也提前接住了 Day 20。但有一处**认知硬伤** + 两处补充：① **你把一致性、可审计性的麻烦都归成「更像成本」——这是误判。** 成本 = 多花钱能解决的；下面这两个是**性质变化 / 正确性风险**，钱买不回来。在你这个合规重的行业，混淆这两者很危险（把 non-functional 取舍错读成纯成本）。② **一致性的真问题（结构性退化，不是存储）：** batch 的杀手锏是「整批钉死同一假设版本 + 原子切版本」——全量在同一快照下算，绝不会有人拿新价、有人拿旧价。切 stream 后保单是**一条条、在不同时刻**被重估 → 任意时间点库里**新旧版本混杂**（policy A 已用新假设、B 还没轮到），破坏了「全局某一时刻的一致快照」。对 reserving（准备金按统一假设汇总）、对账、监管披露（"截至 X 时点、按假设版本 V 的总准备金"）都是真问题。一句话：**从「全局原子一致」退化成「逐条最终一致」**；再叠 event-time 乱序，还得用 watermark / 版本号定序。③ **可审计性的真问题（形态变了）：** batch 的 audit 很干净——「一个批次 = 一个版本 + 一份完整输入输出清单」，可复现；stream 没有清晰「批次边界」，要复现"6/17 10:05 这张保单为什么算这个价"得 **replay 到那个时点的精确状态**（哪条事件、当时哪个费率版本、watermark 在哪）→ 审计**从「批次台账」变成「事件溯源」**，复现难度上一个台阶（正是文档里 **Kappa 架构**要解决的）。④ **还漏一层：不是非此即彼。**「保单一变更就重估」是 per-policy 事件触发，走 stream 没错；但**费率表换版 / 精算假设变更**这种全局变更仍要**批量重算所有受影响保单**——一条消息搞不定。现实里两者并存（Lambda / Kappa）：触发方式变了，全量重算的 batch 场景没消失。

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 批处理与流处理的关键区别在于有界/无界——批处理可以等待数据到齐然后进行任务，延迟高一些但吞吐高，成本低；流处理因为数据无界所以没有“到齐”这一说，但是数据到达即进行任务，所以延迟很低，然而由于只能看到当前单一一条数据，所以做一些需要上下文聚合的任务（比如算某一天的保费总额）会很复杂，需要引入window，watermark，处理late data这些方法。再就是现在云端数据仓库的应用使得ELT比ETL更常用，ELT的好处是能保留原始数据在云仓库内，transformation做了什么也能被记录下来，对审计友好。
