## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法,再来 Claude Code 聊;聊完我会在每条下面补点评(像 Day 01–11 那样)。

1. 网络分区把 QuoteFlow 的 leader 和 follower 切成两半:「实时报价」和「保单签发」各应该选 C 还是 A?为什么答案可以不同?再用 PACELC 推一步:没有分区的平时,这两条路径各愿意为一致性付多少延迟?
   
   - 我的想法: 实时报价应该选A，保单签发应该选C。答案可以不同的原因在于不同的业务任务它们对数据丢失和出错的tolerance不同。对于保单签发来说，consistency非常重要，如果出现给一个用户签发出两个报价不同的保单这种情况，属于造成了合规问题，所以必须保证一致性。而对于实时报价来说，相对更重要的是能让用户拿到实时报价，由于此时还不涉及到实际的买卖行为，对数据出错的tolerance相对高一点，而且通过版本化和Quote快照等方式可以保证报价的可复现可追溯。对于没有分区的平时，保单签发由于对一致性的要求高，会更多牺牲延迟，实时报价latency低（不让用户很长时间看不到报价）是重要的NFR，且数据丢了也能通过系统里的数据重算，所以会更多牺牲一致性来降低延迟成本。

   - **Claude 点评：** 结论(报价 A、签发 C)和 PACELC 方向都对。三处磨锋利:① **报价选 A 的真正理由不是「出错 tolerance 高一点」**——是费率表版本钉死、发布后不可变,replication lag 根本不会让报价**算错**,顶多让「新版费率晚几秒可见」。是「这条路径没有错值可容忍」,不是「容忍偶尔错」;你落到了事后 auditability,真正的点是**实时正确性**(没有错误答案存在)。② **签发的 E 侧不是「无限牺牲延迟」**——保单库是 semi-sync ≈ PC/EC,只付**一跳**延迟,而且故意不上 full-sync(太脆:一个慢 follower 堵死所有写)。「为一致性付延迟」有上限、本身也是一次 durability vs availability 取舍。③ 判别式可换成文档那把更锋利的尺:不是「业务对错的 tolerance 不同」,而是「**这份数据错了/丢了,代价是什么**」——签发代价 = 合规事故,报价代价 ≈ 0(可复现、可重算)。

2. 文中说「版本化、不可变的费率表天然免疫一致性问题」。QuoteFlow 里还有哪些数据具有(或可以改造出)这个性质?哪些数据**永远不可能**有这个性质、只能老老实实付一致性的钱?
   
   - 我的想法: 可以有这个性质的数据应该都是不会实时变化，较长时间才更新一次，且能被版本化的信息，除了费率表以外，还有就是报价的用户问卷内容，实际的定价算法模型本身，一些定价可能需要的外部数据（比如CPI数据）等。反之，不可能有的就是保单签发的数据，用户的数据（不可能一个用户信息变化就记录一个新版本，因此无法被版本化），audit log里的数据等。

   - **Claude 点评：** 「可以有」列表(问卷快照、定价模型、CPI 外部数据)都对。但「不可能有」列表(audit log、用户数据、保单)**至少两个是错的**,而且错在同一处:**把「能不能版本化/不可变」当成数据实体的固有属性**——这正是你 Day 10 记进 confusable 的坑「快照 or 引用不是字段固有属性,而是按表要回答的问题定」,这次没掏出来用。① **audit log 恰恰是 append-only 不可变数据的教科书例子**:每条写下永不修改,免疫了「读到半新半旧的错值」。它仍要付钱,但付的是**另一根轴 durability**(别丢条目——文档让 audit 写用 QUORUM 就是为这根轴),不是 mutability;你把两根轴混成了一根。② **用户数据**:你说「信息一变记新版本→无法版本化」,但这正是 Day 10 的 **SCD Type 2 / effective dating**——寿险里你常常**必须**知道「出报价那一刻这个人的吸烟状态」(point-in-time),所以它不是不能版本化,恰恰是被设计来版本化的典型。📐 真正「永远要付一致性钱」的不是这些**实体**,而是任何**可变、权威、被并发写的「当前值」**:余额、计数器、当前 in-force 状态、「quote 转成 application 了没」的 live 指针——判别式:有没有一个「此刻必须全局一致的可变格子」。**收口**:几乎每个实体都有两张脸——「当前值」(可变、付钱)与「在 T 时刻是什么」(不可变历史、免疫 lag);问「这份数据能不能免疫」问错了,要问「我现在读的是哪张脸」。

## 提问 & 解答

> 讨论时冒出来的问题记这。每条:先记自己的问题,再记讨论后的结论(用自己能看懂的话)。

### Q1. 「新版费率表晚几秒可见」是不是报价应用「取不到最新 version → sleep 重试」?

**问:** 你说 lag 下「新版费率晚几秒可见」,指的是报价应用如果取不到最新 version 对应的费率,就 sleep 一段时间再重试吗?(之前课程好像讨论过类似的)

**答:** 不是。这个框架里藏了误解:报价应用**根本不知道有更新的版本存在**,所以谈不上「取不到」「重试」。机械走一遍:费率表 v07 发布 = 写进 leader → 复制到报价路径读的 replica 要几秒 → 这几秒内 replica 手上最新就是 v06,报价服务问的是「**当前 effective 是哪个**」、拿到 v06 就用 v06 算,并把版本号钉进这张 quote,**不报错、不重试**。lag 只是把「切换到新版本那一刻」在这个 replica 上推迟几秒。用 v06 算出来的报价**不是错的**——是用一个合法、已发布、只是刚被取代几秒的费率表算的,版本钉死 → 可复现、可审计。「完全可接受」的依据是业务判断:费率表是**月级**变动的东西,晚几秒切换无所谓。

sleep / retry 真正的用武之地是 **read-your-writes**:「我**刚写了** X、想立刻读回 X」(提交投保申请后立刻看「我的申请」)——你有一个明确该存在的目标,才需要重试去等它。区分一句:报价路径**没有「我刚写的」这个目标**,只读「当前值」拿啥算啥;read-your-writes **有**一个确定该存在的目标。

**边角(你的直觉在这才对):** 若「**哪个版本算 effective**」是一个指针、和「**费率表内容**」是两份数据,复制速度不同——指针先到(说「该用 v07 了」)、内容后到——报价服务就真的会「知道该用 v07、却读不到 v07」,这时重试 / 读 leader 才有意义。但这已经是**两份数据之间的一致性问题**(沾上 consistent-prefix / causal),不是基础情形。

### Q2. 用户报价请求发两次,一次 v06 一次 v07 → 两次报价不一样,会造成问题吗?和之前的类似问题有什么区别?

**问:** 如果一个用户发两次报价请求,因 lag 一次用 v06、一次用 v07 导致报价不一样,这不会出问题吗?和之前讨论过的类似问题(重复申请 / 幂等)有什么区别?

**答:** 先纠正用词:**两次不一样本身不是「一致性被破坏」,是 staleness——而 staleness 正是你为报价路径主动买的 A**。v06、v07 都是完整、合法、已发布的费率表,不是半写脏数据;读到 v06 = 读到「旧但有效」的版本,恰是 eventual/A 的定义。问题不是「系统错了」,而是「这次 staleness 的后果能不能接受」。拆成两个担忧:

- **技术层——只有「时光倒流」才是真异常。** 两次打到 lag 不同的两个 replica,先看到**新**(v07)再看到**旧**(v06)= **monotonic reads 违例**(Day 12 异常二)。反过来旧→新不是异常,只是费率**真的变了**(跟「9:00 查机票、9:05 涨价」一样)。修法不是加强一致性,是 **sticky routing**(同一用户固定到同一 replica)。
- **业务层——价格跳动是 UX / 公平问题,不在 DB 层解。** 用**冻结的 artifact**:quote ID + validity period(「此报价 $50,有效期至 X」),给了就认。而「能冻结、能事后照原样 honor」靠的正是**版本钉死**——版本化不只是审计用,它是「冻结报价」这个业务能力的底座。

**和之前问题的区别(这才是问题的核心):**
- **vs Day 12「重复投保申请」(read-your-writes 那个):** 那是个**写**——创建权威、有法律意义的记录,重复 = 真出两份保单 = 合规事故。报价是个**读 / 计算**,再算一遍很便宜,多一份不构成问题。这个「写不能重、读可以重」的不对称,**就是 C vs A 的选择本身**:签发选 C(不许分叉)、报价选 A(多算几份无所谓)。
- **vs Day 10「两行是两份事实,不是 duplication」/ 幂等:** 两次用了**不同 version = 不同输入 = 两份不同事实**,不是该去重的 duplication。对照:若两次用的是**同一个 version**、你还想去重,那才轮到 **idempotency key**(同一逻辑请求被重试 → 返回同一张 quote)。真正决定「该不该是两份」的不是「请求发了两次」,而是「**两次的输入(version)一样不一样**」。

### Q3. PM 要求「绝不许两个用户同一秒拿到不同版本报价」,要把 replication 调成同步吗?

**问:** (我的答案)我会调 replication 一致性。这个要求意味着所有 replica 的费率版本都得是最新,应该属于 synchronous 了吧(semi-sync 也不行)?

**答:** **对了一半**——semi-sync 不够、方向往 C 走、意识到这是「写确认」旋钮,都对。但有两个 trap:

- **Trap 1:调错了旋钮。** PM 的要求「所有读看到同一版本」是一个**读侧**保证(任何两个读必须看到同一「当前版本」= **linearizability**);而 synchronous replication 是**写侧**的 durability 旋钮(管「写返回前几台先存好」)。在**写**路径拧旋钮去解一个**读**路径的问题,方向偏了。
- **Trap 2:就算上全 sync,也解决不了。** 发布 v07 = 一次写,它的**传播窗口**里不同 replica 仍一个有 v07、一个还在 v06,读打到不同 replica 仍看到不同版本。sync 只保证「**写返回时**已确认副本都有 v07」,**不保证**「全部 replica 同一瞬间对外可见同一版本」(sync 等的是 WAL 收到 / flush,不是所有 standby 同时 apply)。真要做到,只有两条路、且都在**读**路径动刀:所有相关读走**单一真相源**(读 leader),或 **consensus 协调的 linearizable read**。

**优雅解:拆「指针」和「内容」。** 「当前是哪个 version」是个**极小指针**——读 leader(便宜、线性化,人人看到同一个「当前 = v07」);「version vN 的费率内容」是**不可变大块**——读任意 replica(读扩展不丢)。只给「需要一致的那一小块」付钱。

**但最重要的一步:先别实现,先质疑需求。** 报价路径当初选 A,就因为版本不可变让 lag 无害。为这条要求把**每次报价读**都线性化 / 打回 leader = 亲手砍掉你建 replica 换来的**读扩展 + 低延迟**,去防一个「两个**陌生人**、在 3 秒窗口里、各自拿到一个**合法、已钉版本、会被 honor** 的报价」这个**不伤害任何人**的「问题」。senior 的动作不是实现 linearizability,是 **push back**:回到 Day 1 问 PM「这条 NFR 防的是哪个**真实损害**?」——八成是个假需求,是把工程师对「不一致」的本能不适,误当成了业务约束。

## 我的理解(用自己的话复述今天的核心)

> 不看文档,凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 数据的复制是为了解决latency，durability，availability，scale out这些NFR的需要，但是复制就会导致一定程度上的一致性问题。因此我们依据CAP/PACELC理论需要对C和A/L进行取舍，不同的取舍带来了不同对分区数据进行读写的方法，比如Leader-Follower, Quorum等。一个系统里，根据不同业务任务对数据丢失/出错的容忍度不同，可以存在对A/C（或是无分区时L/C）的不同取舍带来的不同设计。

- **Claude 点评：** 四个动机、账单是一致性、CAP(分区时)/ PACELC(平时)、逐路径取舍——主干全抓住了。加两条这次讨论磨出来的:① **一致性不是全系统一个开关,是逐条数据、逐条路径的预算分配**——同一个 QuoteFlow 里签发(C)、报价(A)、批量(钉快照)、audit(QUORUM 保 durability)四种答案并存,判别式始终是 Day 1 那句「错了 / 丢了代价是什么」。② 多一条**手艺**:会对**假一致性需求**说不——「绝不许两人同一秒读到不同版本」这类要求,先回 Day 1 问「防的是哪个真实损害」,别急着拧 sync 旋钮买你不需要的一致性。③ 还有一个**定价系统专属红利**:版本化、不可变的数据(费率表 / 模型 / CPI)让整条读路径天然免疫 lag,这是别的行业未必有的便宜(接 Day 10)。
