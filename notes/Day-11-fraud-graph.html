Day 11 补充图解 · Graph Database

“3 跳遍历”到底是哪 3 跳?

把文档里那句欺诈检测查询画出来:“这个新申请人,是否和三个月内两次被拒保的申请人共享电话、地址和受益人?”

一跳一跳走

先记住一个口径:1 跳(hop)= 沿一条边从一个节点走到相邻节点。“3 跳”数的是从起点到答案的深度。

1

N → 电话节点。从今天的新申请人 N 出发,沿 HAS_PHONE 边走到他登记的号码 0412 555 808。注意:电话号码在图里是独立节点,不是 N 的一个字段——这是整张图能成立的关键(下面细说)。

2

电话节点 → 申请人 M。站在号码节点上反向问:“这条边的另一头还有谁?”——发现申请人 M 也连着同一个号码。图库的边天然可以双向走,“共享同一个电话”就是“两条 HAS_PHONE 边汇到同一个节点”。

3

M → 他的申请记录。从 M 沿 SUBMITTED 边走到他的投保申请,过滤 status = 'DECLINED' 且 decided_at 在 3 个月内——数出 2 条 → 报警条件满足。

“共享同一个地址和受益人”是两条平行路径(图中虚线):N → 地址节点 ← M、N → 受益人节点 ← M。它们和电话路径长得一模一样,只是换了边的类型——平行路径增加的是 pattern 的宽度(同时命中才算欺诈信号),不增加深度,所以这仍叫 3 跳查询。

建模的关键一步:把“识别符”升级成节点
在关系库里,电话/地址/受益人通常是申请人的字段(或 junction 表),“共享”只能靠 self-join 找值相等的行来发现。图建模把它们升级成一等公民节点——“共享”从“值恰好相等”变成“边汇到同一个节点”,肉眼可见、一跳可达。这和 Day 10 判断 entity 的尺子一脉相承:在欺诈检测这个问题里,电话号码“有了身份”,所以配得上自己的节点。

同一个问题,两种写法

Cypher(Neo4j 的查询语言)里,查询长得就和上面那张图一样——你是把图案(pattern)画给数据库,让它去找匹配:

fraud_check.cypher — 把图案画给数据库
MATCH (n:Applicant {id: $new_id})-[:HAS_PHONE]->(:Phone)<-[:HAS_PHONE]-(m:Applicant), // 跳①②
      (n)-[:LIVES_AT]->(:Address)<-[:LIVES_AT]-(m),                       // 平行:共享地址
      (n)-[:NAMES_BENEFICIARY]->(:Person)<-[:NAMES_BENEFICIARY]-(m),      // 平行:共享受益人
      (m)-[:SUBMITTED]->(a:Application {status: 'DECLINED'})              // 跳③
WHERE a.decided_at >= date() - duration('P3M')
WITH  m, count(DISTINCT a) AS declines
WHERE declines >= 2
RETURN m.id, declines

SQL 里,每一跳 = 一次 JOIN,“共享” = junction 表 self-join。下面只写了电话这一条路径:

fraud_check.sql — 只有电话路径,地址/受益人还要再各叠一组
SELECT  mp.applicant_id, COUNT(DISTINCT a.app_id) AS declines
FROM    applicant_phone np                                 -- 跳①:N 的电话
JOIN    applicant_phone mp ON mp.phone_id = np.phone_id    -- 跳②:谁还用这个号(self-join)
                          AND mp.applicant_id <> np.applicant_id
JOIN    applications a     ON a.applicant_id = mp.applicant_id  -- 跳③:他的申请
WHERE   np.applicant_id = :new_id
  AND   a.status = 'DECLINED'
  AND   a.decided_at >= CURRENT_DATE - INTERVAL '3 months'
GROUP BY mp.applicant_id
HAVING  COUNT(DISTINCT a.app_id) >= 2;

-- 「同一个地址」+「同一个受益人」:再各加一组 junction self-join(或 EXISTS 子查询)。
-- 欺诈团队明天问「受益人 R. Chen 的电话又连到哪个申请人?」(深度 +2 跳)→ SQL 结构性重写;
-- Cypher 只是在 MATCH 里把 pattern 多画一段。

为什么图库走这条路更快

关系库:每跳一次,付一次 JOIN 的钱。每个 JOIN 是去另一张表的索引里查一遍(B+tree,O(log N),Day 9)——表越大越贵,而且多跳的 fan-out 逐层放大:第 1 跳出来 10 行,每行再各查一次第 2 跳……

图库:index-free adjacency(免索引邻接)。每个节点身上直接存着自己那些边的物理指针。只有起点 N 需要用索引找一次,之后每一跳都是顺指针走,成本只和这个节点的度数(连了几条边)成正比,和全库总量无关——10 亿申请人和 100 万申请人,从 N 出发走 3 跳的代价几乎一样。遍历越深,和 SQL 的差距越大。

别忘了天平另一端(Day 11 对照表第四行):图库为遍历付出的代价,是大规模扫描和聚合不擅长——“全体保单的平均保费”这种问题它很笨。而且多数系统的关系查询深度 ≤ 2 跳,关系库 + 几个 JOIN 完全够用。文档的判语:只在“核心问题长成网络的形状”时才引入图库——欺诈环检测恰好是,因为欺诈者的本质就是“用共享的识别符把假身份连成了网”,而他们自己藏不住这些边。
