## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01/02 那样）。

1. 给 QuoteFlow 估算时，「**日请求量**」和「**峰值因子**」这两个数你会怎么定来源？如果**夜间批量重定价的窗口**不小心和 **broker 早高峰报价**撞在一起，容量估算要怎么改？
   
   - 我的想法：我的做法会是进行一段时间(比如30天)对日请求量数据的观察记录，然后对于一般日请求量的话，看50percent qunatile落在哪里；对于峰值因子，看90percent quantile以上的日请求量是多少，然后取其中的平均值，除以一般日请求量得到峰值因子的估算。如果重定价窗口和早高峰报价撞在一起，我觉得要看这两个流程是否是互相独立的，如果完全独立不互相占用任何资源，那么估算按照max(重定价请求量，broker报价请求量)来；如果互相占用资源，我觉得估算的话我会假设它们的资源占用是mutually exclusive, 因此直接把它们的请求量相加来进行估算。

   - **Claude 点评：** 用历史数据 + 分位数定基线，数据科学家的本能，方向完全对。三处要校准：
     1. **粒度错配（最关键）：** 峰值因子量的是 **intraday（日内瞬时高峰）**——夜里近 0、晚高峰冲起来；你用 day-level 总量的分位（p50 当一般、p90+ 当峰值）测的是 **day-to-day（旺日 vs 淡日）**，是另一个维度。很少有哪天总量是均值的 5×，但日内某刻 QPS 是日均 5× 很常见 → 用日总量分位会**严重低估**峰值因子。正确量法：把时间桶切细（按分钟 / 小时统计 QPS），取一天里的 peak 桶 ÷ 当天均值。两个维度其实都要：高分位「旺日」定日总量基线，**再**乘日内峰值因子。
     2. **历史 only 会漏增长：** 容量按未来备。历史定 baseline，增长率 / 营销 / 新品要靠业务预测叠上去（文档「日请求量是产品给的预测」）。
     3. **撞车逻辑修一下：** ①「独立 → max」用错了——真独立 = 各自独立资源池，那就各估各的、不存在合并；②「共享 → 相加」**方向对**，但你写的 `mutually exclusive`（互斥事件 = 不同时发生）术语反了，那其实不该加；撞车是 `concurrent / overlap`（同时发生）才叠加，且要 **peak + peak** 最保守；③ 你后来澄清的「资源使用互斥，一个用了另一个不能用」是**另一个同名概念** `mutual exclusion`（互斥访问 / 锁），它正好**强化**了「相加」：两边抢同一资源、同一刻只一个能用，另一个排队 → 总需求叠加；④ 升华（接 Day 01）：撞车最好的解法常是**别让它发生**——资源隔离（`bulkhead`，Day 20）、错峰调度、或共享时给批量限流 / 降优先级。

2. 审计日志按合规**只增不删、保留 7 年、~10TB**——这对存储选型（热 / 温 / 冷分层、对象存储 vs 在线数据库）意味着什么？哪些数据必须**随时可查**、哪些可以归档到**便宜的冷存储**？
   
   - 我的想法：意味着要合理分配储存资源，把需要储存但不需要经常调用的数据用花费较低的方式储存（其实你第二个问题已经回答了第一个问题）。我觉得最终quote（用户购买了保险产品）的数据要是随时可查的，历史费率表最好也是随时可查，但是quote了但没产生购买行为的quote数据可以归档到便宜的储存。 不过我不知道“热/温/冷”的分层是具体怎么实现的。

   - **Claude 点评：** 抓住了核心动机（按访问频率分配存储成本），区分成交 / 未成交是合理的业务维度。三点校准 + 正面回你的「怎么实现」：
     1. **归档 ≠ 删除（最重要）：**「只增不删、保留 7 年」里，冷存（cold tier）**依然可查**，只是慢 / 便宜 → 完全满足「保留 + 可查」，审计日志放冷存没问题。但要分两类数据：**业务数据**（quote 记录）没成交的可归档、甚至按隐私法规该删（留着没成交的 PII 反而是合规风险）；**审计轨迹（audit log）不论成不成交都要留**——监管可能查「给那个没买的人当时为什么报这个价、用哪版费率」。别用「成交与否」决定审计日志留不留。
     2. **分层依据是 access frequency + 时间降温**，不全是业务重要性。数据会随时间自动降温（今天热的最新 quote / 当前费率表，几年后变冷）→ 常按时间自动迁移（`lifecycle policy`）。
     3. **热 / 温 / 冷怎么实现：** 热 = 在线 DB（Postgres 等 OLTP）/ Redis（贵、ms 级、随时复杂查询）；温 = 便宜些的 DB / 对象存储标准层；冷 = 对象存储归档级（S3 Glacier / Azure Archive，便宜几十倍、取回慢、按取回收费）。**怎么搬**：配 lifecycle policy / tiering 自动降级；DB 按时间 `partition`、旧分区导出对象存储。**对象存储 vs 在线 DB**：DB 支持 SQL / 索引 / JOIN / 事务、低延迟点查、贵；对象存储只能按 key 取 blob、不支持 SQL（除非上 Athena / BigQuery），但极便宜、海量、高耐久 →「写完很少改、偶尔整批捞」的审计日志教科书 use case。
     4. **加分（对口受监管审计）：** 合规「不可篡改 + 保留期」用 **WORM**（Write Once Read Many）/ `object lock` / immutability（S3 Object Lock、Azure immutable blob）——锁定后保留期内谁都改不掉删不掉。

## 提问 & 解答

### Q1. 缓存大致怎么工作？为什么 hit 缓存就快？是因为离 CPU 更近吗？

**问：** 缓存怎么工作？为什么命中缓存数据抓取就变快？我猜是物理上离 CPU / 操作系统更近？

**答：** **缓存 = 把「贵的获取」结果暂存到「取起来更便宜」的一层，下次直接拿、跳过那次贵的获取。** 工作机制（`cache-aside` 读路径）：先查 cache → **命中（hit）** 直接返回；**未命中（miss）** 去源头（DB / 磁盘 / 远程）取，取到顺手**写回 cache**，下次就命中。缓存装得下，是因为只放**热数据子集**（`working set`），靠 `locality`（少部分数据占大部分访问）。

「为什么快」其实有**三种不同来源**，看是哪一层缓存：
1. **介质更快** —— RAM > SSD > HDD（电子访问 vs 机械寻道）。Redis 缓存主要吃这类。
2. **物理 / 网络更近** —— L1 cache 在 CPU 芯片上、CDN 在用户边上。**你的「更近」直觉对在这一类。**
3. **省掉重新获取** —— 把上次算好的结果存下来，跳过整个 fan-out + 计算。跟距离、介质都无关，是应用层缓存最主要的快。

所以你的「更近」在 CPU cache 和 CDN 两层对（真·物理近）；但平时说的「上个 Redis」，快的主因是**介质（RAM vs 磁盘）+ 省掉那次贵的获取**，不是 CPU 距离。落到 QuoteFlow：当前费率表常驻内存，省的是「磁盘→RAM」+「不再每次远程拉表」。详见配图 `notes/Day-03-storage-hierarchy.html`。

### Q2. SSD 是什么？

**问：** SSD 是什么？

**答：** **SSD = Solid-State Drive，固态硬盘。**「固态」=**没有任何会动的机械部件**：用 `NAND 闪存`芯片把数据以电荷形式存在晶体管里，断电不丢。对比老式 **HDD（机械硬盘）**——靠旋转磁碟 + 来回移动的磁头读写，每次随机读都要**物理移动磁头到位**（寻道），约 10ms；SSD 没磁头要移，直接寻址闪存单元 → 随机读约 16µs，**快约 600×**，且抗震、省电、安静，代价是每 GB 更贵。nuance：SSD 内部 `NVMe`（走 PCIe）接口比老 `SATA` 快好几倍。

串今天容量估算：RAM（最贵最快，当前费率表）→ SSD（贵但随机读快，在线 DB / 热数据）→ HDD / 对象存储（便宜慢，审计 7 年归档）。「哪份数据放哪层」= 在存储金字塔上按访问频率挑一层。

### Q3. 文档里的「链路」是什么？

**问：** 带宽估算里提到「1 Gbps 链路」「占几条链路」，链路是什么？

**答：** **链路 = `link` = 两个网络节点之间传数据的那条「连接 / 通道」**（物理上一根网线 / 光纤，逻辑上一条数据通路）。估算里只关心它一个属性——**带宽（容量）**，用**水管**类比：链路 = 水管，带宽 = 管子多粗 = 每秒能搬多少数据；流量超过上限就换粗管或并几根。

⚠️ **那个 ÷8 的坑：** 网络带宽用 **bit/秒**（Gb**p**s，小写 b），数据量 / 存储用 **Byte/字节**（大写 B），`1 Byte = 8 bit` → `1 Gbps = 1000 Mbit/s ÷ 8 = 125 MB/s`。**带宽报 bit、数据算 byte，永远差 8 倍**，不换算就错一个数量级。落到 QuoteFlow：报价 JSON 才几 KB、QPS 上百，远够不到 125MB/s，所以**带宽通常不是报价路径瓶颈**；但大附件 / 图片 / 批量导出就可能撞上限。（Day 4 网络基础会展开）
