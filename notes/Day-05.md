## 今日思考题

1. QuoteFlow 的**网站、App、broker** 三类调用方，你会给他们**同一套 API 还是不同风格**？各自的取舍是什么？（提示：接入成本 vs 性能 vs 灵活取数）
   
   - 我的想法：会给他们不同风格的API。对于网站和broker来说，用一般的REST风格即可，目的是能提供清晰的API调用逻辑，方便客户上手。对于Broker来说可以使用mTLS做安全层，虽然相比普通TLS更繁琐一点，会增加一点latency，但是由于broker数量较少所以总体的成本不会太高。面向一般客户的网站由于可能承接许多用户的request，去验证每一个用户的身份成本就会过高，所以不使用mTLS，只用TLS。对于App来说因为要把多个方面的信息同时集成在app界面上，如果用REST的话会需要在不同的API多次调用，这样可能会让信息返回的时间过长，所以选用GraphQL，一次调用返回全部需要的字段信息，可以减少latency。虽然服务器端需要做得更复杂，但是latency成本会下降。灵活取数这方面我有点忘记具体指的是什么了。

   - **Claude 点评：** 主轴完全对——App 用 GraphQL 解决「一屏拼多块、REST 得发好几次」、broker 叠 mTLS、「服务端更复杂换 latency 下降」这个取舍都抓得准。三点补强：
     1. **mTLS 的本质是「机器 ↔ 机器互信」，不是「逐个验终端用户」。** 你说「网站用户多、逐个验证成本太高所以不用 mTLS」——结论对，但更准的原因是 **mTLS 验的是调用方那台机器/服务的身份**（双方各持证书），天生适合 server-to-server 的可信合作方。broker 少、已知、可**预先分发证书** → 划算；普通消费者**没法给每人发/管证书**，他们的身份是用**应用层 token / OAuth**（Day 25）认证的。所以是「消费者场景天然不适用证书分发模型」，不只是「成本高」。
     2. **「灵活取数」就是你忘了的那个词 = GraphQL 让客户端「自己点菜」。** 它解决两个毛病，你只说中一半：**under-fetching**（你说的，数据散在多接口、要发多次）+ **over-fetching**（一个接口返回一大坨、只用得上一半字段）。GraphQL 让客户端**声明只要哪些字段**，一次精确拿全。
     3. **补全景（题没问但值得记）：** 三类是「对外」。QuoteFlow **内部**服务之间（报价服务调核保服务）通常用 **gRPC**（强类型、二进制、低延迟）。所以完整画面 = 文档图 1 的 **对外 REST、移动端 GraphQL、内部 gRPC**，三种并存。

2. 投保 `POST /applications` 上了 idempotency key——这个 key 该由**谁生成、存多久**？如果**同一个 key 配了不一样的 body**，服务端该怎么处理？
   
   - 我的想法：key由客户端生成，这样服务端遇到客户端有同一个idempotency key发来的请求，就只会return之前的结果，但不再执行客户端的请求。存的时间一般是24小时，不能太短，因为太短的话实际的同一请求就可能被识别为不同请求导致问题。如果同一个 key 配了不一样的 body，服务器端应该报错（422还是啥的），因为body变了意味着请求内容有变化，这表示客户端可能出现了错误（本应是新请求但用的还是旧key），不能因为key一致就还是return之前的结果而不报错。

   - **Claude 点评：** 这题基本满分，四个点全踩中文档——客户端生成 / 命中就返回旧结果不再执行 / 存 24h / 同 key 不同 body 报 422。两点微调 + 一个钩子：
     1. **「存多久」的因果再准一点。** key 在**保存期内**，重试能命中缓存结果（安全）；**过期后**，同样的 key 再来会被当成**新请求重新执行**（重复风险回来）。所以 24h 是「**覆盖掉合理的重试窗口**」的取舍（重试一般几秒~几分钟内发生，24h 留足余量）——不是「太短会认错请求」，而是「太短会让**晚到的重试**落在过期之后、失去保护」。
     2. **同 key 不同 body 怎么「比对」？** 服务端通常存的不是整个 body，而是 body 的 **hash 指纹**；新请求来了比对 hash，不一致 → 422。
     3. **留个钩子（Day 18 展开）：** 真正的硬骨头是**并发**——两个带同一 key 的请求**几乎同时**到达，第一个还没处理完第二个就来了，两个都以为自己是「第一次」。解法是处理前先**占位 / 加锁**（先写一条 `processing` 状态）。

### Q1. 「一致 / 可预测」那句「所有列表都用同一套分页参数」具体啥意思？

**问：** 文档说好 API 要「一致 / 可预测」，举的例子是「所有列表都用同一套分页参数，不用每个接口现学」——这具体在说什么？

**答：** 一个 API 里有很多返回列表的接口（`GET /policies`、`/quotes`、`/applications`、`/claims`…），每个都要分页。「一致」=**这些接口全用同一套分页参数 + 同一种返回结构**。反面（各搞各的）：`/policies?page=2&size=20`、`/quotes?offset=40&limit=20`、`/applications?cursor=abc&count=20`——调用方每接一个新接口都得翻文档搞清楚「到底叫 page 还是 offset」，又费时又易出 bug（这就是「每个接口现学」）。正面：全站统一 `?cursor=<token>&limit=20` + 返回体都长 `{data:[…], next_cursor:…}` 一个样 → 调用方**学一次、处处通用**，SDK 能写一个通用 `paginate()` 吃下所有列表，甚至没看文档也能**猜对**新接口长什么样。对 QuoteFlow：对外 broker、对内批处理看到的都是同一种翻页方式 → 降接入成本 + 审计日志格式统一好对账。

### Q2. offset 分页 vs cursor 分页，技术上各自怎么实现？

**问：** 这两种分页底层是怎么实现的？

**答：** 直觉：**offset = 「数到第 40 个再给我接下来 20 个」**（每次从头数）；**cursor = 「从我上次夹的书签往后给我 20 个」**（直接翻到书签）。
- **offset：** SQL `... ORDER BY created_at DESC LIMIT 20 OFFSET 40`（`offset=(page-1)*limit`）。数据库**真的会走过前 40 行再丢掉**。两个硬伤：① **越翻越慢**——`OFFSET 1000000` 要先走过一百万行，代价 O(offset)；② **数据变动会重复/漏算**——你读完第 1 页时若有人在最前面插了一行，第 2 页的 `OFFSET 20` 就把原第 20 行又读一遍（重复）；删一行则跳过（漏）。优点：能**跳任意页**、能算**总页数**。
- **cursor（keyset）：** 不按位置数，而是记住「上次最后一行是谁」，要「排在它后面的」。SQL `WHERE created_at < :last_seen ORDER BY created_at DESC LIMIT 20`。cursor token 里编码的就是上一页最后一行的排序键值（base64 成不透明字符串）。只要排序列有**索引**，数据库能**直接 seek 到那个位置**往后读 20 行、不走前面所有行 → 代价 O(limit)，**第 1 页和第 5 万页一样快**；且游标锚定在固定值上，前面增删**不影响窗口** → 不重复不漏。代价：**不能跳任意页**、一般给不了总数。
- **必知的坑：** 排序键要**唯一**。`created_at` 不唯一（同毫秒可能两行）→ 实战用复合键 `(created_at, id)` 做行值比较 `WHERE (created_at, id) < (:last_created_at, :last_id)`，`id` 当 tiebreaker。
- **QuoteFlow 选型：** 全站统一 cursor，因为核心场景是「稳定地从头扫到尾几百万张保单（夜间批量重定价）」——offset 在这里又慢又会算错。（「为什么索引能让它直接 seek」留给 Day 9 索引。）

### Q3. 无限滚动（infinite scroll）前端怎么用 cursor？

**问：** 那种「滑到底自动加载更多」的无限滚动，前端是怎么配合 cursor 的？

**答：** 一次完整滚动：① 首次打开 `GET /quotes?limit=20`（无游标），服务端返回 `{data:[…20条…], next_cursor:"abc"}`，前端**渲染 20 条 + 存下 next_cursor**；② 用户滑到快见底 → 带上书签 `GET /quotes?cursor=abc&limit=20`，返回接着的 20 条 + 新书签，前端**追加渲染 + 更新书签**；③ 重复，直到 `next_cursor` 为 `null` → 停止加载、显示「没有更多了」。前端**完全不关心** cursor 里装什么，原样收发（所以要 base64 让它不透明，服务端日后改游标实现也不破坏调用方）。**为什么必须用 cursor 不能 offset：** 列表一边滑一边在变，若用 offset，刷到一半前面插了新报价，整列表往下挪一格 → 同一条被加载两遍，列表出现**重复项**（很穿帮）；cursor 锚定在「上次那条的 id」上，前面插多少都不重不漏。**配套口诀：** 无限滚动 / 下拉加载 ↔ cursor；带页码的后台表格 ↔ offset。

### Q4. 「endpoint」到底是什么？怎么理解？

**问：** 工作和文档里老见 endpoint（比如 Azure 调大模型就是去一个 endpoint），它到底是什么？

**答：** **Endpoint = 一个具体的网络地址（URL），客户端把请求发到这个地址就能触发 API 的某一个具体功能。** 它是请求旅程的「终点」。结构 = **主机 + 路径 + HTTP 方法**，如 `POST https://api.quoteflow.com/v1/quotes`：主机 `api.quoteflow.com`（哪栋楼）+ 路径 `/v1/quotes`（楼里哪个窗口）+ 方法 `POST`（做什么）。类比：① 大楼里一排挂牌的**服务窗口**（报价窗口 / 投保窗口 / 查保单窗口）；② **公司总机 + 分机号**（主机=总机，路径=分机，拨「总机+分机」直接接到报价部）。**Azure 调大模型**：你部署一个模型，Azure 给你一个 endpoint（如 `.../deployments/gpt-4/chat/completions`），意思是「你那个模型摆在了这个地址上」，你把 prompt 放进 body POST 过去就用上了它；换模型 = 换 endpoint。**厘清两词：** **API** = 整个服务的接口集合（整栋楼）；**endpoint** = 其中一个具体访问点（一个窗口）。一个 API 通常有很多 endpoint。

### Q5. GraphQL 怎么做到「客户端声明只要哪些字段」？名字里 Graph / Q / L 各指什么？

**问：** GraphQL 怎么实现「客户端在请求里声明要哪些字段」？Graph、Q、L 分别指什么？Graph 和 CS 的「图」有关系吗？我猜是因为只有 1 个 endpoint 所以只能按 API 设计来选字段？

**答：** **先纠正因果**：「单 endpoint」**不是**字段选择的原因——两者是**同一个设计选择（「把要什么写进请求 body」）的并列副产物**：既然要什么都写在 body 里，URL 就不用区分了（→ 单 endpoint），而 body 里那套写法就是字段选择的来源。你「只能按 API 设计选」这半句**对的**——那叫按 **schema** 点菜。**名字：** **Q**=Query、**L**=Language、**Graph**=数据被建模成一张图，合起来「面向图数据的查询语言」。**怎么做到字段选择**靠三样：① **Schema**（菜单）——服务端预先声明有哪些类型/字段/怎么连（你只能点菜单上有的）；② **Query**（点菜单）——客户端在 body 里写查询，把想要的字段按想要的形状挑出来；③ **Resolver**——服务端给每个字段配取数函数，引擎逐字段调、**只拼装你点过的字段**返回（这就是消灭 over-fetching 的方式）。**Graph 就是 CS 的图：** 节点 = 实体（Customer / Policy / Quote），边 = 关系（`owner: Customer`、`quotes: [Quote]` 这种「字段类型是另一个对象」就是边）。写**嵌套查询** `customer{ policies{ quotes{…} } }` 本质就是**沿边遍历这张图**（graph traversal），从一个节点出发把相连节点一路拉出来——这也正是它优雅消灭 under-fetching 的原因（REST 里散在三个 endpoint 的数据，在图上本来相连，一次遍历全拿回）。
