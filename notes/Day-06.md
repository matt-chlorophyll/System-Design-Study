## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01/02/03/04/05 那样）。

1. 我们把单点从应用服务器移走了，可**负载均衡器自己**会不会成为新的单点？生产里该怎么避免？
   
   - 我的想法：如果只有一个负载均衡器，那么它会成为新的单点，一旦这唯一一个负载均衡器出现问题，那么会导致整个分发出现问题而导致请求处理失败。避免的方式和把单点从服务器移走一样，就是在系统里设置多个负载均衡器来共同进行分发活动，如果有出问题的负载均衡器，就把分发任务停止分给它，而用其他健康的进行分发，同时也要对负载均衡器的健康情况进行regular的检查来及时发现failure。

   - **Claude 点评：** 方向完全对——冗余消除单点 + 对 LB 也做健康检查。但跳过了这题的**精髓：一个递归追问**。你说「设置多个 LB、出问题就停止分给它」——那是**谁**在「把请求分给这几个 LB」、又是**谁**在对 LB 做健康检查、把坏的摘掉？你其实把「客户端该连哪台机器」原封不动往上推了一层，变成「客户端该连哪个 LB」。冗余本身**不会自动解决「入口怎么被找到」**。两种生产答案：
     1. **Active-Passive（主备）**：主备共享一个**虚拟 IP（VIP）**，靠 **VRRP / keepalived 心跳**互相盯着；主挂了备接管同一个 IP → 客户端永远连同一个 IP、切换无感。
     2. **Active-Active（多活）**：**DNS 多 A 记录** 或 **Anycast IP**（同一 IP 多地广播）把客户端分到多个 LB，没有「备用」、全在干活。
     关键：盯 LB 健康的**不是另一个应用层组件**（否则又要问「谁盯它」无限套娃），而是 LB **同伴之间的心跳** 或 **DNS / 客户端重试**这种不在请求路径上的机制。文档那句「云厂商托管 LB 如此常用」，本质就是**把这整个递归问题外包**给云。

2. QuoteFlow 的报价请求**轻重差别很大**（简单产品秒出、含核保的慢得多）。在这种情况下，round robin 可能出什么问题？换成哪种算法、为什么会更好？
   
   - 我的想法：这种情况下round robin有可能会导致特定机器积压过多处理速度慢的请求，导致latency增加，返回结果的速度变慢。换成least connections会更好。这样可以让有快有慢的请求相对均匀的被分配给不同机器，因为有最少connection的机器意味着会相对更快的把余量任务处理完，这样就能减少慢请求全部集中在特定机器上的情况。

   - **Claude 点评：** 正确，理由也对，和文档答案一致。两个精度上的小修正值得记住：
     1. **因果说反了一点。** 不是「最少 connection 的机器会**更快地把任务处理完**」，而是「它**现在手头活少 = 更闲**」。least connections 用**活跃连接数**当作「这台有多忙」的一个 **proxy（代理指标）**：慢请求会让连接**挂在那台机器上更久**，连接数自然高，LB 就自动少发给它。
     2. **round robin 的毛病更本质的是「盲发」。** 它只数「轮到第几个」、**完全看不到某台此刻忙不忙**；哪怕某台已被几个慢请求压住，轮到它照发不误，队列越积越长。least connections 的关键优势就是它**读实时状态**（呼应文档伪代码：「轮询只数到第几个，最少连接看实时状态」）。

## 提问 & 解答

> 讨论时冒出来的问题记这。每条：先记自己的问题，再记讨论后的结论（用自己能看懂的话）。

### Q1. 文档里 L7 / 会话粘性都提到 cookie——cookie 到底是什么？

**问：** L7 能看到 Cookie、sticky session 也按 cookie——cookie 是什么？

**答：** **cookie = 服务器让浏览器替它存的一小块数据，浏览器之后每次请求同一域名都自动把它带回来。** 它解决的根本问题接今天的主题：HTTP 是 **stateless** 的（Day 4/5），服务器天生不知道「这个请求和 2 分钟前登录的是同一个人」，cookie 就是跨请求**携带一点身份 / 状态**的机制。机制三步：① 登录成功 → 服务器在响应头塞 `Set-Cookie: session_id=...`（"存好"）；② 浏览器存下来；③ 之后每个请求浏览器自动加 `Cookie: session_id=...`（不用写代码）。关键：cookie 里**通常不存真数据**，只存一个随机看不懂的 **session_id**，真正「你是谁 / 你的报价进度」存在**服务器那边**，用这个 id 当钥匙查。
- **接今天**：L7 能读 cookie → 这就是「按 cookie 做 sticky session」的原理；而 session 数据存哪？若存在某台**本地内存** → 重试落到别台读不到 = 今天的 **stateless 问题**，干净解法是**下沉到共享存储**（Redis，Day 7）。
- **后面再见**：Day 25 安全（`HttpOnly` / `Secure` 防偷、session vs token / JWT），cookie/session 也是「谁在何时操作了保单」审计链的起点之一。

### Q2. header 和 cookie 是什么关系？

**问：** header 和 cookie 的关系？

**答：** **cookie 本质就是一对特殊的 HTTP header，它就住在 header 里**，不是独立的东西。HTTP 请求 / 响应都分 **headers（元信息，一堆 `名字: 值`）+ body（正文）**。cookie 只是其中两个**约定好名字**的 header：服务器下发用 `Set-Cookie:`、浏览器回传用 `Cookie:`。一句话：**header 是大类**（请求 / 响应所有元信息，如 `Content-Type`、`Authorization`），**cookie 是 header 里被浏览器「特殊对待」（自动存 + 自动回传）的那一种**。所以「L7 能看 header、能看 cookie」其实是同一件事——L7 拆开 HTTP 后读得到所有 header，cookie 就在里面。

### Q3. 路由（routing / route）是什么？

**问：** 文档老提「按内容路由」「按路径路由」——路由是什么？

**答：** **routing = 决定「这个请求该去哪里」的过程**；一条「什么样的请求 → 送到哪」的规则叫一个 **route**。核心一个意思：**把进来的东西映射到它该去的地方 / 该由谁处理**（像邮局按地址分拣）。同一个词在多层出现、意思相同，只是「目的地」不同：
- **网络路由（Day 4）**：看 **IP** → 决定数据包走哪条网络路径（router 的本职，最原始含义）。
- **L7 LB 路由（今天）**：看 **URL 路径 / header** → 决定发给哪个**后端集群**（`/quotes`→定价集群、`/policies`→保单集群）。
- **应用 / API 路由**：看 `POST /v1/quotes` → 决定哪个**函数**处理（= 我 vibe-coding 时定义的 **endpoint** 就是在写 route）。
所以路由对我不是新东西，今天只是**往上挪了一层**：从「哪段代码处理」变成「哪台 / 哪群机器处理」。一句话：**routing 的聪明程度 = 它能看到多少信息**（呼应 L4/L7——L4 看不到路径，所以做不了按业务路由）。

### Q4. L4 / L7 之外，其他 LX 是哪些？

**问：** 文档提了 L4 和 L7，其他的 LX 都是哪些？

**答：** 来自 **OSI 七层参考模型**。从底到顶**层号越大、拆得越深、看到的「意义」越多**（= 今天「越深越聪明」的来源）：
- **L1 Physical 物理层**：比特信号（网线 / 光纤 / Wi-Fi 无线电）
- **L2 Data Link 数据链路层**：同段链路传帧，**MAC 地址**（Ethernet / 交换机 switch）
- **L3 Network 网络层**：跨网络寻路，**IP 地址**（router，Day 4「路由」的原意）
- **L4 Transport 传输层**：端到端、端口，**TCP / UDP**（← 今天 L4 LB 看这层）
- **L5 Session 会话层**：建立 / 维持会话（理论层，实践很少单独提）
- **L6 Presentation 表示层**：加密 / 编码 / 序列化（TLS 常算这附近）
- **L7 Application 应用层**：**HTTP / DNS**，真正的业务内容（← 今天 L7 LB 看这层）

三个要记住的点：① **OSI 是参考模型、不是现实**，真实互联网用更简单的 **TCP/IP 模型（4–5 层）**，L5/L6 现实里对应不清、基本被并入 L7 → 实践只谈 **L1–L4 和 L7**，没人说「L5/L6 负载均衡」；② **「L4 vs L7 LB」是简称**，意思是这个 LB **最多看懂到第几层**（L4 只到传输层看 TCP/端口、看不懂 HTTP；L7 一路拆到应用层、看得懂路径/header）；③ **和 Day 4 对上**：DNS/HTTP 在 L7、TLS 在 L6 附近、TCP/UDP 在 L4、IP 在 L3。简记：**层号 = 理解力**，L1 只看到电信号、L7 看到完整业务含义。

### Q5. 重试时 idempotency key 是 LB 识别后路由回同一台机器判重的吗？

**问：** 重试发出相同 idempotency key，是 LB 自动识别这个 key、把请求发给同一台机器，那台发现执行过就返回旧结果吗？还是 LB 那里就能识别已执行？

**答：** **两处都不对**，纠正它们正好把今天的 stateless 和昨天的幂等打通。
- **偏差 1：LB 不认识 idempotency key。** 它是**应用层概念**，就是 header 里一个值；LB 的职责是「送到一台健康机器」，**不解读业务语义**——哪怕 L7 能**读到**这个 header，它也**不理解**「这操作已执行过」。判断执行没执行过是**应用代码**的事。
- **偏差 2：根本不需要、也不应该把重试发回同一台。** 那恰是 **sticky session 反模式**；而且**重试经常正是因为那台挂了才发生的**，发回去只会再次失败。
- **正确流程**：幂等判断**不在任何单台内存里，而在共享存储**（DB / 缓存）。任何一台收到带 key 的请求都一样做——查共享存储「见过这个 key 吗？」：没见过 → 执行 + 把「key→结果」写进共享存储 + 返回；见过 → **不再执行，直接返回存好的结果**。所以重试落到**完全不同的机器**也对，**因为应用 stateless、幂等记录在共享存储、哪台都查得到**。反过来：若记录存在某台**本地内存**，重试分到别台查不到 → **会签出第二张保单**（这就是今天「状态下沉共享存储」在写操作上的后果）。
- **一句话收口**：**LB 管「送到任意一台健康机器」（高可用）＋ 共享存储 + 幂等键管「无论哪台都不重复执行」（不出错）**，正交两层、各管各的。（细节埋 Day 18：重试太快、第一台还没执行完 → 共享存储加「处理中」锁。）

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 为了能让服务器端满足对latency， throughput和availability等non-functional requirments，可以通过增加机器（scale out）的方式来使用复数机器处理客户端发来的请求，也同时避免Scale Up单机所带来的single point of failure和处理能力提升有上限的问题。当有复数机器时，需要有一个功能来把客户端请求合理的分发给不同的机器，这个功能就通过反向代理（reverse proxy）和负载均衡（load balancer）来实现，而“合理”通过选择合适的分发方法来实现，同时也要保证对机器进行健康检测，避免发给出问题的机器。Load Balancer可以在L4传输层和L7应用层同时出现来配合进行合理分发，也可以是多个，从而避免Load Balancer也成为SPOF。此外，机器要保证是stateless的，避免被分发的请求因缺少之前被储存在单个机器中的信息而失败。

- **Claude 点评：** 写得很全，整条链路（scale out → reverse proxy / LB → 分发算法 → 健康检查 → L4/L7 → stateless）都串起来了，因果也对。一处小修正 + 一个按你行业值得加深的点：
  1. **小修正**：「LB 可以在 L4 和 L7 同时出现来**配合进行合理分发**」——「配合分发」略含糊。更准的说法是两层**职责不同**：L4 在最外层扛海量连接、做**粗分流**；L7 在内层拆开 HTTP、按**内容（路径 / header）精细路由**。不是简单「一起分」，而是「**先粗后细**」。
  2. **往合规视角加一层**：你把 stateless 理解成「避免请求因缺少本地信息而失败」——对，但对 QuoteFlow 这种受监管系统还有更深一层（文档 Case）：状态（尤其**费率表版本 / 核保规则 / 定价模型**）必须来自**共享、版本化的源**，目的不只是「别断流程」，而是**每台机器算出完全一样的数** → 这才是 **reproducibility / auditability** 的前提。随机分到一台「规则没更新」的机器就出一个不可复现的报价，在你行业是要命的。
