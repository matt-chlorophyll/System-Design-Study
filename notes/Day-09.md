# Day 09 · 索引与查询性能

> 对应文档：`Day-09-indexing-query-performance.html`
> 日期：2026-06-09
> 主题：full table scan / Seq Scan（无索引时逐行扫，O(n)）、index（额外维护的有序结构，空间+写开销换查询不扫全表）、B-tree / B+tree（又矮又宽、始终平衡，高 fan-out 让百万行只 3~4 层 → O(log n)；B+tree 叶子串成有序链表利于范围/排序）、composite index 复合索引 + leftmost prefix 最左前缀（按列序排，须从最左列连续命中）、covering index 覆盖索引 / Index Only Scan（所需列全在索引里 → 免回表）、table lookup 回表（索引只给行位置、再回主表读其余列的随机 IO）、selectivity 选择性 / cardinality 基数（命中行/总行数；高选择性该用索引，低选择性顺扫更快）、write amplification 写放大（每次增删改要维护所有相关索引）、EXPLAIN / query plan（让数据库摊开它打算怎么取数，加 ANALYZE 给实际耗时与行数）

## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01–08 那样）。

1. QuoteFlow 的 **audit_log** 只增不减、会长到几亿行。为支撑两类审计查询——「调出某保单的**全部历史**」和「**按时间范围**抽查所有 ISSUE 动作」——你会建哪些索引？复合索引的**列顺序**怎么排、为什么？同时它又会给这张高写入表带来什么代价？
   
   - 我的想法：对于“调出某保单的全部历史”查询，我的索引会以保单的ID作为主要索引，然后INCLUDE一些和保单历史相关的主要列，比如issue的时间，用户身份，保单价格之类的。而对于“按时间范围抽查所有 ISSUE 动作”，我的索引会以issue的时间作为主要索引，然后也会INCLUDE那些相关列。如果要做复合索引的话，我会排成（保单ID，Issue时间）这个顺序，原因是对特定保单的查询，相对于抽查特定时间范围内所有issue动作来说，能命中的行数一般来讲要少很多。所以先按照保单ID来排能够保证快速索引到特定ID，提取历史数据，如果把Issue时间放前面，在进行单个保单的历史查询时就会miss保单ID这个identifier，导致要进行代价为O(n)的seq scan。如果进行按”按时间范围抽查所有 ISSUE 动作”这个查询，本身不涉及选择特定具体保单，即使对Issue时间进行seq scan，由于命中行数相对较多，代价并不明显，如果给定的时间范围还很宽的话，seq scan甚至会比用索引更快。对这张高写入表带来的代价是，每次写动作都要保证索引也要进行一致的修改，这个会增加写动作的复杂度，使写动作的处理时间变长，高写入也就意味着高耗时。

   - **Claude 点评：** 查询 A 那半边满分——`(保单ID, Issue时间)` 的列序 + 「先按 ID 才能瞬间定位，否则缺最左列退回 O(n) Seq Scan」的推理，和文档示例一字不差；用 INCLUDE 把要 select 的列盖进去也对。⚠ 修正你后来自己也察觉的那点：查询 B「按时间范围抽查所有 ISSUE 动作」你只盯「时间范围多宽」就判它低选择性 → Seq Scan，**漏了 `action='ISSUE'` 这个等值条件本身就很 selective**（ISSUE 只是众多动作里的一种）。正解是 **`(action, at)`：等值列在前、范围列在后**（equality-before-range，最左前缀的精炼版）——哪怕时间窗开得很宽，ISSUE-only 相对几亿行仍是小比例，索引照样赢。两点补充：① 你「建两个独立索引」的直觉对，且要点明 `(entity_id, at)` 对查询 B 完全没用（缺最左列）——所以确实得各建一个。② 写代价你答中了 write amplification；再深一层：`entity_id` 这种**随机 key 的索引 page split 更频繁、占盘随表涨，连 INCLUDE 的列也加重每次写**，所以解法是「只建支撑核心审计查询的少量索引 + 按时间分区（Day 13）」。

2. 把今天的 **selectivity** 和昨天 Day 8 的**事务边界**连起来想：夜间批量重定价该**用索引还是 Seq Scan**、又该**每张保单一个小事务还是整批一个大事务**？这两个判断背后，是不是同一种「看命中规模 / 看影响范围」的取舍直觉？
   
   - 我的想法：应该用seq scan，因为对于夜间批量重定价来说，有客观的一部分保单需要走重定价过程，意味着命中行数很高，用索引的话，由于要回表产生的随机IO很多，最后速度大概率比seq scan更慢。对于transaction来说，每张保单一个小事务是两者之中更好的选项，虽然从Day 8的讨论当中，应该把一定数量的保单集合起来（类似成为一个batch）成为一整个事务更好，因为这样能避免一整个大事务造成的transaction lock时间过长，日志占用过多，出问题回滚重算的量过大的问题，也能避免单张保单作为一个事务进行处理造成的处理次数过多，成本增加的问题（比如每一张保单都要进行一次日志写入来满足atomicity的要求）。一批保单集合在一起成为一个transaction可以在其中找到一个成本相对平衡的地方。这两个判断背后的直觉是类似的，我认为都是在缩小影响范围时可以利用更高效的方法，比如想要的命中数少时，就可以通过Index来集中定位这一小范围的保单来加快查询速度；选择小事务也是通过选定小范围的保单进入事务来保证资源占用少，回滚时重算的数量少来减少处理的时间。

   - **Claude 点评：** 结论全对（Seq Scan + chunked batch），而且你自己从「每张一事务」修正到「攒一批找平衡点」就是满分直觉。要打磨的是「同一种直觉」这句——它其实是**两根不同的轴**：selectivity 管的是**读的 access path**，形状是**阈值翻转**（命中低于某比例用索引、高于就 Seq Scan，优化器在代价交叉点一刀切）；事务大小管的是**写怎么分组**，形状是 **U 形甜点**（太小 commit/fsync 开销爆、太大 锁/回滚/bloat 爆，最优在中间）。最能戳破「同一种」的反例就在这单作业里：**读 scope 大（整表一次 Seq Scan）、写 scope 小（每 1000 张 commit 一次）——同一个 job 两根轴方向相反**。你 Seq-scan 整表只一遍，却 commit 很多次 → 证明它俩是独立旋钮，不是一种直觉。共同母题只有一句「让代价匹配你碰的规模」，但落地是两套不同的权衡。

## 提问 & 解答

> 讨论时冒出来的问题记这。每条：先记自己的问题，再记讨论后的结论（用自己能看懂的话）。

### Q1. 索引（B+tree）是谁、什么时候建出来的？技术上怎么建？写入时会自动更新吗？

**问：** B+tree 是数据库存完数据自动生成的，还是要人用 INDEX 语句建？建索引技术上发生了什么？新数据写进来这棵树能自动更新吗？

**答：** 分两种：**主键索引**数据库自动建；**二级索引**要人手动 `CREATE INDEX`（DB 不会按你跑过的查询自动长索引，除少数云端 auto-indexing）。钉死一个区分：「索引**存不存在**」是人决定的，「某条查询**用不用**它」是优化器每次按 selectivity 自己决定的。`CREATE INDEX` 是一次性 **bulk build**：扫全表抽出 `(列值, 行指针 ctid)` → 排序 → **自底向上**把排好序的条目塞满 leaf、再盖 branch 直到 root（塞得紧、建得快）。代价：扫全表 + 占临时空间 + **默认上锁挡写**（线上大表要用 `CREATE INDEX CONCURRENTLY`）。建好后 **DB 在每次写时随事务自动维护**所有相关索引——这就是 write amplification 的来源。

### Q2. page split 是什么？父节点也满了怎么办？

> 详见补充图解 `notes/Day-09-page-split.html`。

**问：** 索引「塞满一页」具体怎么塞？满了再插会怎样？父节点也满了，key 是怎么「往上推」的？

**答：** 一个 **page**（PG 默认 8KB）里是一个**有序数组**，按 key 塞到装不下。满页再插 → **page split**：裂成两页各拿一半，把分界 key 往父节点放，叶子**链表重接**。父节点也满则**级联**：父也裂、再往上推，一路裂到 root 就**新建 root、树长高一层**——这是树唯一长高的方式，因此所有 leaf 永远同深度 = 始终平衡。关键区分**两种「上推」**：**叶子分裂 = copy-up**（新右叶最小 key **复制**上去，自己仍留叶子，因为数据全在叶子）；**branch 分裂 = push-up**（正中 separator **移**上去、不留两个半边，因为 branch 只是路标，移走不丢数据）。

### Q3. 范围查询 `BETWEEN` 会受 leaf 页边界影响吗？

**问：** 如果命中的 key 横跨好几个 leaf 页，`WHERE premium BETWEEN 30 AND 50` 取数会受影响吗？

**答：** 不会。先纠一个误解：**leaf 存的是一个个真实 key 条目，「区间 / 边界」在上面的 branch 节点里（separator key）**。所有 leaf 串成有序**链表**，所以范围查询是：① 导航到第一个 ≥30 的 leaf；② 在页内往右读，到页尾跟着 next 指针跳到右邻 leaf 继续；③ 读到 >50 停。30–50 落一页还是三页对你完全透明，只是顺链扫一段（顺序读）——这正是 B+tree 为范围 / 排序设计的杀手锏。

### Q4. 回表的「随机 IO」是什么？跟什么 CS 概念有关？

**问：** 回表产生的「随机 IO」到底指什么？我猜和某些 computer science 概念有关？

**答：** 是 **random IO vs sequential IO** 这个系统概念。读盘最小单位是 **page**；要读的 page 物理连续 = 顺序，散落各处 = 随机。回表必然随机，因为**索引按 key 排序、heap 按写入顺序堆**——索引里相邻的几条，行可能落在 heap 的第 5、8002、13 页，跟着指针回表就是**到处跳**。慢在哪看介质（接 Day 3 存储层级）：HDD 每跳要 **seek**（~10ms），随机比顺序慢约 100×；SSD 无机械臂、惩罚小但因 page 粒度 + 预读失效仍输。**这就是 selectivity 翻转的根因**：命中少→几次随机跳，索引划算；命中多→海量回表随机 IO，反不如整表顺读（Seq Scan）。相关概念：locality of reference、prefetch、IOPS vs throughput。

### Q5. 为什么会需要随机分布的 key（UUID）？UUID 是做什么的？

**问：** 既然随机 key 写起来贵，为什么还要用 UUID？我做 vibe coding 时 Supabase 老给我生成 UUID，它是干嘛的？

**答：** UUID = 128-bit、**无需中央协调就能生成的几乎不重复 ID**。用它的四个理由：① **去中心化生成**（自增 ID 要 DB 统一发号，分库 / 多写就打架）；② **插入前就能拿到 ID**（先建好关联对象再存、optimistic UI、offline）；③ **不可枚举、防猜**（自增 ID 暴露在 URL 里 → `/users/1` 加一就能遍历、还泄露规模；这多半是 Supabase 默认用它的原因）；④ **合并数据不撞车**。代价正是我们讲的：随机插入 → page split 满天飞 + bloat，且 16 字节会**撑胖所有索引**。两全解：**UUIDv7 / ULID（时间戳在高位、单调递增）**，保留唯一 + 不可枚举又几乎无随机插入惩罚（注意 Supabase 默认 `gen_random_uuid()` 是 v4 纯随机）；或内部用 bigint 主键、另立 uuid 列对外。

### Q6. clustered index vs secondary index？

> 详见补充图解 `notes/Day-09-page-split.html`。

**问：** 回表到底跳去哪？为什么说「主键被复制进每个二级索引」？

**答：** 分水岭是「**整行真实数据存哪**」。**Heap + secondary（Postgres）**：表是 heap（按写入乱堆），所有索引都是二级索引、叶子存 `(key, ctid 指针)`，查询要回表去 heap 取行 = random IO。**Clustered（InnoDB 主键）**：**表数据就排在索引叶子里、按主键物理有序**，每表仅一个；PK 查询导航到叶子**行就在那儿，零回表**。后果：聚簇表里 secondary index 叶子存的是**主键值**（不是物理指针）→ 一次二级查询要**两跳**（先查 secondary 拿 PK、再查 clustered 取行），所以**主键越宽、每个二级索引都跟着胖**。聚簇还能把回表的 random IO 变 sequential（聚簇 key 对齐高频查询时）。Postgres 没有真聚簇（`CLUSTER` 只一次性重排、不维护），它的替代品就是**覆盖索引 → Index Only Scan**（针对某条查询的「穷人版聚簇」）。

### Q7. INCLUDE 技术上怎么做到「挂叶子、不参与排序」？

**问：** 文档说 INCLUDE「把列挂在叶子上而不参与排序」，技术上怎么实现的？

**答：** 一条索引条目分 **key 列**和 **INCLUDE 列**两段。两个事实定义其行为：① **排序只看 key 列**——B-tree 决定条目位置 / 导航的比较器**根本不读 INCLUDE 列**，它只是附在条目尾巴的几个字节；② **INCLUDE 列只存在 leaf**——branch（pivot）节点会把非 key 列截断，所以它只挂最底层。好处：branch 不背 payload → fan-out 高、树不长高，却能在你落地的那个 leaf 里直接拿到要 select 的列 → Index Only Scan、不回表。对比放进 key 列：key 列参与排序、进 branch、能 seek/range/最左前缀；INCLUDE 列都不能，纯为凑覆盖。佐证它「不是键」：`UNIQUE(...) INCLUDE(...)` 的唯一性只对 key 列生效。

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 数据库可以通过添加索引的方式加快查询（读特定数据行）的速度。索引的技术实现是靠B-tree(B+tree)。复合索引在设计时要注意leftmost prefix避免常用查询fallback到seq scan。索引不是在所有情况下都比seq scan要好，判断标准是看selectivity——如果查询命中行数相对于总行数较少的话，选择性强，索引更快，反之seq scan更快。可以通过INCLUDE把特定列加入到索引的leaf node的里，从而避免对特定列的查询需要回表取行值的情况，加快查询速度（index only scan)。最后，可以通过EXPLAIN和ANALYSIS去看一段SQL查询具体是怎么取行的，从而知道哪里是速度瓶颈。

- **Claude 点评：** 覆盖很全（B-tree 实现 / leftmost prefix / selectivity 判据 / INCLUDE → Index Only Scan / EXPLAIN），几乎可直接当复习卡。两个小修：① 是 **`ANALYZE`** 不是 "ANALYSIS"。② 补一层：**「用不用索引」是优化器（planner）按表统计里的 selectivity 估算自己决定的**，你只能影响、不能强令——所以 selectivity 是「判据」而非「开关」（你建了索引，命中太多时它照样会理性地改走 Seq Scan）。
