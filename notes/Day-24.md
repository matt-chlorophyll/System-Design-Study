## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01–23 那样）。

1. QuoteFlow 的「实时报价」和「夜间批量重定价」NFR 截然不同——你会分别给它们定哪几个 SLI？批量任务的「latency」还有意义吗，该换成什么？
   
   - 我的想法：实时报价服务需要重点关注的是latency和availability，所以SLI我会定P99 < 一个规定值的比例，报价请求最终失败的比例，重试次数的高峰有没有出现等。对于夜间批量重定价，关键在于要在特定的时间窗口内完成整个重定价任务，所以关注重点在throughput，latency的意义不大（因为跨服务的通信很少）。对于SLI，我会定一段window内的平均throughput（如果持续低可能导致在夜间窗口算不完），有无worker的计算持续慢，以及重定价窗口接近到期时的剩余重算任务数（如果发现可能算不完，就要分配资源和进度，在白天继续算完）。

   - **点评（答得很好，纠一个 slip + 补一条最该有的 SLI）：** 实时报价抓得准——latency + availability，`P99 < 阈值的比例` 是教科书式 SLI（SLI 的精髓就是「**好请求占总请求的比例**」），「最终失败比例」就是你的 availability SLI。⚠ 一个修正：**「重试次数高峰」不该当 SLI**——它是 cause-side（原因侧）的诊断信号，不是用户感受到的症状，正撞今天「**对症状告警、不对原因**」那条；放 dashboard 帮排查可以，但 SLO 的锚要绑「成功率 / p99」。批量这边「关键是 throughput、latency 意义不大」结论对，但**理由 slip 了**：真正的原因不是「跨服务通信少」，而是 **batch 不面向用户、没人在等单条记录** → 度量单位从 *per-request* 变成 *per-job*，「单请求 latency」本身就失效了；你说的「窗口内完成 / 剩余任务数」其实就是它的替代——可以更干脆地命名为 **完成时间 / 是否在 deadline 前跑完（job completion time / freshness）**。三个 SLI（throughput、worker 是否持续变慢、临近 deadline 的剩余量）都对、很实战。✅ 但漏了对**受监管批量最致命**的一类——**正确性 / 数据质量 SLI**：批量最怕「跑完了但算错了 / 悄悄跳过一批保单」，要加一条 `重定价失败或异常的保单比例`（throughput 再高，一半算错等于没跑）。

2. 全量存 trace/log 太贵，必须采样。但 audit 又要求「每一笔报价都可追溯」。这两个诉求冲突吗？你会怎么设计，既控成本又不丢审计？
   
   - 我的想法：这个其实也是我读完学习文档之后想问的最关键的问题。我的理解是，如果audit完全依赖trace/log的话，如果有某个没被采样的请求恰好出了问题，这就变成了审计事故，因为对这个请求是在哪一跳出问题，具体发生了什么，怎么算的都没有任何记录，这肯定是不合规的。但“每一笔报价都可追溯”我觉得跟上面的诉求可以不冲突，我们可以单独记录一个audit log，里面只记录作为pointer的定价相关的数据的版本，比如费率表版本，assumption版本，核保规则版本，计算流程的版本等，然后这些实际的数据存在数据库里不丢。当需要审计时，只要根据这些版本号就可以回去找到这个定价请求所需要的相关信息，然后能推出来在当时应该如何报价。这样既不增加trace/log的成本，又能使报价可复现。

   - **点评（几乎是标准答案，补两把刀）：** 核心判对——**两条线分开**：trace/log 排障用（可采样、可过期、成本敏感），audit 合规用（一条不丢），而 audit 那条**很瘦**（只记版本指针），所以「全量留 audit」和「采样 trace」根本不冲突。你还跳过了题目埋的坑——它故意让你以为「可追溯 = 要完整 trace」，其实**可追溯 = 输入 + 决策 + 版本能复现，不需要每一跳的 verbose trace**。两处加固：① **「存数据库里不丢」要升级成「不可变 / 版本化（immutable / versioned）」**——光「不丢」不够，若有人把 `rate_table v2026-06` 原地改了，你的指针就指向被篡改的数据、复现出错的保费。复现的保证 = 瘦 audit log 的版本指针 + 被指向的费率 / 假设 / 模型本身 append-only、永不原地覆盖（接上 Day 23「钉死版本指针」）。② **采样不是「全采 or 全丢」——用 tail-based sampling 堵你担心的那个洞**：决定采不采样放在请求**结束之后**（已知它是否出错），成功又快的只留 1%、**出错 / 超慢的 100% 全留** →「出问题却没 trace」基本不会发生，叠上 ① 的 audit 线就是双保险。

## 提问 & 解答

> 讨论时冒出来的问题记这。每条：先记自己的问题，再记讨论后的结论（用自己能看懂的话）。

### Q1. SLI / SLO / SLA 里的 “SL” 是什么缩写？

**问：** SL 是什么的缩写？

**答：** **SL = Service Level（服务级别 / 服务水平）**，三个都共享这个前缀，区别只在最后一个字母：
- **SLI** = Service Level **Indicator**（指标）—— 实际测量的那个数
- **SLO** = Service Level **Objective**（目标）—— 内部给那个数定的目标
- **SLA** = Service Level **Agreement**（协议）—— 写进合同、违约要赔的对外承诺
- 记忆线：**Indicator 测 → Objective 定 → Agreement 诺**，前面 “Service Level” 不变。

### Q2. “灰度” 是什么？

**问：** error budget 那段说预算有富余就「上灰度」，灰度到底是什么？

**答：** **灰度（灰度发布，gray release）= 新版本不一次性全量上线，先放给一小部分流量 / 用户，观察没问题再逐步扩大比例，直到 100%。** 名字来自旧版「黑」、新版「白」，中间新旧并存、按比例切流量的过渡态就是「灰」。
- **为什么要灰度**：直接全量上线 = 万一有 bug 所有用户瞬间中招；灰度把**爆炸半径（blast radius）**先框在 1% 里，出事只伤这 1%、立刻回滚。
- **QuoteFlow 例子**（接 error budget 那段）：发一版新核保规则，先让 **1% 的报价**走新规则，盯今天学的 SLI——p99 / 错误率 / 有没有算出异常保费，稳了再 10%→50%→100%，任一 SLI 一崩就把流量拨回 0%。
- **和今天的关系**：灰度期间靠 **metrics / traces「看见」新版本好不好，才敢往上加比例**——没有可观测性，灰度就是闭着眼睛放量。
- **几个相关词**（Day 26「部署与发布」展开）：**Canary（金丝雀）**≈ 灰度同义（先放一小撮当探子，典故是矿工带金丝雀下井探毒气）；**蓝绿（blue-green）**= 两套完整环境、新版就绪后**整体一次性**切过去，不渐进。
- **对照记**：**灰度 / 金丝雀 = 按比例渐进切**；**蓝绿 = 整体一刀切（但留着旧的好秒回滚）**。

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 在一个受监管的系统里，auditability和observability可以共用同一套基础设施。首先区分monitoring和observability，一个是监控有没有出问题，一个是能详细的解答问题出在哪了，以及具体是什么问题。要实现observability，需要三大支柱：monitor（追踪监控整合好的数据，方便告警），log（具体的事件记录，信息最全，解答具体怎么出了问题），和trace（通过trace和span来知道是流程里哪一跳带来了问题，来定位问题位置）；他们全部靠trace_id串联起来。还要区分SLI（实际追踪的指标），SLO（团队内部决定要满足的特定指标的目标），SLA（和外部达成的合同，没满足目标就赔偿，因此SLO要比SLA更保守）。SLO的设定会同时告诉团队error budget有多少，方面团队在稳定和迭代中间做量化的决定。

> **点评：** 整段串得很顺（monitoring vs observability、三支柱靠 trace_id 串、SLI/SLO/SLA + error budget、SLO 比 SLA 保守）。一个**术语精度**问题：三支柱是 **metrics / logs / traces**——你写的「monitor」把「**monitoring 这个动作**」和「**metrics 这个数据形态**」混了：monitoring 是「拿 metrics 去盯、去告警」的行为，metrics 才是那根支柱本身。改成 **metrics** 就精确了。（已收进易混对子，标 ⚠。）
