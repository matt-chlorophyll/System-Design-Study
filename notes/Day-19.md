## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01–12 那样）。

1. QuoteFlow 夜间批量重定价靠 etcd 选了 coordinator，可它续约的网络刚好抖了一下、租约过期，新 coordinator 被选出来——但旧的其实还活着、还在跑批。**光靠选主够不够防止「重算两遍」？还需要昨天（Day 18）的哪样东西兜底？**
   
   - 我的想法：光靠选主coordinator不够，因为在选主的过程中，还是有可能出现跑批在继续，从而导致一些重算需要被重试的情况。这个时候就需要昨天的幂等，让这些少量的重试不会出现被重复执行的情况。

   **点评（Claude）：** 方向对了——兜底确实是 Day 18 的**幂等**。但有一处 framing 要拧紧：你把重复的来源说成「**重试**」，真正的来源更要命，是「**假死双跑**」。旧 coordinator 不是干净崩溃，而是**网络抖一下被孤立**——它自己**还以为是 leader、还在跑批**，可 etcd 联系不上它，租约一过期就把新 coordinator 选出来了。于是在「租约过期 → 旧节点察觉自己被换掉」这段窗口里，**两个 coordinator 物理上同时在跑同一批**，各写各的保费。这不是「重试」，是**真·并发双跑**。把这点想透，就抓到了今天最该记住的那句精度：**选主只保证「同一刻多数派逻辑上只认一个 leader」，它管不住一个假死的旧 leader 在租约窗口内继续写——物理上的「只有一个在干活」它给不了。** 这正是幂等要兜的那段窗口（让重叠写覆盖成同一个值、无害）。再加一层你在「待深挖」里已经标到的 **fencing token**（很好的嗅觉）：它和幂等是**不同层**的两道防线——**幂等被动**（重复来了当 no-op，让它无害），**fencing 主动**（每次抢租约 token 单调 +1，被写资源校验 token、**直接拒绝**旧持有者那张迟到的低 token 写）。一个让它无害、一个根本不让它落地，生产里常两个都上。已整理成「逻辑唯一 vs 物理唯一」「幂等 vs fencing token」两张易混卡。

2. 既然共识写很贵，为什么我们仍坚持把「当前生效的 `rate_table_version`」放进 etcd，而不是放进那台又快又熟悉的关系库？**这里 auditability 和 consistency 各自要的是什么？**
   
   - 我的想法：把当前生效的 rate_table_version放进etcd可以把当前计算任务需要使用的费率表版本钉死，并且保证全局一致，让所有worker都读同一份表，避免出现一部分用新表计算，一部分用旧表计算的情况，这个是consistency要的东西。对于auditability来说，还需要的就是这个费率表版本切换的历史也被记录下来，使费率计算可追溯，而费率表本身（不同的version）还是存在关系数据库里，版本改变的只是指针指在哪个费率表数据上。

   **点评（Claude）：** 这题**答得很扎实，接近满分**——consistency / auditability 的拆分都对，「费率表数据留关系库、etcd 只放指针」也精准。补两刀让它更利：① **consistency 那层点破到「linearizable」**：你说的「避免一部分用新表、一部分用旧表」，根因是 etcd 给的是**线性一致（linearizability）**——版本切换是一个**原子的、全集群同一瞬间可见**的点，没有中间态。而那台「又快又熟悉的关系库」若走主从复制（Day 12），**read replica 有 replication lag**：你切了指针，有的节点从主库读到新版、有的从滞后的从库还读到旧版。**「又快」恰恰因为它放松了一致性**，而这里你要的就是不能放松的那样东西。② **把两者的关系再串一下——consistency 是 auditability 的前提**，不是两件平行的事：审计要回答「这批保单当时**到底按哪一版**算的」；如果指针放在会有复制延迟的地方，你连「当时全集群用的是同一版」都保证不了，那「可追溯」就是**假的可追溯**。所以**先有强一致的生效版本，可审计才立得住**；关系库那边管的是另一半——切换动作本身的**历史留痕**（谁、何时、`2026-05 → 2026-06`，事务 + 历史表，这是关系库的强项）。一个管「此刻生效哪版」，一个管「历史怎么变过来的」，缺一不可。已整理成「etcd 配置中心 vs 关系库 read replica」易混卡。

> 讨论时冒出来的问题记这。每条：先记自己的问题，再记讨论后的结论（用自己能看懂的话）。

今天没有额外提问——内容相对没那么好理解，但两道思考题答出来后核心就通了。讨论集中在两题的点评上（见上），重点拎出来三条：

- **逻辑唯一 ≠ 物理唯一**：选主保证多数派「认」一个 leader，挡不住假死旧 leader 在租约窗口里物理上还在写。
- **幂等 vs fencing token**：被动让重复无害 vs 主动拒绝旧写，不同层、常并用。
- **配置指针为何放 etcd**：要 linearizable（全局同一瞬间切换），关系库 read replica 有 lag、会读到旧值；而强一致是 auditability 的前提。

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 当有多个节点存在时，节点之间需要共识性，这个共识性由Raft这个共识性算法来提供。这个算法主要有三部分内容，第一是把节点分为leader follower（以及触发选举时的candidate），以及引入term来确定谁是最新的唯一leader；第二是leader的选举，通过leader发送心跳和follower的随机time-out来触发选举（time-out到但还没收到心跳信号）。为了保证选举能够成功，引入了多数派（quorum）的机制：candidate必须拿到半数+1的选票才能当选leader（并把term向前递增），避免了split-brain的情况；第三是Log Replication，写入时先追加到leader的日志，之后在过半数节点写入成功后再commit，这样可以保证多数派写入成功，防止数据丢失。

  _（Claude 补：Raft 这台「机器」复述得很完整、三块顺序也对。补一个**精度点**和**应用层**：① 多数派防 split-brain 的真正机理，是「**两个多数派必有交集**」这条算术——分区成 3+2 时，最多一边能凑齐多数（≥半数+1），另一边永远选不出 leader、主动停写，所以**最多一边能动**，两份冲突真相不可能同时产生；随机 timeout 防的是另一件事（split vote，选票被瓜分谁都不过半）。② 你这段全是「Raft 内部怎么转」，别忘了**应用层**那半——现实里你**不手写 Raft**，而是用封装好共识的**协调服务（etcd / ZooKeeper）**，靠它的**租约（lease/TTL）+ 原子 CAS** 来选主和上锁；只往里放「少量、关键、要全局一致」的元数据（leader 是谁、配置指针、锁），别塞业务数据。这是「共识用在控制平面、不用在数据平面」。）_

## 待深挖 / 存疑

> 还没想透、或想之后回头补的点。

- [ ] 思考题 1 接 Day 18：选主只保证「同一时刻多数派只认一个 leader」，但**假死的旧 coordinator 在租约过期前还能继续写**——这正是 idempotency / fencing token 要兜底的窗口。想清楚「选主」和「幂等」各防的是哪一段。
- [ ] 思考题 2：etcd 给的是**强一致 + 单调可线性化的读写**（谁是当前版本，全集群秒级一致），关系库给的是**事务 + 可审计的历史**。两者要的不是同一样东西——一个管「现在生效哪个」，一个管「历史可追溯」。
- [ ] 回看 Day 12（quorum / CAP / PACELC）：Raft 的「多数派必有交集」就是 quorum 防脑裂的算术基础；共识在 CAP 里是明确选 C 舍 A 的一类系统。
- [ ] **Fencing token**：租约过期后，光靠「停止续约」还不够，被保护的资源（如批处理写入）还得校验 token 递增，拒绝旧持有者的迟到写——这个机制今天没展开，值得单独补。
- [ ] Day 26（部署与编排）：Kubernetes 拿 etcd 当状态后端——今天学的「Raft + 租约 + 选主」就是 k8s 控制面可靠性的底座，到那天会再撞上。
