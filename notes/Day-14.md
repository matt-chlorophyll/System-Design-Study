## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01–12 那样）。

1. QuoteFlow 里哪些操作**绝对不能**容忍中间状态可见、必须收进单库本地事务？哪些反而可以放心交给 saga？
   
   - 我的想法：是否能容忍中间状态可见取决于特定业务的中间状态短暂可见是否会造成合规，用户交互，或是下游应用上的问题。绝不能容忍的比如说double-entry ledger，同一笔钱的借贷必须在一个单独事务里一起完成，不然出现中间状态就会导致ledger两边无法配平。可以放心交给saga的比如说整个投保流程，例如收费步失效要导致补偿，用户可能会短暂看到保单已经签发，但由于最终付款没有完成，撤销签发保单还属于可容忍的范围。

   **点评：** 判别式 ✓（合规 / 用户 / 下游三看）、ledger 必须单库 ✓、投保可交 saga ✓——两个例子都选对了。补两刀把「为什么」拧紧：
   - **更锋利的判别标准**：不是「会不会有问题」，而是这个半成品**是不是即时自相矛盾**。ledger 中间态**不自洽**（账不平、钱在半路），**任何一次读都直接炸**，且没有任何业务语义能解释它 → 绝不能露。投保中间态**自洽**（保单确实签发了、只是没付钱，是个合法状态），且「撤销签发」有明确业务含义（这单没成）→ 可容忍。
   - **「可容忍」不是免费，且 saga ≠ 不要单库事务**：① saga 的**每一步内部往往本身就是一个必须原子的单库事务**（T4 收费那步「扣客户 + 记应收」在 billing 库里仍得一个本地事务包住）——单库事务与 saga 是**嵌套**而非二选一。② 投保之所以可容忍，**得靠主动设计**把中间态标成 `status = pending_payment`，让下游（再保上报 / reserving）知道「别拿这条当真」；否则再保上报恰好在「幽灵保单」窗口跑批、把它当 in-force 报给再保人，再补偿撤销 = 向再保报了一张不存在的保单。可容忍 ≈ 下游被 gating 拦住或能等，而非「反正会撤销就没事」。

2. 「补偿事务」和「真正回滚」有什么本质区别？对寿险的 audit log 来说，前者其实是优点还是麻烦？
   
   - 我的想法：补偿事务并不是类似真的时光倒流，把数据直接复现成业务事务未发生前的样子（这个是真正回滚），而是新记录一条撤销/回退的动作来表示特定的回滚的发生。对于audit log来说，这反倒是优点，因为这使回滚的过程也被记录在audit log里，更方便审计去查看回滚是如何发生的。

   **点评：** 「补偿是新记一条反向动作、不是时光倒流」——抓得**非常准**。把本质区别再钉死一层：
   - **真正回滚（rollback）** 发生在 **commit 之前、事务内部**：外界从没见过那些改动，引擎用 undo log 把未提交改动抹掉，**不留痕迹**。
   - **补偿（compensation）** 发生在 **commit 之后**：前一步早已提交、是既成事实，**没法假装没发生**，只能用一笔**语义相反的正向新交易**去抵消它。
   - 关键推论：补偿是「**新增反向记录**」而非「抹除」→ **天生 append-only**，跟 audit log 的 append-only 本质严丝合缝（接 Day 12 immutable log）。这才是它对寿险是优点的**真正原因**：真正回滚会让「曾经签发过又撤销」彻底消失（看似从没发生），而监管恰恰要这条「签发→撤销、谁做的、为什么」的链留痕。你说对了，只是「优点」根因是 **append-only 与合规留痕的契合**，不只是「过程被记下来」。
   - 诚实补一个**麻烦面**：补偿只能在**语义层**回退，**物理副作用未必收得回**——中间态窗口里若已给客户发了「保单已生效」邮件、已真扣过钱、再保已上报，补偿撤不回那封邮件。这正呼应文档「补偿不是撤销，且要幂等」。对 audit log 是优点，对「真把世界恢复原样」是有局限的。

### Q1. 文档 lost update 那段 SQL，两个并发事务从哪来的？乐观锁又是什么？

**问：** 「下面用一段 SQL 把 lost update 演示清楚」那段没看懂——例子里两个并发事务是从哪来的？乐观锁是什么意思来着？

**答：**
- **两个事务是「脑补」出来的**：SQL 块只字面写出**一个** `BEGIN…COMMIT`，第二个事务藏在注释「两个并发事务都读到 100」里。要想象**两个独立数据库会话**各跑这同一段、在时间上**交错**。具体到 QuoteFlow：同一张保单同一时刻进来两笔扣款（auto-debit + 手动补缴），两个连接各跑一遍。
- **命门**：会话 B 在会话 A 写回之前就 `SELECT` 到了旧值 100 → 两边都基于内存里的 100 算 138.20 → 后写的那个**覆盖**而非**累加**，一期 38.20 凭空蒸发（正确应是 176.40）。凡是「读出来 → 应用里改 → 写回去」，并发下默认就有此洞。
- **乐观锁（optimistic locking）**：赌**冲突罕见** → 平时**不上锁**，只在**写时校验**有没有被人动过；撞上了这一次写失败 → 重试。对立面是**悲观锁**（赌冲突常发生 → 先 `SELECT … FOR UPDATE` 上锁，别人排队）。
- **版本号怎么挡**：行加 `version` 列，读时连版本一起拿（`paid_ytd=100, version=7`）；写时 `… WHERE id=… AND version=7` 当门闩。若 A 先提交把版本抬到 8，B 的 `WHERE version=7` 匹配 **0 行**（影响行数=0）→ B 察觉被抢先 → 重读重算重试。
- **辨析**：写法一 `paid_ytd = paid_ytd + 38.20` 既非乐观锁也非手动锁，而是**让数据库在自己的行锁内一气呵成读-改-写**、不留窗口，最该优先；**但**只在「新值是旧值的纯函数」时管用，要在读写间做复杂逻辑就退回乐观锁 / 悲观 `FOR UPDATE`。

### Q2. 「中间状态短暂可见」的「中间状态」指什么？

**问：** 2PC vs Saga 对比表下那句「你能不能容忍中间状态短暂可见」——中间状态指什么？举例。

**答：**
- **中间状态 = 一个多步业务操作「做到一半」的状态**——前面几步**已各自 commit、对外是真的了**，但整件事还没走完。关键不在「一半」，而在**这个半成品对外界是否看得见**。
- **2PC 看不见**（全 prepare 再一起 commit，外面要么全成要么全没）；**Saga 看得见**（每步立刻在自己库提交，T1~T4 之间外界真能查到半成品）。
- QuoteFlow 例子：投保 saga `T1 创建申请→T2 核保占额→T3 签发保单→T4 首期收费`，T4 失败。在 **T3 已提交、补偿 C3 还没跑**的窗口里，`policies` 库真真实实躺着一张 `status=in-force` 却一分钱没收到的保单——客户 App 看到「已生效」、再保上报把它当有效保单统计、别的服务读到它。这就是中间状态被外界看见。叫「短暂」是因为 C3 很快撤销它，但窗口里它真实可观测。
- **反例（绝不能容忍）**：ledger 借贷分开提交，中间窗口有人查账 = 钱从 A 扣了还没到 B、账不平 → 必须收进单库一个本地事务。
- **串回**：这就是 **isolation 在跨服务层面的延伸**——saga **主动放弃**跨步隔离换 availability。「能不能容忍中间状态」= 「愿不愿拿 isolation 换 availability」。

### Q3. Saga 全名 / 命名由来？补偿期间撞上并发正向事务，不会有 isolation 问题吗？

**问：** Saga 全名是什么（或为什么叫这名）？反向跑补偿事务时若有其他并发的正向事务，它们之间不会产生 isolation 问题吗？

**答：**
- **命名**：不是缩写，就是英文 **saga**（古诺尔斯语，分章节展开的**长篇史诗故事**）。出处 1987 年 Garcia-Molina & Salem 论文《Sagas》。比喻：长业务像一部**长篇故事**、由一串各自完整的章节（子事务）接续讲完；原始动机是 **LLT（Long-Lived Transaction）** 用大事务包住会长时间持锁 → 改成「一章一章讲，讲砸了就倒叙补偿」。
- **isolation 问题：会，而且这正是 saga 主动放弃的。** 记一句：**saga 给的是 ACD，唯独没有 I**（A 靠补偿、C 最终一致、D 每步提交、~~I~~ 无）。补偿窗口尤其毒，冒出有名字的异常：**dirty read**（别人读了将被补偿的数据，如再保上报读了幽灵保单）、**lost update**、补偿正在**抽掉别人已踩上去的地基**。
- **怎么补回 I（countermeasures）**：① **Semantic lock（语义锁）**——中间态带显式标记（`pending_payment`），别的事务被编码成对 pending 行特殊对待（跳过/拒/等），是**应用层锁**不是 DB 锁；这正是思考题①那个 `pending` 标记的正式身份。② **Commutative updates（可交换更新）**——把操作建模成计数器增减（占额 `-1`/`+1`），补偿与并发正向任意顺序交错净值都对（对比 `SET=绝对值` 会丢更新）。③ **Reorder**——把易失败步前置，缩短暴露窗口。④ **Re-read / 版本校验**——动手前重读（乐观锁）。
- **收口**：isolation 是真缺、补偿窗口正是 dirty-read / lost-update 的产房；不是免费拿到隔离，而是**在真正在乎处用 semantic lock + 可交换设计手工焊回 I**，不在乎处接受异常。也因此 **orchestration**（中心化编排）对 QuoteFlow 友好——orchestrator 清楚走到哪、能集中持语义锁、且让 pending 状态可观测可审计。

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 事务隔离（Isolation）是很容易踩坑的点。在单一数据库里，不同的隔离等级可以帮助规避不同的隔离问题，例如dirty read, non-repeatable read, phatom read等问题（还有SQL数据库里没提到的lost update, write skew），要根据业务按需选择隔离等级，常见的隔离方法有locking，MVCC，SSI。但到了业务流程需要多数据库聚合，或是数据分区的情况下，想要满足atomicity就要付出一定代价。比如说2PC的确可以满足跨库的原子性，但是速度慢（被最慢库/分区拖累），availability下降，还有可能出现coordinator在发出commit指令前挂掉造成事务卡住的情况。所以还可以选择Saga，牺牲了一部分isolation换availability，出错时可用补偿事务撤销之前的改动，但问题是会有短暂的中间状态暴露给外界的时间。所以取舍要看对中间状态暴露的容忍度。
