## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法,再来 Claude Code 聊;聊完我会在每条下面补点评(像 Day 01–10 那样)。

1. 有同事提议「把 in-force 保单全量搬到 MongoDB,夜间批量重定价会快很多」。你怎么评估这个提议?哪些访问模式支持它、哪些 NFR 反对它?
   
   - 我的想法: 我觉得要通过做这件事的收益和成本对比来评估，或者说搬到MongoDB做按聚合整存整取带来的好处是否大到可以忽略这种做法带来的问题。从好处方面看，整存整取是有可能让夜间批量重定价更快的，因为可以一次整取出重算需要的所有信息而不需要通过join table来在关系表中把定价需要的信息整合在一起，所以重算处理的时间会有所降低。如果访问模式是我前面描述的这样，确实会让夜间批量重定价变快，尤其是保单对应的价格计算方式差别较大的情况，可以省下一些抓取Null value所花的时间。但是这样做会带来很多的成本，具体来说就是会造成一些NFR的violation。主要受影响的NFR就是auditability和repoducibility。由于是scheme-on-read这就要求重算的应用层需要能满足所有历史有过的不同计算方式和它们需要的对应数据。如果出问题就会导致审计无法完成，或是无法reproduce之前计算结果的情况。还有一个我认为隐性的问题是，in-force保单的集合每天都会变动，如果要把in-force 保单全量搬到 MongoDB，意味着每天都要进行一次数据迁移——把in-forced的保单filter出来，然后存到MongoDB，这个增加了很多数据迁移成本和出错风险。

   - **Claude 点评：** 评估姿势(收益 vs 成本)、整存整取免 JOIN 的支持面、schema-on-read 把校验挪到应用层→威胁 auditability / reproducibility,这三块都答对了(第三块和文档自测 Q3 完全对上)。要补三点:① **最大漏点:没挑战「会快很多」这个前提本身**——夜批重算的访问模式是全量顺序扫,恰是 Postgres 擅长的(Day 9:低选择性大扫描走 Seq Scan 是优化器的正确选择;JOIN 贵在 OLTP 单行查询的随机回表,批处理 hash join 一次建表、摊到每行很便宜),「快很多」是未经测量的假设,第一步是 EXPLAIN / benchmark 不是搬家——Day 10 写下的「不要靠猜」,场景换了尺子没换。② **「全量搬」= 为一个访问模式搬走全部访问模式**:收益只来自夜批一条路径,但 in-force 保单同时服务签发(跨表事务:保单+保障+账务,Day 8 ACID)、外键守数据质量、监管要的备份/恢复/审计工具链、下游 reserving 的 SQL 分析;文档判语「核心记录留关系库是合规上的保守正确」,再叠 Day 10 的尺子:in-force 保单是「可变状态」,最该老实待在关系库。③ **你的「每天迁移」论点翻转视角就是正解**:不动 system of record,给夜批派生一个 read model(重算前物化「定价输入文档」,JSONB / 文档 / 文件皆可)——派生数据可重算、丢了不是审计事故(Day 10「汇总表 = 长成表的缓存」同款逻辑);你当缺点列的东西就是正确替代方案的形状,区别只在「谁是权威记录」。📐 术语小修:「省下抓取 NULL value 的时间」不准——NULL 用 null bitmap 存,读写几乎免费,性能不是它的罪;异构问卷塞一张表的真实痛点是 schema 僵硬(新产品 = ALTER TABLE 加几十列)和语义混乱,文档模型的好处记成「**每条记录自带形状**」。

2. QuoteFlow 的报价**输入快照**(Day 10)既可以做成 Postgres JSONB,也可以放独立文档库。两个方案各自的取舍是什么,你选哪个?
   
   - 我的想法: 独立文档取得是schema的灵活度，不同文档可以有不同形状，舍的是join，跨事务整合数据的能力，还有数据库能提供的校验（需要在应用层实现）；Postgres JSONB保留了一般关系数据的架构，保证了跨表的join还是可以实现，和关系数据的好处（保留ACID的实现），但是会让整个数据库变得更加复杂。我会选则Postgres JSONB，因为报价输入快照需要满足审计和可复现的要求，Postgres JSONB保留了ACID，因此比独立文档库更加安全，能够保证审计不出问题。

   - **Claude 点评：** 两边取舍的方向、选 JSONB(正解——文档明示问卷 payload / 快照走 JSONB,「够用就不引入新数据库」)、拿审计 / 可复现当决策轴,都对。要修三处:① **「JSONB 保留了数据库校验」不准**——JSONB 列内部**同样是 schema-on-read**,Postgres 不会校验 JSON 里有没有 `smoker`、类型对不对(除非显式加 CHECK);`schema_version` + 写入口应用层校验**两个方案都逃不掉**。JSONB 真正拿回来的是:同事务原子写、JSONB 之外列的约束/外键、一整套现成的备份/恢复/权限/审计工具链。② **杀手论据是原子性,不是笼统的「ACID 更安全」**:快照必须和 Quote 行**同一个事务**写入、同生同死;独立文档库 = **dual write**——Postgres 写 Quote 成功、文档库写快照失败(或反过来)就出现「有报价没快照」= 审计事故。跨两个系统天然没有原子性,缝合要 Day 14 的 saga,而且很贵。③ **「JSONB 让数据库更复杂」方向反了,要分两层看**:单库内部确实多一点东西(JSONB 列、大字段 TOAST),但**系统层面 JSONB 是更简单的方案**——独立文档库才是 +1 套备份、监控、故障模式、权限审查、灾备;且快照是 write-once、read-rarely(审计时才读),文档库的灵活查询和横向扩展全用不上——为用不到的能力付全套运维费,和文档自测 Q1「为用不到的查询能力付费」同一把尺子。

### Q1. 欺诈检测的「3 跳遍历」具体是怎么走的?

> 详见补充图解 `notes/Day-11-fraud-graph.html`(整张图 + 一跳一跳的走法 + Cypher / SQL 对照)。

**问:** 文档说「新申请人的电话是否和三个月内两次被拒保的申请人共享同一个地址和受益人」是典型的 3 跳遍历——给个具体图例,3 跳到底是哪 3 跳?

**答:** 口径:**1 跳(hop)= 沿一条边走到相邻节点,「3 跳」数的是从起点到答案的深度**。从新申请人 N 出发:跳① N —`HAS_PHONE`→ 电话节点;跳② 站在电话节点上**反向**问「这条边另一头还连着谁」→ 发现申请人 M(图的边天然可双向走,「共享电话」= 两条 `HAS_PHONE` 边汇到同一个节点);跳③ M —`SUBMITTED`→ 他的申请,过滤 DECLINED + 3 个月内 → 数出 2 条,报警。「共享地址和受益人」是两条**平行路径**(N → 地址 ← M、N → 受益人 ← M),和电话路径同形状只换边类型——平行路径加 pattern 的**宽度**(三条同时命中才算高风险),不加**深度**,所以仍叫 3 跳查询。看懂的前提是建模那步:**把识别符升级成节点**——关系库里电话/地址是申请人的字段(或 junction 表),「共享」靠 self-join 找值相等;图建模把它们变成一等公民节点,「共享」变成「边汇到同一个节点」,一跳可达(Day 10 entity 尺子的延伸:在欺诈检测这个问题里,电话号码「有了身份」)。SQL vs Cypher:SQL 每跳 = 一次 JOIN(去另一张表的 B+tree 索引查一遍,O(log N) 随表涨),每种共享属性 = 再叠一组 junction self-join,加一跳深度 = 结构性重写;Cypher 的 MATCH pattern 长得就和图一样,加一跳 = 多画一段。性能根源 = **index-free adjacency(免索引邻接)**:每个节点身上直接挂着自己那些边的物理指针,只有起点用索引找一次,之后每跳顺指针走,成本 ∝ 节点度数、**与全库总量无关**——10 亿和 100 万申请人,3 跳代价几乎一样。天平另一端(对照表第四行):图库不擅长大规模扫描/聚合,「全体保单平均保费」它很笨——只在「核心问题长成网络形状」时引入;欺诈环恰好是:欺诈者用共享识别符把假身份连成网,**边本身藏不住**。

### Q2. LLM / RAG 里的 QKV 是借用 KV store 的概念吗?

**问:** KV 店的概念,是不是 LLM 和 RAG 里的 QKV 借用的?

**答:** **同一个祖先,不是直接借用**——两者都源自 CS 最古老的抽象之一:dictionary / associative array(key→value 查找)。Attention 论文("Attention is All You Need", 2017)的原文定义就是检索隐喻:"mapping a **query** and a set of **key-value pairs** to an output",这套词来自 information retrieval / 数据库语汇,直接前身之一就叫 Key-Value Memory Networks(2016)。**关键区别 = hard lookup vs soft lookup**:KV store 是 hard lookup——`hash(key)` 精确命中**唯一** value,O(1),要么命中要么 miss;attention 是 soft lookup——query 和**所有** key 算相似度(dot product)→ softmax 归一成权重 → 输出是**所有 value 的加权平均**,没有「命中/未命中」,人人按相似度贡献一点。为什么做成软的:**hard lookup 不可导**,梯度下降穿不过「要么取到要么没取到」的离散操作——attention 的本质是「**可微分的字典查找**」。RAG / 向量库的连接更字面:向量库的访问模式 = 「给我 query 向量,找最相似 top-k」,几乎就是 attention 打分那步,只是最后**硬化**回离散 top-k(ANN 近似最近邻)而不是加权平均。用 Day 11 的尺子看:**向量库就是又一个「为单一访问模式专精的存储」**,和 KV/文档/宽列/图并排坐(Day 29 放进同一张地图)。顺手收掉第三个 KV——**KV cache**:LLM 推理时缓存已生成 token 的 K/V 张量,避免每生成一个新 token 把前文全部重算,名字里的 KV 指 attention 的 K/V,干的事是 Day 7 的 precompute/缓存。三连记法:**KV store 是一类数据库、QKV 是 attention 的三个角色、KV cache 是推理时对 K/V 张量的缓存**——三个 "KV" 各管各的,只是都姓「键值」。

## 我的理解(用自己的话复述今天的核心)

> 不看文档,凭记忆写 2–4 句。能写清楚 = 真的懂了。

- NoSQL不是不要SQL，而是“Not Only SQL”，选择的关键在于数据查询的方式，根据不同的需求，除了正常的SQL关系数据储存形式外，还可以选择KV，Document整存整取，宽列，和图。实际业务中，可以根据数据和对应业务的需求，选择更合适的数据储存方式，不管是SQL还是NoSQL。

- **Claude 点评：** 「Not Only SQL」+「按查询方式选型」两个核心都抓住了。补一句文档的精髓加固:NoSQL 的每个强项都是**用放弃换的**(对照表第四行:KV 放弃查询能力、文档放弃 JOIN/跨文档事务、宽列放弃临时查询、图放弃扫描聚合),共同账单是大多数默认放弃强一致(Day 12 展开)。所以选型第一问是「查询长什么样」,第二问紧跟着:「**这家放弃的东西,我付得起吗**」。
