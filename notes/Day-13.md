## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01–12 那样）。

1. QuoteFlow 的保单库，如果当初选了 `customer_id` 而不是 `policy_id` 当分区键，哪些查询会变好、哪些会变糟、哪些运营场景会埋雷？（提示：团体保单渠道、客户改信息、夜间重算。）
   
   - 我的想法：针对同一customer的所有保单进行的查询会变好，因为很容易处在同一分区直接抓取，而针对特定set保单的查询会变差，因为policy id会散落在各个分区，导致需要scatter-gather，查询得到结果的速度会变慢。会埋雷的运营场景一个是团体保单查询，假设一个客户有大量不同保单，针对这个客户进行查询时客户所在的分区就容易成为热点。还有一些提示我还没联系起来。

   **点评：** 变好 ✓、团体大客户分区成热点 ✓。两处要拧紧 / 补：
   - 「变糟」的主角不是「特定 set 保单」，而是**按 `policy_id` 单号点查**——客服 / 理赔 / 客户自助查一张保单本是最高频、最延迟敏感的操作，换键后退化成 scatter-gather。这恰好踩中铁律的反面：「让最高频、最延迟敏感的查询单分区可达」。
   - 漏的两个提示这样咬合：**① 客户改信息 → 分区键须 immutable。** `policy_id` 终身不变；而「保单归属哪个客户」会变（保单转让、团体成员归属调整、客户合并去重）→ 分区键一变，记录就要跨分区**搬家**（rebalancing 之外最讨厌的单记录搬家）。**② 夜间重算 → 倾斜分区成 straggler。** 重算是 per-partition 并行，扛着数千张团体保单的那片最慢，**整晚批处理完成时间被它钉死**（Day 2 tail latency 换场景重现）。`policy_id` 哈希则负载均匀、无 straggler。

2. 夜间批量重算按分区并行后，某一个分区的 worker 失败了。重跑**整晚**还是只重跑**那个分区**？这个选择对「重算结果可审计、可复现」提出了什么要求？（这题是给 Day 17/18 埋的伏笔。）
   
   - 我的想法：应该只需要重跑那个分区，因为定价重算对于每个policy来说应该是独立的，policy的重算结果对彼此没有影响，所以不需要重跑整晚。提出什么要求这个问题我还真知道怎么回答，想听听你的说法。

   **点评：** 「只重跑那个分区」✓。但理由「per-policy 独立」只是一半——它解释了「不必重跑别的分区」，却没解释「能安全重跑那一片」：还得加 **幂等（idempotent）**，靠 Day 10 的 `UNIQUE(policy_id, run_date)` + DO NOTHING，让重复写变 no-op、不污染已成功的部分。
   对「可审计 / 可复现」的两条硬要求：
   - **① 输入版本钉死（pin）。** 重跑可能晚几分钟、甚至换了一批机器，但 `rate_table_version`、核保规则、模型版本必须和原批**同一组**——不能因重跑时费率表更新就用了新版，否则同一晚不同分区用了不同版本，结果不可复现。（Day 12「版本引用钉死时点」的直接应用。）
   - **② 每条结果可追溯。** `run_id` / `partition_id` / `attempt` 一起留痕，失败 → 重跑 → 成功三态可见，审计师能看出「分区 7 第一次失败、第二次重跑成功」，而非数据凭空出现 / 消失。
   反向理解：**重跑整晚反而更差**——若重跑时版本漂了，已落库的成功分区结果和重跑结果就成了「同一晚两个版本」的不一致。所以「只重跑失败分区 + 钉死版本」反而审计性更强，不是图省事。（伏笔 Day 17/18。）

### Q2. Hash 是怎么把空间「首尾相接成环」的？先讲讲 hash 原理。

**问：** 「把哈希值空间首尾相接想象成一个环」——这个首尾相接数学上怎么做到？另外我忘了 hash 本身的原理，先讲一下。

**答：** 做成了图解 → **`notes/Day-13-hash-ring.html`**（三张图）。浓缩结论：
- **Hash = 确定性地把任意输入搅成一个定长整数**，落在 `[0, 2³²−1]` 这种固定区间。四性质：deterministic（存得进、找得回）、定长输出（无限输入压进有限空间）、均匀 + avalanche（相似 key 也打散）、必然碰撞（鸽笼原理）。内部就是「乘大质数 / 位移 / XOR / 取模」把每个 bit 搅匀。分区 / 哈希表用 non-crypto hash（Murmur/xxHash，要快 + 匀），不是 SHA-256（要抗攻击、慢）。
- **「首尾相接」= 给这个定长整数空间套上模运算**：规定 `(2³²−1)+1 ≡ 0 (mod 2³²)`，所有位置活在 `ℤ/2³²ℤ` 里、加法自动回绕。和钟面（mod 12：11→12/0→1）是同一招——环就是一个刻度多到 2³² 的时钟，**不是物理的圆**。
- key 归属 = 环上 **successor**：`owner(p) = ≥p 的最小节点位置；越界则绕回取最小那个`。那个「绕回」分支就是「环」唯一真正用到的地方（否则落在接缝前的 key 无家可归）。
- **只搬 1/N 的根源**：加节点只改「被接管那段弧」的归属（局部）；`hash mod N` 改的是整个映射函数（全局），N:4→5 ≈80% 全搬。virtual nodes 把每个物理节点的弧切碎撒满全环 → 负载趋近 1/N，且搬动由所有幸存节点平摊。

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 复制是拷贝副本，是为了解决可用性和读扩展，分区/分片是把完整数据切分成subset在不同机器中存储，解决的是容量和写扩展。实际操作中两者都需要——每一个分区的数据都会有自己的leader-follower。切分的方式围绕分区键进行，主要有两种，一种是按key的range分，这能让分区的相邻数据有一定的逻辑顺序，方便一些有顺序的查询，但是容易产生热点；另一种是按hash分，好处是分的相对均匀，减少单一分区成为热点的情况（但单一数据还是有可能成为热点），但是数据需要增加分区时可能会增加migration（rebalancing）的cost，这个可以用consistent hashing来mitigate。最后，分区可能带来二级索引的问题，local index和global index各有好坏（重视读/写），需要根据数据最常用的被查询方式来进行索引的选择。

> 一处精确化（讨论后）：「hash 分区扩容增加 migration cost、用 consistent hashing mitigate」——更准的说法是，rebalancing 的高成本根源**不是 hash 分区本身，而是朴素的 `hash(key) mod N`**：`N` 一变余数全变（≈80% 搬家）。consistent hashing 是对「mod N 这种分配法」的改进（环 + virtual nodes，降到 ≈1/N）。
