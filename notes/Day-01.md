## 今日思考题

> 文档里的思考题（先写下自己的初步想法，再去 Claude Code 讨论）。

1. 我现在的 pricing engine，**最被低估**的 non-functional 需求是哪个？
   
   - 我的想法：这里先要厘清「pricing engine」指的是哪一种系统。如果指的是 QuoteFlow 里那种给 Analyst/Actuary 用的、半自动的内部配置工具，那我会说最被低估的 NFR 是易用性——操作的人得清楚每一步在做什么，才能给出合理的 input 和 configuration、或发现潜在问题，进而才能把它推向更自动化。不过我们这门课要讨论的 QuoteFlow 是另一种定义：全自动、根据 quote 直接给出 price 的面向客户系统。这个更适合作为 system design 的 case，所以之后的回答我都按这个全自动定义来。
   
   - **Claude 点评：** 在「人工参与的半自动工具」语境下，这是有想法、不流于表面的回答。两点补强：
     
     1. **「易用性」在 system design 里通常不算独立 NFR**，它更接近 UX。我真正想说的那个东西，用系统设计词汇是 **operability（可操作性）/ explainability（可解释性）**——系统每一步对操作它的 Analyst 透明、可理解、可干预。换这个词论点立刻更硬，而且它正是决定系统能否从「半自动」走向「全自动」的质量属性。
     2. **回到「全自动」定义上**，在 life insurer，最被低估的几乎一定是 **auditability / traceability / reproducibility**。「被低估」的定义就是：大家默认它会自己满足，但赶进度时它最先被牺牲。检验场景——*两年后监管来查一笔当时的报价，能不能用当时的 rate table 版本、规则版本、模型版本，把那个数字一模一样地复现出来？* 能复现 = 这条 NFR 真设计进去了。
     - 一句话：**当前现实**被低估的是 operability/explainability；**全自动目标态**被低估的是 reproducibility/auditability。两个都对，关键是分清语境。

2. 把「实时单笔报价」和「夜间批量重算」拆成两条独立路径，会带来什么好处、又要付出什么代价？
   
   - 我的想法：好处是能分别去实现这两个需求，满足各自的需要，代价是由于这两个需求互相是对方的限制，所以可能会出现optimise了一个路径，而导致另一个路径完全达不到标准需求的问题，需要解决一些trade-off的问题。
   
   - **Claude 点评：** 方向对，但答案偏「循环」了——「互相是对方的限制」更像是**不拆**的代价，而拆开恰恰是为了解开这个牵制。把账算清：
     
     - **好处（拆开后）：**①各自按相反目标优化——实时要 low latency，批量要 high throughput；②独立扩展 + 故障隔离——批量吃满机器不拖慢实时报价，批量崩了报价接口照活；③各自独立的 SLA 与技术选型。
     - **代价（重点警惕，尤其在受监管定价里）：逻辑漂移（logic drift）**——两套代码算同一件事，某天在实时路径修了规则忘了同步到批量 → **同一张保单，实时报价和夜间重算给出两个不同 price**，审计噩梦。
     - 这把 Q2 接回了 Q1：**拆两条路径最大的代价是 reproducibility / consistency 变难了**——必须保证两条路共享同一份 rate table / 规则 / 模型版本。解法是把定价逻辑抽成一个 **shared core**，两条路都调它，而不是各写一遍。
     - 我漏掉的关键代价不是「性能 trade-off」，而是**一致性 / 可复现性**，而它恰是我这一行的一等公民需求。

## 提问 & 解答

> 每条：先记自己的问题，再记讨论后的结论（用自己能看懂的话）。

### Q1. 为什么需要「实时报价」和「夜间批量」两套路径？

**问：** 实时报价我理解，但夜间批量没接触过（我的经验在后端定价分析/建模，没碰过面向 customer 的 quote system）。这个双路径设计的 purpose 是什么？

**答：** 关键认知——**两条路径服务的是两批完全不同的人、由完全不同的事件触发**：

- **实时报价** = 面向**潜在客户（new business，还没买）**，由客户/broker 此刻在网站点「报价」触发，一次一张，关心 **latency**。
- **夜间批量** = 面向**已有保单持有人（in-force book，已经买了）**，因为「时间到了 / 假设变了」触发，整批百万级，关心 **throughput**。

为什么 in-force 保单的 premium 要反复重算（寿险是几十年期的长寿命对象）：①**stepped/age-based premium** 随年龄逐年涨，到 anniversary 要重算；②**indexation**——sum insured 每年按 CPI 自动上调，cover 涨 premium 跟着变（澳洲常见）；③**reviewable premium** 产品定期 review 费率；④**假设/rate table 更新**（mortality basis、lapse、discount rate 改了）→ 整批 in-force 重算。

为什么必须「批量+夜间」：最硬的理由是 **billing**——每月得向客户收**正确的** premium，会变的产品必须在 billing run 之前算好；下游（billing、对账单、reinsurance 上报、reserving）都等着这批数字。攒到维护窗口集中跑，既不抢实时资源，又赶在早上 billing 前完成。

> 一句话：不是「同一件事的两种实现」，而是 **new business quoting** 与 **in-force repricing/revaluation** 两个本质不同的 business 流程，恰好都调用同一套定价逻辑。

### Q2. 批量具体是怎么触发的？

**问：** 夜间批量到底由什么触发？

**答：** 拆成**两层**看就透了：

- **第一层 —— 什么「启动」job（trigger）：** ①**定时触发（cron）**——scheduler 到点拉起（Control-M / Airflow / 云 scheduler），「到点就跑」，是 anniversary roll、月度 billing 的主力；②**事件触发（event-driven）**——状态变了才跑，如 actuary 批了新 rate table 版本 → 发出事件 → 触发针对性重算（第 15/16 天 message queue 的预告）；③**手动 / ad-hoc**——重跑错误、应监管一次性 request。
- **第二层 —— job 启动后「挑出」算哪些（working set）：** 通常**不是**每晚把百万张全算，job 第一步是一个**查询**圈出今晚该算的（anniversary=今天 / indexation 到期 / 还挂旧费率版本）。**cron 决定何时开跑，这个查询决定算谁。**

**新学到的坑 —— watermark（水位线）：** 选 working set 不写「算今天的」，而写「算**上次成功跑完之后到现在**所有该算的」（`anniversary_date > last_successful_run AND <= today`）。这样昨晚挂了今晚能补、不漏；同一批算两遍结果也一样（**idempotent**）。这是第 18 天「幂等、重试」的核心。

> 三件事分开：**trigger（cron/event/手动）管「开跑」，选择查询管「算谁」，watermark 管「不漏不重」。**

### Q3. 从技术/硬件层面，为什么这两条路径会出现 trade-off？

**问：** 为什么 low latency 和 high throughput 在硬件上是对立的？

**答：** 不是工程师偷懒，是几条硬墙：

1. **批处理的本质**——每次操作有固定开销（网络往返/syscall/query planning/磁盘寻道）。throughput 靠**攒批**摊薄它，但攒批=要等→延迟升。实时不能等，每条单独付一遍固定开销→吞吐低。**batching 是 throughput 的朋友、latency 的敌人。**
2. **利用率的数学墙**——排队论 `平均延迟 ∝ 1/(1−ρ)`。要 p99 低必须**留余量**（ρ 30–50%）；要 throughput 高必须**吃满**（ρ 90%+）。ρ→100% 时尾延迟爆炸。同一台机没法又「留很多空闲」又「几乎不闲」。
3. **数据访问模式相反**——实时=按 key 取单张（随机点查，行存+B-tree+内存）；批量=整本顺序扫（sequential scan，列存+大块 I/O）。同一份数据布局没法对两种访问都最优。
4. **缓存/内存**——实时要热 rate table 常驻内存（cache miss=延迟死）；批量工作集=全量 book，塞不进缓存，反而会**冲刷掉**实时的热缓存。
5. **资源争抢**——共享机时批量带来锁争用/GC/内存带宽打满/长任务占核 → 实时**平均也许没事，但 p99 尾延迟被拖垮**。

> 本质：**throughput 要「批量+高利用率+顺序扫+流式」，latency 要「单条+留余量+随机点查+热缓存」，每一项都顶着干。** 所以拆成两条路各配各的硬件与数据布局，是被逼出来的，再共享中间「定价 Core」守住 reproducibility。

### Q4. p99 是什么？

**问：** p99 是什么？

**答：** **p99 = 99th percentile latency（延迟的 99 百分位）**：把一段时间所有请求延迟从小到大排，第 99% 位置的值。「p99 < 300ms」= 99% 请求在 300ms 内返回，只有最慢 1% 超过。

为什么不用**平均**：平均会被一堆快请求拉低、把糟糕的尾巴藏起来。例：99 个 50ms + 1 个 5000ms，平均≈99.5ms（看着好），但 p99=5000ms（真相）。而那「最慢 1%」恰恰是会投诉/流失的客户。常用：p50（典型）/ p95 / p99（常作 SLA）/ p99.9（极端尾部）。

> 串回来：实时路径「留余量、ρ 压低」就是为了**压住 p99 尾巴**；批量根本不在乎单条多慢（没客户在等），所以能把利用率拉满换吞吐。**用不用 p99 约束自己，本身就是两条路径性质相反的体现。**

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- functional vs non-functional 的区别：functional指的是这个系统本身，要实现它的目的必须要存在的功能，比如对一个pricing engine来说，必要功能就是拿到用户信息->生成quote。而non-functional指的是系统里这些功能需要完成的多好——比如latency不能太高（即便最终能出quote，但是要让用户等很久的话，系统还是不好用），price的结果要有consistency，可追溯性等等。他们不是功能本身存不存在，而是这个功能能不能被有效的使用。
- 为什么说「没有最优解，只有取舍」：因为不同的requirement之间由于各类限制（比如物理上的，数学上的等等），导致他们会有一定冲突——maximise一个功能的指标，可能会影响其他功能的指标的实现，所以没有完美的解法，只能根据实际的需要进行取舍，满足一部分需求，并在牺牲程度上牺牲另一部分需求。我个人理解为是一个在system整体上进行optimise的过程。
