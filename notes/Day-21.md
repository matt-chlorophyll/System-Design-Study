1. 夜间批跑到一半，worker 集群崩了一半、窗口也快到点了——你怎么设计才能**安全地从断点续跑**，而不是从头再来、也不重复收费？
   
   - 我的想法：利用两个方法：checkpoint和幂等。当出现worker崩了的情况时，根据checkpoint从checkpoint位置续跑，不重复计算已经过checkpoint的那些保单。但是worker崩溃就算有checkpoint也还是会有一些保单在续跑重试时会被重复纳入计算处理，这个时候就需要用幂等来确保重算在效果上是exactly-once，避免重复收费。除此之外，那些满足夜间批跑本身NFR的方法也要都在，比如说快照钉死保单和费率表等数据，记audit log确保reproducibility和auditability等等。

   - **点评（方向对，缺一层）：** 红线抓得稳——**幂等**保证「重叠那段重算 = 重算一次」，守住「不乱收费」，这是题眼。一个精度修正：在这个设计里 **checkpoint 和幂等其实是同一张去重表**——worker 每处理完一条就在 `audit.already_done` 标记完成；崩溃后整批重投、对每条先查「做过没」，做过就 ack 跳过。那张去重表**既是幂等闸门、又天然是进度记录**，不必再单独维护一个 checkpoint 文件。**最关键的缺口：漏了 Day 19 协调层。** 题目是「集群崩了一半」，要答三件事：① 崩掉 worker 没干完的活谁接管 → 队列的**租约 / visibility timeout**（没在租约内 ack 的消息自动重新可见、被别的 worker 接走——这才是「断点续跑」在队列层的真机制，不靠显式 checkpoint）；② 防**假死旧 worker 迟到写** → **fencing token**（旧 worker GC/网络抖动后缓过来还在写，靠单调令牌拒掉）；③ 调度器自己崩了谁顶 → **leader 选举**（图里那句「leader 选举」）。还有个没回应的约束——**「窗口快到点」**：续跑也可能跑不完，要么按优先级先跑今天必须完成的（如 billing 到期）、其余延到明天（延到明天安全也正因为幂等），要么临时扩 worker。

2. 如果把这个「攒一晚一次算」的批，改成「保单一到周年就实时重算」的流（stream），QuoteFlow 会**得到什么、又要多付出什么**？（这正是 Day 17 批 vs 流的现实抉择）
   
   - 我的想法：能得到的是用户在保单生效时能实时拿到新的报价，公司内的分析服务也能时刻拿到最新的信息。要付出的代价，最重的是失去重算引用数据的一致性，比如由于流处理，可能有些保单在费率表更新前后会导致一些用旧表一些用新表的情况，给审计增加负担。再就是流处理要处理event time和process time不一致的问题，需要更复杂的系统设计，要付出更高的维护成本。

   - **点评（答得好，命中题眼）：** 「失去引用数据一致性 → 审计负担」是这道题的灵魂，你**精准命中**了——批的杀手锏是「整批共享一份不可变快照」；改成流后每条在不同时刻算、费率表中途换版 → 同一逻辑批次里版本不一致 → reproducibility / auditability 受损。**这恰恰是受监管寿险系统「批往往是默认」的根本原因**，建议把这句结论在笔记里明写出来。`event time vs processing time` / 乱序迟到你也点到了（再加一层：watermark + 状态管理，「周年」这种按时间触发的尤其难）。**得到那一侧漏了一个实打实的好处：平滑负载**——批是「攒一晚一次性砸下来」，逼你为峰值配 ~16 个 worker 且只在窗口用几小时；流是来一条算一条，**负载摊平到全天**，没有夜间大尖峰，资源利用更稳。新鲜度之外，这是流的第二个卖点。

### Q1. 分片（shard）和分区（partition）有区别吗？

**问：** Day 21 图里队列标「分区」、保单库标「分片」，两个词到底有没有区别？

**答：** 有区别，但更像「**总称 vs 特例**」，而且业界用得很乱（所以它进了易混对子）。三层拆开：

- **概念层**：Partition 是「按 key 把一坨切成小块」的**通称**；Shard **特指这些块还被分到了不同机器/节点上**做水平扩展。→ **所有 shard 都是 partition，但不是所有 partition 都是 shard**（shard = partition + 跨节点）。例：单台 Postgres 把大表按月切 12 块 = partition（还是一台机）；200 万保单散到 8 台 DB = sharding。
- **切分维度**（另一组，别和上面混）：**horizontal** = 切行（每块 schema 相同、行不同，sharding 属这类）；**vertical** = 切列。日常说的几乎都是 horizontal。
- **实践层 = 看生态叫法**：混乱的真正来源——Kafka / Cassandra / DynamoDB / PG 单机叫 **partition**，MongoDB / Elasticsearch / Citus / Vitess 叫 **shard**。权威锚点 DDIA 干脆把 **partition 当通用词**：「我们叫 partition 的，MongoDB 叫 shard、HBase 叫 region、Bigtable 叫 tablet、Cassandra 叫 vnode」——同一概念的不同商品名。安全做法：**别抠词，看跨不跨节点**。
- **回到 Day 21 图**：队列标「分区」是随 Kafka 叫法（一条 topic 切几片，让 ~16 worker 并行各读一片）；保单库标「分片」是 sharding（百万保单跨多 DB 节点扩）。两处**底层是同一个动作**——按一个 key 切开好并行——只是一个随队列生态、一个随数据库生态。我会问「有没有区别」，正是因为同一张图用了两个词指同一类操作。
- **关联**：分片要决定「key → 哪个节点」的映射，那套方案就是 [[Day 13]] 的 **consistent hashing**（加减节点只搬 ~1/N，不是 mod N 那样全量重洗）。
