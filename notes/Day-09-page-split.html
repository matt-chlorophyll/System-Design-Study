页满了
就裂一个出来

B+tree 在写入时怎么自动保持平衡?核心机制叫 page split(页分裂)。配一张分裂前/分裂后的图,顺带回答两个问题:leaf 到底存什么、范围查询为什么不在乎页边界落在哪、以及为什么随机 key 的索引写起来更贵(接你思考题 1 的 write amplification)。

page split 图解 leaf vs branch 单调 vs 随机写
0先分清两层

leaf 存「条目」,branch 存「边界」

讨论里最该先纠正的一点:你想象 leaf 节点存的是「25–45」「45–65」这样的区间——其实不是。区间(separator key,边界)住在上面的 branch 节点里;leaf 存的是一个个真实的 key 条目,按序紧挨着排,每个条目 = (key 值, 指向数据行的指针)(覆盖索引再加 INCLUDE 的列)。

两层各干各的
  • branch 节点:只存边界,像路标——「< 60 往左,60–100 走中间,≥ 100 往右」。它不存数据,只负责把你导航到对的 leaf。
  • leaf 节点:存真实条目 [10·25·55·80]。一个 leaf「范围是 10–80」只是它碰巧装了哪些 key 的副产物,不是它存了「10–80」这段。
  • 一个 page 是固定大小的磁盘块(PostgreSQL 默认 8 KB),里头就是一个有序数组,从前往后塞条目、塞到装不下为止。key 小的话一页能装几百个——这就是「高 fan-out → 树只 3~4 层」的物理来源。
1核心机制

page split:一页满了,裂成两页

树建好后再 INSERT,如果目标 leaf 已经满了,新 key 进不去——这时触发分裂。下面整张图就是「往满页 [10·25·55·80] 插入 60」会发生什么。

级联与「树长高」
  • 如果父 branch 节点也满了,塞不下新 separator → 父节点也分裂、再往上推;一路推到 root 也满 → 创建新 root,整棵树长高一层。
  • 这是 B+tree 唯一会长高的方式——只在顶上长、且对称传播,所以所有 leaf 永远在同一深度 = 始终平衡,查询稳定在 O(log n) 不退化。
  • 这些分裂动作都走 WAL(Day 8):崩溃恢复时索引和数据一起 redo,索引不会和数据对不上。
2级联分裂

父节点也满了:把中间 key 顶成新 root

上面 callout 说「父节点也满会继续往上裂」——这一步最容易模糊,单独走一遍。先记住一个关键区分:往上「推」其实是两种不同动作。

copy-up vs push-up
  • 叶子分裂 → 复制上去(copy-up):新右叶的最小 key 被复制一份当父节点 separator,但它本身仍留在叶子里——叶子必须存全部真实数据。
  • branch 分裂 → 移上去(push-up):branch 裂开时,正中那个 separator 被「移」到父节点,不再留在两个半边——branch 只是路标,真实数据在叶子,路标移走不丢数据。

具体例子:假设一个 branch 最多装 3 个 separator。起点——root 已经满了 [40|80|120],带 4 个叶子。现在插入 100,落进第 3 个叶子 [80·95·110]:

三点收尾
  • 80 同时出现在两处不矛盾:作为路标在新 root、作为真实数据在叶子 [80·95]。branch 里的 key 本就是导航副本,移上去不影响数据。
  • 验证一下查 95:root 95≥80 走右 → 右 branch 95<100 走 [80·95] ✓,路由依然正确。
  • 长高很罕见、代价被摊薄:只有「一路裂到 root」才长高一层,而每长一层 fan-out 让总容量乘上几百倍,所以百万、上亿行也就 3~4 层。绝大多数 INSERT 连一次 split 都不触发。
3顺带答你

范围查询为什么不在乎页边界

你问:WHERE premium BETWEEN 30 AND 50,如果命中的 key 横跨好几个 leaf 页,会影响取数吗?不会。因为所有 leaf 串成一个有序链表(图 1 里那条绿线),取数就三步:

BETWEEN 怎么走
  • ① 从 root 用 separator 导航,找到第一个 ≥ 30 的 key 所在的 leaf;
  • ② 在这页里从那个位置往右顺读;读到页尾,跟着 next 指针跳到右邻 leaf 继续;
  • ③ 一旦读到某个 key > 50,停。

所以 30–50 落在一页还是三页对你完全透明——你只是顺着链表扫一段。代价就是 命中条目数 ÷ 每页条目数 那么多页的顺序读,跟「range 正好卡在页边界」基本无关(顶多多读一页,可忽略)。这正是 B+tree 为范围 / 排序查询设计的杀手锏:定位一次 + 顺链扫,不必回根。

4接回 write amplification

为什么随机 key 的索引写起来更贵

一次触发分裂的 INSERT,远比不分裂的贵:要申请新页 + 搬一半条目 + 改父节点 + 全部写 WAL。而写入的 key 模式,决定了分裂多不多——这正是你思考题 1 里 audit_log「写放大」的机制层真身。

落到 QuoteFlow 的 audit_log

audit_log 是 append-only、高写入。在 at(时间,单调递增)上建索引很便宜——永远插最右、几乎不裂。但若在 entity_id(随机)上建复合索引,写入点散落 → split 频繁、页半满、bloat 重。这就是为什么对这张表要只建支撑核心审计查询的少量索引,并配合 Day 13 的按时间分区(partition):把表按 at 切成一段段,既限制单个索引的体量,又让旧分区可以整体归档。

5收口

clustered index vs heap + secondary

把今天所有线头收口的概念,分水岭只有一句:「整行真实数据,到底存在哪?」——存在另一处的 heap(索引只给指针,回表是 random IO),还是就排在索引叶子里(物理有序,PK 查询零回表)。

三句话记住
  • Postgres 没有真正的 clustered index(只有一次性的 CLUSTER 命令,不维护)。它的替代品就是覆盖索引 → Index Only Scan——可理解成「针对某条查询的穷人版聚簇」。
  • 聚簇把 random IO 变回 sequential:聚簇 key 对齐你的高频查询时(如 audit_log 按 (entity_id, at)),「某保单全部历史」物理连续 → 顺序读。
  • 这也让上一段 UUIDv4 当主键的警告更尖锐:在聚簇表里,随机主键撕碎的是表本体,不只是某个索引 → 用 UUIDv7 / bigint。
A→Z术语表

这页用到的词

Page / Block
索引和表在磁盘上的最小读写单位,固定大小(PostgreSQL 默认 8 KB);一页里是一个有序的条目数组。
Leaf Node
B+tree 最底层,存真实的 (key, 行指针) 条目;所有 leaf 串成有序链表,利于范围扫描。
Branch / Internal Node
非叶节点,只存 separator key(边界),负责把查询导航到正确的 leaf,不存数据。
Separator Key
branch 节点里的边界值,如「<60 走左、≥60 走右」;page split 时由下层最小 key 推上来生成。
Page Split
页满了再插入 → 裂成两页、各拿一半,并把分界 key 推上父节点;可级联到 root 使树长高一层。
Fillfactor
建索引时每页只填到一定比例(PG b-tree 默认 90%)、留空给后续插入,以减少 split。
Write Amplification
写放大:一次写要顺带维护所有相关索引,触发 split 的写尤其贵;随机 key 比单调 key 更严重。
Index Bloat / REINDEX
频繁随机增删后页半满、碎片化(膨胀);REINDEX 重建索引把它压实。
Heap Table
行按写入顺序乱堆、无物理排序;PostgreSQL 的表都是 heap,所有索引都靠 ctid 指针回表。
Clustered Index
表数据就排在索引叶子里、按聚簇 key 物理有序;每表仅一个。PK 查询零回表、范围扫顺序读(InnoDB 主键)。
Secondary Index
非聚簇的二级索引。heap 里存 ctid 指针;聚簇表里存主键值 → 查询要两跳,且主键越宽它越胖。
random IO vs sequential IO
随机=读散落的 page、到处跳(HDD 要 seek);顺序=读连续 page。回表是随机、Seq Scan 是顺序——selectivity 翻转的根因。
