## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01–22 那样）。

1. QuoteFlow 现在只有「报价/核保/保单」一个模块化单体 + 一个独立的「夜间批量」服务。这个规模，你会上 service mesh 吗？如果不上，东西向的重试/超时/加密你用什么替代？
   
   - 我的想法：这个规模我不会上service mesh，因为service mesh适合于服务数量较多，且跨多种语言的情况，在只有一个模块化单体和一个独立服务的情况下用service mesh是把问题复杂化了。东西向的重试/超时/加密可以用数据库自带的功能来实现，或者用客户端SDK。

   - **点评（结论对，纠一个 slip + 送你一个更漂亮的洞察）：** 「不上 mesh」判对了，理由也踩准——**服务少 + 单语言，上 mesh 是过度工程**（文档原话：几个服务用库或共享客户端 SDK 就够）。两处加固：① **「数据库自带的功能」是个 slip。** 东西向是「服务↔服务」的通信，重试/超时/加密不归数据库管：数据库的 retry/timeout 说的是「你的服务↔DB」那条连接（另一个轴），服务间加密是 **mTLS / TLS（传输层）**，也不是 DB 功能。这半句删掉，留「**客户端 SDK / 库**」就对了——比如 **gRPC 自带的 deadline + retry**，或 resilience4j / Polly 这类弹性库。② **更狠的一招你漏了：这个规模下，大部分「东西向」根本不过网络。** 报价/核保/保单都在**同一个模块化单体进程内** → 它们之间是**进程内函数调用**，没有网络，也就谈不上重试/超时/mTLS。真正算「跨服务一跳」的，只有 **单体 ↔ 夜间批量** 那一条缝。所以这个规模「东西向问题」本来就很小——这才是「不必上 mesh」**最有力的论据**（比「服务少」更具体、更能说服人）。

2. 网关已经在注入 `trace_id` 做技术追踪了，为什么对寿险定价来说还**不够**、非要再有一条独立的业务级 audit 事件流？这两条线分别能回答监管的哪种问题？
   
   - 我的想法：因为trace_id只能追踪这一套报价流程是在逻辑上是如何实现的，走过了哪些服务，但是对于寿险定价的审计来说，只是知道定价过程如何实现还不够，还需要知道报价流程里应用的数据是哪些，比如说费率表，假设，具体的定价模型/算法，来保证根据这些信息可以完整复现当时的报价，这样才满足了审计的要求，而这就需要通过audit事件流来提供和记录。

   - **点评（答得很好，几乎是标准答案，补两条加固）：** 你抓住了核心——`trace_id` 回答「走过哪些服务」，业务 audit 回答「用了哪版费率表/假设/模型、能否复现」，方向完全对。两处磨锋利：① **题目还问「两条线各回答监管的哪种问题」，把对照点明：** `trace_id`（技术追踪）回答的是**运维/排障**问题——「这个请求当时在系统里走了哪几跳、哪一跳慢了或失败了」，是**短时、出故障时**用的；业务 audit 事件流回答的是**复现/合规**问题——「三年后监管翻出这张保单，凭哪版 `rate_table` / 哪套假设 / 哪个模型算出这个保费，能不能**逐字复现**」，是**长期**的。② **一个很硬的技术理由你没提：** trace 通常是**采样的**（生产里常只采 1%～几% 的请求）、而且**短期过期**（几天～几周就清）；而 audit **一条都不能丢、不可篡改、要留好几年**。光凭这一条——「会被采样丢、会过期」——trace 就**当不了** audit。（小补充：`trace_id` 可以**写进** audit 事件里当关联键，把两条线挂上钩；但它本身不承载业务语义。）

## 提问 & 解答

> 讨论时冒出来的问题记这。每条：先记自己的问题，再记讨论后的结论（用自己能看懂的话）。

### Q1. 点评里说东西向用「库」替代 mesh，这个「库」是数据库吗？

**问：** 「库」是不是就是数据库？

**答：** 不是。中文「库」有歧义：可指 **数据库（database）**，也可指 **软件库 / 代码库（library）**；这里是后者——一段别人写好、你 `import` 进自己代码直接调用的可复用代码（一个依赖包）。
- **数据库**：存数据的系统（Postgres / Redis），在你服务**外部**、走网络连过去。
- **库（library）**：一坨可复用代码，编译 / 打包进你的程序，跑在你服务**进程内**。
- 例子：gRPC 客户端库（自带 deadline + retry）、resilience4j（Java）、Polly（.NET）。
- **和 mesh 的对照正是今天的关键**：两者都能搞定东西向重试/超时/加密，区别在「逻辑放哪」——**库 = 编译进业务代码、同进程**（轻，但每种语言各配一份、升级要重发服务）；**mesh sidecar = 服务旁独立代理进程**（重，但跨语言统一、改策略不动代码）。

### Q2. 「客户端 SDK」里的 SDK 是 Software Development Kit 吗？

**问：** SDK 具体是什么？和「库」什么关系？

**答：** 是，**SDK = Software Development Kit（软件开发工具包）**。
- **库 vs SDK**：库是**一个**聚焦的代码包（一把螺丝刀）；SDK 是一**整套 kit**——通常 = 一或多个 library + 认证 + 辅助工具 + 数据类型 +（有时）CLI / 示例，**为对接某个特定平台配齐**（一整个工具箱）。SDK 里通常装着 library；不是每个库都是 SDK。
- 例子：**Supabase client**（我用过）`supabase.from('x').select()`、AWS SDK（boto3）、Stripe SDK——平台方给一套包，几行代码就接上它的服务。
- 类比：API 是后厨，SDK 是会说你母语的服务员（替你翻译成正确调用、忙时帮你重试、验你的会员卡 = auth）。
- 点评里的「客户端 SDK」特指**内部共享的 client SDK**：QuoteFlow 自己写一个内部包，每个服务调别的内部服务时 `import` 它，里面预置服务发现 / 重试超时熔断 / mTLS 证书 / `trace_id` 透传。这就是**不上 mesh** 时的替代方案；**软肋** = 只要全是同一种语言就好使，一旦混进别的语言就得维护多套 SDK → 这时 mesh 才划算。

### Q3. 「横切」的英文是啥？为什么用「横切」来表达？

**问：** cross-cutting 为什么译成「横」切？

**答：** **横切 = cross-cutting**，完整术语 **cross-cutting concern（横切关注点）**，源自 **AOP（Aspect-Oriented Programming，面向切面编程）**。
- **为什么是「横」**：架构图通常按**业务功能**画成一根根**纵向柱子**（报价 / 核保 / 保单，各自 API→逻辑→DB）；而认证、限流、加密、追踪、日志这些**不属于任何单一功能、却每根柱子都要**的关注点，是**横向穿过所有纵向模块**的 → 横着切，故称横切。英文 cross-cutting = cut across（交叉切过）。
- **这正是今天一整天的母题**：横切关注点若让每根柱子各实现一遍 = 在十几个服务里重复同一段代码。**网关和 mesh 存在的全部理由，就是把横切关注点从业务柱子里抽出来、收进一条专门的层**——网关在**边界**收南北向横切（authn / 限流 / TLS / 路由），mesh sidecar 在**服务旁**收东西向横切（mTLS / 重试 / 熔断 / 追踪）。

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 一个系统的流量和通信分为南北向——客户端和后端交互的流量数据，和东西向——后端内部不同服务之间的通信。对于南北向的通信，需要API网关来管理不同前端一致的通信需求，比如限流，身份认证，路由等；而对于不同前端不同的通信需求（比如app端需要打包好的简易数据，broker的后端需要内容更丰富的数据），则需要靠BFF来进行数据的整理整合，以满足特定前端的需求。对于东西向的通信，在服务较多，用不同语言，有较高的合规要求时，需要使用service mesh来管理内部服务之间的通信。mesh分为两个主要部分：control plane，来统一管理重试策略/安全证书分发/路由规则；data plane，提供sidecar来承载和处理接收到的请求，是业务代码旁边一个代理进程。这样在这些策略规则需要更新的时候，不用碰业务代码和重新发布服务，直接对control plane里记录的内容进行修改就好。
