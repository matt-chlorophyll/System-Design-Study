## 今日思考题

> 文档结尾「带着这两个问题回来讨论」。先写下自己的初步想法，再来 Claude Code 聊；聊完我会在每条下面补点评（像 Day 01–21 那样）。

1. 在 QuoteFlow 里，除了「夜间批量重定价」，你还会把哪个部分**第一个**切出去成独立服务？用今天四条判据说说理由。
   
   - 我的想法：我会把内部的数据分析服务切出去。根据四个判据得到的理由如下：
     - 高内聚：数据分析需要的分析流程是一套完整相连的逻辑（比如读取相关保单数据，进行数据清理整合，进行分析，画dashboard）
     - 低耦合：数据分析相对于报价/重定价来说是相对独立的服务，比如保单报价/重算之后并不会立刻触发数据分析，而是在固定时点根据当前数据进行分析
     - 数据自洽：数据分析用的是清洗合并之后的数据，报价/重算服务不会用数据分析服务里的这种数据
     - 独立节奏：可以独立发布，独立扩展，由独立的数据分析团队负责，数据分析对其他服务不产生影响
     - （但是数据分析的确要用到报价/重算服务产出的数据，但我觉得这个不算是数据不自洽或没有独立节奏）

   - **点评（选得好，补两条 + 一个 typo）：** 选「数据分析」很稳，还贴你背景。两处加固：① **数据自治的红线是「拥有自己的存储」，不是「我不读别人」**——分析服务**不能直接 SQL 读报价/核保的库**（那就打穿了人家的数据边界，回到文档里「偷看别人家的表」那个反例）；正确姿势是上游经 **事件流 / CDC / ETL** 把数据**推**到分析自己的 store（数仓 / OLAP）。所以「自治 = 拥有存储 + 只经接口/事件交换」，而不是「我不读别人」。② 你漏了最硬的一条拆分理由——**workload isolation（工作负载隔离）**：分析是**重扫描、长事务**，跟在线报价挤同一个 OLTP 主库，一个全表 join 就能拖慢白天的实时报价；把它切出去（独立 read replica / 数仓）本质是「**别让 OLAP 拖垮 OLTP**」，比高内聚低耦合更能说服人。另一个常见标准答案是 **billing**（独立合规 PCI、独立发布节奏、跟核心报价耦合低）。Typo：你写「4 个**判例**」→ 应是**判据**（criteria）；判例是法律词。

2. 如果把「报价」和「核保」拆成两个独立服务，要保证它们用的是**同一个 `rate_table_version`**、且审计链不断，你会怎么设计？这暴露了拆服务的什么隐性代价？
   
   - 我的想法：要有一个类似Kafka那样的系统去让一个coordinator钉死费率表版本，然后把这个费率表版本放在任务消息里，分别发送给报价和核保服务。此外，要有一个可用的key（比如policy_id+datetime+整体的task_id）来确定报价和核保服务针对的是同一个保单，并且能作为幂等键使重试时系统也能识别到是同一个保单的完整任务（尤其因为需要靠网络通信）。再就是要有完整的audit log，确保整个流程可追溯可审计。这暴露了拆服务一个代价是整个系统在确保一致性和可审计性方面要下更多功夫，设计维护审计的成本都更高。

## 我的理解（用自己的话复述今天的核心）

> 不看文档，凭记忆写 2–4 句。能写清楚 = 真的懂了。

- 整个系统的设计主要有三种选项：单体monolith，微服务microservice，以及模块化单体modular monolith。这三种选择各有取舍，一般选情况下都以模块化单体为起点：既获得了单体在进程内通信调用的好处，又给不同服务定义了清晰的逻辑边界，方便日后在需要时把单个服务独立出来成为微服务。要注意区分逻辑边界（代码的边界）和物理边界（是不是在独立进程/容器），以及代码耦合和团队耦合（系统的结构会长成组织沟通结构的样子）。怎么分服务要依据4个判例：高内聚，低耦合，数据自洽，独立节奏；一个切法是DDD里的bounded context。
