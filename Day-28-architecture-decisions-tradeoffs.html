1为什么决策要被记录

架构会留下来，但「为什么」会蒸发

系统会活很多年，但做决策的人会换、会忘。两年后某个工程师盯着代码里一处别扭的设计，问出那句最危险的话：「这玩意儿为什么要这样？看着没必要，删了吧。」——他不知道，当年这么做是为了满足一条监管要求 / 绕开一个第三方的坑 / 在那个流量量级下的合理取舍。这就是软件工程里著名的 切斯特顿的篱笆(Chesterton's Fence)：在你弄清一道篱笆为什么立在那儿之前，别拆它。

关键认知是：架构里真正会蒸发的不是「我们选了什么」，而是「为什么这么选、当时否决了哪些、基于什么假设」。代码本身记录了结果，却记录不了权衡的过程。一旦那个 context 丢了，后人要么盲目沿用一个早已过时的决策，要么鲁莽推翻一个其实仍然成立的决策——两种都很贵。

解药出奇地朴素：把每个重要决策，在做出的当下，写成一份短文档。这就是 ADR(Architecture Decision Record)。它不是繁文缛节的「架构大文档」——那种文档没人维护、写完就烂；ADR 是轻量、一决策一篇、只增不改(immutable)的小记录，像 git commit 一样按时间累积成一条「决策历史」。对 Matt 这种受监管的定价系统，它还有第二重身份：决策的审计轨迹——监管或内审问「你们当初为什么选这套定价架构、评估过哪些替代方案、谁批的」，ADR 就是现成的答案。

2ADR 的解剖

一份 ADR 长什么样

ADR 的格式有很多流派(最有名的是 Michael Nygard 的版本)，但骨架都一样。核心就五段，刻意保持短——一篇一页以内，写不动说明决策还没想清楚：

小节回答什么写作要点
Title + Status这是关于什么的决策？现在处于什么状态标题用一句话；状态在 Proposed → Accepted → Deprecated → Superseded by ADR-N 之间流转
Context
背景		我们面对什么问题？有哪些约束和力(forces)在拉扯最重要的一节。写清需求、NFR、团队/预算/时限/合规等约束——这是未来理解决策的钥匙
Decision
决策		我们决定怎么做用主动语气、肯定句：「我们将采用 X」。一句话能说清最好
Alternatives
被否决的选项		还考虑过什么？为什么没选★ 最值钱的一节。把否决理由钉死，未来才不会反复重提同一个废案
Consequences
后果		这么选，得到什么、付出什么诚实写出负面后果(新增的运维负担、技术债)，不只写好处

▲ 注意 ADR 同时记录了「正面」和「负面」后果。一份只写好处的 ADR 是营销文案，不是决策记录——它的诚实度，恰恰是它日后可信的来源。

两条容易被忽略的纪律

第一，ADR 是不可变的(immutable)。决策变了，不要去改老 ADR，而是写一篇新的，把老的状态标成 Superseded by ADR-0042。这样你保留的是一条决策演化史，而不是一份被反复覆盖、丢失了过去的文档——和 Day 16/18 反复强调的「用不可变的事件日志而非可变状态」是同一个思想，只不过这次记录的是人的决策。第二，在决策做出的当下写，趁 context 还热乎；事后补写的 ADR 往往把当时真实的犹豫和约束粉饰掉了，价值大打折扣。

3结构化权衡

怎么把「我觉得」变成「我们比过」

ADR 是记录决策的容器；但决策本身怎么做得不拍脑袋？方法其实你这 28 天一直在用，今天把它显式化成四步。核心洞察是：评价架构选项的那些「维度」，恰恰就是 Day 1–2 讲的 non-functional requirements。权衡，本质就是「不同选项在各条 NFR 上各有高下，按当前最重要的 NFR 来选」。

几个让这套方法不流于形式的要点。① 永远把「什么都不做 / 维持现状」列为一个选项——很多时候它就是最优解，引入新组件的复杂度往往被低估。② 维度要带权重：QuoteFlow 的实时报价路径里 latency 和 auditability 权重极高，而一个内部工具里开发速度可能压过一切——没有放之四海的打分。③ 警惕假精确：给每个选项打 1–5 分加权求和看着科学，但分数是你拍的，很容易反向编造来「证明」早有的偏好。打分表是组织讨论的脚手架，不是替你做决定的机器；真正的产物是「为什么」，不是那个总分。

4成本是第一类需求

把钱和「可逆性」摆上台面

工程师做权衡时最常漏掉的维度就是成本——既包括钱，也包括复杂度和时间。一个技术上更优雅的方案，如果贵三倍、或让团队要养一套谁都不熟的新系统，它在整体上可能是更差的决策。成熟的架构判断，是把成本当成和 latency、availability 平起平坐的一条 NFR。

看成本要看 TCO(Total Cost of Ownership，总拥有成本)，而不是只看眼前的开发或采购价。TCO 包含：建设成本(人月)、运行成本(算力/存储/带宽/license)、运维与人力成本(谁来 on-call、谁来打补丁——这块常被严重低估)、以及认知成本 / 复杂度税(团队为理解和维护它持续付出的脑力)。这把尺子直接喂进经典的 build vs buy(自建 vs 采购) 决策：自建掌控力强、无 license 费，但全部 TCO 压在自己团队；采购/用托管服务起步快、运维外包，但有持续订阅费和供应商锁定(vendor lock-in)。

一刀切开所有决策：可逆 vs 不可逆
  • Amazon 有个极好用的分类：双向门(two-way door)是可逆决策——选错了能低成本退回来(比如选哪个缓存库、用哪种序列化格式)；单向门(one-way door)是几乎不可逆的(比如核心数据模型、对外 API 契约、是否把单体拆成微服务)。两者该花的决策力气完全不同：双向门别过度分析，快选、错了再改；单向门才值得动用完整的权衡 + ADR + 评审。把精力按「门的方向」分配，是资深和新手的一个分水岭。

6贯穿案例

给 QuoteFlow 写一份真实 ADR

来个具体分歧。QuoteFlow 要做夜间批量重定价(周年、CPI indexation、费率表变更，百万级保单)。团队吵起来：是复用现有的同步报价服务循环调用，还是引入一套独立的异步批处理管道(Day 15–17 那套：队列 + worker + 事件日志)？把第 3 节的四步走一遍，再落成 ADR。

Case · QuoteFlow · 决策过程

① 选项

A：维持现状，用实时报价服务循环跑批；B：搭独立异步批处理管道；C：买一个托管的工作流编排服务(SaaS)来调度。

② 评价维度(= 关键 NFR + 成本)

吞吐(能否在维护窗口内跑完百万级)、对实时报价的隔离性(批量不能拖垮线上 p99)、可复现 / 可审计(每条重定价要能回放、对监管解释)、TCO、团队熟悉度。

③ 对照

A 复用方便、TCO 最低，但吞吐撑不住、且会和实时流量抢资源——隔离性差，触犯了报价路径的高优先级 NFR。C 起步最快，但批处理里嵌着受监管的定价逻辑，丢进第三方 SaaS 带来数据驻留与vendor lock-in 风险，审计链也更难掌控。B 吞吐与隔离最好、事件日志天然满足可回放/审计，代价是引入新组件、TCO 与认知成本上升。

④ 决策

选 B。批量与实时是两条性质不同的路径(Day 1 就埋的伏笔)，强行合并两头不讨好；可审计 + 隔离性的高权重压过了 B 多出来的复杂度成本。这是一道单向门(数据管道一旦铺开很难回退)，值得完整权衡 + ADR。

下面把这次决策定格成一份 ADR。留意它怎么把上面的过程压成五段、尤其是「被否决的选项」如何把 A 和 C 的否决理由钉死，省得半年后有人又提一遍：

docs/adr/0042-batch-repricing-pipeline.md · QuoteFlow ADR(示意)
# ADR-0042: 夜间批量重定价采用独立异步管道
Status:  Accepted  (2026-06-28, 决策人: 架构组; 评审: 定价 + 合规)

## Context
# 把约束和「力」写清——这是未来读懂决策的钥匙
- 需求: 每夜对 ~1.2M in-force 保单做重定价(周年/CPI/费率表变更)
- NFR: 维护窗口内跑完(throughput); 不得拖垮实时报价 p99(隔离);
        每条结果可回放、可审计(监管一等需求)
- 约束: 团队已用过 Kafka/worker; 合规要求定价逻辑数据留在本区域

## Decision
我们将为批量重定价构建独立的异步管道:
事件日志(Day 16) + 幂等 worker(Day 18) + 跨 AZ 持久化,
与实时报价服务物理隔离、各自独立扩展。

## Alternatives considered  # ★ 最值钱的一节
- A. 复用实时报价服务循环跑 → 否决:
    吞吐撑不住百万级; 且与线上流量抢资源, 违反隔离性 NFR
- C. 采购托管工作流 SaaS → 否决:
    受监管定价逻辑入第三方 = 数据驻留风险 + vendor lock-in,
    审计链更难掌控; TCO 的订阅费长期未必更省

## Consequences
+ 吞吐与隔离达标; 事件日志天然支持回放/审计(合规加分)
+ 批量与实时可独立演进、独立扩缩
- 引入新组件 → 运维 + 认知成本上升(需培训/on-call)
- 这是单向门: 管道铺开后回退代价高 → 已据此提高评审规格

看这份 ADR 的密度：它没有长篇大论，却把约束(Context)、决定(Decision)、为什么不选别的(Alternatives)、和诚实的代价(Consequences)全锁住了。对受监管的 QuoteFlow，这份文档同时是工程记忆和合规证据——两年后无论是新同事问「为什么不直接复用报价服务」，还是监管问「这套定价架构怎么决策的、评估过哪些方案」，答案都在这一页里，可追溯、可解释。

★关键要点

今天带走这四句

1

架构里会蒸发的不是「选了什么」，而是「为什么这么选」。用 ADR 在决策当下把它写下来——尤其是被否决的选项。

2

权衡 = 列选项(含「不做」)→ 按关键 NFR 定维度 → 对照 → 记录。评价维度就是这 28 天的 non-functional requirements。

3

4

没有最优解，只有当前最重要的 NFR 指向的取舍。在 QuoteFlow，ADR 同时是工程记忆与合规审计证据。

?今日小测 + 思考题

读完自测一下

Q1ADR 五节里，哪一节最常被省略、却往往最值钱？为什么？
「被否决的选项(Alternatives)」。它把「为什么没选别的」钉死，避免未来有人反复重提一个早就评估过的废案，也让决策的权衡过程对后人(和审计)透明。只写最终决定的 ADR，丢掉了最难重建的那部分 context。
Q2「选用哪个 JSON 序列化库」和「核心保单数据模型怎么设计」——决策力气该一样吗？
不一样。前者是双向门(可逆)，选错低成本就能换，别过度分析、快选即可；后者是单向门(几乎不可逆)，改动牵一发动全身，值得动用完整的结构化权衡 + ADR + 评审。把精力按「门的方向」分配。
Q3一个方案技术上更优雅，但要团队养一套全新系统。为什么它可能仍是更差的决策？
因为只算了技术优雅，没算 TCO(总拥有成本)——尤其是运维/人力成本和认知/复杂度税。成本(钱 + 时间 + 复杂度)是和 latency、availability 平级的一条 NFR；整体最优 ≠ 单看某一维度最优。
Q4决策变了，应该直接改掉那份旧 ADR 吗？
不应该。ADR 是不可变(immutable)的：写一篇新 ADR，把旧的状态标成 Superseded by ADR-N。这样保留的是一条决策演化史，而不是一份丢失过去的可变文档——和「用不可变事件日志而非可变状态」是同一个思想。

A→Z术语表

今日术语

ADR
Architecture Decision Record，架构决策记录：一决策一篇、不可变的轻量文档，记录背景/决定/替代方案/后果。
Trade-off
取舍：在相互冲突的目标(常是不同 NFR)之间做出的有依据的权衡，没有放之四海的「最优」。
Context (in ADR)
ADR 里写清问题、约束与各种拉扯的「力」(forces)的一节——未来理解决策的钥匙。
Consequences
决策带来的正面与负面后果；诚实写出代价(技术债、运维负担)才是有用的 ADR。
TCO
Total Cost of Ownership，总拥有成本：建设 + 运行 + 运维人力 + 认知复杂度的全周期成本，而非眼前价。
Build vs Buy
自建 vs 采购：自建掌控力强无 license，采购起步快但有订阅费与供应商锁定，用 TCO 来权衡。
One-way / Two-way Door
单向门(几乎不可逆)vs 双向门(可逆)决策；前者值得重投决策力气，后者快选即可。
Vendor Lock-in
供应商锁定：过度依赖某第三方/云服务后，迁移成本高到难以更换的状态，是采购方案的隐性成本。
