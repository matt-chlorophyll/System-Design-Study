—— API 网关、Service Mesh 与 BFF

1两类流量

先分清南北向和东西向

微服务一多,新手很容易把所有「服务间通信」的问题搅成一团。其实只要先切一刀,整张图立刻清楚:把流量分成两类方向。

North-South(南北向):从系统外部进来、再出去的流量——浏览器、手机 App、broker 的后端打到 QuoteFlow。它穿过你的「边界」,因此天然要处理:身份认证、限流、TLS 终结、把一个外部请求路由到正确的内部服务。守这道门的,就是 API Gateway(以及给特定前端定制的 BFF)。

East-West(东西向):系统内部服务之间的流量——报价服务调核保服务、批量服务调保单服务。它不出边界,但量更大、链路更长,要处理的是:服务发现、重试与超时、熔断、服务间的 mTLS 加密、把每一跳都接进链路追踪。管这层的,是 Service Mesh。

一句话记牢:网关守南北门,mesh 管东西巷。它们不是二选一,而是各管一类流量。下面这张图把三件套和两类流量一次摆清。

2南北门

API Gateway:边界上的单一入口

当你只有一个单体时,客户端直连它就行。可一旦拆成十几个服务,问题来了:难道让 App 自己记住「报价在 a.svc、核保在 b.svc、保单在 c.svc」,还各自实现一遍登录鉴权?这叫客户端直连后端的反模式——前端被内部拓扑绑死,内部一改,所有客户端跟着改。

API Gateway 是横在客户端和后端之间的单一入口。所有外部请求先打到它,由它统一干掉那些每个服务都要做、但不该各做一遍的横切活,再转发给内部服务:

网关典型职责(把横切关注点集中处理)
  • 路由 / 聚合:把 /v1/quotes 转给报价服务,/v1/policies 转给保单服务;有时还把多个后端结果聚合成一个响应。
  • 认证与授权(authn/authz):校验 token、解析身份,内部服务就不必各自重做(Day 25 会专讲 OAuth2/OIDC)。
  • 限流与配额:给每个 broker、每个 API key 配速率上限,挡住打爆后端的流量(Day 20 的 rate limiting 在这里落地)。
  • TLS 终结、协议转换:外面收 HTTPS、对内可走 HTTP/gRPC;也能把老的 REST 客户端翻译到新的内部协议。
  • 可观测性入口:统一打访问日志、注入 trace id(Day 24),给每个外部请求一个可追溯的起点。

关键区别要记清:load balancer 在 L4 按连接分发,不看内容;reverse proxy 在 L7 转发、可做缓存,但路由相对死板;API gateway 是「带业务感知的 L7 入口」——它认得 API、懂认证、能限流、按路由规则把请求送到正确的微服务。网关常常就跑在一个反向代理 / 负载均衡之后,但职责更上层。别把网关做成「什么逻辑都往里塞」的新单体——那是它最常见的退化方式。

3给前端定制的门

BFF:一个前端,一扇专属门

有了网关,还会遇到一类更细的问题:不同前端要的东西不一样。手机 App 屏幕小、网络差,想要一个「报价 + 保单摘要」打包好的精简响应;而 broker 的后端要的是字段齐全、可批量的接口;网站又是另一套。如果让同一个通用 API 同时伺候所有前端,它会被各方需求撑成一个谁都不满意的怪物。

BFF(Backend for Frontend)的思路:每一类前端,配一个专属的后端适配层。App BFF、broker BFF、Web BFF 各自面向一个前端,负责为这个前端裁剪、聚合、塑形下游服务的数据。下游的报价 / 核保 / 保单服务保持通用、不被任何单一前端的口味污染;「这个屏幕需要哪几个字段」这种易变逻辑,被收进对应的 BFF 里。

BFF 和网关不矛盾,而是分层:网关管所有前端共通的横切事(认证、限流、TLS),BFF 管某一个前端特有的聚合与塑形。小系统里两者可以合一;前端种类一多、各自演进速度不同时,拆出 BFF 就开始划算——它让 App 团队能改自己的 BFF 而不惊动 broker 那条线。

一个判断口诀
  • 横切、所有前端都一样 → 放网关;某个前端独有、会随它的 UI 频繁变 → 放它的 BFF。把这两类活混在一处,是后期最难拆的债。
4东西巷

Service Mesh:把横切关注点搬出业务代码

南北向解决了,东西向更隐蔽。报价调核保、批量调保单……每一次服务间调用,都得处理:对方在哪(服务发现)、调失败要不要重试、多久算超时、连续失败要不要熔断(Day 20)、这一跳要不要加密、怎么把它接进链路追踪(Day 24)。问题是:这些逻辑如果写进每个服务的业务代码,就要在十几个服务、几种语言里各实现一遍,还很难统一升级。

Service Mesh 的核心招法是 sidecar:给每个服务实例旁边塞一个轻量代理进程(如 Envoy),让所有进出该服务的网络流量都先过这个 sidecar。于是上面那串横切活——mTLS 加密、重试、超时、熔断、负载均衡、流量镜像、生成追踪 span——全部由 sidecar 代劳,业务代码只管发一个普通的本地调用,对这些一无所知。

Data plane vs Control plane

mesh 分两层,这是它最该记住的结构:data plane(数据面)就是那一堆 sidecar 代理,真正搬运每一个请求字节;control plane(控制面)是大脑,负责把路由规则、重试策略、安全证书下发给所有 sidecar。你想让「报价→核保」的调用统一加 200ms 超时、失败重试 2 次、全程 mTLS?在控制面改一条策略,它推给相关 sidecar 即可——不动一行业务代码、不重新发布服务。

mesh 不是免费的
  • 每个服务多一个 sidecar = 多一跳网络、多一份内存/CPU、多一层要运维和排障的东西。服务不多时,mesh 往往是过度工程——几个服务用库(如 gRPC 自带的重试)或一个共享的客户端 SDK 就够了。等服务数量、语言种类、安全合规要求都涨上来,mesh 把「东西向治理」标准化的价值才压过它的复杂度成本。
5对照

网关 vs Mesh:别混为一谈

这两个最容易被搅在一起。一张表钉死它们的分工:

▲ 记忆锚点:网关是「一扇大门」,mesh 是「给每个房间都配了门卫的内部走廊」。两者经常同时存在,各管一向流量。

6贯穿案例

把三件套摆进 QuoteFlow

沿用昨天的切法(模块化单体起步,先切出夜间批量)。即便服务还不多,南北门也该先立起来;东西向先用轻量手段,长大了再上 mesh。

Case · QuoteFlow

① 网关:所有渠道的统一前门

网站、App、broker 全部打到一个 gateway:它做 TLS 终结、校验 token、给每个 broker 配速率配额(防止某个 broker 批量打报价拖垮系统)、把 /v1/quotes 路由到报价服务。关键合规点:网关是给每个外部请求注入 trace_id 的地方——这个 id 会一路贯穿到 audit log,让「这条报价从哪个渠道、哪个 broker 发起」可追溯。

② BFF:给 broker 和 App 各裁一套

broker 要批量、字段全的报价接口;App 要轻量、聚合好的「报价 + 保单摘要」。各配一个 BFF,下游报价/核保/保单服务保持通用。broker 那条线的接口演进,不会逼着 App 团队跟着改。

③ Mesh(等长大再上)+ 横切的审计线

服务还少时,报价↔核保走进程内或一个共享客户端 SDK 即可;等服务拆多、跨语言、对「服务间 mTLS + 统一重试策略」有合规诉求时,再引入 mesh,把这些治理从代码里搬到控制面。但无论用不用 mesh,审计都不能交给它:mesh 的追踪解决「技术链路连不连得起来」,而「为什么是这个保费」的业务级审计(rate_table_version、rules_applied)必须由业务事件流承载(Day 16),横切所有服务。受监管定价系统的铁律:基础设施层的 trace 和业务层的 audit,是两条都要有、且不能互相替代的线。

下面用一段网关路由配置(示意),感受「横切关注点被声明在入口、而非散落在每个服务」是什么意思:

gateway.yaml · QuoteFlow 网关路由(示意)
# 所有外部请求先过这里,横切活集中声明
routes:
  - match: { path: /v1/quotes, methods: [POST] }
    authn:    oidc                 # 校验 token,内部服务不必重做
    rate_limit:                      # 每个 broker 单独配额(Day 20 落地)
      key: broker_id
      limit: 100/s
    inject_headers:
      x-trace-id: $generated      # 注入 trace_id → 一路贯穿到 audit log
      x-channel:  $client.kind     # 渠道留痕:可追溯报价来源
    forward_to: quote-svc          # 路由到内部服务(对外隐藏拓扑)

  - match: { path: /broker/v2/* }
    authn: mtls                    # broker 走更强的双向证书
    forward_to: broker-bff         # 交给 broker 专属 BFF 去聚合/塑形

# 注意:这里没有任何"保费怎么算"的业务逻辑。
# 网关只做横切;业务留在服务里;业务级审计走事件流,不归网关也不归 mesh。
★关键要点

今天带走这四句

1

先分流量方向:north-south 找网关,east-west 找 mesh。分错方向,后面全乱。

2

API Gateway = 边界单一入口,集中处理认证/限流/路由/TLS;别把业务逻辑塞进去,否则它退化成新单体。

3

Mesh 用 sidecar 把服务间的重试/熔断/mTLS/追踪搬出业务代码,control plane 改策略不动代码——但它有实打实的复杂度成本,服务不多别上。

4

在 QuoteFlow,网关的 trace_id 是技术追踪;而「为什么是这个保费」的业务审计必须走事件流。两条线都要,不能互相替代。

读完自测一下

Q1「报价服务调用核保服务时的重试和 mTLS」属于 north-south 还是 east-west?该由谁管?
East-West(服务↔服务,在系统内部)。由 service mesh 的 sidecar 管,而不是 API gateway——网关只管从外部进来的 north-south 流量。
Q2API Gateway 和 BFF 的核心分工是什么?
网关管所有前端共通的横切事(认证、限流、TLS、路由);BFF 管某一个前端特有的聚合与塑形(App 要精简打包、broker 要批量全字段)。共通的放网关,某前端独有且随其 UI 变的放它的 BFF。
Q3service mesh 的 data plane 和 control plane 各是什么?改一条服务间超时策略要不要重新发布服务?
data plane = 那堆真正搬运请求的 sidecar 代理;control plane = 下发路由/策略/证书的 大脑。改超时策略只在控制面改一条配置、推给 sidecar 即可,不用动业务代码、不用重新发布服务——这正是 mesh 的卖点。
带着这两个问题回来讨论

① QuoteFlow 现在只有「报价/核保/保单」一个模块化单体 + 一个独立的「夜间批量」服务。这个规模,你会上 service mesh 吗?如果不上,东西向的重试/超时/加密你用什么替代?
② 网关已经在注入 trace_id 做技术追踪了,为什么对寿险定价来说还不够、非要再有一条独立的业务级 audit 事件流?这两条线分别能回答监管的哪种问题?
