1先把事务想清楚

事务是「一组操作」的全有或全无

Day 8 我们见过 ACID:Atomicity(原子性)、Consistency(一致性)、Isolation(隔离性)、Durability(持久性)。一句话复习:事务是一组读写,数据库承诺把它们当作一个不可分割的整体来处理。要么整组生效(commit),要么整组当没发生过(rollback)——绝不会停在半路。

为什么这件事是刚需?看 QuoteFlow 签发一张保单:要① 在 policies 表写入新保单、② 在 ledger 表生成首期保费的应收、③ 把报价 quote 标记为「已转化」。如果第 ② 步写完机器崩了,你就有了一张「存在但没有任何账目」的保单——在受监管的寿险里,这是会被审计直接点名的数据不一致。事务保证的就是:这三步要么全成,要么全不成,绝不留下半张保单。

ACID 里 A 和 D 相对直观(全有全无、落盘不丢),C 在很大程度上是前三者加上你写的约束共同产生的结果。真正让无数系统翻车的是 I —— Isolation。因为现实里,事务从不孤独运行:成百上千个事务同时在读写同一批数据。隔离性回答的问题是:「并发的事务之间,该装作互相看不见到什么程度?」

这里藏着今天的核心张力:隔离越强,正确性越好,但并发度和性能越差。完美隔离(像所有事务排成一队挨个跑)最安全,但慢得没法用。所以数据库给了你一个旋钮——isolation level——让你按业务选「松一点换快」还是「严一点换稳」。

2松了会出什么事

四个隔离级别,与它们放过的 anomaly

理解隔离级别的最好方式,不是背它们的名字,而是看每一级各自「放过」了哪种并发 bug。SQL 标准定义了四级,从松到严,对应放过的异常逐级减少:

先认识几种 anomaly(并发异常)

Dirty read(脏读):读到了别的事务还没提交的数据——对方一回滚,你读到的就是幻觉。Non-repeatable read(不可重复读):同一事务里读同一行两次,值变了(因为中间别人改完提交了)。Phantom read(幻读):同一事务里跑同样的范围查询两次,行数变了(别人新插/删了符合条件的行)。Lost update(更新丢失):两个事务都「读-改-写」同一行,后写的覆盖了先写的,一次更新凭空消失。Write skew(写偏斜):两个事务各读一批数据、各自基于「快照」做了看似合法的写,合起来却破坏了一个跨行约束——最隐蔽的一种。

隔离级别脏读不可重复读幻读典型实现代价
Read Uncommitted可能可能可能几乎不加锁,最快也最危险
Read Committed挡住可能可能只读已提交;多数库的默认
Repeatable Read挡住挡住可能*快照/行锁;MySQL 默认
Serializable挡住挡住挡住等价于串行执行,最稳最慢

▲ 越往下放过的异常越少、代价越高。* 注:标准里 Repeatable Read 仍允许幻读,但 PostgreSQL/MySQL-InnoDB 的快照实现实际上挡住了大部分幻读——「标准」和「某数据库叫什么名字的那一档」常常对不齐,务必查你用的库的具体文档。

两个要命的细节:第一,各家数据库对同名级别的实现不一样。Oracle 没有真正的 Read Uncommitted,它的「Serializable」其实是快照隔离;PostgreSQL 的 Repeatable Read 是快照隔离。同一个级别名,在不同库里挡的东西不同。第二,lost update 和 write skew 这两个最坑的异常,SQL 标准的那张表根本没列——它们要到快照隔离/Serializable 才真正被处理。所以「我用了 Repeatable Read 就高枕无忧」是危险的错觉。

3隔离是怎么做出来的

Locking、MVCC、SSI

数据库实现隔离主要靠三类机制,理解它们能解释「为什么 Serializable 慢」「为什么读不该阻塞写」:

Two-phase locking(2PL,两阶段锁):读加共享锁、写加排他锁,事务结束才统一释放。正确性强,但读写互相阻塞、并发度低,还可能死锁。MVCC(多版本并发控制):每次写生成一个新版本,每个事务读它开始那一刻的「快照」。读不加锁、不阻塞写,写也不阻塞读——这是 PostgreSQL、MySQL-InnoDB、Oracle 高并发的基石。代价是要存多版本、定期清理旧版本(vacuum)。SSI(可串行化快照隔离):在 MVCC 快照之上,额外监测事务间的读写冲突,发现可能破坏可串行性的组合就让其中一个事务失败重试——用「乐观 + 重试」拿到 Serializable,而不必全程上重锁。

下面用一段 SQL 把 lost update 演示清楚,并给出两种正确写法。场景:QuoteFlow 给某 in-force 保单的当年累计已付保费 paid_ytd 加一期 38.20。

lost_update.sql · 并发更新同一行
-- ❌ 危险:读到内存里加完再写回。两个并发事务都读到 100,
--    各自写回 138.20,结果只加了一期 —— 另一期凭空蒸发。
BEGIN;
  SELECT paid_ytd FROM policies WHERE id = 'pol_8f3a';  -- 读到 100.00
  -- 应用层算 100.00 + 38.20 = 138.20
  UPDATE policies SET paid_ytd = 138.20 WHERE id = 'pol_8f3a';
COMMIT;

-- ✅ 写法一:原子自增,让数据库在行锁内完成读-改-写
UPDATE policies SET paid_ytd = paid_ytd + 38.20 WHERE id = 'pol_8f3a';

-- ✅ 写法二:乐观锁 / 版本号。写时校验版本,被人抢先就重试
UPDATE policies SET paid_ytd = 138.20, version = version + 1
  WHERE id = 'pol_8f3a' AND version = 7;  -- 影响行数=0 → 重读重试

记住这条经验法则:凡是「读出来、在应用里改、再写回去」的模式,在并发下默认就有 lost update 风险。要么用原子操作、要么用乐观锁版本号、要么把隔离级别提到能挡它的那一档。

4走出单库

当一次业务跨越多个服务:2PC 的困境

上面所有美好,都建立在「数据在同一个数据库里」这个前提上。一旦 QuoteFlow 拆成多个服务(保单服务、计费服务、再保上报服务),或者数据分到了不同分片,一次业务就要同时改好几个独立的数据库——单库事务管不了它们了。

第一个本能方案是 2PC(two-phase commit,两阶段提交):引入一个协调者(coordinator)。阶段一 prepare:协调者问所有参与者「你能提交吗?」,各自锁好资源、写好预备日志,回答 yes/no。阶段二 commit:只要有一个说 no,全体回滚;全说 yes,协调者下令全体提交。它确实能给跨库的原子性——但代价很硬:

① 同步阻塞:prepare 到 commit 之间,所有参与者都得锁着资源干等,延迟被最慢的那个拖死。② 协调者是单点:如果协调者在「大家都说 yes」之后、下达 commit 之前崩了,参与者就卡在「已锁定、不敢提交也不敢回滚」的状态(in-doubt),可能挂很久。③ 可用性差:任一参与者不可用,整个事务就做不下去。在高吞吐、要高可用的系统里,2PC 通常被认为太脆、太慢——所以现代分布式系统多半绕开它。

5更实用的解法

Saga:把大事务拆成「本地事务 + 补偿」

Saga 换了个思路:不再追求「跨库的瞬时原子性」,而是把一个长业务拆成一串各自独立的本地事务,每一步都在自己的库里正常提交。一旦某步失败,就反向执行前面已完成步骤的「补偿事务(compensating transaction)」,把世界回退到一个语义上一致的状态。它换来的是高可用和低耦合,放弃的是「中间状态绝不可见」——saga 给的是最终一致性(eventual consistency),不是隔离性。

Saga 有两种编排方式。Orchestration(编排,中心化):一个 saga orchestrator 像总指挥,显式地一步步调用各服务、决定下一步或触发补偿。逻辑集中、好观测、好审计——对 QuoteFlow 这种需要清晰追溯每张保单走到哪一步的合规场景很友好。Choreography(协同,去中心化):没有总指挥,各服务通过事件互相触发(下周 Day 16 的事件驱动)。耦合更低,但流程散落在各处,出问题时「这单到底卡在哪」很难追。

2PCSaga
一致性强一致(原子提交)最终一致 + 补偿
中间状态对外不可见可见(需业务容忍)
阻塞 / 锁prepare 期间长时间锁定每步立即提交,不跨步持锁
可用性差(协调者/参与者单点)高(步骤解耦)
失败处理统一回滚写补偿逻辑(开发负担↑)
适用少量参与者、强一致刚需跨服务长流程、要高可用

▲ 选择本质是:你能不能容忍「中间状态短暂可见」。能容忍 → saga;绝不能(如同一笔钱的借贷必须瞬时配平)→ 想办法收进同一个库用本地事务,而不是硬上 2PC。

补偿不是「撤销」,且要幂等
  • 补偿事务往往不能真正「回到过去」:T3 已签发的保单,C3 通常是另写一条「撤销/作废」记录而非物理删除——这反而正合寿险的 auditability:每一步正向和补偿都在 audit log 留痕,整条 saga 完整可回溯。另外,失败重试会让同一步被执行多次,所以每个步骤和补偿都必须幂等(idempotent)——这正是 Day 18 的主题。
6贯穿案例

给 QuoteFlow 的三类操作各配一条策略

Case · QuoteFlow

① 保单签发(单库内)→ 本地事务 + 合适隔离级别

policies / ledger / quote 三张表若在同一个库,直接用一个本地事务包住,Read Committed 或 Repeatable Read 足矣;涉及金额自增的地方用原子更新或乐观锁防 lost update。这是最简单、最该优先采用的路子——能不分布式就不分布式。

② 夜间批量重算(高吞吐)→ 不要大事务,分批 + 幂等

百万保单重定价绝不能塞进一个巨型事务(会长期持锁、撑爆 undo/版本)。做法是切成小批、每批一个短事务,配合版本号与幂等键,失败的批次可单独重跑——吞吐优先,牺牲「全局瞬时一致」,反正这是离线批处理(Day 17 细讲)。

③ 跨服务投保流程(申请→核保→签发→收费)→ Saga(编排式)

这条链跨了多个服务/库,且单步耗时长,正是 saga 的主场。用orchestration 让流程集中可观测、每步与补偿都进 audit log。收费失败就补偿撤销签发、释放核保占额、作废申请——对客户而言这单「没成」,但系统状态干净、且全程可追溯,满足合规。

一句话收口:事务策略不是全局选一个,而是逐条业务按「一致性要多强 / 能不能容忍中间状态 / 是实时还是批量」来配。这正是 Day 1 那句「没有最优解,只有约束下的取舍」在数据层的又一次现身。

读完自测一下

Q1同一事务里两次读 SELECT * FROM rates WHERE band='A',第二次多出了几行。这是哪种 anomaly?需要哪一级隔离才挡得住?
Phantom read(幻读):范围查询结果集的行数在事务内变了。SQL 标准里要到 Serializable 才保证挡住(注:InnoDB/PostgreSQL 的快照实现实际上在 Repeatable Read 就大体挡住了——以你用的库的文档为准)。
Q2为什么大多数 OLTP 系统不直接默认开 Serializable?
太慢。Serializable 等价于让冲突事务串行执行(靠重锁或 SSI 的频繁重试),并发度和吞吐大幅下降。多数库默认 Read Committed,把更强的隔离留给确实需要的关键路径——又是一次 trade-off。
Q3投保 saga 走到「签发保单」成功、但「首期收费」失败。系统该怎么办?最终一致性体现在哪?
触发补偿事务:撤销签发(写一条作废记录)、释放核保占额、作废申请,逐步回到「未承保」的一致状态。最终一致体现在:这中间存在一小段「保单已签发但还没收到费」的可见中间态,系统不保证它绝不出现,只保证最终会被补偿收敛到一致——代价换来了跨服务的高可用。
