1没有索引会怎样

全表扫描:行数翻倍,时间翻倍

先建立最朴素的认知。一张表在磁盘上,本质就是一摞按写入顺序堆着的行(heap)。现在你执行:

SELECT * FROM policies WHERE applicant_id = 'a_1043';

如果这一列上没有索引,数据库别无选择,只能从第一行一行一行读到最后一行,逐行比对 applicant_id 是否等于 'a_1043'。这叫 full table scan(全表扫描),在 PostgreSQL 的执行计划里写作 Seq Scan。它的代价是 O(n):表里有 100 万行就要读 100 万行,有 2 亿行就读 2 亿行——行数翻倍,时间也翻倍。

换个画面就懂了:一本 800 页、没有目录也没有索引的书,你要找“B-tree”这个词在哪一页,只能从第一页翻到最后一页。而书末的索引页让你“B → 第 312 页”一步跳到。数据库索引就是那张索引页——一个额外维护的、有序的数据结构,让数据库不必把整本书翻一遍。

别急着下结论:Seq Scan 不总是坏事
  • 有一种情况全表扫描反而最快:当你要的行占了全表的一大半(比如“查所有 IN_FORCE 保单”而 95% 的保单都 in-force)。这时一条一条走索引再回表,反而比直接顺序读整张表更慢。记住这个伏笔——第 4 节的 selectivity 会把它讲透,它正是“到底该不该加索引”的判据。
2B-tree 的形状

为什么百万行只需跳 3~4 次

关系数据库默认的索引结构,几乎都是 B-tree(精确说多是 B+tree)。先别被名字吓到,它的核心就一句话:一棵又矮又宽、永远保持平衡的有序树。

“有序”意味着每个节点里的 key 是排好序的,你可以像查字典一样二分地往下走;“矮而宽”是关键——每个节点不是只存 1 个 key、分 2 个叉(那是二叉树),而是存几百个 key、分几百个叉(高 fan-out)。叉一多,树就长不高:百万行的索引,树高通常只有 3~4 层。于是“定位一行”不再是走百万步,而是从根往下跳 3~4 次——每跳一次读一个节点(一次磁盘 IO),复杂度从 O(n) 降到 O(log n)。

两个值得记住的细节。其一,B+tree(数据库实际用的变体)只在叶子节点存数据指针,且把所有叶子串成一个有序链表——所以 WHERE premium BETWEEN 30 AND 50 或 ORDER BY created_at 这种范围/排序查询特别快:定位到起点后顺着链表扫一段就行。其二,树始终保持平衡(每条根到叶的路径一样长),所以无论数据怎么插入删除,查询代价都稳定在 O(log n),不会退化。

3复合索引与覆盖索引

列的顺序很重要,回不回表更重要

真实查询很少只筛一列。QuoteFlow 的报价/保单系统里,一个高频查询是“某投保人、某产品、还在 in-force 的保单”。这时你会建一个 composite index(复合索引),比如 (applicant_id, product, status)。它的内部就是按这个列顺序拼成一个组合 key 来排序的——而这带来一条最容易踩的规则:最左前缀原则(leftmost prefix)。

把复合索引想成电话簿按“姓→名”排序:给定姓(可以再给名),你能瞬间定位;但只给“名”、不给“姓”,这本电话簿对你毫无帮助——你还是得一页页翻。同理 (applicant_id, product, status) 这个索引:

查询条件能用上 (applicant_id, product, status) 吗
WHERE applicant_id=?✅ 用上(命中最左列)
WHERE applicant_id=? AND product=?✅ 用上(命中最左两列)
WHERE applicant_id=? AND status=?⚠️ 部分用上(用 applicant_id 定位,status 跳过了 product 只能在结果里再过滤)
WHERE product=? AND status=?❌ 基本用不上(缺了最左列 applicant_id,只能退回 Seq Scan)

▲ 最左前缀:复合索引只能从最左列开始连续命中。建索引前先想清最常见的查询长什么样,再决定列的顺序——把等值、最常出现、选择性高的列放左边。

第二个关键概念是 covering index(覆盖索引)。普通的二级索引里只存了“索引列 + 一个指向真实数据行的指针”。所以当你 SELECT premium 而 premium 不在索引里时,数据库要先在索引里找到行的位置,再回到主表去把 premium 那一列读出来——这一步叫回表(table lookup),是额外的随机 IO。

如果一个查询所需要的列,全都已经在索引里了,数据库就能“只读索引、不回表”直接返回结果。这种索引对这个查询就是覆盖的,执行计划里会出现最理想的 Index Only Scan。做法是把要 select 的列也放进索引——在 PostgreSQL/SQL Server 里可以用 INCLUDE 把它们挂在叶子上而不参与排序:

CREATE INDEX ... ON quotes (applicant_id) INCLUDE (premium, computed_at);

对 QuoteFlow 的实时报价读路径(Day 2 说的低延迟一等公民)来说,覆盖索引是把 p99 压下去的常用招:让那几个最热的查询全程不碰主表。

索引不是越多越好:写放大与 auditability
  • 每加一个索引,读可能更快,但每一次 INSERT / UPDATE / DELETE 都要顺带维护所有相关索引(write amplification,写放大),还要占额外磁盘。这对 QuoteFlow 尤其要权衡两处:① 夜间批量重定价是海量写,索引越多批处理越慢;② audit_log 表只增不减、会长到几亿行,审计追溯(“调出某保单的全部历史”“按时间范围抽查”)离不开索引,但又不能为了查询便利在这张高写入表上堆一堆索引。典型解法:只建支撑核心审计查询的少量复合索引,并配合 Day 13 要讲的分区(partition)按时间切表。
4读 EXPLAIN

别猜,让数据库告诉你卡在哪

判断一条 SQL 快不快,不要靠肉眼猜,用 EXPLAIN(加 ANALYZE 会真正执行并给出实际耗时与行数)。它把数据库打算怎么取数据的计划摊开给你看。先认识三种最常见的扫描方式:

计划里出现含义快慢 / 何时出现
Seq Scan全表逐行扫描,不走任何索引没有可用索引,或命中行占比太高(低选择性)时优化器主动选它
Index Scan走索引定位到行,再回表读其余列命中行少时很快;但回表是随机 IO,命中越多越不划算
Index Only Scan所需列全在索引里,免回表最理想——覆盖索引命中,读路径最快

▲ 看到 Seq Scan 不必恐慌,先问“它扫了多少行、占全表多大比例”;看到 Index Scan 也别得意,真正最优的是 Index Only Scan。

下面用 QuoteFlow 一条审计追溯查询走一遍——“调出某张保单的全部审计记录”。加索引前后,EXPLAIN 的差别一目了然:

explain.sql · QuoteFlow 审计追溯:加索引前后(示意)
-- 查某保单的全部审计记录(audit_log 有 2 亿行)
EXPLAIN ANALYZE
SELECT action, actor, at, rate_table_version
FROM audit_log
WHERE entity_id = 'p_77a2';

-- ❌ 没有索引:全表扫 2 亿行,几秒甚至更久
Seq Scan on audit_log  (rows=200000000)
  Filter: (entity_id = 'p_77a2')
  actual time=4213.8 ms        -- 读完整张表才挑出那 12 行

-- 建一个复合索引,顺带把 select 的列 INCLUDE 进去
CREATE INDEX idx_audit_entity
  ON audit_log (entity_id, at)
  INCLUDE (action, actor, rate_table_version);

-- ✅ 重跑:走索引、且免回表 → 毫秒级
Index Only Scan using idx_audit_entity on audit_log
  Index Cond: (entity_id = 'p_77a2')
  actual time=0.06 ms          -- 4213ms → 0.06ms,约 7 万倍

这条查询同时演示了今天三件事:索引把 O(2亿) 变成 O(log) 的几次跳转;复合索引 (entity_id, at) 让“某保单按时间排序的历史”天然有序;INCLUDE 覆盖让它免回表、拿到 Index Only Scan。对受监管的寿险来说,这不只是“快”——它让 auditability 在亿级数据下依然可用:监管要随时抽查某保单为何这样定价,查询不能一跑就是几分钟。

Case · QuoteFlow

为什么夜间批量这条线不靠索引

同一个系统,反向的例子同样重要。夜间重定价要扫几乎全部 in-force 保单(命中占比接近 100%)。这种低选择性的全量读,优化器会理性地选 Seq Scan——顺序读整张表比“走索引 + 上亿次回表”快得多。选择性(命中行 / 总行数)才是“该不该用索引”的真正判据:命中越稀越该用索引,命中越密越该老老实实顺扫。索引是给“大海捞针”的,不是给“把海水全舀出来”的。

★关键要点

今天带走这四句

1

没索引就 Seq Scan(O(n)),行数翻倍时间翻倍。索引是一份额外维护的有序结构,把“翻整本书”变成“查目录”。

2

B+tree 又矮又宽、始终平衡:高 fan-out 让百万行只 3~4 层,定位 = O(log n) 的几次 IO;叶子链表让范围/排序查询也快。

3

复合索引认最左前缀(列序很关键);覆盖索引让所需列全在索引里、免回表 → Index Only Scan,是压低读延迟的利器。

4

用 EXPLAIN 看而不是猜。索引非越多越好(写放大);selectivity 才是判据:大海捞针才用索引,捞光海水就老实 Seq Scan。

?今日小测 + 思考题

读完自测一下

Q1你在 policies 上建了复合索引 (applicant_id, product, status)。查询 WHERE status='IN_FORCE'(不带前面两列)能高效用上它吗?为什么?
基本用不上。复合索引按“applicant_id → product → status”的顺序排序,遵守最左前缀原则:必须从最左列开始连续命中。只给 status、跳过了 applicant_id 和 product,就像只报“名”查一本按“姓→名”排的电话簿——索引帮不上忙,优化器大概率退回 Seq Scan。要支持单独按 status 查,得调整列序或单独给 status 建索引(但注意 status 选择性低,索引收益也有限)。
Q2SELECT premium FROM quotes WHERE applicant_id=?,你在 (applicant_id) 上建了索引,EXPLAIN 显示 Index Scan 但仍有回表。怎么把它变成 Index Only Scan?
把 premium 也放进索引,让它“覆盖”这个查询。当前索引只有 applicant_id,所以拿到行位置后还要回表读 premium 那一列。改成 (applicant_id) INCLUDE (premium)(或复合索引 (applicant_id, premium)),查询要的列就全在索引里了,数据库免回表直接返回 → Index Only Scan,读路径最快。
Q3同一张表,查 WHERE applicant_id='a_1043'(命中 3 行)走了 Index Scan;但查 WHERE status='IN_FORCE'(命中 95% 的行)优化器却选了 Seq Scan。为什么?
因为 selectivity(选择性)不同。applicant_id 命中极少、高选择性,走索引精准定位几行最划算。而 status='IN_FORCE' 命中几乎整张表、低选择性:走索引意味着对几乎每一行都做一次回表(大量随机 IO),反而比直接顺序读整张表(Seq Scan)更慢。优化器据此理性地放弃索引——这也是夜间全量重定价不靠索引的同一个道理。
带着这两个问题回来讨论

① QuoteFlow 的 audit_log 只增不减、会长到几亿行。为支撑两类审计查询——“调出某保单的全部历史”和“按时间范围抽查所有 ISSUE 动作”——你会建哪些索引?复合索引的列顺序怎么排、为什么?同时它又会给这张高写入表带来什么代价?
② 把今天的 selectivity 和昨天 Day 8 的事务边界连起来想:夜间批量重定价该用索引还是 Seq Scan、又该每张保单一个小事务还是整批一个大事务?这两个判断背后,是不是同一种“看命中规模 / 看影响范围”的取舍直觉?

今日术语

Index
额外维护的有序数据结构,用空间和写开销换取查询时不必扫全表。
Full Table Scan / Seq Scan
逐行读整张表,O(n);无可用索引或低选择性时发生。
B-tree / B+tree
又矮又宽、始终平衡的有序树索引;高 fan-out 使定位为 O(log n),B+tree 叶子串成链表利于范围查询。
Composite Index
多列拼成的索引,按列序排序;查询须满足最左前缀才高效命中。
Leftmost Prefix
最左前缀原则:复合索引只能从最左列开始连续命中。
Covering Index / Index Only Scan
查询所需列全在索引里 → 免回表,执行计划出现 Index Only Scan。
Table Lookup(回表)
索引只给行位置,再回主表读其余列的额外随机 IO。
Selectivity / Cardinality
选择性 = 命中行 / 总行数;高选择性该用索引,低选择性顺扫更快。基数 = 列不同值的数量。
Write Amplification
写放大:每次增删改都要维护所有相关索引,索引越多写越慢。
EXPLAIN / Query Plan
执行计划:数据库展示它打算如何取数据;加 ANALYZE 给出实际耗时与行数。
