1第一刀:authn vs authz

「你是谁」和「你能干什么」是两件事

这是整个安全话题里最重要、也最常被搞混的一对概念,务必先钉死:

Authentication(authn,认证) 回答 「你是谁」。它验证身份——你声称是 broker acme-insurance,系统要确认你确实是它。手段:密码、API key、客户端证书、一次性验证码、或一张已经签发过的 token。

Authorization(authz,授权) 回答 「这个已确认的你,被允许做什么」。身份确认之后,你能不能调批量重定价接口?能不能读别人的保单?能不能改费率表?这是一套规则 + 策略的判断。

顺序是固定的:先 authn,后 authz。没确认身份就谈权限毫无意义;确认了身份不等于什么都能干。一个生活类比:进写字楼,前台核对你的工牌照片是不是你本人——这是 authn;但你的工牌只能刷开 8 楼,刷不开数据中心机房门——这是 authz。同一张工牌,两道独立的关卡。

为什么混淆它们是事故之源
  • 最经典的漏洞 IDOR(Insecure Direct Object Reference):用户已登录(authn 通过),于是系统就直接信任他,让他把 URL 里的 policy_id=1001 改成 1002 去读别人的保单——因为开发者只做了 authn,漏了「这个身份有没有权读这一条」的 authz。登录≠有权,这一步必须每次单独判。
2委托授权

OAuth2 与 OIDC:发「授权」 vs 发「身份」

很多人把 OAuth2 当成「登录协议」,这是误解的根源。

OAuth2 是一个授权委托框架:它解决的是「我想让 A 应用,在不交出我密码的前提下,代我去访问 B 上我的资源」。比如 QuoteFlow 想代 broker 调用某个第三方风险评分服务——broker 不该把自己的主密码交给 QuoteFlow,而是签发一个范围受限、可撤销、会过期的 access_token。OAuth2 产出的是「能做什么」(scopes),它本身不告诉你「用户是谁」。

OIDC(OpenID Connect)是架在 OAuth2 之上的身份层:它补上 OAuth2 缺的那块,额外签发一个 id_token(一个 JWT),里面装着「用户是谁」(sub、email、name 等 claims)。所以「用 Google 登录」用的是 OIDC,不是裸 OAuth2。

OAuth2OIDC
解决什么授权委托:代我访问资源身份认证:这人是谁
产出access_token(带 scopes)额外的 id_token(身份 claims)
回答的问题能做什么(authz 输入)你是谁(authn 结果)
QuoteFlow 用处broker 授权第三方代调报价 API用户/员工用 SSO 登录后台
一句话「钥匙卡能开哪几扇门」「卡上印着这是谁」

▲ 记一句:OAuth2 管授权、OIDC 管身份。把 OAuth2 当登录用,正是历史上一堆身份泄露的根因。

授权码流程(Authorization Code Flow)长什么样

这是最常见、也最安全的一条流程(配合 PKCE 用于 App / SPA)。注意:密码从头到尾只交给可信的 Authorization Server,第三方应用永远拿不到它——这正是 OAuth2 的价值。

3令牌

JWT:把身份和权限焊进每个请求

HTTP 是无状态的——每个请求都是陌生人。怎么让网关一眼认出「这是已登录、且有权调批量接口的 pricing 工程师」?两条路:

不透明令牌(opaque token):token 只是一个随机串,服务端拿它去 session 库 / Auth Server 查「这是谁、有什么权」。好处是能即时撤销(删库里那条就失效),代价是每次都要多查一跳。

JWT(JSON Web Token):token 本身就装着信息,且带签名。它三段式 header.payload.signature,payload 里是 claims(sub 谁、scope 权限、exp 过期时间…),signature 用 Auth Server 的私钥签。网关用公钥验签就能确认「没被篡改、确实是可信方签发的」——无需回查数据库,这是它扩展性好的根本原因。

JWT 的三个必背陷阱
  • 签名 ≠ 加密。JWT 默认只是 Base64 编码 + 签名,payload 是明文可读的。别把密码、完整 PII 塞进 JWT。
  • 难以即时撤销。JWT 一旦签发,在 exp 到期前都有效——这正是「无需回查」的另一面。所以 access_token 要短命(几分钟~1 小时),配一个长命但可撤销的 refresh_token 去换新的;真要紧急失效,得靠黑名单或轮换签名密钥。
  • 算法陷阱。历史上著名的 alg: none 和「RS256 当 HS256 验」漏洞——务必固定校验算法、绝不接受客户端指定 alg。
网关验 JWT 并做 authz(伪代码)
// 请求头:Authorization: Bearer eyJhbG...（一个 JWT）
function handleQuoteRequest(req) {
  const token = parseBearer(req.headers.authorization)

  // ── 第一关:authn —— 验签 + 验时效，确认「你是谁」 ──
  const claims = jwt.verify(token, AUTH_PUBLIC_KEY, {
    algorithms: ["RS256"],        // 固定算法，堵住 alg 陷阱
    issuer:    "https://auth.quoteflow.example",
    audience:  "quoteflow-api"
  })                                // 签名/exp 不对 → 直接 401

  // ── 第二关:authz —— 这个身份「能不能做这件事」 ──
  if (!claims.scope.includes("quotes:write"))
    throw Forbidden(403)        // 已登录但无权 → 403，不是 401

  // ── 防 IDOR:不止「能写报价」，还要「能写这一条」 ──
  if (req.body.broker_id !== claims.broker_id)
    throw Forbidden(403)        // 不能替别的 broker 报价

  audit.log({ who: claims.sub, action: "quote.create", at: now() })
  return createQuote(req.body)
}

留意两个细节:401 vs 403 —— 401 是「我不知道你是谁」(authn 失败),403 是「我知道你是谁,但你不许」(authz 失败);以及那行 audit.log —— 在受监管系统里,谁在何时做了什么本身就是必须留痕的安全要求,和昨天的 observability 共用一套基建。

4授权模型

RBAC vs ABAC,与最小权限

验完身份,「能不能做」这道判断怎么组织?两种主流模型:

RBAC(Role-Based Access Control,基于角色):把权限打包成角色,人挂到角色上。例:pricing_engineer 角色 = 可读费率表 + 可触发批量重定价;broker 角色 = 只能对自己的客户报价。简单、好审计、99% 的系统够用——QuoteFlow 后台从这里起步。

ABAC(Attribute-Based Access Control,基于属性):用属性 + 规则动态判断,能表达 RBAC 表达不了的细粒度。例:「只有 department=pricing 且 region=AU 的人,在工作时间、从公司网络,才能改 in_force 保单的费率」。更灵活,但规则会膨胀、更难审计。

维度RBACABAC
判断依据你属于哪个角色主体/资源/环境的一组属性
粒度粗,角色为单位细,可到「这条记录 + 此刻」
易审计性高:列角色即可低:要跑规则才知道谁能干啥
复杂度低,起步首选高,规则易爆炸
QuoteFlow员工后台、broker 分级对 in-force 保单的合规化细粒度管控

▲ 实务常见做法:RBAC 打底 + 少量 ABAC 规则补细粒度。不要一上来就上全套 ABAC。

贯穿全系列的原则 · Least Privilege(最小权限)
  • 每个用户、每个服务、每个 token,只授予完成本职工作所需的最小权限,默认拒绝(deny by default)。报价服务不该有改费率表的权;一个临时分析任务不该拿到能删保单的凭证。最小权限的意义在于缩小爆炸半径:某个凭证一旦泄露,攻击者能碰到的东西越少越好。这条原则今天讲、但贯穿整个系统设计。
5密钥与加密

秘密怎么存,数据怎么护

认证授权背后,处处依赖「秘密」:签 JWT 的私钥、数据库密码、第三方 API key。两条铁律:

① 密钥绝不进代码 / git。用专门的 secrets manager(如云上的 KMS / Secrets Manager / Vault)集中保管,应用运行时按需拉取、定期轮换(rotation)。硬编码在仓库里的密钥一旦随代码泄露,等于把家门钥匙印在明信片上。

② 数据加密分两种场景,都要做:

场景加密什么QuoteFlow 落地
In transit(传输中)网络上流动的数据,用 TLS/HTTPS报价 API、broker 调用、服务间通信全程 TLS(回到 Day 4 的 TLS)
At rest(静态)落盘的数据:DB、备份、日志保单库、PII、审计日志加密存储;密钥放 KMS
敏感字段PII 额外的字段级加密 / 脱敏身份证号、健康信息等单独加密,日志里脱敏
Case · QuoteFlow · 合规视角

为什么寿险定价对安全格外苛刻

QuoteFlow 握着大量高度敏感的 PII:年龄、性别、健康状况、吸烟史——这些既是定价输入,也是受隐私法规重点保护的数据。安全在这里不是「加固」,而是一等公民的 non-functional 需求,和 Day 1 讲的 auditability 并列:

谁在何时访问/修改了哪条保单、动了哪个版本的费率表,都必须留痕、可追溯、可向监管解释。所以本日的 audit.log、最小权限、字段级加密,不是锦上添花,而是「能不能合规上线」的硬门槛。安全控制本身,也成了审计对象。

Q1一个已登录的 broker,把 URL 里的 policy_id 换成别人的,就读到了别人的保单。这是 authn 还是 authz 的问题?
authz 问题。他的身份是真的(authn 通过了),漏的是「这个身份有没有权读这一条」的授权判断——典型 IDOR。修法:每次访问对象都校验归属,而不是「登录了就放行」。
Q2「用 Google 登录」到底用的是 OAuth2 还是 OIDC?token 验签失败应返回 401 还是 403?
OIDC(它在 OAuth2 之上加了身份层,签发 id_token 告诉你「这人是谁」;裸 OAuth2 只管授权)。验签失败 = 认不出你是谁 = 401 Unauthorized;身份没问题但权限不够才是 403 Forbidden。
Q3为什么把 access_token 设得很短命(几分钟),反而更安全?长命怎么办?
因为 JWT 难即时撤销——签发后在 exp 前一直有效。短命把「泄露后还能被滥用的窗口」压到最小。用户不会每几分钟重登一次:配一个长命但可撤销的 refresh_token，在后台静默换发新的短命 access_token；真出事就吊销 refresh_token。
