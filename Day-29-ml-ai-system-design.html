1ML 系统哪里不一样

多了一个「会自己变」的依赖

前 28 天里，系统的行为是代码决定的：代码不改，行为不变；要复现一个 bug，把同样的输入喂进同一版代码就行。ML 系统打破了这个假设——它的行为由代码 + 数据 + 训练出的权重三者共同决定。数据会随真实世界漂移，于是同一份代码、明年的表现可能完全不同。

这带来三个普通系统没有的麻烦。第一，data is a dependency（数据是一种依赖）：上游数据源的口径一变、某个字段悄悄改了单位，模型就会无声地变差，而不是抛异常。第二，training/serving skew（训练-服务偏斜）：训练时算特征用的是一套离线代码，线上服务时又是另一套，两边对「同一个特征」算出不同的值，模型在线上表现远不如离线评估。第三，drift（漂移）：用户群体、市场、监管在变，去年训练的模型今年慢慢失准——没人改任何代码，准确率却在往下掉。

所以一句话定调今天：模型本身往往是整个系统里最小的一块。真正占工作量的，是喂给它的数据管道、保证两端一致的特征供给、把每个模型版本钉死的治理，以及上线后持续盯着它有没有变坏的监控。这些恰恰都是系统设计问题，不是建模问题。

受监管定价的提醒
  • 在 QuoteFlow 这类受监管的寿险定价里，「模型行为由数据决定」直接撞上 compliance：你必须能回答「这条核保决定，是哪一版模型、用哪一版特征、基于哪些训练数据做出的」。这就是为什么 ML 系统里 reproducibility（可复现） 不是加分项，而是上线的前提。
2生命周期

从原始数据到一个在线决策

把一个 ML 系统拆成五个阶段，每个阶段都对应一个你已经学过的系统设计部件。注意中间那条反馈回路——线上跑出来的真实结果，会回流成下一轮训练的标签，这是 ML 系统区别于普通系统的灵魂。

逐段看它对应哪个老朋友

① 特征（feature store）：把原始数据加工成模型吃的特征，并解决一个核心矛盾——离线训练要批量算海量历史特征（高 throughput），在线服务要毫秒级取单条特征（低 latency）。这正是 Day 7 缓存、Day 17 批 vs 流的组合拳：离线一套管道、在线一套低延迟存储，但用同一份特征定义，否则就是 skew。

② 训练（pipeline）：一条可复现的批处理管道（Day 17 ETL 的近亲），产出模型 + 评估报告。关键是把训练数据快照、特征版本、超参、代码 commit 全部钉住——这就是 Day 28 ADR 精神在 ML 里的体现。

③ 模型注册表（model registry）：模型的「版本化仓库 + 发布闸门」。每个模型有不可变版本号、谱系（lineage）、审批状态。它对模型，就像 Day 26 的制品库对代码。

④ 在线服务（serving）：把模型包成一个低延迟 API。它需要 Day 6 的负载均衡、Day 20 的限流熔断、Day 24 的可观测性——和普通服务一模一样。

⑤ 监控（monitoring）：除了 Day 24 的延迟/错误率，还要盯数据分布漂移、预测分布漂移、以及（滞后到来的）真实准确率。这是 ML 独有的一层。

3在线服务的取舍

Batch inference vs Online inference

「模型怎么对外提供预测」有两条根本不同的路径，选错了，整套架构都拧巴——这和 Day 1 就埋下的「实时报价 vs 夜间批量」是同一种张力。

Batch inference（离线批量）Online inference（实时在线）
什么时候算提前、成批算好，存起来待查请求来了当场算
主导 NFRhigh throughputlow latency（p99 卡得死）
特征来源离线特征仓库，随便算多重在线 feature store，必须毫秒返回
新鲜度滞后到下一批（小时/天级）实时反映最新输入
QuoteFlow 例子夜间批量给 in-force 保单重算风险分新业务实时报价时的核保风险分
复杂度 / 成本低，像一个定时 job高：要扩容、降级、缓存、保 SLA

▲ 多数成熟系统两者都有：同一个风险模型，夜间用 batch 给存量保单刷分，白天用 online 给新报价打分。务必保证两条路径用的是同一版模型，否则同一个人晚上和白天得到不同结论。

上线一个新模型：别直接切

换模型 = Day 26 的发布问题，但风险更隐蔽：新模型可能延迟没变、错误率没变，却悄悄把某个人群的报价系统性抬高了。所以 ML 上线偏爱两种「先观察、后切流」的姿势：

Shadow（影子）部署：新模型和旧模型同时收到真实流量，新模型的输出只记录、不生效。用真实流量验证它的预测分布和延迟，零业务风险。Canary / A-B（Day 26）：确认无误后，先放 1% 流量给新模型，比对真实业务指标，再逐步加码。受监管场景里，这一步往往还要叠一道人工审批 + ADR 留痕。

4LLM 时代

RAG、向量库与 agent harness

前面讲的是「自己训练的预测模型」。但今天很多 AI 系统是围着一个预训练大模型（LLM）搭的——你不训练它，而是给它喂对的上下文、给它接上工具。两个核心模式：

RAG —— 给模型一个「开卷考试」

RAG（Retrieval-Augmented Generation，检索增强生成）解决的是：LLM 不知道你私有的、最新的知识，而且会一本正经地编（hallucinate）。做法是在提问前，先去你自己的知识库里检索出相关片段，塞进 prompt，让模型基于检索到的材料作答，并附出处。

这套流程拆开看，全是老部件：把文档切块、用 embedding 模型转成向量、存进向量库（vector DB）；查询时把问题也转成向量，做相似度检索（ANN，近似最近邻）取回 top-k 片段——本质是 Day 9 索引思想在高维空间的版本；检索其实是个读密集服务，Day 7 的缓存、Day 6 的负载均衡照样适用。

rag_answer() · QuoteFlow 内部 broker 知识助手（示意）
def rag_answer(question, user):
    # 1) 把问题向量化（embedding 模型也是一个版本化依赖）
    q_vec = embed(question, model="embed-v3")

    # 2) 向量库做 ANN 检索 —— 像高维空间里的索引查找
    chunks = vector_db.search(q_vec, top_k=6,
                             filter={"acl": user.role})   # 权限过滤(Day 25)

    # 3) 把检索到的材料拼进 prompt，要求“只依据材料作答 + 给出处”
    prompt = build_prompt(question, chunks)
    answer = llm.generate(prompt, model="llm-2026-05")  # 钉版本=可复现

    # 4) 留痕：问题 / 命中片段 / 模型版本 / 答案 —— 审计与追溯
    audit_log.write(question, chunk_ids=[c.id for c in chunks],
                    model="llm-2026-05", answer=answer)
    return answer, [c.source for c in chunks]   # 带出处返回

Agent harness —— 给模型接上「手脚」

再进一步，让 LLM 不只回答，还能调用工具、执行多步任务，就需要一个 agent harness（智能体框架）。它围着模型搭了一圈控制结构：一组可调用的 tools（查保单、跑报价 API、查费率表）、一个「思考→调工具→看结果→再思考」的循环、以及一层护栏（guardrails）——限制能调哪些工具、对写操作要人工确认、设步数与预算上限防止失控。

从系统设计角度，agent 是个放大器：它把前 28 天所有教训都放大了。它的每一次工具调用都要 Day 25 的鉴权、Day 20 的限流、Day 18 的幂等（同一步别重复扣费）、Day 24 的全链路 tracing。一个没有护栏和可观测性的 agent，在受监管系统里是不能上线的。

5贯穿案例

QuoteFlow 的自动核保风险评分

把今天的骨架落到一个具体模型：QuoteFlow 自动核保里的风险评分模型——输入投保人特征，输出一个风险分，喂给核保规则决定「直接承保 / 加费 / 转人工」。它同时活在两条路径上：新业务实时报价（online）、夜间存量重估（batch）。

Case · QuoteFlow

五段骨架怎么落

特征：年龄、BMI、既往病史、职业风险等，由 feature store 统一定义，离线管道供训练、在线低延迟存储供报价，同一份定义杜绝 skew。训练：每次产出钉死训练数据快照 + 特征版本 + 超参 + 代码 commit。注册表：模型拿到不可变版本号 risk-v7，进发布闸门走精算 + 合规审批。服务：报价时返回风险分，并把 model_version 焊进报价记录。监控：盯输入分布漂移、分数分布漂移，以及理赔结果滞后回流后的真实校准度。

为什么 auditability 是这里的一等公民

监管或客户某天会问：「三年前这张保单为什么被加费？」系统必须能精确重建：当时是 risk-v5 模型、feat-2023Q2 特征、某个具体输入，算出某个分，触发了某条核保规则。这要求模型版本、特征版本、输入快照、决策全部不可变留痕——也意味着旧模型不能随便删，因为复现历史决策需要它。

注意这一连串需求里，没有一条是「把模型调得更准」。它们全是系统设计问题：版本治理、谱系追踪、不可变审计、漂移监控、灰度发布。这正是今天最想留下的认知——把模型做出来是数据科学，把模型变成可上线、可审计、可长期维护的系统，是系统设计。

一个常见反模式
  • 把 ground truth 的滞后忘了。核保模型的「真实答案」（理赔是否发生）可能几年后才到。这意味着你没法用「准确率掉了」来快速发现模型变坏——只能靠盯输入/输出分布漂移这种 leading indicator 提前预警。在寿险这类长尾反馈的领域，这一点尤其致命。
★关键要点

今天带走这四句

1

ML 系统的行为 = 代码 + 数据 + 权重。数据是会漂移的新依赖，所以 reproducibility 是前提，不是加分。

2

模型只是最小一块。特征供给、版本治理、漂移监控才是工作量，而它们全是你已学过的系统设计问题。

3

Batch vs Online inference 是「夜间批量 vs 实时报价」的翻版；两端务必同源，否则 training/serving skew。

4

RAG / agent 没发明新原理：检索是高维索引，agent 是放大器——鉴权、限流、幂等、tracing 一个都不能少。

读完自测一下

Q1训练时特征算出来一个值，线上服务算同一个特征却是另一个值，这叫什么？为什么危险？
Training/serving skew。危险在于：模型离线评估很好，上线却变差，且很难定位——因为它喂到的输入和训练时根本不是同一分布。解法是让两端共用同一份特征定义 / feature store。
Q2要给新业务报价当场算风险分、p99 卡得很死，该用 batch 还是 online inference？
Online inference。请求来了当场算，主导 NFR 是 low latency。夜间给存量保单刷分才用 batch（主导 NFR 是 throughput）。同一个模型常常两条路径都跑。
Q3RAG 主要解决 LLM 的什么问题？「向量库检索」对应你前面学过的哪个概念？
解决两件事：让模型用上私有/最新知识，并通过「基于检索材料作答 + 给出处」压制 hallucination。向量库的相似度检索（ANN）本质是 Day 9 索引在高维空间的版本——把全表扫描变成快速近邻查找。
带着这两个问题回来讨论

① QuoteFlow 的核保风险模型，「真实答案」(理赔) 可能几年后才到。在这种 ground-truth 严重滞后的场景里，你会监控哪些 leading indicator 来提前发现模型变坏？
② 如果要给 broker 上线一个 RAG 知识助手，从 auditability / compliance 角度，你会强制留痕哪些东西、设哪些护栏？

A→Z术语表

今日术语

Feature Store
统一定义、存储与供给特征的系统，让离线训练与在线服务共用同一份特征定义。
Training/Serving Skew
训练时与服务时对同一特征算出不同值，导致线上表现劣于离线评估。
Model Registry
模型的版本化仓库与发布闸门，记录版本号、谱系与审批状态。
Batch vs Online Inference
提前成批算好预测 vs 请求到来时当场算；前者重 throughput，后者重 latency。
Drift
数据/预测分布随时间变化，导致模型在无代码改动下逐渐失准。
Shadow Deployment
新模型与旧模型同收真实流量，新模型只记录不生效，用于零风险验证。
RAG
检索增强生成：作答前先检索私有知识塞进上下文，让模型基于材料回答并给出处。
Vector DB / ANN
存储 embedding 并做近似最近邻相似度检索的存储——高维空间里的「索引」。
Agent Harness
围绕 LLM 的控制框架：工具调用、思考循环与护栏，让模型能多步执行任务。
Reproducibility
能用钉死的代码/数据/特征/模型版本，精确重建任一历史预测——受监管系统的上线前提。
