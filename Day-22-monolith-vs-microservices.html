1三种形态

不是「单体 vs 微服务」两选一

大多数人把这件事讲成一道二选一题:老旧的单体,还是时髦的微服务。这是个误导。真正有用的是一条谱系,中间那个常被忽略的选项,往往才是大多数系统该待的地方。

Monolith(单体)

整个应用是一个可部署单元:报价、核保、保单、billing 全部编译进同一个进程,共享同一个数据库,一次构建、一次部署。它的好处常被低估:一次进程内函数调用就完成的事,没有网络、没有序列化、没有分布式事务;本地就能跑起整个系统;一次改动一次发布。缺点是随着代码长大,内部边界会糊掉——任何模块都能直接读另一个模块的表,改一处牵动全身;而且整个进程一起扩、一起挂、一起发版。

Microservices(微服务)

把系统拆成许多个独立部署的小服务,每个有自己的进程、自己的数据库、自己的发布节奏,彼此通过网络(REST/gRPC/消息)通信。它换来的是独立部署、独立扩展、技术异构、团队自治、故障隔离。代价也实打实:进程内调用变成网络调用(会超时、会失败、要重试——回到 Day 18 的幂等);一个数据库变成多个,跨服务的一致性要靠 saga(Day 14)而非事务;还多出一整套运维负担——服务发现、链路追踪、部署编排。分布式是一种成本,不是一种成就。

Modular Monolith(模块化单体)

常被忽略的中间项,也常是最优起点:一个部署单元,但内部用强纪律切成清晰模块。每个模块有明确的公开接口,模块之间只许走接口、不许直接碰对方的表。它保留了单体的部署简单与进程内调用的高效,同时把「将来要拆」的逻辑边界提前画好。一旦某个模块真的需要独立扩展或独立发布,把它「切出去」成微服务的代价,远小于从一团泥球里硬撬。

2两个最常被混的区分

边界有两种,耦合也有两种

这一节是今天的核心,也是面试最容易暴露「是否真懂」的地方。两组概念,长得像、其实正交:

逻辑边界 vs 物理边界

逻辑(模块)边界是代码层面的「这块归报价、那块归核保」;物理(部署)边界是运行层面的「这是不是一个独立进程/容器」。微服务的本质,是把两者对齐——每个逻辑模块就是一个物理部署单元。但关键认知是:你可以有清晰的逻辑边界,却不付物理拆分的代价——那就是模块化单体。先把逻辑边界画好,物理拆分等到有真实理由时再说。反过来,把物理边界拆得很碎、逻辑边界却糊成一团,就是最糟的「分布式单体」:既要付网络的钱,又没换来独立性。

代码耦合 vs 团队耦合(康威定律)

Conway's Law:系统的结构会长成组织沟通结构的样子。这话反过来用,是微服务最被低估的真实驱动力——很多时候拆服务不是为了性能,而是为了让团队能独立发版、不互相阻塞。三个人的小团队硬上十个微服务,是给自己上刑;而当报价和核保是两个不同团队、不同发布节奏时,把它们拆开反而是顺势而为。先看组织,再定边界。

一句话戳破常见误区
  • 微服务≠高性能。把进程内调用换成网络调用,单看延迟通常更慢。它买的是独立性(部署/扩展/团队/故障隔离),不是速度。需要更快,先想缓存和扩容,不是拆服务。
  • 拆服务≠拆数据库就够了。真正的难点是「一笔业务原本一个事务能做完,现在要跨两个服务保证一致」——这是 Day 14 saga 的领地,成本远超想象。

▲ 经验法则(Martin Fowler 的「Monolith First」):除非你已经非常确定边界、且组织规模撑得起,否则从模块化单体起步,在它真正长疼的地方再拆。先拆错的边界,比晚拆贵得多。

4边界划在哪

切服务的四条判据

「该不该拆」之外,更难的是「沿哪条缝拆」。好的服务边界不是按技术分层(controller / service / dao 那种),而是按业务能力切。判断一条边界划得好不好,看这四点:

1

高内聚:一起变化的东西在一起。改一个业务规则,理想情况只动一个模块,不用跨三个服务联合发版。

2

低耦合:边界上接口要窄。如果两个模块每天要互相调几十个细粒度方法,这条缝多半划错了。

3

数据自治:每个服务拥有自己的数据,别人只能经接口访问。若两服务非得共享一张表才能干活,它们其实是一个。

4

独立节奏:能独立发布、独立扩展、(理想上)由独立团队负责。对齐康威定律。

一个好用的切法是 Domain-Driven Design 的 bounded context:沿着业务语言的「方言边界」切。当「policy(保单)」这个词在两个地方含义不同——新业务里它是「一份待签发的申请」,在 in-force 运营里它是「一份正在收费的合同」——这往往就是一条天然的服务缝。

5贯穿案例

QuoteFlow 该怎么切

把四条判据套到 QuoteFlow 上。结论不是「全拆」也不是「全不拆」,而是分清三类:

Case · QuoteFlow

① 天然该独立的:实时报价 vs 夜间批量重定价

这俩的 NFR 根本是两种生物(Day 1 就埋过):实时报价要 low latency、白天峰值流量大;夜间批量要 high throughput、跑在维护窗口。把它们拆成独立部署,就能各扩各的、各挂各的——白天给报价加机器,夜里给批量加机器,互不拖累。这是「独立扩展」判据的教科书案例。

② 暂时别拆的:报价 ↔ 核保

一次报价里,定价和核保规则评估耦合极紧、要在一个请求里同步完成,还共享费率表/规则版本这类数据。强行拆成两个服务,等于把一次进程内调用换成网络往返,还得跨服务保证「用的是同一个 rate_table_version」——徒增延迟和一致性风险。让它们先做同一个模块化单体里的两个模块,接口画清,日后真要拆再说。

③ 一等公民、横切所有边界的:audit log

无论怎么切,auditability / traceability 都不能被边界切碎。每条报价、每次重算「为什么是这个数」必须能完整复现——所以审计是一条贯穿所有服务的横切关注点(常做成统一的事件流,Day 16),而不是塞进某一个服务里。受监管定价系统拆服务时,第一个要回答的问题往往是:拆完之后,审计链还连得起来吗?

所以 QuoteFlow 的理性路径是:起步用模块化单体(报价/核保/保单/billing 各是清晰模块,共库分 schema),只把「夜间批量重定价」这种 NFR 截然不同的部分第一个切出去独立部署;其余等组织变大、边界变稳、确有独立发布需求时再渐进拆分。下面用伪代码感受一下「模块边界靠接口、而非靠自觉」是什么意思:

// ── 正例:只通过核保模块公开的接口拿结果 ──
interface UnderwritingModule {            // 唯一允许的入口(将来这就是服务的 API)
  assess(applicant, product): RiskDecision
}

function quote(req, underwriting: UnderwritingModule) {
  const decision = underwriting.assess(req.applicant, req.product)  // ✓ 经接口
  if (decision.declined) return reject(decision.reason)
  const premium = price(req, decision.loadings, req.rate_table_version)
  audit.emit({ quote_id, rules_applied: decision.rules, rate_table_version })  // 横切:审计不归任何一边
  return { premium, quote_id }
}

// 进程内调用 → 网络调用,业务代码几乎不动。这就是模块化单体的价值。
★关键要点

今天带走这四句

1

不是「单体 vs 微服务」二选一。模块化单体是常被忽略、却最适合多数系统的默认起点。

2

逻辑边界(代码)和物理边界(部署)是两回事。先把逻辑边界画清,物理拆分等有真实理由再付钱。

3

微服务买的是独立性(部署/扩展/团队/故障隔离),不是性能。它是一种成本,先看组织(康威定律)再定边界。

4

沿业务能力 / bounded context 切,看高内聚、低耦合、数据自治、独立节奏。受监管系统拆服务,先问审计链还连得起来吗。

?今日小测 + 思考题

读完自测一下

Q1团队想「让系统更快」,于是把单体拆成微服务。这个理由站得住吗?
通常站不住。拆服务把进程内调用换成网络调用,单次请求往往更慢不是更快。微服务买的是独立部署/扩展/故障隔离,要更快应先考虑缓存、扩容、优化查询。
Q2「模块化单体」和「单体」的关键区别是什么?
逻辑边界的纪律。两者都是一个部署单元,但模块化单体强制模块间只走公开接口、不许直接碰对方的数据。这让逻辑边界清晰,将来切成微服务时,基本只需把进程内调用换成网络调用。
Q3什么是「分布式单体」,为什么它是最糟的形态?
物理上拆成多个服务,逻辑上却仍紧耦合(服务间频繁互调、共享数据库)。结果是既付了网络/运维/一致性的全部成本,又没换来独立部署/扩展的任何好处——两头不讨好。
带着这两个问题回来讨论

① 在 QuoteFlow 里,除了「夜间批量重定价」,你还会把哪个部分第一个切出去成独立服务?用今天四条判据说说理由。

A→Z术语表

今日术语

Monolith
整个应用作为单一可部署单元,共享一个进程与数据库。
Microservices
系统拆成多个独立部署、各自拥有数据、经网络通信的小服务。
Modular Monolith
单一部署单元,但内部按清晰模块切分、模块间只走公开接口。
Service Boundary
把系统切成服务/模块的那条缝,理想上沿业务能力划分。
Conway's Law
系统结构倾向于长成组织沟通结构的样子。
Bounded Context
DDD 概念:一段业务语言含义自洽的边界,常是天然服务缝。
Distributed Monolith
物理上拆成多服务、逻辑上仍紧耦合的反模式,两头吃亏。
Cohesion / Coupling
内聚:一起变的放一起;耦合:边界间的依赖强度。好边界高内聚、低耦合。
