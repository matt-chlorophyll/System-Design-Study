1为什么要复制

单点的脆弱,和拷贝的代价

到目前为止,QuoteFlow 的 PostgreSQL 一直被画成一个框。一个框意味着:那台机器宕机,整个平台拿不到报价、签不了保单;那块磁盘损坏,保单数据就没了。这在 Day 2 的 availability 语言里完全不可接受。解法看起来朴素:同一份数据,在多台机器上各保留一份拷贝——这就是 replication。

动机有四个:① Availability —— 一台挂了,另一台顶上,服务不断;② 读扩展 —— 报价路径是典型的读密集负载(读费率表、读规则、读客户记录),多副本可以分摊读流量,呼应 Day 6 的 scale-out;③ Durability —— 已确认的写入不因单机损毁而丢失,对保单和 audit log 这是合规底线;④ 低延迟 —— 把副本放到离用户近的地方(QuoteFlow 单国经营,这条权重不高,但跨州灾备同理)。

代价也只有一个,但很深:同一份数据现在有了多个版本的可能。写入怎么传播到所有副本?传播完成之前,读到旧副本的人看到的是什么?网络断开、两边各自更新时,谁说了算?今天剩下的全部内容,都是在回答这一个问题。一句话立住:复制是手段,一致性是账单。

2主流方案

Leader-follower:写一个口,读很多口

最常见的复制架构是 leader-follower(主从,single-leader):所有写入只走 leader,leader 把变更日志(如 Postgres 的 WAL)发给若干 follower 重放;读则可以走 leader 或任意 follower。为什么写只留一个口?因为这直接消解了最难的问题——写冲突。两个节点同时接受对同一行的修改,事后谁说了算?单 leader 让这个问题不存在:写有唯一的全序。

Sync 还是 async:一个 durability vs 延迟的旋钮

leader 把变更发给 follower 之后,要不要等 follower 确认再告诉客户端“写成功”?这是复制里最重要的旋钮:

SynchronousSemi-synchronousAsynchronous
确认时机所有 follower 确认后至少 1 个 follower 确认后leader 落盘即返回
Durability最强:已确认的写绝不丢强:至少两处有拷贝leader 挂时未复制的写丢失
写延迟最高,且受最慢 follower 拖累多一跳网络往返,可控最低
Follower 故障一台挂/慢 → 写全堵死换一台继续,可容忍无影响(它本来就不被等)
QuoteFlow 落点(几乎不用:太脆)保单库、audit log报表/分析用的 read replica

▲ 实务上的主流是 semi-sync:用一跳网络延迟,买“已确认的保单写入至少存在于两台机器”。全 sync 太脆,全 async 对受监管数据太险。

Failover:leader 挂了之后的惊险十秒

leader 宕机后要 failover:选一个 follower 晋升为新 leader,客户端改连它。听起来流畅,实际有两个深坑。坑一,丢写:如果复制是 async 的,旧 leader 上还没传出去的写入就永远丢了——客户看到“投保成功”,保单却不存在,在寿险场景这是合规事故而不只是 bug。坑二,split brain:旧 leader 只是网络抖动“假死”,新 leader 已经晋升,等它回来——两个节点都自认是 leader、都在接受写入,数据从此分叉。所以成熟系统的 failover 要带 fencing(强制旧 leader 退位)机制,而且自动 failover 是一种危险的便利:对核心保单库,很多团队宁可“自动检测 + 人工确认晋升”,慢一两分钟,换不分叉。Day 19 讲共识(Raft、leader election)时会回到“怎么安全地选主”。

3账单明细

Replication lag 与一致性谱系

async follower 总会落后 leader 一点——几毫秒到(极端时)几分钟,这就是 replication lag。lag 存在的每一刻,“从 follower 读”都可能读到旧数据。它制造的异常非常具体:

异常一:读不到自己的写。客户在 QuoteFlow 提交投保申请(写 leader),页面跳转后立刻加载“我的申请”(读 follower)——follower 还没收到这条写,列表是空的。客户的合理结论是“提交失败”,然后再提交一次,你就有了重复申请。需要的保证叫 read-your-writes consistency:常见做法是自己刚写过的数据从 leader 读,或写后一小段时间内强制读 leader。

异常二:时光倒流。两次刷新打到 lag 不同的两个 follower:第一次看到申请“核保中”,第二次变回“已提交”。需要的保证叫 monotonic reads:同一用户的读固定路由到同一副本即可。(还有第三种“因果错乱”——回答比问题先出现——对应 consistent prefix reads,知道名字即可。)

把保证从弱到强排成一条谱:最弱端是 eventual consistency——“停止写入后,所有副本最终会收敛到同一个值”。注意这个承诺有多弱:它没说期限,也没说收敛前你会读到什么。最强端是 linearizability(线性一致 / 强一致)——整个系统表现得仿佛只有一份数据,任何读都能看到最新确认的写。中间是刚才那几个“够用的实用保证”。强一致当然舒服,但每一步都要跨副本协调,延迟和可用性都要掏钱——谱系的意义就在于:按业务挑“刚好够”的那一档,而不是无脑买最贵的。

4没有 leader 的世界

Quorum:用交集对抗不确定

另一派系统(Dynamo 一脉:DynamoDB、Cassandra、Riak)干脆不设 leader:客户端直接把写发给多个副本。协调靠一个优雅的算术:数据存 N 个副本,写入要 W 份确认才算成功,读取要等 R 份响应、取版本最新者。只要 W + R > N,写集合和读集合必有交集——任何一次读,至少会碰到一个拿着最新值的副本。

quorum 读写(伪代码)· N=3, W=2, R=2
// 写:发给全部 N 个副本,等 W 份确认
def write(key, value):
  version = next_version()              // 版本号:谁新谁说了算
  send_all(replicas, PUT(key, value, version))
  wait until acks >= W                 // 2/3 确认即成功,容忍 1 台慢/挂
  return OK

// 读:等 R 份响应,取版本最新者
def read(key):
  responses = send_all(replicas, GET(key))
  wait until len(responses) >= R
  latest = max_by_version(responses)
  if stale_found: read_repair()        // 顺手把旧副本修到最新
  return latest

// 旋钮:W=3,R=1 → 读极快,写又贵又脆
//      W=1,R=1 → 都快,但 W+R=2 ≤ N=3:可能读到旧值(交集没了)

W 和 R 是一对可以按业务调的旋钮——Cassandra 甚至允许每条查询指定 consistency level:QuoteFlow 的 audit 事件写入可以用 QUORUM 保不丢,分析查询用 ONE 换速度。两句省得将来踩坑的话:quorum 给的是“读到最新值”的高概率保证,并不等于严格的 linearizability(节点故障后的 sloppy quorum、并发写冲突等边角会漏);并发写的“谁新”也不总能靠版本号裁决——这正是它放弃单 leader 全序的代价。

5给取舍起名字

CAP 的真话,和 PACELC 的补全

CAP 定理大概是系统设计里被误用最多的三个字母,流行说法“C、A、P 三选二”是错的。P(partition tolerance)不是可选项:网络分区——节点之间断联但各自还活着——在分布式系统里一定会发生,你不能“选择不要它”。CAP 真正说的只有一句话:当分区发生时,你必须在 C(所有节点看到一致数据)和 A(每个请求都得到响应)之间二选一。分区没发生时,C 和 A 可以兼得。所以“我们的系统是 CA”在分布式语境下是句空话——除非你的“系统”是一台单机 Postgres,但那是用放弃分布换的。

CAP 只覆盖了“分区时”这个罕见时刻,日常 99.9% 的时间它什么也没说。PACELC 补上了后半句:if Partition → A or C;Else → Latency or Consistency。平时没有分区,你照样要选:每次写都跨副本同步确认(一致,但慢),还是 async 复制(快,但有 lag)?——这正是第 2 节那个 sync/async 旋钮,PACELC 只是给了它学名。

系统(典型配置)分区时(P→?)平时(E→?)一句话
DynamoDB / Cassandra(默认)A:继续服务,接受不一致L:低延迟优先PA/EL —— 可用性派
HBase / 强一致存储C:拒绝部分请求也要一致C:一致优先PC/EC —— 一致性派
Postgres semi-sync 主从C:分区侧 follower 不接写C 偏向,付一跳延迟≈PC/EC —— QuoteFlow 保单库
Redis 报价缓存(async)A:缓存宁可旧,不可无L:亚毫秒是它存在的意义PA/EL —— 丢了能重算的数据

▲ 同一个 QuoteFlow 里两派共存,而且都是对的:选哪派不取决于技术品味,取决于那份数据“错了/丢了的代价”是什么。

6贯穿案例

QuoteFlow:逐条路径选边站

把今天的概念落到 QuoteFlow 的三条主路径上——你会发现“分区时保 C 还是保 A”在同一个系统里有三个不同答案:

Case · QuoteFlow

保单签发:选 C —— 宁可暂停,不可分叉

Postgres,1 leader + 2 follower,semi-sync。客户点“确认投保”,写必须等至少一个 follower 确认——leader 当场烧掉,保单也已存在于第二台机器。分区发生时,少数派一侧拒绝写入:宁可几分钟签不了新保单,也不能 split brain 之后出现“两边各签了一份、保费还不一样”的保单——那不是 bug,是要向监管报告的事故。failover 用“自动检测 + 人工确认晋升”,慢而稳。

实时报价:选 A —— 旧一点的费率表,好过没有报价

报价路径读密集,从 read replica + Redis 缓存读。这里有个定价系统的隐藏优势:费率表、核保规则、定价模型都是版本化、发布后不可变的(Day 10)。复制的天敌是“变更”——不变的数据没有一致性问题:follower 上读 rate_table v2026-06,永远不会读到“半新不旧”的费率。报价请求钉住版本号计算,连 replication lag 都伤不到它的正确性;lag 唯一的影响是新版本费率表“晚几秒可见”,完全可接受。所以报价路径大胆选 A:分区时用手头的版本继续报,把 quote 连同版本号留痕,事后照样可复现、可审计。

夜间批量重算 与 audit log:各有各的钉法

批量重算读专用 replica,与 OLTP 隔离(Day 11 说过别打主库)——但要钉住快照和版本跑批:8 小时的批次不能前 4 小时用旧假设、后 4 小时用新假设,否则 reproducibility 碎一地。audit 事件写入用 QUORUM 级确认:audit log 的 durability 是合规底线,“写丢了一条审计记录”不可辩解;分析侧读它可以用最弱级别,旧几秒无所谓。

注意贯穿三条路径的判断标准始终是同一个 Day 1 的问题:这份数据错了或丢了,代价是什么?代价是合规事故 → 付延迟买一致和持久;代价是体验略差 → 买可用和速度。一致性从来不是全系统一个开关,而是逐条数据、逐条路径的预算分配。

读完自测一下

Q1客户提交投保申请后页面跳转,“我的申请”列表偶尔是空的,再刷新又出现了。这是什么问题?怎么修?
Replication lag 导致的 read-your-writes 违例。写进了 leader,读却打到还没追上的 follower。修法:用户读自己刚写过的数据时路由到 leader(或写后一小段时间内强制读 leader);同一用户的读固定到同一副本还能顺带拿到 monotonic reads。不需要为此把全系统升级成强一致——按谱系买刚好够的那档。
Q2N=3 的 quorum 系统,为什么 W=2、R=2 能保证读到最新值?把两者都改成 1 会发生什么?
因为 W+R=4 > N=3,鸽笼原理保证读集合与写集合必有交集——任何一次读至少碰到一个持有最新版本的副本,再按版本号取新即可。改成 W=1、R=1 后 W+R=2 ≤ 3:写只落在 R1、读只问 R3 的情况完全可能,读到旧值不再是小概率而是结构性漏洞。换来的是更低的延迟和更高的可用性——对缓存类数据可以,对保单数据不行。
Q3同事说:“我们的保单数据库选 CA,不需要操心分区。”这句话错在哪?
P 不是可选项。只要系统分布在多于一台机器上,网络分区就一定会发生,“选不选 P”不存在——CAP 真正的内容是分区发生时在 C 和 A 之间二选一。说“CA”要么意味着系统其实是单机(用放弃分布换的),要么意味着没为分区设计行为,真分区时会以最糟糕的方式替你“随机选”。正确的提问是:分区时这份数据保哪个?平时(PACELC 的 E)又愿意为一致性付多少延迟?
带着这两个问题回来讨论

① 网络分区把 QuoteFlow 的 leader 和 follower 切成两半:「实时报价」和「保单签发」各应该选 C 还是 A?为什么答案可以不同?再用 PACELC 推一步:没有分区的平时,这两条路径各愿意为一致性付多少延迟?
② 文中说“版本化、不可变的费率表天然免疫一致性问题”。QuoteFlow 里还有哪些数据具有(或可以改造出)这个性质?哪些数据永远不可能有这个性质、只能老老实实付一致性的钱?

A→Z术语表

今日术语

Replication Lag
异步复制下 follower 落后 leader 的时间窗口;窗口内从 follower 读可能读到旧值。
Failover
leader 故障后将某个 follower 晋升为新 leader 并切换流量的过程。
Split Brain
两个节点同时自认是 leader、各自接受写入,导致数据分叉的故障模式。
Linearizability
最强一致性:系统表现得仿佛只有一份数据,任何读都能看到最新确认的写。
Eventual Consistency
最弱承诺:停止写入后所有副本最终收敛;不保证期限,也不保证收敛前读到什么。
Read-your-writes
保证用户总能读到自己刚完成的写入;常以“自己的数据读 leader”实现。
Quorum
N 副本中写 W 份、读 R 份,W+R>N 时读写集合必有交集,从而读能撞上最新值。
PACELC
CAP 的补全:分区时选 A 或 C;无分区的平时,选低延迟(L)还是一致(C)。
