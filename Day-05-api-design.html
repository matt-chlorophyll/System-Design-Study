1API 是一份契约

一旦有人用,它就不再只是你的代码

API(Application Programming Interface)是系统对外暴露的接口:别人不需要知道你内部怎么实现,只要照着这份“合同”发请求、按约定收响应。Day 1 我们画过 QuoteFlow 的 POST /v1/quotes 契约草图——今天我们认真把它当“合同”来设计。

为什么把它叫合同?因为 API 一旦发布、有人开始集成,它就不再是你能随便改的内部代码了。QuoteFlow 的报价 API 一旦给 broker 接入,对方的系统就硬编码了你的字段名、路径、状态码。你这边删一个字段、改一个含义,可能就让对方的夜间对账批量任务在凌晨三点全线报错——而你甚至不知道有谁在用。API 设计的本质,是设计一份“以后还要长期遵守、且很难反悔”的承诺。

所以一个好 API 的几个性质,都是围绕“好用 + 好演进”来的:

好 API 的性质含义对 QuoteFlow 的体现
一致 / 可预测命名、结构、错误格式全站统一所有列表都用同一套分页参数,不用每个接口现学
明确的错误出错用对状态码 + 结构化错误体参数非法 400、限流 429,而不是一律 200 塞 body
可安全重试网络抖动时重发不会出乱子投保申请重试不会签出两张保单
可演进能加功能而不破坏老调用方报价响应加字段,broker 的旧代码照常跑
可审计每次调用可追溯、可解释每条报价带 quote_id 与用的规则版本(合规一等公民)

▲ 注意最后两行——可演进和可审计是今天的两条暗线,后面每一节都会踩到它们。

2四种风格

REST / RPC / gRPC / GraphQL,各管一摊

“API 风格”说的是:你把对外接口组织成什么形状。主流有四种思路,核心差别是“以资源为中心”还是“以动作为中心”,以及谁决定返回哪些数据。

REST —— 以资源为中心

把系统看成一堆资源(名词):报价、保单、申请。用 HTTP 方法(动词)去操作它们:POST /quotes 建报价、GET /policies/123 读保单、DELETE /policies/123 删保单。无状态、用 HTTP 状态码、人类可读。它是公开 API 的事实标准——broker、第三方最容易理解和接入。

RPC —— 以动作为中心

RPC(Remote Procedure Call)把远程调用当成调一个本地函数:repricePolicy(policyId)、runUnderwriting(appId)。围绕“动作”而不是“资源”。适合那些天然是“命令/操作”、套不进 CRUD 资源模型的内部接口。

gRPC —— 高性能的 RPC

gRPC 是 Google 的 RPC 框架:跑在 HTTP/2 上(还记得 Day 4 的多路复用吗),用 Protocol Buffers 做二进制序列化,先写 .proto 契约再生成各语言的强类型代码。优点是快、省带宽、强类型、还支持流式。代价是不那么人类可读、浏览器直连支持差。所以它的主场是内部服务之间,而不是面向公众。

GraphQL —— 让客户端自己点菜

REST 常有两个烦恼:over-fetching(一个接口返回一大坨,客户端只用得上一半)和 under-fetching(一屏要的数据散在 3 个接口,得发 3 次请求)。GraphQL 用单个 endpoint + 一套查询语言解决:客户端在请求里声明自己要哪些字段,服务端按需返回,一次拿全。代价是服务端更复杂、缓存更难做、容易被一个“巨型查询”打爆。

RESTgRPCGraphQL
组织方式资源 + HTTP 动词动作 / 函数调用图 + 客户端声明字段
数据格式JSON(文本,可读)Protobuf(二进制,高效)JSON,字段按需
取数粒度服务端定,易 over/under-fetch服务端定,强类型客户端定,精确
最佳场景公开 API、第三方集成内部微服务间、低延迟高频聚合多源、前端一屏多数据
主要代价多端点、易冗余传输不易调试、浏览器不友好服务端复杂、缓存/限流难

▲ 没有“最好”,只有“最合适”。同一个公司里三种风格常常并存:对外用 REST,内部用 gRPC,前端聚合层用 GraphQL。这正是 Day 1 说的“约束下的取舍”。

QuoteFlow 会怎么混用
  • 对外报价 / 保单 API → REST:broker 和第三方最熟悉,JSON 可读、好调试、好接入。
  • 内部定价、核保、再保服务之间 → gRPC:调用频繁、要低延迟、字段契约要强类型不能传错——昨天讲的 HTTP/2 多路复用在这里直接派上用场。
  • App 首页一屏要拼“保单 + 待缴账单 + 最近报价” → GraphQL / BFF:一次请求按需取齐,省掉移动端的多次跨洲往返(Day 23 的 BFF 会再回到这)。
3幂等性与安全重试

同一个请求发两次,会不会出两张保单

这是 Day 4 埋的伏笔。幂等(idempotent)的定义很简单:同一个请求,执行一次和执行多次,对系统状态的影响完全相同。它之所以是 API 设计的核心,是因为网络天生不可靠:客户端发了请求却没等到响应(可能请求丢了,也可能响应在回来的路上丢了),它无法区分这两种情况,于是只能重试。问题来了——这次重试,是“补发”还是“重复操作”?

HTTP 方法本身就带幂等语义,设计 API 时要顺着它:

方法语义幂等?重试安全吗
GET读,不改状态是(也安全)随便重试
PUT把资源整体设成某个值是重试结果一样
DELETE删除是(删两次还是没了)安全
POST创建 / 触发动作否裸重试会重复创建

▲ PUT /policies/123 {status:"lapsed"} 发几次结果都是“把 123 设为 lapsed”,幂等;而 POST /applications 每发一次就想新建一张申请——这才是真正危险的地方。

那 QuoteFlow 最怕的场景就清楚了:用户点“提交投保”,网络抖了一下没收到响应,前端自动重试——结果签出了两张保单、扣了两次首期保费。解决办法是行业标准做法:idempotency key(幂等键)。客户端为这次“逻辑操作”生成一个唯一 key 放进 header;服务端第一次处理时把 key → 结果 存下来,后续带同一个 key 的请求直接返回当时的结果,不再执行第二次。

POST /v1/applications · 用 idempotency key 防重复
// 第 1 次:客户端为这次"提交投保"生成一个唯一 key
POST /v1/applications
Idempotency-Key: "a3f1c9e2-..."      // 同一逻辑操作复用同一个 key
{ "quote_id": "q_8f3a", "applicant_id": "u_55" }

201 Created
{ "application_id": "app_77", "status": "submitted" }

// 响应没收到 → 客户端超时重试,key 不变 ↓
POST /v1/applications
Idempotency-Key: "a3f1c9e2-..."      // 服务端认出这个 key 处理过了
{ "quote_id": "q_8f3a", "applicant_id": "u_55" }

200 OK                                // 返回第一次的同一结果,不再新建
{ "application_id": "app_77", "status": "submitted" }
//      ↑ 只有一张 app_77,只扣了一次费

几个工程细节值得记:key 由客户端生成(它才知道“这是同一次操作”);服务端要给 key 设一个保存期限(比如 24h);还要防一种坑——同一个 key 配了不同的 body,这通常说明客户端用错了,应该报 422 而不是默默返回旧结果。这套机制 Day 18(幂等、重试、死信队列)还会从异步消息的角度再讲一遍。

4版本化与演进

怎么改 API 才不在凌晨三点炸掉 broker

回到第 1 节的核心焦虑:API 有人用之后就很难改。但业务一定会变——新增产品、调整字段、改规则。关键概念是向后兼容(backward compatibility):老的调用方不改一行代码,也能继续正常工作。分清哪些改动安全,是 API 长寿的关键。

改动安全吗为什么
响应里加一个新字段✅ 通常安全(additive)老调用方忽略不认识的字段即可
新增一个可选的请求参数✅ 安全不传就用默认行为,老调用方无感
删字段 / 改字段名❌ breaking老调用方读不到它依赖的字段
改字段含义或类型❌ breaking(最阴险)编译不报错,但语义变了,悄悄算错
把可选参数改成必填❌ breaking老调用方没传,直接被拒

▲ 黄金法则:只增不改不删(additive only)能走得很远。真要做破坏性变更,就得上版本号。

当不得不做 breaking change,就开新版本,让新老并存、给调用方迁移时间。常见三种放法:放 URL 路径 /v2/quotes(最直观、最常见)、放 header Accept: application/vnd.quoteflow.v2+json(URL 干净但不显眼)、放 query 参数 ?version=2(简单但易被忽略)。多数公开 API 选 URL path 版本,胜在一眼可见、好路由、好缓存。

别把两种“版本”搞混(合规视角)
  • API 版本(/v1):管的是接口契约的形状——字段、路径怎么变。是给调用方看的。
  • 业务版本(rate_table_version: "2026-06",Day 1 见过):管的是这条报价用哪一版费率表/规则算的。是给审计与可复现用的。
  • 对 QuoteFlow,两者都要、且要分开:同一个 /v1 契约下,昨天和今天的报价可能用了不同版本的费率表;监管要的是“这条报价当时用哪版规则、能否原样重算”——这跟 API 怎么演进是两个正交的维度。
5分页与错误设计

列表不能一次吐百万条,出错要说人话

最后两件天天用到、却最容易做随便的事。第一件是分页(pagination):GET /policies 背后可能是百万级 in-force 保单,绝不能一次全返回——会拖垮数据库、撑爆带宽、超时。要分页。常见两种:

Offset 分页Cursor 分页(keyset)
形式?limit=50&offset=10000?limit=50&cursor=eyJpZCI6...
深翻页性能越翻越慢(要跳过前 N 行)稳定快(从游标位置接着走)
数据在变时会漏/会重(行号漂移)稳定,不受新增删除干扰
能跳到第 N 页吗能不能,只能顺序往下
适合小数据集、要页码跳转大数据集、无限滚动、批量遍历

▲ QuoteFlow 的夜间批量重定价要遍历全部 in-force 保单——这种“稳定地从头扫到尾”的场景,cursor 分页几乎是唯一正确选择:offset 在百万行深处又慢又会因为同时有保单签发/失效而漏算重算。(底层为什么 cursor 快,要等 Day 9 索引那天才能说透。)

第二件是错误返回。承接 Day 4:用对状态码(400 参数错、401 没认证、409 冲突、429 限流、500 服务端炸),并配一个全站一致的结构化错误体——让调用方能用程序判断、能给用户显示、还能留痕审计:

一致的错误体 · QuoteFlow 报价校验失败
422 Unprocessable Entity
{
  "error": {
    "code": "INVALID_SUM_INSURED",        // 机器可判断,稳定不变
    "message": "sum_insured 超出该产品上限",   // 人能看懂
    "field": "sum_insured",                  // 定位到具体字段
    "max_allowed": 2000000,
    "request_id": "req_5c1a"               // 可追溯:对上日志,审计/排障
  }
}

注意那个 request_id:它把一次失败的调用钉在了日志里,客服、排障、合规审计都能凭它把整条链路捞出来——这正是 Day 1 那条“auditability 是一等公民”的暗线,落到了错误设计这一层。

为什么这套划分是“合理取舍”而不是“炫技”

对外只暴露 REST,是因为 broker 和第三方的接入成本最低、最好排障——公开契约的首要目标是别人好用、好演进。内部服务间用 gRPC,是因为定价/核保/保单之间调用频繁、要低延迟、字段不能传错,强类型 + 二进制正好对症。移动端那条 GraphQL,是为了省掉跨洲多次往返(呼应 Day 4 的延迟预算)。三种风格不是堆叠,而是每一类调用方的约束不同,就给不同的合同。

合规的线,从契约层就拉好

投保这类“一次不能多”的写操作上 idempotency key;每条报价带 quote_id 和 rate_table_version 做可追溯 + 可复现;错误体带 request_id 让审计能对上日志;面向 broker 的机器通道叠 mTLS(Day 4)。受监管定价里,API 不只是“功能接口”,它是审计链条的第一环。

★关键要点

今天带走这四句

1

API 是一份难反悔的契约:一旦有人用,删字段/改语义都可能在凌晨炸掉调用方。设计时就为演进留余地。

2

REST / gRPC / GraphQL 常并存:对外 REST、内部 gRPC、前端聚合 GraphQL。按每类调用方的约束选,不是非此即彼。

3

幂等性决定能否安全重试。GET/PUT/DELETE 天然幂等;POST 不是,写操作用 idempotency key 防重复(投保不签出两张保单)。

4

演进守则:只增不删不改;破坏性变更才上版本号。分页选 cursor 扛大数据集;错误用对状态码 + 一致错误体 + request_id。

?今日小测 + 思考题

读完自测一下

Q1用户提交投保后没收到响应、前端自动重发,怎么保证不签出两张保单?
用 idempotency key。客户端为这次"提交投保"生成一个唯一 key 放进 header;服务端第一次处理后记下 key → 结果,之后带同一个 key 的重试直接返回原结果、不再执行。因为 POST 不是幂等的,裸重试会重复创建。
Q2给报价响应加一个新字段 risk_band,是 breaking change 吗?那改一个字段的含义呢?
加字段通常不是(additive)——老调用方忽略不认识的字段即可。改含义/类型是,而且最阴险:编译不报错,但语义变了,调用方会悄悄算错。真要做破坏性变更,就开新版本(如 /v2)让新老并存。
Q3夜间批量要遍历百万条 in-force 保单,该用 offset 还是 cursor 分页?为什么?
cursor。offset 在深处要"跳过前 N 行",越翻越慢;而且批量跑的同时有保单签发/失效,行号漂移会导致漏算或重算。cursor 从游标位置接着走,既稳定又快,正适合"从头扫到尾"的遍历。
带着这两个问题回来讨论

① QuoteFlow 的网站、App、broker 三类调用方,你会给他们同一套 API 还是不同风格?各自的取舍是什么?(提示:接入成本 vs 性能 vs 灵活取数)
② 投保 POST /applications 上了 idempotency key——这个 key 该由谁生成、存多久?如果同一个 key 配了不一样的 body,服务端该怎么处理?
