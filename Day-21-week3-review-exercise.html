周主题解决主线的哪一步
第 1 周
基础与思维		需求拆解、量化 NFR、估算、网络、API、负载均衡、缓存步骤 1–4:把「做什么 + 做多好」问清楚,估出规模,定义接口契约,搭好请求进出的前门(LB / 缓存 / API)。
第 2 周
数据层		ACID、索引、建模、NoSQL、复制、分片、事务隔离步骤 5:数据放哪、怎么存、怎么扩。系统的记忆与真相住在这一层——也是最难改、最该想清楚的一层。
第 3 周
分布式与异步		消息队列、Kafka/事件、批 vs 流、幂等、共识、限流弹性步骤 6:当同步、单机扛不住时,用异步解耦把组件拆开,用幂等/重试容错,用共识协调,用限流防雪崩。

▲ 三周不是三堆知识,而是同一条主线越钻越深。今天的练习会一次踩满这三层。

第三周内部也有一条隐线,值得单独串一下,因为它最容易混:

  • queue(队列,Day 15)是「把活儿丢出去、稍后再做」——解耦生产者和消费者,削峰填谷。
  • log / pub-sub(Kafka,Day 16)是「把发生过的事记成一条不可变的流」——一份数据,多个消费者各读各的,可回放。
  • batch vs stream(Day 17)是「攒一大批一次算」对「来一条算一条」——QuoteFlow 的夜间重定价是批,实时报价是流。
  • idempotency(幂等,Day 18)是异步世界的安全带:消息会重复投递,所以「同一条处理两次 = 处理一次」必须成立,否则保费会被重算两遍。
  • consensus(共识,Day 19)解决「谁说了算」:谁是 leader、配置以谁为准。
  • resilience(弹性,Day 20)保证压力下「优雅地少做」,而不是雪崩。
2复用流程

任何设计题,都按这条路走

Day 1 给过六步主线;经过三周,我们可以把它打磨成一套能背下来、临场不慌的动作。面试白板也好、真实立项也好,顺序一样:

五步动作清单
  • ① 厘清需求:列 functional(做什么)+ non-functional(多快/多稳/多可审计)。先别画图。
  • ② 估算规模:QPS、数据量、峰值倍数。一个数能否成立,往往这一步就看出来。
  • ③ 定接口:对外的 API / 对内的事件契约长什么样。把 NFR「焊」进契约。
  • ④ 画高层架构:主要组件 + 数据流。哪里同步、哪里异步、数据落在哪。
  • ⑤ 找瓶颈、标取舍:哪会先垮?用缓存/分片/队列/限流补;每补一处,明说代价。

注意第 ⑤ 步的「明说代价」——这是区分「画了个框图」和「做了个设计」的关键。下面的练习,每个决定我们都会顺手标出它换来什么、又牺牲了什么。

3设计练习

QuoteFlow 夜间批量重定价子系统

Exercise · QuoteFlow

题目

QuoteFlow 有数百万张 in-force(有效)寿险保单。每晚维护窗口里,要对其中一大批保单做重定价 / 重估:因为保单到了周年、触发 CPI indexation、或者精算团队发布了新版费率表 / 假设。要求:在窗口内跑完、每张保单只重算一次(算两次会乱收费)、用的费率版本要钉死可复现、每条结果留完整审计痕迹,而且这个夜间批跑绝不能拖慢白天的实时报价。

① 厘清需求

Functional:选出今晚要重算的保单 → 对每张拉取对应版本的费率/规则/假设 → 计算新保费与准备金 → 落库、生成 billing 变更、写审计日志 → 把结果上报下游(reserving / 再保 / 分析)。

Non-functional:高吞吐(百万级 / 几小时窗口);exactly-once 的业务效果(每单恰好重算一次);reproducibility(钉版本,明年能一字不差重跑);auditability(每条为什么是这个数,留痕);隔离(批跑不能吃掉实时报价的资源)。

② 估算规模(back-of-envelope)

设 200 万张保单,维护窗口 4 小时 = 14,400 秒。要求平均吞吐 ≈ 2,000,000 / 14,400 ≈ 139 单/秒。但单条重算要拉费率、跑模型、写多张表,假设单 worker 约 20 单/秒,则需要 139 / 20 ≈ 7 个并行 worker——留余量按峰值 2× 配 ~16 个 worker。这个数立刻告诉你:这是个能水平扩展的并行批问题,不是单机 for 循环。

③ 定契约:用「事件 / 任务」而非同步调用

关键判断:重定价是批 + 异步(Day 15/17),所以对内契约不是 REST 请求,而是一条任务消息。每张待重算保单 = 队列里的一条 task,带上钉死的版本号和一个幂等键:

repricing_task.json · 夜间重定价任务消息(示意)
{
  "task_id":        "rprc_2026-06-21_p_8f3a91",  // 幂等键 = run_date + policy_id
  "policy_id":      "p_8f3a91",
  "run_id":         "nightly_2026-06-21",
  "reason":         "ANNIVERSARY+CPI",
  "rate_table_version":   "2026-06",   // ← 钉死版本 = 可复现
  "assumption_set":       "AS_2026Q2",  //   整批共用一份快照
  "enqueued_at":    "2026-06-21T02:00:00Z"
}

把版本号写进任务本身(而不是让 worker 去读「当前最新版本」),是 reproducibility 的命门:整批共享同一个不可变快照,即使精算团队半夜发了新版,今晚这批也不受影响。这正是 Day 1「把 NFR 焊进契约」的延续。

整条链路:调度器(谁来跑、跑哪些)→ 选单器(查出今晚的保单,按 policy_id 分片灌进队列)→ 队列 → 一组幂等的 worker 并行消费 → 写库 + 审计 + 下游事件。下图把它画出来:

限流 + DLQ

最后落一段 worker 的核心伪代码,把幂等 + 钉版本 + 审计三件事放在同一个事务边界里——这是整道题的灵魂:

worker.py · 幂等重定价消费者(示意)
def handle(task):
    # 1) 幂等闸门:这条 task_id 处理过就直接跳过(消息可能重投)
    if audit.already_done(task.task_id):
        return ack()                      # 重复 → 安全地确认掉

    # 2) 读“钉死的版本”,而不是当前最新 → 可复现
    rates = snapshot.get(task.rate_table_version)
    asmp  = snapshot.get(task.assumption_set)

    new_premium = reprice(task.policy_id, rates, asmp)

    # 3) 一个事务里:写结果 + 写审计 + 标记 task 完成(原子)
    with db.tx(shard_of(task.policy_id)):
        policies.update(task.policy_id, new_premium)
        audit.record(task.task_id, task.run_id,
                     inputs=[task.rate_table_version, task.assumption_set],
                     result=new_premium)        # 为什么是这个数,留痕

    events.emit("policy.repriced", task.policy_id)  # 通知下游(再保/分析)
    return ack()

注意第 3 步:结果、审计、完成标记必须在同一个事务里(Day 14)。否则可能「钱改了、审计没写」或「算完了、没标记完成 → 下次又算一遍」。把幂等键的写入和业务结果绑成原子,是异步系统正确性的地基。

读完自测一下

Q1为什么把 rate_table_version 写进任务消息,而不是让 worker 去读「当前最新版本」?
为了 reproducibility(可复现)。整批共享一份不可变快照——即使半夜精算发布了新版费率,今晚这批仍用钉死的旧版,明年原样重跑结果一致。若读「最新」,同一批不同时刻处理的保单可能用上不同版本,审计与复现全乱。
Q2队列「至少投递一次」,worker 凭什么保证「每张保单只重算一次」的业务效果?
靠幂等。用 task_id = run_date + policy_id 当幂等键,处理前先查「这条做过没」,做过就直接 ack 跳过;并把完成标记和业务结果写进同一个事务。这样消息重投也只生效一次——这是 exactly-once「效果」,而非传输层真的只投一次。
Q3如果不用队列,直接让选单器同步循环调用计算服务,会丢掉哪些好处?
丢掉解耦、削峰和隔离。同步循环里,选单器要等每次计算返回,慢一个卡一串;无法独立水平扩展 worker;最危险的是批跑会和白天实时报价抢同一批资源,夜间作业一重,300ms 报价 SLA 就可能被拖垮。队列把两条路径物理隔开。
带着这两个问题回来讨论

① 夜间批跑到一半,worker 集群崩了一半、窗口也快到点了——你怎么设计才能安全地从断点续跑,而不是从头再来、也不重复收费?
② 如果把这个「攒一晚一次算」的批,改成「保单一到周年就实时重算」的流(stream),QuoteFlow 会得到什么、又要多付出什么?(这正是 Day 17 批 vs 流的现实抉择)

A→Z术语表

今日术语

Batch Processing
攒一大批数据后一次性集中处理,优化吞吐而非延迟(如夜间重定价)。
Worker Pool
一组并行消费任务队列的处理进程,可水平扩展以提高吞吐。
Idempotency Key
唯一标识一次操作的键,用于去重,保证重复执行只生效一次。
Reproducibility
钉死输入版本(快照),使同一计算日后能一字不差重跑出相同结果。
Snapshot
某一时刻数据的不可变副本(如费率/假设),供整批共享、保证一致。
Dead Letter Queue
反复处理失败的消息被转入的旁路队列,待人工或补偿流程处理,避免阻塞主流程。
Shard Skew
分片负载不均——某些分片数据/请求远多于其它,拖慢整体的并行作业。
Transactional Boundary
把若干写操作绑成一个原子单元的范围,要么全成功要么全回滚。
