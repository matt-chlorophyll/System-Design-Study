1地基：容器与镜像

「在我机器上能跑」的终结

部署最古老的痛，是环境漂移：开发机能跑、测试机能跑，一上生产就崩——因为 Python 版本差了一个小号、某个系统库没装、环境变量不一样。容器把这个问题从根上解决：把应用连同它的运行环境(依赖、库、配置)一起打包成一个标准化的单元，到哪都一样。

先钉死两个常被混用的词。镜像(image) 是一个静态、只读的打包产物——像一张「光盘」，里面是代码 + 依赖 + 启动指令，构建一次、内容固定。容器(container) 是镜像跑起来的一个运行实例——像光盘放进播放器后正在播放的那一份。一个镜像可以同时启动出几十个一模一样的容器。

容器最关键的性质是不可变(immutable)：你不在跑着的容器里改东西。要改，就重新构建一个新镜像、打一个新 tag、再用它启动新容器。这条纪律带来三件好事：每个版本都有一个确定的、可寻址的产物(镜像摘要 digest)；回滚变成「把流量切回上一个镜像 tag」这么简单；而且——对 QuoteFlow 尤其重要——你能精确说出「2026 年 6 月那批报价，跑的是哪个镜像、哪个 commit」。

容器 ≠ 虚拟机
  • VM 虚拟化的是整台硬件，每个 VM 自带一套完整 OS，启动以分钟计、占几个 GB。容器共享宿主机内核、只隔离进程与文件系统，启动以秒/毫秒计、占几十 MB。这份「轻」正是能横向扩到成百上千份、能快速滚动替换的前提——也是编排得以存在的物理基础。
2编排：声明，而非操控

你说「我要 12 个」，编排器负责始终是 12 个

一个容器好管。但生产上你有几十个服务、每个跑几十份、分布在一堆机器上，还要处理：某台机器宕了上面的容器怎么办？流量涨了怎么自动加份数？发新版怎么逐个替换不中断？手动管这些是不可能的。这就是编排器(orchestrator) 的活，事实标准是 Kubernetes(K8s)。

编排的核心思想是声明式(declarative)：你不写「先停这个、再启那个」的操作步骤，而是描述期望的最终状态——「report-pricing 这个服务，我要 12 份，用镜像 v2.4.0，每份给 2 核 4G」。编排器持续比对期望状态和实际状态，不一致就自己想办法拉平：挂了一份就再起一份，机器没了就调度到别处。这个「持续校正」的循环叫 reconciliation(调谐)。

几个会反复遇到的概念，先建立词汇：Pod 是 K8s 调度的最小单位(通常裹着一个容器)；ReplicaSet 维持「N 份副本」；Deployment 管「怎么从旧版本滚动到新版本」；Service 给一组会变动的 Pod 一个稳定的访问入口(配合昨天的负载均衡)。你声明 Deployment，剩下的编排器全包了。

3流水线：CI ≠ CD

从一次 commit 到生产，路上有几道闸

这两个缩写老被连在一起说，但解决的是不同问题。CI(Continuous Integration，持续集成) 管的是代码合并那一侧：每次有人推代码，自动构建 + 跑测试 + 静态检查，确保新改动没把主干弄坏。它的目标是「频繁、小步地合并，并立刻知道有没有破」。

CD 有两层含义，注意区分：Continuous Delivery(持续交付) 指流水线自动把通过 CI 的产物打包好、推到「随时可以上生产」的状态，但最后按钮是人点的；Continuous Deployment(持续部署) 更进一步，连最后那下也自动——通过所有关卡就直接上生产，无人工干预。受监管的金融/保险系统，绝大多数停在持续交付：要保留一道人工审批和审计签字。

一条典型流水线，就是一串越往后越接近生产、越难回头的关卡。任何一关红了，整条线停下，产物不再前进。这正是「快速发布」与「不翻车」能同时成立的原因——速度来自自动化，安全来自每道闸。

.ci/pipeline.yaml · QuoteFlow 报价服务流水线(示意)
# 每次推到 main 触发；任一 stage 失败则整条停下
stages:
  - build:                       # ── CI ──
      docker build -t quoteflow/pricing:${GIT_SHA} .
  - test:
      run: unit + 核保规则回归 + 合同测试      # 算得对是底线
      run: pricing-replay --golden-set     # 用历史样本验复现性
  - scan:
      run: 镜像漏洞扫描 + 依赖审计           # 安全闸(承接 Day 25)
  - push:
      docker push quoteflow/pricing:${GIT_SHA}  # 不可变产物入库
  - deploy_staging:                # ── CD：自动到预发 ──
      kubectl set image deploy/pricing app=...:${GIT_SHA}
  - approve:                       # ⛔ 人工审批 + 审计签字
      gate: "pricing-lead + compliance"     # 持续交付，非全自动部署
  - deploy_prod:
      strategy: canary                # 见下一节

留意两件 QuoteFlow 特有的事：pricing-replay --golden-set 用一批历史报价样本跑新代码、比对结果，守住reproducibility(定价不能因为重构悄悄变了数)；而 approve 这道人工闸，就是把合规签字嵌进发布流程，让「谁批准了这次上线」本身可审计。

4发布策略与回滚

新版本不是「啪」一下全换，而是慢慢放量

产物到了生产门口，最后一个问题：怎么把流量从旧版本切到新版本？一次全切风险最大——万一新版本有 bug，所有用户瞬间中招。成熟做法是控制 blast radius(爆炸半径)，三种主流策略：

滚动发布(rolling)：编排器默认做法，逐批用新 Pod 替换旧 Pod(替几个、健康了、再替几个)，全程保持总量在线。简单、省资源，但新旧版本会短暂共存，且回滚要再滚一轮、不够快。

蓝绿发布(blue-green)：同时跑两套完整环境——蓝(旧)在服务，绿(新)在旁边备好。验证 OK 后，负载均衡一刀把流量从蓝切到绿。优点是切换瞬间完成、回滚就是把流量切回蓝(秒级)；代价是要双倍资源。

金丝雀发布(canary)：先把一小撮流量(比如 1%→5%→25%)导到新版本，盯着指标(错误率、延迟、业务正确性)，没问题才逐步放大，有问题立刻收回。它把「上线」变成一次受控的实验，是高风险变更的首选。名字来自矿工带下井的金丝雀——它先出事，矿工就知道该撤了。

三者不是互斥的，常组合：用金丝雀控制放量节奏、底层靠 Deployment 的滚动机制替换 Pod。但无论哪种，回滚都是一等公民——因为产物不可变，「回滚」本质就是把流量指回上一个已知良好的镜像，而不是手忙脚乱地反向改代码。一个健康的团队，回滚应该比修复更快、更不需要思考。

策略怎么切资源开销回滚速度适合
滚动 Rolling逐批替换 Pod低(几乎不额外)慢(要再滚一轮)低风险常规更新
蓝绿 Blue-Green整体一刀切换高(双倍环境)快(切回旧环境)要瞬间切换、强回滚保障
金丝雀 Canary按比例渐进放量中快(收回小流量)高风险变更、要边发边观测

▲ 选择本质是 trade-off：用多少资源、换多快的回滚和多小的爆炸半径。没有「最好」，只有「这次变更的风险配得上哪一档」。

5贯穿案例

QuoteFlow 上线一个新定价模型版本

把今天四块拼起来。假设精算团队更新了一版定价模型(新的风险评分曲线)，要推到生产。这不是普通的发版——它会改变客户拿到的保费数字，所以风险和合规要求都顶格。

Case · QuoteFlow 发布新定价模型

从 commit 到生产

① 不可变产物：模型代码 + 依赖打成镜像 pricing:v2.4.0，并钉死它引用的 rate_table_version 与 model_version。这个镜像 = 一个能精确复现的定价单元。

② 流水线把关：CI 跑核保规则回归 + golden-set replay(确认新模型在历史样本上的变化全都是预期内的，没有意外漂移)；安全扫描过关；预发环境自动部署后，pricing lead + compliance 双签才放行——这道人工闸本身写进审计日志。

③ 金丝雀放量：先 1% 真实报价流量走新模型，盯三类指标——技术(p99 延迟、错误率)、业务(报价分布有没有异常偏移)、合规(每条报价的 model_version 都留痕)。稳了再 5%→25%→100%。

④ 回滚预案：任一阶段指标异常，一键把流量切回 v2.3.x。因为镜像不可变、版本号钉死，回滚后能立即说清「这一刻起，报价又回到了哪个模型」——监管要的就是这种可追溯性。

注意一个寿险定价特有的转折：在大多数互联网产品里，金丝雀盯的是技术指标(别变慢、别报错)。但 QuoteFlow 还得盯业务正确性——新模型即使又快又不报错，如果它让某个客群的保费系统性地偏了，那也是必须中止的「事故」。发布的成功标准，本身就带着合规的维度。

读完自测一下

Q1镜像(image)和容器(container)的区别是什么?
镜像是静态只读的打包产物(代码+依赖+启动指令，像光盘)；容器是镜像跑起来的一个运行实例(像正在播放的那一份)。一个镜像可启动出多个一模一样的容器。镜像的不可变性质，是版本可追溯和快速回滚的基础。
Q2「声明式编排」和你手写一串「先停旧的、再启新的」脚本，本质差别在哪?
声明式你只描述期望的最终状态(要 12 份、用某镜像)，编排器持续比对实际状态并自动校正(调谐 / reconciliation)：挂了自己补、机器没了自己挪。命令式脚本只跑一遍那串步骤，机器之后再坏掉它不会管。声明式带来的关键能力是自愈。
Q3QuoteFlow 要上一版新定价模型，三种发布策略你倾向哪个?为什么?
倾向 金丝雀。新模型会改变客户保费，风险高，需要边放量边观测——而且不只看延迟/错误率，还要盯业务正确性(报价分布有没有异常偏移)和合规留痕。先 1% 验证、有问题立刻收回，爆炸半径锁在最小。蓝绿也行(回滚极快)但要双倍资源且是「一刀切」、不利于渐进观测业务指标。
带着这两个问题回来讨论

① QuoteFlow 的夜间批量重定价(百万保单)和实时报价 API，要不要用同一套发布策略?批处理作业「金丝雀放量」该怎么理解、还是说它需要完全不同的发布思路?
② 「持续部署(全自动到生产)」在受监管的寿险定价里到底能不能用?如果不能全自动，那道人工闸具体该卡在流水线哪一步、由谁签、留什么痕?
