1问题:为什么需要共识

当「真相」要存在多个节点上

到目前为止,我们很多设计都依赖某个单一权威:一个 leader 数据库(Day 12)、一张去重表(Day 18)。单点的好处是「谁说了算」毫无歧义——只有它一个嘴。坏处也很直接:它一挂,整个系统就停摆。

于是我们想把这个权威做成一组节点(通常 3 或 5 个),挂掉一两个还能继续。但麻烦立刻来了:这组节点之间靠网络通信,而网络会延迟、丢包、分区。于是出现一个要命的问题——它们怎么保证大家认的是同一个「真相」?

最危险的失败模式叫 split-brain(脑裂):网络把 5 个节点切成「3 + 2」两堆,两边都以为对面死了、都自封 leader、都开始接受写入。等网络恢复,你有两份互相冲突的真相,无法合并。对 QuoteFlow 来说,这可能意味着同一批保单被两个节点各重算了一遍、各写了一套保费——审计时根本说不清哪个数算数。

共识算法(Paxos、Raft 等)就是为根治这件事而生。它给的保证可以浓缩成一句:即使节点会宕机、网络会延迟和分区,只要多数节点还活着并能互通,这组节点对外就表现得像「一个永不自相矛盾的节点」。注意它不解决拜占庭故障(节点撒谎/被攻陷)——它假设节点会宕机、会慢,但不会恶意造假。

共识 ≠ 你日常会手写的东西
  • 请把共识算法当成地基设施:你几乎永远不会自己实现 Raft,而是用现成的协调服务(etcd / ZooKeeper / Consul)或内建共识的数据库。今天的目标是看懂它给你什么保证、代价是什么,从而知道在 QuoteFlow 里该把哪些「必须只有一个答案」的状态托付给它。
2Raft 概念级

把共识拆成三件能讲清的事

Paxos 以「难懂」著称;Raft 是 2014 年专门为可理解性设计的等价方案,今天工业界的协调服务大多用它。Raft 把共识拆成三块,逐块看就不神秘了。

① 角色与任期(term)

每个节点在任一时刻是三种角色之一:Leader(唯一能接收写入的)、Follower(被动复制 leader 的日志)、Candidate(选举期间的临时状态)。时间被切成一段段term(任期),每个 term 是一个递增的编号,最多有一个 leader。term 就像「第几届」——它是 Raft 判断信息新旧、识别过期 leader 的逻辑时钟。

② Leader election(选主)

Leader 会周期性地向所有 follower 发心跳(heartbeat)。每个 follower 有一个随机的 election timeout(比如 150–300ms);只要在超时前收到心跳,就继续当 follower。一旦超时没收到——它认为 leader 挂了,于是:把自己 term +1、变成 candidate、给自己投一票,并向其他节点拉票(RequestVote)。谁先拿到多数票(majority),谁就成为新 leader,立刻开始发心跳压住其他人。

这里有个精巧的细节:election timeout 是随机的。如果所有 follower 同时超时、同时拉票,选票会被瓜分、谁也拿不到多数,只能重选——随机化让某个节点大概率先超时、抢跑成功,把「选不出来」的概率压到极低。

③ Log replication(日志复制)

客户端的每个写操作,leader 先追加到自己的日志(append to log),然后并行发给所有 follower。当多数节点都确认写入,leader 才把这条日志标记为 committed(已提交)、应用到状态机、并回复客户端「成功」。注意顺序:先落到多数派,再算数。这正是它在故障下不丢已确认数据的根本原因。

3多数派:为什么是「半数 + 1」

quorum 是脑裂的解药

Raft(以及几乎所有共识算法)的安全性,全压在一个朴素的算术事实上:两个不同的「多数派」一定有交集。5 个节点里,任意两个 ≥3 的子集必然共享至少一个成员。

这句算术直接根治了脑裂。回到那个「3 + 2」分区:

  • 3 个节点那边:能凑齐多数(3 ≥ 多数 3)→ 可以选出 leader、可以提交写入,正常服务。
  • 2 个节点那边:永远凑不齐 3 票 → 选不出 leader、拒绝任何写入,主动「躺平」等网络恢复。

于是无论网络怎么切,最多只有一边能动,两份冲突真相不可能同时产生。代价也清楚:少数派那边宁可不可用,也不愿不一致——这是 Day 12 CAP 里 CP 取向的活生生例子。共识系统在分区时选择 C 而非 A。

顺带说明一个常被问的点:为什么集群节点数偏好奇数(3、5、7)? 因为容错能力由「多数派门槛」决定。3 节点和 4 节点都只能容忍挂 1 个(4 节点的多数是 3,挂 1 还剩 3 能动,挂 2 就只剩 2 < 3),但 4 节点要多养一台机器、还多一个故障点——白花钱不提升容错。所以用奇数。

集群规模多数派门槛能容忍宕机数
3 节点21
4 节点31 (没比 3 强,却更贵)
5 节点32
7 节点43 (更耐故障,但每次写要等更多确认 → 更慢)

▲ 节点越多越耐故障,但每次提交要等的确认也越多 → 写延迟上升。多数生产集群停在 3 或 5。

4选主时序

一次 leader 故障到恢复,发生了什么

把上面的机制串成一条时间线。假设 5 节点集群,leader(N1)突然宕机:

raft-leader-election.log · 一次故障切换(示意)
// term 8:N1 是 leader,正常发心跳
t=0ms    N1(leader,term8) ──heartbeat──> N2 N3 N4 N5   // 一切正常

// N1 宕机,心跳停止
t=20ms   N1 ✗ crash                                    // 不再发心跳

// follower 各自的随机 election timeout 开始倒数
t=190ms  N3 election_timeout 先到 → 成为 candidate
         N3.term = 9                              // 任期 +1
         N3 vote for self, 广播 RequestVote(term=9)

// 其他节点检查:term 9 比自己新、且本任期还没投过 → 投给 N3
t=205ms  N2 → vote N3   ✓
         N4 → vote N3   ✓                              // N3 已得 3 票(含自己)

// 3 票 ≥ 多数(3)→ N3 当选,立刻发心跳压住选举
t=210ms  N3(leader,term9) ──heartbeat──> N2 N4 N5

// N1 复活,带着过期的 term 8 回来
t=900ms  N1 revived, 自称 leader(term8)
         N1 收到 N3 的 heartbeat(term9 > 8)
         → N1 退位为 follower,服从 term9 的 N3   // 旧 leader 自动让位

关键看最后一段:term 是个单调递增的逻辑时钟。复活的旧 leader 一看到更高的 term,立刻知道「世界已经换届了」,自觉退位。这就是为什么 Raft 里不可能出现两个 leader 同时被大家认可——任何写入都带 term,带着旧 term 的写入会被多数派直接拒绝。整个故障切换通常在几百毫秒到一两秒内完成,期间集群短暂无法写入(但读旧值可继续)。

5协调服务

etcd / ZooKeeper:把共识当服务用

你不会自己写 Raft,而是用一个把共识封装好的协调服务(coordination service)。最常见的是 etcd(Raft,Kubernetes 的大脑)和 ZooKeeper(ZAB 协议,Kafka/Hadoop 生态常用),还有 Consul。它们对外就是一个强一致的小型 KV 存储,但内部用共识保证你写进去的每个值,所有客户端读到的都是同一份。

它们典型替你扛四类活:

用途解决什么QuoteFlow 里的例子
Leader election一堆对等的 worker,选出唯一一个来干「只能一个干」的活夜间批量重定价:多个 batch 节点里只让一个当 coordinator
分布式锁跨进程互斥:同一资源同一时刻只有一个持有者某个 in-force 保单正在被重算时,锁住它防止并发改写
配置中心一份权威、强一致的配置,改一次全集群可见「当前生效的 rate_table_version」放这里,所有节点读到同一个
服务发现谁在线、地址是什么,动态注册与感知报价服务实例上线/下线,网关据此更新路由

实现选主和锁的关键原语,是协调服务提供的两样东西:租约(lease/TTL) 和 原子的 compare-and-swap。下面用 etcd 风格的伪代码演示「抢锁当 leader、靠租约自动释放」——这正是 QuoteFlow 夜间批量需要的:

elect_batch_coordinator.py · 用 etcd 选主(示意)
def try_become_coordinator(node_id):
    # 1) 申请一个 10 秒租约;只要不续约,key 会自动过期
    lease = etcd.grant_lease(ttl=10)

    # 2) 原子写:仅当 key 不存在时才写成功(compare-and-swap)
    ok = etcd.put_if_absent(
        key="/quoteflow/nightly-reprice/leader",
        value=node_id,
        lease=lease,
    )

    if not ok:
        return "follower"     # 已有别人占住 → 我当 follower,不跑批

    # 3) 抢到了 → 我是 coordinator;必须持续续约,否则租约一过
    #    key 自动消失,其他节点会立刻补位(防止我假死后无人接管)
    while still_alive:
        etcd.keep_alive(lease)      # 心跳续约
        run_nightly_reprice_batch()
    return "leader"

注意租约 + 自动过期这个组合解决了一个很微妙的故障:如果 coordinator 不是干净地崩溃,而是卡死/网络孤立(还以为自己是 leader,但没人能联系它)。靠租约,它一旦停止续约,key 在 10 秒后自动消失,其他节点马上补位——不需要任何人去「确认它真的死了」。这就是为什么协调服务比你手搓一个「在数据库里插一行当锁」要稳得多:数据库那行不会因为你卡死而自动消失。

别把协调服务当通用数据库
  • etcd/ZooKeeper 为强一致和高可靠优化,不是为吞吐优化:每次写都要走一轮共识(落到多数派),写很贵、容量很小。只往里放「少量、关键、必须全局一致」的元数据——leader 是谁、配置版本、锁。千万别把业务数据(保单、报价记录)塞进去,那是关系库/对象存储的活。
6贯穿案例

共识在 QuoteFlow 的两个落点

QuoteFlow 里真正需要共识的地方不多,但每一个都「错了会出大事」——尤其在可审计这条红线下。

Case · QuoteFlow

① 夜间批量重定价:必须「只有一个在跑」

夜间要对百万级 in-force 保单做重定价(周年、CPI indexation、费率表变更)。为了高吞吐,跑批的是一组 worker 节点。但「谁来切分任务、谁来标记进度、谁来收尾对账」这件协调工作,必须只有一个 coordinator——否则两个节点各跑一遍,同一批保单会被重算两次、写两套保费,审计时根本对不上。用 etcd 选主:抢到租约 key 的当 coordinator,挂了租约自动释放、别人秒级补位。批次本身的幂等(Day 18)是第二道保险:即使切换瞬间有重叠,幂等键也能让重复无害。

② 版本化配置:「当前生效的费率表」要全局一份

QuoteFlow 的 rate_table_version、underwriting_rules_version 是定价的命脉,而且和 auditability 死死绑定:必须保证所有报价节点在同一时刻读到的是同一个生效版本,绝不能新旧混用、算出两个口径的保费。把「当前生效版本指针」放进 etcd——一次原子切换,全集群强一致可见;切换本身也留痕,谁在何时把生效版本从 2026-05 切到 2026-06,可回溯。真正的费率表数据仍存关系库,etcd 里只放那个「指向哪一版」的小指针。

一个值得记住的设计判断:共识用在「控制平面」,不用在「数据平面」。选主、配置指针、锁——这些低频、关键、要求全局一致的协调决策交给共识;而海量的报价计算、保单读写这些数据流量,走常规的负载均衡 + 数据库分片(Day 6、Day 13)。把共识用在错的层,会直接把它做成系统瓶颈。

★关键要点

今天带走这四句

1

共识让一组节点表现得像一个永不自相矛盾的节点:挂掉少数还能服务,且永远不产生两份冲突真相。代价是分区时选 C 牺牲 A。

2

Raft = 选主 + 日志复制 + 多数派。随机超时选出 leader,写入要落到多数节点才算 commit,term 让过期 leader 自觉退位。

3

多数派(quorum)是脑裂的解药:两个多数派必有交集,所以分区时最多一边能动。集群用奇数(3/5),写延迟随节点数上升。

4

你不手写共识,而用 etcd/ZooKeeper。只往里放少量关键元数据(leader、配置指针、锁),靠租约实现「死了自动释放」。

?今日小测 + 思考题

读完自测一下

Q1一个 5 节点的 Raft 集群,最多能容忍几个节点同时宕机仍正常工作?
2 个。多数派门槛是 3(半数+1),所以只要还剩 ≥3 个能互通,就能选主和提交写入。挂第 3 个就只剩 2 < 3,集群停止接受写入(保一致性、牺牲可用性)。
Q2Raft 的 election timeout 为什么要做成随机的?
避免选票被瓜分(split vote)。如果所有 follower 同时超时、同时拉票,可能谁都拿不到多数,只能反复重选。随机化让某个节点大概率先超时、抢先拉票成功,把「选不出来」的概率压到极低。
Q3一个旧 leader 宕机后又复活,带着过期的 term 回来,会不会和新 leader 冲突?
不会。term 是单调递增的逻辑时钟。旧 leader 一收到带更高 term 的心跳/消息,立刻知道自己过期,自动退位为 follower。任何带旧 term 的写入也会被多数派直接拒绝,因此不可能出现两个被认可的 leader。
Q4为什么把分布式锁交给 etcd,比在关系库里「插一行当锁」更可靠?
因为租约会自动过期。etcd 的锁 key 绑定一个 TTL 租约,持有者必须持续续约;一旦它卡死/网络孤立(不是干净崩溃),停止续约后 key 自动消失,别人秒级补位——无需任何人去判定它「真的死了」。数据库里那行锁不会因为持有者假死而自动释放,容易死锁。
带着这两个问题回来讨论

① QuoteFlow 夜间批量重定价靠 etcd 选了 coordinator,可它续约的网络刚好抖了一下、租约过期,新 coordinator 被选出来——但旧的其实还活着、还在跑批。光靠选主够不够防止「重算两遍」?还需要昨天(Day 18)的哪样东西兜底?
② 既然共识写很贵,为什么我们仍坚持把「当前生效的 rate_table_version」放进 etcd,而不是放进那台又快又熟悉的关系库?这里 auditability 和 consistency 各自要的是什么?
