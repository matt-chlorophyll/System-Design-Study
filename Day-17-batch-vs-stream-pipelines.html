1分水岭

有界 vs 无界:一切的起点

批处理和流处理最干净的区分,不是「快和慢」,而是数据有没有尽头。Batch(批处理)处理的是一份 bounded(有界)的数据集:它有明确的开始和结束——比如「6 月 16 日全部 in-force 保单」。你知道总量,可以等它到齐,一次性扫一遍算完,然后任务结束、进程退出。

Stream(流处理)处理的是 unbounded(无界)的数据:事件一条接一条永远来,没有「到齐」这回事。所以流处理程序是一个常驻、永不退出的进程,来一条(或一小撮)就地处理、立刻产出结果,然后等下一条。它不能说「等全部数据来了再算」——因为永远等不到全部。

这个区别一旦看清,其他特性都是它的推论。Batch 因为能看到全量,适合做需要全局视野的重活(全表重算、复杂聚合、训练模型),代价是高延迟:结果要等整批跑完才有,通常以小时计。Stream 因为来一条算一条,能做到秒级甚至毫秒级延迟,代价是每条只能看到「眼前这点」上下文,做全局聚合要费很大劲(后面第 4 节会看到为什么)。

一个反直觉的统一视角
  • 其实 batch 只是 stream 的一个特例:把无限的流「切一段、规定它有头有尾」,就得到一个 batch。反过来,流处理就是「永不结束的 batch」。现代引擎(如 Flink、Spark Structured Streaming)正是用同一套编程模型同时表达两者——这也是为什么今天要把它们放一起讲。
2贯穿案例

QuoteFlow 的夜间批量重定价,是一条 batch pipeline

QuoteFlow 白天做的是实时报价(Day 2 那条 p99 < 300ms 的路径)——但 in-force 保单的重定价 / 重估是另一回事。每晚维护窗口里,系统要把上百万张在保保单按新假设重算一遍:周年调整、CPI indexation、费率表换版、精算假设变更。这件事天然是 batch——它处理一份有界数据(「昨天收盘时的全部 in-force 保单」),要全局一致地算完,而且延迟不敏感、吞吐才是王道(只要在天亮前的窗口内跑完即可)。

Case · QuoteFlow 夜间重定价 pipeline

把它拆成一条标准的数据管道,四个阶段首尾相接:

① Extract(抽取)——从 in-force 保单库、版本化 rate table、核保规则、CPI 指数表里,圈定「这一批要算的快照」。这里钉住版本是合规命脉:整批必须基于同一组假设版本,绝不能算到一半费率表换了。

② Transform / Compute(计算)——对每张保单套用定价模型,算出新保费、新准备金、周年变化。百万级 → 这步是并行分片的重头戏(把保单按 key 切成上千个 partition 并行算,正是 Day 13 分片思想的复用)。

③ Load(落库)——把结果写回保单库 / billing,并原子地切换为新版本(要么整批生效,要么整批回滚——绝不能让一半客户拿新价、一半拿旧价)。

④ Reconcile & Report(对账 + 上报)——汇总给 reserving、再保上报、分析;留下完整 audit log:这批用了哪个假设版本、跑了哪些保单、每张的输入输出,全部可复现。

3管道的装配顺序

ETL vs ELT:先变形还是先入库

不管批还是流,数据从源头搬到目的地这条「管道」都有一个经典的字母游戏。ETL = Extract → Transform → Load:抽取出来,先在管道里把数据清洗/变形好,再把成品装进目标库。ELT = Extract → Load → Transform:先把原始数据原样灌进目标库(通常是强大的云数仓 / 数据湖),再在库里用 SQL 就地变形。

顺序换了一下,差别却很大。ETL 在云仓出现前是主流:目标库(传统数仓)又贵又弱,你不敢把脏数据全塞进去,只能在外面的 ETL 服务器先加工成干净的星型模型再入库——好处是入库即整洁、省存储,坏处是变形逻辑写死在管道里,想换个口径就得重跑整条管道,而且原始数据没留底。

ELT 是云数仓(Snowflake / BigQuery / Redshift 这类)带火的:存储便宜、算力可弹性扩,于是策略反过来——先无脑把原始数据全部入库留底,变形交给数仓内部的 SQL 按需做。好处是原始数据永远在、口径随时能改(改个 SQL 重算即可,呼应昨天 Kafka 的 replay 精神),坏处是库里堆着大量未清洗数据、治理要求更高。对 QuoteFlow 这种极重 auditability 的系统,「原始数据留底 + 变形可追溯重算」的 ELT 思路尤其契合合规诉求。

ETL(先变形)ELT(先入库)
变形发生在管道里 / 独立计算层目标库内部(SQL)
入库的是清洗好的成品原始数据(再就地加工)
原始数据通常不留底完整留底,可重算
改口径改管道、重跑改 SQL、重算即可
前提目标库弱/贵,需先减负云数仓:存储便宜、算力弹性
合规友好度原始追溯较弱留底 + 重算 → 审计友好

▲ 不是新旧之争:对 PII 敏感、必须在入库前脱敏的场景,ETL 仍有位置;但云时代默认 ELT 居多。

4流处理的真难点

时间不是你以为的那个时间

批处理为什么省心?因为数据已经全到齐了,你随便排序、随便聚合。流处理的痛,全来自「数据还在源源不断地来,而且会迟到、会乱序」。这里有一对必须分清的概念:

Event time(事件时间)是这件事真实发生的时刻——比如某客户的保单 23:59:50 真正生效。Processing time(处理时间)是这条事件被系统读到/算到的时刻——可能因为网络、积压,到 00:00:30 才进到流处理引擎。两者几乎从不相等。如果你按「处理时间」分天,这笔本该算进 16 号的保单,就会被错误地算进 17 号——在受监管的定价里,这种归期错误可能直接导致对账和披露出问题。

因为流是无界的,「算 16 号这一天的总额」就不能傻等(永远等不完)。流处理用 window(窗口)把无界流切成有界小段来聚合(比如「按 event time 每 1 小时一个窗口」)。但难点来了:什么时候能宣布「这个窗口该收口出结果了」?万一还有迟到的数据呢?引擎用 watermark(水位线)来下注——它是一个「我赌 event time 小于 X 的数据都到齐了」的推进信号;水位线一过,窗口就触发计算。比水位线还晚来的,就是 late data(迟到数据),要么丢弃、要么触发已闭合窗口的修正。这套机制,正是流处理比批处理难写一个量级的根源。

stream · 按 event time 开窗(示意伪代码)
// 一个永不结束的流处理任务:实时盯 broker 渠道的报价转化
stream("quote-events")
  .assignTimestamps(e => e.event_time)            // ← 用事件时间,不是处理时间
  .withWatermark(lateness = 5.minutes)         // 容忍最多迟到 5 分钟
  .keyBy(e => e.broker_id)
  .window(Tumbling(1.hour))                 // 每个 broker、每小时一个窗口
  .aggregate(count_quotes, sum_bound)

// watermark 推过 10:00 → 触发 09:00-10:00 窗口出结果
// 9:58 发生、但 10:03 才到的事件 = 迟到 5 分钟内 → 仍算进 9 点窗口
// 10:30 才到的同款事件 = 超过容忍 → late data,单独走修正/告警

对比一下:同样「按小时统计 broker 转化」,batch 版本就是一句 GROUP BY broker_id, hour 跑在昨天的完整数据上——因为数据已经全到齐,根本不需要 watermark 这套东西。这就是延迟换简单性的代价。

5怎么选 + 混合架构

该批、该流,还是两个都要

选择其实回到 Day 2 的老朋友:你的延迟要求是什么。结果可以等到明天早上 → batch,简单、便宜、好审计。结果必须秒级出现(实时风控、欺诈拦截、实时大盘) → stream。中间还有个折中:micro-batch(微批)——每隔几秒攒一小撮一起算(Spark Structured Streaming 的经典做法),用「几秒延迟」换回「batch 的简单与高吞吐」,是工程上极常用的甜区。

当一个业务既要实时近似值、又要事后精确值时,就出现了两种著名的混合架构。Lambda 架构:同一份数据同时喂给一条 batch 层(慢但准、定期重算出权威结果)和一条 speed/stream 层(快但近似、补足实时性),查询时把两者合并——准是准,但同一套逻辑要用批和流各写一遍,维护翻倍。Kappa 架构(呼应昨天 Kafka 的 replay):干脆只保留流这一条路,需要「重算历史」时,就把事件日志的 offset 拨回去重放一遍——用一套代码搞定批与流,代价是对流引擎和日志保留能力要求很高。

维度BatchStream
数据bounded(有界、到齐)unbounded(无界、持续)
延迟高(分钟~小时)低(毫秒~秒)
吞吐 / 成本每条成本低、吞吐高常驻进程、运维更贵
实现复杂度低:数据全在,随便算高:窗口/水位/迟到/状态
出错重跑重跑整批,直观靠 checkpoint + replay
QuoteFlow 落点夜间重定价、reserving、月度对账实时报价转化看板、欺诈/异常告警

▲ QuoteFlow 现实里两者并存:重定价是 batch 的主场,而「broker 渠道实时转化监控、异常报价告警」更适合 stream。

读完自测一下

Q1「QuoteFlow 每晚把全部 in-force 保单按新费率重算一遍」—— 这更适合 batch 还是 stream?为什么?
Batch。数据是有界的(「昨日收盘的全部保单」)、延迟不敏感(只要天亮前跑完)、需要全局一致并整批原子切版本。这些正是 batch 的主场;用 stream 反而把简单问题做复杂了。
Q2一笔保单 23:59:50 真实生效,但因积压到次日 00:00:30 才被处理。event time 与 processing time 分别是哪个?按哪个分天才对?
Event time = 23:59:50(真实发生),processing time = 00:00:30(被算到)。该按 event time 归到 16 号;按处理时间会错误地算进 17 号,在受监管定价里可能引发对账/披露问题。
Q3ELT 相比 ETL,在「可审计 / 可复现」上有什么天然优势?
原始数据完整留底。ELT 先把原始数据原样入库再就地变形,所以任何口径变化都能改 SQL 重算、且能回溯到最原始输入——这与昨天 Kafka 的 replay 精神一致,对 QuoteFlow 这种重 auditability 的系统尤其契合。
带着这两个问题回来讨论

① 夜间重定价跑到一半挂了(比如第 60 万张保单时崩溃),你希望它具备什么性质才能安全地重跑、而不会把已经算过的保单算两遍?(提示:这正好是明天 idempotency 的核心。)
② 如果监管要求把「夜间重定价」从「T+1 出结果」改成「保单一变更就近实时重估」,你会从 batch 切到 stream 吗?这一改,会给一致性、成本、可审计性各带来什么新麻烦?

A→Z术语表

今日术语

Batch Processing
对一份有界(已到齐)的数据集一次性扫描计算,任务有始有终。高延迟、高吞吐。
Stream Processing
对无界、持续到来的数据来一条(或一小撮)算一条,进程常驻不退出。低延迟。
Bounded / Unbounded Data
有界 = 有明确开始结束、可等到齐;无界 = 永远在来、没有「全部」。batch/stream 的根本分界。
ETL
Extract→Transform→Load:先在管道里变形,再把成品入库。
ELT
Extract→Load→Transform:先把原始数据入库留底,再在库内(SQL)就地变形。云数仓时代主流。
Event Time vs Processing Time
事件真实发生的时刻 vs 被系统处理到的时刻;乱序/迟到时两者不等,聚合应按 event time。
Window
把无界流切成有界小段来聚合的机制(如每小时滚动窗口 tumbling window)。
Watermark
流引擎对「event time ≤ X 的数据已基本到齐」的推进信号,用来决定窗口何时收口出结果。
Late Data
比 watermark 还晚到的数据;需丢弃或触发已闭合窗口的修正。
Micro-batch
每隔几秒攒一小撮一起算,用少量延迟换 batch 的简单与高吞吐。
Lambda / Kappa
混合架构:Lambda 同跑批+流两条路再合并;Kappa 只留流一条,靠 replay 重算历史。
Data Pipeline
把数据从源头搬运、变形、落到目的地的一连串处理阶段。
