1从业务到表

先找实体和关系,再谈字段

数据建模的第一步不是开表,而是问两个问题:这个业务里有哪些实体(entity)——值得拥有自己身份(主键)的“东西”;它们之间是什么关系(relationship)——一对一、一对多、多对多。

对你来说这一步其实很熟:精算建模先定义“什么是一张保单、什么是一个 life insured”,数据建模做的是同一件事,只是产出物是表和外键而不是模型假设。把 QuoteFlow 的新业务流程顺一遍,实体自然浮出来:

一个 Customer 可以发起多次 Quote(报价);某次报价可能转成一份 Application(投保申请);申请通过核保后签发成 Policy(保单);保单下挂一个或多个 Coverage(险种/保障);每条报价和每份保单都要钉住一个 RateTableVersion(版本化费率表);所有关键动作进 AuditLog。全是一对多,外键的方向也随之确定——多的一侧持有外键。

注意 RateTableVersion 的画法:它不是普通的一张参数表,而是不可变的版本快照——发布即冻结,改费率 = 发新版本。这一个建模决定,直接决定了报价能不能复现。第 4 节会展开。

2范式化

Normalization 在防什么:三种异常

范式(normal forms)听起来学院派,但它防的问题非常实际。假设 QuoteFlow 图省事,把报价做成一张大宽表,客户姓名、地址、吸烟状态跟着每条报价存一遍:

Update anomaly(更新异常):客户改了地址,他名下 8 条报价里的地址要改 8 处——漏改一处,数据就自相矛盾,你再也说不清哪个是对的。Insert anomaly(插入异常):客户还没报过价,就没有任何一行能放他的信息——“客户存在”这个事实没地方落。Delete anomaly(删除异常):删掉他唯一一条报价,客户信息跟着消失了。

三种异常的病根是同一个:一份事实存了多处。范式化的全部直觉就是一句话——每个事实只存一处(single source of truth),其他地方用外键去引用它。各级范式只是把这句话逐步收紧:

1NF:每个格子只放一个原子值——不要在一个字段里塞 "TERM_LIFE;TPD;TRAUMA" 这种逗号串(该拆成 Coverage 子表)。2NF / 3NF 合起来记一句口诀就够:每个非主键字段只依赖主键——the key, the whole key, and nothing but the key。客户地址依赖的是 customer_id 而不是 quote_id,所以它属于 Customer 表,不属于 Quote 表。

到 3NF 为止,你已经覆盖了实务中 95% 的场景。更高的范式(BCNF、4NF…)知道存在即可,工程上极少专门追求。

3反范式

什么时候该故意打破规则

范式化的代价在读路径:事实拆得越散,查询时要 JOIN 回来的表越多。Day 9 讲过,每次 JOIN 都是一轮索引查找 + 可能的回表;客户保单概览页要 JOIN 五张表的话,p99 latency 很难看。Denormalization(反范式)就是有意识地把冗余加回来,用写时的维护成本换读时的速度。

关键词是有意识:先有度量(慢查询、EXPLAIN 证据),再决定冗余什么、由谁负责维护一致性。常见三种形态——冗余列(把客户姓名抄进保单概览表)、汇总表(预计算好的每日新业务统计,而不是每次现算)、快照(把某一刻的事实整体复制一份、之后不再跟随源头变化)。

Case · QuoteFlow

快照不是冗余,是审计需求

报价记录该存什么?如果 Quote 只存 customer_id 外键,三个月后客户改了吸烟状态、费率表也更新了两版,你拿什么向监管解释“当时为什么报这个价”?按范式的标准答案(只引用、不复制)在这里恰恰是错的。

正确做法:Quote 行里同时存输入快照(报价当时的年龄/吸烟状态/保额)+ 版本引用(rate_table_version、rules_version)。看起来“冗余”,其实两者记录的是不同的事实:Customer 表存的是“客户现在的状态”,Quote 存的是“报价那一刻我看到的状态”。时点不同,就不是同一份事实——这不违反范式,这是把时间维度建对了。Reproducibility 靠的就是:不可变输入 + 不可变版本 = 任何时候都能重算出同一个数。

Normalization(范式)Denormalization(反范式)
优化目标写的正确性:一份事实一个家,改一处处处生效读的速度:少 JOIN、少回表,查询路径短
代价读要 JOIN 多张表,复杂查询变慢写要同步多处冗余;同步逻辑出 bug = 数据矛盾
适合的数据频繁变化的主数据:客户资料、in-force 保单状态读多写少 / 写后不变:报价快照、汇总报表、审计记录
QuoteFlow 例子Customer / Policy / Coverage 拆表 + 外键Quote 的输入快照、夜间批算的每日 in-force 汇总表
出错的样子报表要 8 个 JOIN,夜间批算窗口爆掉客户改了地址,三处冗余只更新了两处

▲ 默认从 3NF 出发,有证据再反范式——方向反过来(先宽表后补救)几乎总是更痛。

4时间维度

Effective dating:随时间变化的事实

寿险数据建模真正的“行业难点”不是范式,是时间。费率表、核保规则、CPI indexation 因子……这些事实都带生效期:“2026-07-01 起,费率表 v2026-07 生效”。而你的查询经常是时间旅行:夜间重算要用“保单周年日当天有效”的那套假设,审计要用“报价当天有效”的那套费率。

标准建模手法是effective dating:版本表带 valid_from / valid_to 两列,当前版本 valid_to = NULL(或 9999-12-31)。更新永远是“关旧开新”:把旧行的 valid_to 填上,插入新行——从不 UPDATE 业务内容本身。这和数据仓库里的 SCD Type 2(slowly changing dimension)是同一个思想,你在分析侧大概率见过它的另一副面孔。

schema.sql · QuoteFlow 核心表(节选)
-- 主数据:范式化,一份事实一个家
CREATE TABLE customer (
  customer_id   UUID PRIMARY KEY,
  full_name     TEXT NOT NULL,
  date_of_birth DATE NOT NULL,
  smoker        BOOLEAN NOT NULL      -- “现在”的状态,会变
);

-- 版本化费率表:effective dating,只增不改
CREATE TABLE rate_table_version (
  version_id   TEXT PRIMARY KEY,      -- 如 '2026-06'
  product      TEXT NOT NULL,
  rates        JSONB NOT NULL,        -- 发布即冻结
  valid_from   DATE NOT NULL,
  valid_to     DATE                   -- NULL = 当前生效
);

-- 报价:输入快照 + 版本引用 = 可复现
CREATE TABLE quote (
  quote_id           UUID PRIMARY KEY,
  customer_id        UUID REFERENCES customer,
  applicant_snapshot JSONB NOT NULL,  -- 当时的年龄/吸烟/保额
  rate_table_version TEXT REFERENCES rate_table_version,
  monthly_premium    NUMERIC(10,2) NOT NULL,
  created_at         TIMESTAMPTZ NOT NULL
);

-- 时间旅行查询:保单周年日那天,哪版费率有效?
SELECT version_id FROM rate_table_version
WHERE product = 'TERM_LIFE_20Y'
  AND valid_from <= '2026-09-14'          -- 周年日
  AND (valid_to IS NULL OR valid_to > '2026-09-14');

再加一条:AuditLog 天然是 append-only 的——审计记录如果能被 UPDATE,它就不叫审计记录了。“只增不改”的表有个工程红利:没有 update anomaly(事实从不变),反范式随便用(尽管冗余,反正不会改),还和 Day 8 的事务压力解耦。把系统里“不可变的事实”(报价、审计、版本)和“可变的状态”(客户资料、保单状态)分开建模,是这一天最值得带走的判断力。

?今日小测 + 思考题

读完自测一下

Q1把客户地址同时存在 Customer 表和每条 Quote 行里,客户搬家后只更新了 Customer 表。这叫什么问题,病根是什么?
Update anomaly(更新异常)。病根是同一份“当前地址”事实存了多处、却没人负责同步。注意和报价快照区分:快照存的是“报价当时的状态”,是另一份事实,客户搬家本来就不该影响它。
Q2为什么费率表更新要“关旧行、插新行”,而不是直接 UPDATE rates 字段?
因为历史报价和保单还引用着旧版本。直接 UPDATE 会把旧版本的内容偷换掉,所有引用它的报价瞬间不可复现——审计上等于销毁证据。Effective dating(valid_from / valid_to + 只增不改)让任何时点的“当时生效版本”都能被查回来。
Q3客户保单概览页要 JOIN 五张表、p99 超标了。“立刻反范式”是对的第一反应吗?
不是。先用 Day 9 的工具:EXPLAIN 看执行计划,确认慢在哪——很可能补一个复合索引或 covering index 就解决了,零冗余成本。索引救不动、且读写比悬殊时,再考虑冗余列或汇总表,并明确写路径由谁维护这份冗余。
带着这两个问题回来讨论

① Quote 表里,哪些字段该快照、哪些该引用?试着给一条判断规则(提示:从“这个字段的事实属于哪个时点”想起),再用它检验:保额、客户邮箱、费率表版本、核保规则结果。
② 夜间批量重算要给每份 in-force 保单写一条重算结果。这张结果表你会怎么建——可变还是 append-only?如果同一保单同一晚跑了两次(重试),建模上怎么不留下两条互相矛盾的记录?

A→Z术语表

今日术语

Entity / Relationship
实体 = 拥有自己身份(主键)的业务对象;关系 = 实体间的 1-1 / 1-n / n-n 关联,决定外键放哪。
Normalization
范式化:让每份事实只存一处、其余引用,以消除更新/插入/删除异常。
3NF
第三范式,口诀:非主键字段只依赖 the key, the whole key, and nothing but the key。实务上到这级够用。
Update Anomaly
同一事实多处存放、部分更新后数据自相矛盾;另有 insert / delete anomaly 两兄弟。
Denormalization
反范式:有意识地引入冗余(冗余列/汇总表/快照),用写时维护成本换读时速度。
Snapshot
把某一时点的事实整体复制、之后不再跟随源头变化;是审计与复现的基础,不算违反范式。
Effective Dating
用 valid_from / valid_to 给事实加生效期,更新=关旧开新;数据仓库里的 SCD Type 2 同源。
Append-only
只增不改的表(审计日志、事件记录):没有更新异常,天然适合审计与重放。
