1单台机器的天花板

一台再强,也有撑不住的那一刻

QuoteFlow 刚上线时,一台应用服务器足够:网站发来 POST /v1/quotes,它算完返回,绰绰有余。但只要业务跑起来,两件事会同时逼近——请求量涨(新产品上线、广告投放、broker 接入),以及那台机器会挂(硬件故障、要打补丁重启、机房断电)。单台架构对这两件事都没有答案:量一大就排队变慢,机器一挂就整个报价业务归零。

第二点尤其致命。Day 1 我们把 availability 列为一等公民——可单台服务器就是一个单点故障(single point of failure, SPOF):它的可用性就是整个系统的可用性上限。要突破,唯一的路是摆多台。可一旦有多台,新问题立刻冒出来:客户端该连哪一台?这就需要在它们前面放一个统一入口,由它来分发——这就是负载均衡器和反向代理登场的地方。

反向代理:替这群机器对外说话

Reverse proxy(反向代理)是一个站在服务端这一侧、代表后端机器接收所有外部请求的中间层。客户端只知道这个入口的地址(比如 api.quoteflow.com),根本不知道、也不需要知道后面到底有几台机器、它们的真实 IP 是什么。反向代理收到请求后,挑一台后端把请求转过去,再把响应带回来。

这里有个容易混的对照:Day 4 提过浏览器可能走的 forward proxy(正向代理)是代表客户端出门(替你访问外网、隐藏你);reverse proxy 正相反,代表服务器迎客(隐藏后端、替后端挡在前面)。负载均衡器就是反向代理最常见的一种——它在“转给谁”这件事上做得特别讲究。除了分发,这道关口顺手还能干很多活:TLS 终止(Day 4 的握手在这里统一做)、压缩、限流、把静态内容挡在前面。

一句话分清三个词
  • Reverse proxy:站在服务端前面的统一入口(代表后端迎客)。是个角色。
  • Load balancer:专门负责“把请求公平/聪明地分给多台后端”的反向代理。是个专精的反向代理。
  • API gateway:在负载均衡之上再叠认证、路由、限流、聚合等业务能力(Day 23 专讲)。是个加了料的入口。
2两种长大方式

换台更大的,还是多摆几台

当一台撑不住,扩容(scaling)有两条根本不同的路。这是系统设计里最基础、也最常被考的一组取舍:

Vertical scaling(纵向扩展 / scale up):给同一台机器加资源——更多 CPU、更大内存、更快磁盘。像是把厨房里那个厨师换成一个手更快的。简单、不改架构,代码一行不用动。但它有硬天花板(单机配置就那么高)、价格非线性飙升(顶配机器贵得离谱),而且没解决 SPOF——再强也还是一台,挂了照样全停。

Horizontal scaling(横向扩展 / scale out):多摆几台一样的机器,让负载均衡器把流量摊开。像是再雇几个厨师一起出菜。它几乎没有上限(不够就再加)、用便宜的普通机器拼也很划算,而且天然消除了 SPOF(挂一台,其余顶上)。代价是架构变复杂:要有负载均衡、要处理“状态放哪”、要管多台机器的部署和一致性——这也正是这门课后面大半内容的来由。

Vertical(scale up)Horizontal(scale out)
怎么做同一台加 CPU/内存/磁盘多加几台一样的机器,流量摊开
上限有硬天花板(单机配置封顶)近乎无限(不够就再加)
成本曲线顶配非线性飙升,越往上越贵普通机器线性叠加,更划算
可用性 / SPOF仍是单点,挂了全停天然冗余,挂一台其余顶上
复杂度低,代码/架构不动高:要 LB、要处理状态与一致性
何时先用早期、量小、想快速顶一下要高可用、要长期扩到很大

▲ 现实里不是二选一:常先 scale up 快速顶过早期,等架构理顺再 scale out 做长期。但只要 availability 是硬需求,横向扩展几乎是必经之路——因为只有它能去掉单点。

对 QuoteFlow 的两条路径(呼应 Day 1)
  • 实时报价 API(要 low latency + 高可用):典型的横向扩展——一排无状态的报价服务,前面一个负载均衡器,挂一台不影响出报价。今天主要讲这条。
  • 夜间批量重定价(要 high throughput):也靠“多摆几台 worker 并行跑”来提速,但它的“分发”逻辑和实时请求不同(是切分数据、不是分发请求)——这条线 Day 15/17 讲消息队列与批处理时再展开。
3分给谁

负载均衡器怎么挑后端

有了一排机器,核心问题就剩一个:下一个请求发给哪台?这就是负载均衡算法。它们在“简单”和“均匀”之间各有取舍:

算法怎么挑适合 / 注意
Round Robin
轮询		1→2→3→1→2… 挨个轮最简单;假设每台一样强、每个请求差不多重
Weighted RR
加权轮询		按权重分,强的机器多分机器配置不均时用(8 核的比 4 核的多拿)
Least Connections
最少连接		发给当前活跃连接最少的请求耗时差异大时更均匀(报价快、核保慢)
Least Response Time
最快响应		挑近期响应最快的更聪明,但要持续测量每台的延迟
IP / Key Hash
哈希		按来源 IP 或某个 key 算哈希定台同一来源总落同一台(会话粘性,见第 5 节)

▲ 默认从 round robin 起步足够好用;当请求轻重不均(QuoteFlow 的简单报价 vs 复杂核保)时,least connections 往往更稳——否则轮询可能把好几个慢请求恰好堆到同一台。

用伪代码把前三种放在一起,差别一眼就清楚——注意它们读的是不同的信息:轮询只数到第几个,加权看配置,最少连接看实时状态。

load_balancer.py · 三种挑后端策略(示意)
# 一排健康的后端(只有通过健康检查的才在池子里,见第 5 节)
backends = ["pricing-1", "pricing-2", "pricing-3"]

def round_robin(state):
    # 只记"上次发到第几个",挨个轮 —— 最简单
    state.i = (state.i + 1) % len(backends)
    return backends[state.i]

def least_connections(backends):
    # 看实时活跃连接数,发给最闲的 —— 抗"轻重不均"
    return min(backends, key=lambda b: b.active_conns)

def weighted_pick(backends):
    # 8 核的 weight=2,4 核的 weight=1 → 强的多拿
    pool = [b for b in backends for _ in range(b.weight)]
    return random.choice(pool)

# 关键前提:backends 里永远只有"健康"的机器。
# 一台挂了 → 健康检查把它摘掉 → 这里自动不会再选它。

最后一行注释是今天最重要的伏笔:负载均衡之所以能提供高可用,不只是“会分发”,而是它只往健康的机器分。这就引出了让横向扩展真正成立的两个前提——第 5 节。

4L4 还是 L7

在“第几层”做分发,能看到的东西不一样

负载均衡可以发生在网络的不同层次(回忆 Day 4 的分层)。最常见的两类是 L4 和 L7,差别在于:它拆开请求看了多深。看得越浅越快,看得越深越聪明。

L4(传输层)负载均衡只看 TCP/UDP 这一层的信息——源/目标 IP 和端口。它不拆开里面的 HTTP 内容,基本就是“把这条连接的字节流原样转给某台后端”。因为不解析内容,它极快、开销极低、吞吐极高;但也因此看不懂业务:无法按 URL 路径、Cookie、header 来路由。

L7(应用层)负载均衡会把 HTTP 请求完整拆开:能看到路径(/v1/quotes vs /v1/policies)、header、Cookie、甚至 body。于是它能做聪明的、内容感知的路由:把报价请求发给定价服务集群、把保单请求发给保单集群;还能在这一层统一做 TLS 终止、按路径限流、改写 header。代价是要解析内容,每个请求开销更大、稍慢一点。

L4(传输层)L7(应用层)
看到什么IP + 端口(TCP/UDP)完整 HTTP:路径 / header / cookie / body
能不能按内容路由不能,只认连接能,按 URL/header 精细分流
速度 / 开销极快,开销极低稍慢,每请求要解析
TLS 终止一般不做(透传加密流)常在这里统一做(Day 4 握手)
典型角色最外层入口,海量分流内层智能路由 / API 边缘

▲ 不是二选一,而是常常叠用:最外面用 L4 扛住海量连接、快速摊开,后面再用 L7 按业务做精细路由。下一节的图就是这个两层结构。

5横向扩展的前提

无状态 + 健康检查,缺一不可

“多摆几台、负载均衡摊开”听着简单,但它有两个隐含前提。这两条没做到,横向扩展不仅不工作,还会偷偷算错——对 QuoteFlow 这种受监管系统是大忌。

前提一:应用服务器要无状态(stateless)

无状态的意思是:服务器自己不在本地内存里保存“两次请求之间的关键数据”。每个请求都自带它需要的一切(或从共享存储里取),所以发给哪一台都得到一样的结果。这正是负载均衡能随意分发的根基——既然每台都等价,round robin 才有意义。

反例最能说明问题:假设报价服务把“用户的报价进度”存在本台机器的内存里。客户端第一步请求落在 pricing-1,第二步被负载均衡分到了 pricing-2——pricing-2 根本不知道第一步发生过什么,流程就断了。所以横向扩展的铁律是:状态不要放在应用服务器本地,把它挪到共享的地方去——数据库、或一个共享缓存(Day 7 的 Redis 正是干这个的)。应用层因此可以随便加减机器、随便挂随便换。

前提二:负载均衡要做健康检查(health check)

负载均衡器必须持续探测每台后端是否还活着——通常是定期请求一个轻量的 GET /healthz 端点。探测失败的机器会被自动从池子里摘掉,新请求不再发给它;等它恢复、连续探测成功,再放回池子。这就是为什么“挂一台,其余顶上”能自动发生——客户端甚至无感。第 3 节伪代码里“池子里永远只有健康机器”的承诺,靠的就是它。

会话粘性(session stickiness)——一个诱人的陷阱
  • 有人会用 sticky session(按 cookie/IP 哈希,让同一用户总落同一台)来回避“状态放本地”的问题。它能用,但代价是:那台机器一挂,粘在上面的用户全部丢状态;而且负载会变得不均(热点用户压垮某一台)。所以它是权宜之计——真正干净的解法仍是无状态 + 共享存储。受监管的写路径(如投保、保单变更)尤其不该依赖粘性,否则一次故障转移就可能让审计链路断掉。

顺带一提:负载均衡器自己别成了新的单点

我们把单点从应用服务器挪走,可别让它跑到负载均衡器身上。生产里负载均衡器自身也要冗余(主备或多活 + 健康切换),否则它一挂,前面所有努力归零。这也是云厂商的托管负载均衡(它们内部已做好高可用)如此常用的原因。

6贯穿案例

QuoteFlow 的入口拓扑

把今天的零件拼起来:外层 L4 扛连接、内层 L7 按业务分流、后面是无状态的服务集群、状态全挪到共享存储,健康检查让坏机器自动下线。这就是昨天那份 API 契约真正落地的样子。

Case · QuoteFlow

为什么这套结构对“受监管定价”特别重要

横向扩展 + 健康检查带来的高可用,直接服务 Day 1 的一等公民 availability:承保渠道任何时刻都能拿到报价,挂一台不影响出单。但合规视角还要多想一层——每台报价服务必须算出完全一样的数。这就要求“算报价依赖的东西”(费率表版本、核保规则、定价模型)统一来自共享、版本化的源,而不是某台机器本地的副本。否则负载均衡把你随机分到一台“规则没更新”的机器,就可能出一个不可复现的报价——在受监管场景里这是要命的。无状态在这里不只是工程优雅,更是 reproducibility / auditability 的前提。

和昨天那份契约的接口

昨天讲的 idempotency key 今天有了用武之地:请求被分到哪台、那台中途挂了触发重试,只要写操作带幂等键,就不会因为故障转移而签出两张保单。负载均衡(今天)+ 幂等(昨天)合起来,才凑齐“多机环境下既高可用、又不出错”的下半句。

1

单台机器既有性能天花板又是单点故障。突破靠多摆几台,前面放一个反向代理 / 负载均衡器做统一入口。

?今日小测 + 思考题

读完自测一下

Q1QuoteFlow 报价量翻倍,你会优先 scale up 还是 scale out?为什么?
长期看是 scale out(横向)。纵向有硬天花板、顶配越来越贵,而且没解决单点故障——而 availability 是 QuoteFlow 的一等公民。横向多摆几台 + 负载均衡,既能持续扩,又天然冗余(挂一台其余顶上)。早期想快速顶一下可以先 scale up,但要高可用,横向是必经之路。
Q2为什么说“应用服务器要无状态”是横向扩展的前提?状态该放哪?
因为负载均衡会把同一用户的多次请求分到不同机器。如果把关键数据存在某台机器的本地内存,下一个请求落到别的机器就读不到、流程断掉。所以状态要下沉到共享存储(数据库 / 共享缓存 Redis),让每台应用服务器等价、可随意加减和替换。
Q3L4 和 L7 负载均衡,哪个能“把 /quotes 和 /policies 分到不同集群”?为什么另一个不行?
L7(应用层)能。它会拆开 HTTP 请求、看得到 URL 路径,所以能按内容路由。L4 不行:它只看 TCP 的 IP/端口,不解析 HTTP 内容,因此快但“看不懂业务”。真实系统常两层叠用:外层 L4 扛连接,内层 L7 做精细路由。
带着这两个问题回来讨论

① 我们把单点从应用服务器移走了,可负载均衡器自己会不会成为新的单点?生产里该怎么避免?
② QuoteFlow 的报价请求轻重差别很大(简单产品秒出、含核保的慢得多)。在这种情况下,round robin 可能出什么问题?换成哪种算法、为什么会更好?
