1问题:雪崩怎么发生

一处过载,如何滚成全站崩

前面几周我们一直在「把容量做大」:加缓存、复制、分片。但容量再大也是有限的,而流量和故障是不讲道理的。Resilience 关心的是另一个问题:当负载超过了你的容量、或某个依赖出了问题,系统是优雅地降级,还是彻底崩盘?

最典型的崩盘叫级联故障(cascading failure)。设想 QuoteFlow 的实时报价链路:报价服务要调一个风险评分服务(risk scoring)。某天风险评分服务变慢,响应从 50ms 涨到 5s。会发生什么?

报价服务的每个请求都卡在等风险评分上,线程/连接被一个个占住、迟迟不释放。新请求继续涌入,可用线程很快耗尽——此时报价服务自己也开始超时、拒绝。上游的 API 网关看到报价服务挂了,把流量重试到别的实例,于是每一个报价实例都被同样的慢依赖拖垮。最后:一个本来只是「慢」的下游,让整条报价链路全停。这就是雪崩。

重试风暴:好心办坏事
  • 「失败就重试」是最自然的容错反应,却也是雪崩的头号放大器。当下游已经过载,每个客户端再 retry 3 次,等于瞬间把负载 ×4 砸向那个奄奄一息的服务——它更起不来了。解药:指数退避 + 抖动(exponential backoff + jitter),失败后等的时间逐次翻倍并加随机扰动,避免所有客户端在同一刻齐刷刷重试(thundering herd)。还要给重试设总次数上限和重试预算。

核心心法贯穿今天全篇:过载时,「拒绝一部分、保住其余」永远优于「全收、然后一起死」。下面四件工具,本质都是这一句话在不同位置的落地。

2工具一 · Rate Limiting

限流:在门口就挡住超量

Rate limiting(限流)给「单位时间能进多少请求」设一个上限,超出的直接拒绝(返回 429 Too Many Requests)或排队。它是主动防线——在请求真正消耗资源之前就拦下。用途有三:防滥用/攻击、保护下游容量、以及给不同客户做公平配额(broker A 不能把额度吃光,饿死 broker B)。

最常用的算法:Token Bucket(令牌桶)

想象一个桶,以固定速率(比如 100 个/秒)往里滴令牌(token),桶有最大容量(比如 200)。每来一个请求,就从桶里取走一个令牌;取得到就放行,取不到就拒绝。它的妙处在于:平时桶里攒着令牌,所以允许短时突发(burst)——最多放行「桶容量」个;但长期平均速率被滴入速率死死卡住。这比「每秒就准 100 个、多一个不行」的固定窗口更贴近真实流量。

token_bucket.py · 报价 API 每客户端限流(示意)
class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate = rate          # 每秒滴入的令牌数,如 100
        self.capacity = capacity  # 桶容量 = 允许的突发上限,如 200
        self.tokens = capacity
        self.last = now()

    def allow(self):
        # 按经过的时间补充令牌,但不超过容量
        elapsed = now() - self.last
        self.tokens = min(self.capacity, self.tokens + elapsed * self.rate)
        self.last = now()
        if self.tokens >= 1:
            self.tokens -= 1
            return True            # 放行
        return False               # 拒绝 → 调用方返回 429

# 每个 broker / API key 一个桶,实现公平配额
if not buckets[api_key].allow():
    return Response(429, headers={"Retry-After": "1"})

其它常见算法:leaky bucket(漏桶)——请求以恒定速率流出,平滑突发但不允许 burst;fixed / sliding window——按时间窗计数,实现简单但窗口边界可能放进双倍流量。分布式部署时,计数器通常放在 Redis(Day 7),让多个实例共享同一份配额。别忘了回给客户端 429 + Retry-After,告诉它什么时候再来——这本身就是在引导对方做退避。

3工具二 · Circuit Breaker

熔断:别再去敲一扇已经坏掉的门

限流挡的是「进来的太多」;circuit breaker(熔断器)挡的是「出去的依赖坏了」。它的灵感来自电路里的保险丝:当某个下游(如风险评分服务)连续失败/超时到一定程度,熔断器跳闸——之后的调用立刻失败(fail fast),根本不再发出去。这正是治前面那个雪崩的药:报价服务不再傻等 5s,而是瞬间返回,线程立刻释放,自己先活下来。

熔断器是一个三态机,这是今天必须画进脑子里的图:

三态合起来读:CLOSED 正常工作并统计失败率;失败率冲过阈值(如 10s 内 >50%)就跳到 OPEN,在冷却期内所有调用立即失败、不打扰下游、给它喘息时间;冷却到点进 HALF-OPEN,只放少量探测请求——成功就认为下游恢复、回到 CLOSED,失败就再退回 OPEN 接着等。配合降级(fallback)更完整:熔断打开时,报价可以返回一个保守的缓存值,或明确告知「核保稍后人工跟进」,而不是直接 500。

4工具三 · 工具四

背压与隔离舱:从源头与边界控住压力

Backpressure(背压)

限流和熔断都是「丢弃」式防护。背压是更优雅的一招:当下游处理不过来时,沿调用链向上游传递「慢一点」的信号,让生产者主动减速,而不是把活儿堆成无限长的队列直到内存爆掉。这正对应 Day 15 消息队列里的隐患——一个无界队列(unbounded queue)看着是缓冲,实则是把过载延后并放大成 OOM。

QuoteFlow 的夜间批量重定价(Day 17)是背压的主场:上游读取百万保单的速度,必须受下游计算/写库能力反向节制。实现上常见的是有界队列 + 阻塞(队列满了,生产者就被挡住,自然减速),或拉取式消费(consumer 主动按自己的节奏 pull,如 Kafka 的消费模型)。一句话:让系统按最慢环节的真实速度运转,而不是假装自己无限快。

Bulkhead(隔离舱)

名字来自船体的水密隔舱:船被分成多个密封舱,一个舱进水,不会淹没整艘船。在系统里,bulkhead 就是给不同类别的请求分配各自独立的资源池(线程池、连接池),互不挤占。

回到雪崩那一幕:如果报价服务调用风险评分用的是一个独立的线程池,那么即便这个池被慢依赖占满,处理 broker API、保单查询的其它线程池毫发无伤——一个功能的故障被「关」在它自己的舱里,而不是耗尽全进程的资源拖垮一切。对 QuoteFlow 尤其关键:绝不能让一个低优先级的分析查询把实时报价的资源吃光。

工具拦住哪种过载动作QuoteFlow 落点
Rate Limiting进来的请求太多超额拒绝(429)/ 排队报价 API 按 broker 配额限流
Circuit Breaker调用的依赖坏了跳闸,快速失败 + 降级风险评分服务变慢 → 熔断 + 返回保守值
Backpressure生产快于消费向上游传「慢一点」夜间批量按写库速度反向节流
Bulkhead一处故障蔓延隔离资源池,互不挤占实时报价 / 分析查询用独立线程池

▲ 四件工具不是二选一,而是组合拳:限流挡在最外、熔断守在每个依赖调用前、背压贯穿异步链路、bulkhead 在资源层兜底。

Case · QuoteFlow · 合规视角

降级也要「留痕」

在受监管的寿险定价里,弹性手段不能是黑箱。每一次熔断降级返回的报价、每一笔被限流拒绝的请求,都应写进 audit log:用了哪个 fallback、当时下游什么状态、给客户的数字是不是「正常算出来的」。否则事后审计会问出一个答不上来的问题——「这条报价当时为什么是这个数?」。弹性保住了可用性,但auditability / traceability 仍是一等公民,降级路径也要可解释、可复现。

读完自测一下

Q1限流和熔断,分别是在防「哪个方向」的过载?
限流防「入」——挡住进来的请求太多;熔断防「出」——挡住对一个已经坏掉的下游依赖继续发起调用。前者保护自己的容量,后者保护自己不被慢依赖拖垮(并给下游喘息)。
Q2token bucket 相比「每秒固定放行 N 个」,多了什么能力?为什么有用?
允许短时突发(burst)。平时桶里攒着令牌,瞬时来一波请求可以一次放行「桶容量」个,只要长期平均不超过滴入速率即可。真实流量本就是一阵一阵的,允许合理 burst 比「卡死每一秒」体验更好,也更少误杀正常用户。
Q3熔断器的 HALF-OPEN 状态存在的意义是什么?去掉它会怎样?
用少量探测请求安全地试探下游是否恢复,避免「冷却时间一到就把全部流量一次性放回去、瞬间把刚缓过来的下游再次打死」。去掉它,熔断器要么一直 OPEN(永不恢复),要么从 OPEN 直接全量回 CLOSED(容易二次雪崩)。HALF-OPEN 是平滑、试探性的恢复闸门。

今日术语

Cascading Failure
一处过载/故障沿依赖链蔓延,最终拖垮整个系统的连锁崩溃。
Rate Limiting
对单位时间内的请求数设上限,超出则拒绝(429)或排队。
Token Bucket
限流算法:按固定速率补充令牌,有令牌才放行,允许短时突发。
Circuit Breaker
依赖连续失败时跳闸、让调用快速失败的三态机(CLOSED/OPEN/HALF-OPEN)。
Backpressure
下游处理不过来时,向上游传递减速信号,避免队列无限堆积。
Bulkhead
给不同类别请求分配独立资源池,把故障隔离在各自的「舱」内。
Exponential Backoff + Jitter
重试间隔逐次翻倍并加随机扰动,防止重试风暴与惊群。
Graceful Degradation
压力下主动少做一点(降级/返回保守值),而非整体崩溃。
