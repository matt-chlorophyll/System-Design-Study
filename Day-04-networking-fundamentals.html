1分层:一次请求的骨架

不是一根线,是四层协议叠在一起

最基础的模型是 client-server:一方发起请求(client),另一方给出响应(server)。在 QuoteFlow 里,浏览器、手机 App、broker 的后台系统都是 client;对外的报价 API 是 server。听上去就是“把请求发过去、把结果拿回来”——但这条线里,其实藏着好几层各司其职的协议。

关键认知是 layering(分层):一次 HTTPS 请求不是一个动作,而是四层协议依次叠加,每层只解决自己那一件事,且只依赖下一层提供的能力。这正是网络能被人类理解和演进的原因——你可以单独换掉某一层(比如把传输层从 TCP 换成 QUIC),上层几乎无感。

这一层解决什么用快递打比方
DNS域名 → 服务器 IP 地址查到收件人的门牌号
TCP / UDP把数据可靠(或快速)地送到对面把包裹拆箱、按序投递、签收
TLS加密 + 验证对方身份 + 防篡改给信封上锁、验封
HTTP双方到底“说什么业务”信里写的内容(报价请求/结果)

▲ 自下而上各管一段。下面四节,我们就按 DNS → TCP → TLS → HTTP 的顺序,把一次报价请求走一遍。

2DNS · 先找到服务器在哪

把 api.quoteflow.example 变成一串 IP

人记得住 api.quoteflow.example,机器之间通信却要 IP 地址(如 203.0.113.10)。DNS(Domain Name System)就是互联网的电话簿,负责这一步翻译。它通常发生在你以为的“请求”还没开始之前。

一次完整解析像层层转问:浏览器缓存 → 操作系统缓存 → 递归解析器(recursive resolver,常是 ISP 或 8.8.8.8 这类公共 DNS) → 根服务器 → TLD 服务器(.example)→ 域名的权威服务器(authoritative),最后把 IP 一路带回来。听着步骤多,但因为到处都有缓存,绝大多数查询根本走不到那么深。

这就引出 DNS 最该记住的概念——TTL(Time To Live):每条记录都带一个“保质期”,在 TTL 内任何一层都直接复用缓存,不再重新查。所以同一个域名,第一次解析可能花几十毫秒,之后几乎是 0。这也是为什么 Day 3 的“跨洲 150ms”指的是连接建立后的往返,而首包还得算上偶尔的 DNS 解析。

DNS 不只是查地址,还是一个流量旋钮
  • 权威服务器可以按来源返回不同 IP:让澳洲用户解析到澳洲区节点(geo-routing,降低 Day 3 那个跨洲 150ms),或在多个机房间分流。它也是一种故障转移手段——把流量从挂掉的机房切走。
  • 但有个陷阱:TTL 太长,切换就慢。客户端会拿着旧 IP 直到缓存过期。所以对 QuoteFlow 这种要支持蓝绿/快速故障转移的系统,关键域名常用较短 TTL,且不把故障转移只押在 DNS 上(后面 Day 6 的负载均衡才是更快的开关)。
3TCP vs UDP · 建一条管道

可靠有序,还是又快又省

拿到 IP 后,要在两台机器之间真正“通上”。传输层有两种性格截然不同的协议:TCP 和 UDP。

TCP(Transmission Control Protocol)是“挂号信”:面向连接、保证送达、保证顺序,丢包会重传,还有流控与拥塞控制。代价是要先三次握手(SYN → SYN-ACK → ACK)建立连接——这就是一个 RTT 的开销,也是 Day 3 那个“往返”的第一笔。UDP(User Datagram Protocol)则是“明信片”:无连接、扔出去就不管,不保证到、不保证顺序,但开销极小、延迟极低。

TCPUDP
连接面向连接,先三次握手无连接,直接发
可靠性保证送达,丢包重传不保证,丢了就丢了
顺序保证按序到达不保证顺序
开销 / 延迟较高(握手 + 确认 + 拥塞控制)极低,首字节快
典型用途网页、API、文件传输、数据库实时音视频、游戏、DNS 查询、遥测
一句话慢一点,但对、全、不乱可能掉,但快、轻

▲ 选择逻辑很简单:丢一两个包要命 → TCP;慢一点要命、丢一两个无所谓 → UDP。视频里掉一帧没人care,但报价丢了或乱序则是事故。

所以 QuoteFlow 的报价 API 毫无疑问用 TCP:报价请求不能丢、字段不能乱序、必须确认对方真的收到。一个有意思的转折是 HTTP/3:它跑在 UDP 上,却在应用层自己重建了可靠性与有序性,目的是绕开 TCP 的一些固有瓶颈——这一点我们放到第 5 节讲 HTTP 版本时再说。

4TLS · 在管道上加密与验身

HTTPS = HTTP 跑在 TLS 之上

管道通了,但默认是明文的——中间任何一跳都能看到、甚至篡改内容。TLS(Transport Layer Security)就是加在 TCP 之上的安全层,HTTPS 本质就是 “HTTP over TLS”。它一次解决三件事:

TLS 给你含义对 QuoteFlow 为什么关键
机密性
confidentiality		内容被加密,中间人看不到投保人 PII(年龄/健康/吸烟)在传输中不可泄露
完整性
integrity		内容被篡改能被发现保费、保额不能在路上被改掉
身份
authentication		证书证明“你连的真是它”防钓鱼站冒充 QuoteFlow 套取客户信息

它怎么做到的?简化版握手:client 发 ClientHello(我支持哪些加密套件)→ server 回 ServerHello + 证书 → client 用内置的 CA 信任链验证书是真的、再协商出一把对称密钥 → 之后双方用这把密钥高速加密通信。TLS 1.3 把握手压到约 1 个 RTT,对重连的会话还能做到 0-RTT 恢复——所以“HTTPS 慢”早已不是过去那个量级。

成本就是多一个 RTT 加一点 CPU,但相对它带来的安全收益微不足道,而且能被连接复用 / 会话恢复摊薄。今天的共识是:一切对外流量都该上 HTTPS。

对 QuoteFlow / 合规的意义
  • encryption in transit 是受监管系统的底线:投保人 PII 在网络上必须加密,这是合规要求而非可选项。
  • 面向 broker 的机器对机器 API可以更进一步用 mTLS(双向 TLS):不只 client 验 server,server 也验 client 的证书,双方都确认身份——比单纯的 API key 更强。
  • 证书会过期、要轮换,过期就是一次线上事故。所以证书生命周期要纳入监控(Day 24 可观测性、Day 25 安全会再展开)。
5HTTP · 双方到底说什么

方法、状态码,与三代演进

前四层把“安全可靠的管道”铺好,真正承载业务语义的是 HTTP。它是一份简单的“合同”:请求 = 方法 + 路径 + headers + body;响应 = 状态码 + headers + body。而且 HTTP 是无状态(stateless)的——每个请求自带全部上下文,服务器不靠上一个请求记着你是谁(状态靠 token / cookie 显式带)。

方法(method)有语义:GET 读、POST 创建/触发计算、PUT/PATCH 改、DELETE 删。这些语义直接关系到“能不能安全重试”(幂等性)——明天 Day 5 会专门讲。报价是“给输入算个结果”,所以用 POST /v1/quotes。

状态码(status code)是给调用方的清晰信号,按首位分家族,设计 API 时用对它,等于把“出什么事了”说清楚:

家族含义QuoteFlow 例子
2xx 成功请求被正确处理200 报价算好并返回
3xx 重定向去别处取 / 用缓存301 旧域名跳新域名
4xx 客户端错是你请求的问题400 参数非法 · 401 未认证 · 403 无权 · 429 触发限流
5xx 服务端错是服务器的问题500 定价服务异常 · 503 过载/维护

▲ 一个常见错误:出错却返回 200,把错误塞进 body。这会让调用方、监控、重试逻辑全都误判——状态码用对,系统才好观测、好自动化(Day 18 重试、Day 24 可观测性都依赖它)。

HTTP 本身也在演进,核心都是为了“在一条连接上更快地搬更多东西”:

版本关键变化主要痛点 / 解决
HTTP/1.1一条 TCP 连接基本一次一个请求排队队头阻塞(head-of-line),要靠开多条连接绕
HTTP/2一条连接上多路复用多个请求 + 头部压缩应用层不再排队,但仍受 TCP 丢包拖累
HTTP/3改跑在 QUIC(基于 UDP) 上,握手更快绕开 TCP 层的队头阻塞,弱网/移动端更稳

这就回收了第 3 节的伏笔:HTTP/3 之所以敢用 UDP,是因为它在 QUIC 里自己实现了可靠传输和加密(TLS 1.3 内建),既要 UDP 的低延迟,又不丢 TCP 的可靠性。把整条链路用 curl -v 拉出来,四层一目了然:

curl -v https://api.quoteflow.example/v1/quotes · 一次请求的四层
*  DNS:  api.quoteflow.example  →  203.0.113.10      # ① 域名→IP
*  TCP:  connected (SYN / SYN-ACK / ACK)            # ② 可靠管道,1 RTT
*  TLS:  handshake done, TLSv1.3 / AES-128-GCM      # ③ 加密 + 验证书
*  ALPN: server accepted h2                         # 协商用 HTTP/2

> POST /v1/quotes HTTP/2                            # ④ 应用层:方法 + 路径
> host: api.quoteflow.example
> content-type: application/json
> authorization: Bearer ***                      # 身份靠 token 显式带(无状态)
>
> {"applicant":{"age":42,"smoker":false},"sum_insured":500000}

< HTTP/2 200                                      # 状态码:成功
< content-type: application/json
< cache-control: no-store                          # 报价不缓存:可审计 / 合规
<
< {"quote_id":"q_8f3a","monthly_premium":38.20,"currency":"AUD"}

这张图怎么连回 Day 3 的延迟预算

回忆 Day 2 给报价定的 p99 < 300ms。若把 QuoteFlow 部署在离用户一个洲之外,光 TCP + TLS 握手就是 ~2 个 RTT,跨洲一个 RTT 按 Day 3 的 150ms 算——还没开始算保费,300ms 预算就已被握手吃光。这正是为什么要:就近部署 + DNS geo-routing 把 RTT 压到同区(~0.5ms 级)、连接复用 / TLS 会话恢复 让后续请求免去重复握手、以及对静态内容上 CDN(Day 7)。网络延迟不是代码能救的,只能从架构上躲。

别忘了合规的痕迹

注意响应里的 cache-control: no-store:报价涉及 PII 且要可审计,不该被中间层随意缓存。TLS 保证 PII 传输中加密;quote_id 让每条结果可追溯;broker 的机器对机器通道可上 mTLS 双向验身——网络这一层,处处都在为 auditability 与 compliance 留位置。

★关键要点

今天带走这四句

1

一次 HTTPS 请求是四层叠加:DNS 找地址 → TCP 建可靠管道 → TLS 加密验身 → HTTP 跑业务。各层只管自己那段。

2

TCP 可靠有序(业务 API 必选),UDP 快而省(实时/遥测)。选择只看一句:丢一两个包要不要命。

3

TLS/HTTPS 给你机密性 + 完整性 + 身份;成本是一两个 RTT,可被连接复用摊薄。对 PII 是合规底线,对外一律上。

4

握手是 RTT 大头:跨洲一个 RTT≈150ms,两次握手就能吃掉 300ms 预算。靠就近部署 / 连接复用 / CDN 来躲,而非靠代码。

读完自测一下

Q1QuoteFlow 的报价 API 该用 TCP 还是 UDP?为什么?
TCP。报价请求不能丢、字段不能乱序、必须确认对方真收到——这正是 TCP 的强项。延迟的代价(握手)在可接受范围。UDP 适合“慢比丢更糟”的场景(音视频/遥测),不适合一笔不能错的业务交易。
Q2HTTPS 第一次连接比纯 HTTP 多花的时间花在哪?对寿险定价值不值?
多在 TLS 握手(TLS 1.3 约 1 个 RTT) 加一点 CPU,还要验证书。非常值:它保护投保人 PII(机密性)、防报价被篡改(完整性)、防钓鱼站冒充(身份)——对受监管的 PII 是合规底线。而且成本能被连接复用 / 会话恢复摊薄。
Q3DNS 的 TTL 设很长 vs 很短,各有什么取舍?
长 TTL:缓存命中高、解析快、DNS 负载低,但 IP 变更 / 故障转移生效慢(客户端拿着旧 IP 直到过期)。短 TTL:切换灵敏(利于蓝绿/故障转移),但解析更频繁、首包延迟与 DNS 负载更高。需要快速切换的关键域名倾向短 TTL,且不把故障转移只押在 DNS 上。

今日术语

DNS
Domain Name System,把域名解析成 IP 地址的“互联网电话簿”,层层缓存。
TTL

UDP

TLS
Transport Layer Security,加密层;提供机密性、完整性与服务器身份验证。HTTPS = HTTP over TLS。
HTTP Status Code
响应状态码,按首位分 2xx/3xx/4xx/5xx 家族,向调用方传递“出了什么事”。
mTLS
双向 TLS,client 与 server 互验证书;常用于机器对机器的高信任 API。
