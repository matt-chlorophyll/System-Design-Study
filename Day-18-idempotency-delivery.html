同一件事做了两遍
—— 幂等、重试与 exactly-once 的真相

在分布式系统里，「这条消息到底处理过没有」往往是个无解的问题。于是工程师不去消灭重复，而是让重复变得无害。今天我们把幂等、重试、死信队列串成一条防线，并戳破「恰好一次」这个最常被误解的承诺。

1问题的根源

为什么「到底处理了没」是个无解问题

想象 QuoteFlow 的报价服务，调用下游的支付服务给一笔新保单收首期保费。请求发出去了，然后……超时了。现在客户端面对一个残酷的事实:它无法分辨到底是哪种情况——是请求根本没送到(下游没收钱)，还是下游收了钱、只是返回的应答在半路丢了?这两种情况，从发送方看长得一模一样。

这就是经典的「两将军困境」(Two Generals' Problem):在一个会丢包的网络里，发送方永远无法 100% 确认接收方是否收到了消息。没有任何重试次数、任何 ack 协议能彻底消除这个不确定性——这是被证明了的。所以分布式系统的设计者不去追求「确认」，而是接受这个事实并绕过它。

面对超时，系统通常只有两种选择，各有代价:

投递语义做法风险
At-most-once
(至多一次)		发一次，超时不重试可能丢:这笔保费根本没收到，无人察觉
At-least-once
(至少一次)		超时就重试，直到拿到 ack可能重:万一下游其实成功了，就收了两次钱

▲ 鱼与熊掌:要么冒「丢」的险，要么冒「重」的险。绝大多数系统选 at-least-once——因为「重」可以靠下一节的幂等消化掉，而「丢」往往无法挽回。

结论很关键:几乎所有可靠的消息系统(Kafka、SQS、RabbitMQ)默认都是 at-least-once，宁可重发也不丢。代价就是消费端必然会见到重复。既然重复无法在投递层消灭，那就把它推到处理层——让「处理两遍」和「处理一遍」结果一样。这就是幂等。

2核心武器

幂等:把「重复」变得无害

幂等(idempotent)的定义很简练:一个操作执行一次和执行多次，对系统状态产生的效果相同。数学里 abs(abs(x)) = abs(x) 就是幂等。在系统里，「把保单 P 的状态设为 ACTIVE」是幂等的(设几次都一样);而「给账户余额 +100」不是幂等的(做两次就多扣/多记一次)。

回到昨天的钩子:夜间重定价跑到第 60 万张崩了。如果「写入新保费」这一步设计成覆盖式写入(SET premium = 算出的值 WHERE policy_id = X)，那么重跑时即便前 60 万张被再算一遍，结果也原样覆盖，最终状态不变——这就是幂等让重跑变安全。反之，若那步是「在流水表里 插入一条调整记录」，重跑就会插两条，账就错了。设计写操作时主动把它做成幂等，是分布式可靠性的第一性原则。

HTTP 方法的幂等性(Day 5 的回声)

这也是为什么 GET / PUT / DELETE 被定义为幂等，而 POST 不是。PUT /policies/123 {status: ACTIVE} 重发几次都是同一个状态;但 POST /quotes 每次都新建一条报价——重发就会冒出多条。所以但凡可能产生副作用又可能被重试的 POST,都需要额外的去重机制。

Idempotency key:给每个意图发一张身份证

业界标准做法(Stripe 等支付 API 都这么做):客户端为每一次业务意图生成一个唯一的 idempotency key(比如一个 UUID)，放在请求头里。服务端维护一张去重表:第一次见到这个 key，正常处理并把「key → 结果」存下来;之后再见到同一个 key，不重新执行，直接把上次存的结果原样返回。这样，无论客户端因超时重试了多少遍，真正的副作用只发生一次。

Case · QuoteFlow 首期保费扣款

客户在 App 上点「确认投保」，前端为这次操作生成 idem_key = "pay_a7f3..."。网络抖动，前端没收到应答，自动重试了 3 次，带着同一个 key。支付服务第一次扣款成功、记下 pay_a7f3 → {charged: 5820, txn: t_99};后面 3 次请求一进来就命中去重表，直接返回那条已有结果——客户只被扣了一次，前端也拿到了确定的成功应答。审计日志里这笔扣款只有一条，traceable 且金额无误。

payment-service · 用 idempotency key 去重(示意伪代码)
def charge_premium(idem_key, policy_id, amount):
    # ① 先查去重表:这个意图以前处理过吗?
    existing = db_get("idempotency", idem_key)
    if existing:
        return existing.result          # 命中 → 直接还回旧结果,不再扣款

    # ② 在一个事务里:既扣款,又登记 key(两者要么都成,要么都不成)
    with db_transaction():
        txn = do_charge(policy_id, amount)        # 真正的副作用,只此一次
        db_put("idempotency", idem_key, {
            "result": { "txn": txn.id, "charged": amount },
            "created_at": now()
        })                                  # 把 key 与结果一并落库(同一事务!)
    return { "txn": txn.id, "charged": amount }

# 关键:扣款 + 写 key 必须在同一事务里原子提交,
# 否则「扣了款但没记下 key」时,重试会再扣一次 —— 破功。

两个常被忽略的细节:其一，登记 key 和真正的副作用必须原子(同一个事务，或借助 Day 17 提过的 outbox 思路)，否则「做了但没记下」的窗口会让幂等失效。其二，去重表不能无限长，要给 key 设 TTL(比如保留 24 小时)——这是用存储成本换防重窗口的取舍。

3重试的艺术

重试是把双刃剑:用错了会引爆系统

既然选了 at-least-once，重试就是家常便饭。但「失败就立刻重试」是新手最危险的写法。设想下游支付服务因为过载开始变慢，于是所有调用方同时超时、同时立刻重发——本就喘不过气的下游瞬间被双倍流量砸中，更慢，触发更多超时，更多重试……这就是 retry storm(重试风暴) / cascading failure,一个小抖动被重试放大成全面雪崩。

做对重试有三件套:

① Exponential backoff(指数退避)——每次重试的等待间隔翻倍:1s、2s、4s、8s……给下游喘息和恢复的时间，而不是火上浇油。
② Jitter(抖动)——在退避时间上加一点随机扰动。否则一千个客户端会在同一秒整齐划一地重试(thundering herd / 惊群)，退避也救不了。加了 jitter，重试被打散在时间轴上，下游负载平滑。
③ 重试上限 + 只重试该重的——设最大重试次数，超了就放弃(进下一节的 DLQ);并且只对可重试错误重试:503 / 超时 / 网络抖动这类瞬时(transient)错误值得重试，而 400 参数非法 / 401 鉴权失败这类永久错误重试一万次也是错，只会白白浪费资源。

client · 指数退避 + 抖动(示意伪代码)
def call_with_retry(request, max_attempts=5):
    for attempt in range(max_attempts):
        resp = send(request)                    # 带同一个 idempotency key 重发,才安全
        if resp.ok:
            return resp
        if not is_retryable(resp):           # 400/401 永久错误 → 立刻放弃,别空转
            raise PermanentError(resp)

        base = 2 ** attempt               # 指数退避: 1, 2, 4, 8, 16 秒
        wait = base + random(0, base)     # + jitter 抖动,打散惊群
        sleep(wait)

    send_to_dlq(request)                   # 重试耗尽 → 进死信队列,等人工/补偿
    raise RetriesExhausted()
重试与幂等是绑定出现的
  • 注意上面每次重发都带同一个 idempotency key。重试和幂等必须成对使用:没有幂等的重试，等于主动制造重复副作用;有了幂等，重试才是安全的。明天的 circuit breaker(熔断器)会再加一层保护——下游连续失败时干脆停止重试一段时间，从根上掐断重试风暴。(这正是 Day 20「限流、熔断、背压」的内容。)
4兜底防线

死信队列:毒丸消息的隔离区

有些消息无论重试多少次都会失败:格式损坏、引用了一个早已不存在的保单、触发了某个永远过不去的 bug。这种叫 poison message(毒丸消息)。如果放任它卡在队列头反复重试，它会堵住后面所有正常消息——一颗毒丸毒死整条队列。

DLQ(Dead Letter Queue，死信队列)就是它的隔离区:当一条消息重试达到上限仍失败，系统不再死磕，而是把它移到一个专门的队列搁置起来，主队列继续处理后面的消息、不受拖累。DLQ 里的消息不会丢，而是等待人工检查、修复后重新投递(replay)，或触发告警。它把「自动重试解决不了的问题」从快速失败路径里隔离出来，交给慢速的人工/补偿流程，既保住了吞吐，又不丢数据。

5戳破神话

exactly-once 的真相:它不是你以为的那个意思

「Exactly-once(恰好一次)」是分布式系统里最性感、也最被误解的词。很多人以为它意味着「消息在网络上只传一次、绝不重复」。那是不可能的——第 1 节的两将军困境已经判了死刑:只要网络会丢包，发送方就无法保证「只投一次」既不丢又不重。

把它刻进脑子的一句话
  • at-least-once 投递(允许重复)　+　幂等消费 / 去重(消化重复)　=　effectively-once 效果。底层照样可能投递好几遍，但因为消费端用 idempotency key 或去重逻辑把重复吃掉了，对最终状态而言，就好像只发生了一次。这才是工程上能落地的「恰好一次」。

那 Kafka 等系统宣传的「exactly-once semantics(EOS)」是骗人的吗?不是，但要看清它的边界:Kafka 的 EOS 通过幂等 producer + 事务，能在「Kafka 读 → 处理 → 写回 Kafka」这条闭环内部做到精确一次。可一旦你的副作用跨出了这个边界——比如要给外部支付网关扣款、给第三方发邮件、写一个非事务的数据库——Kafka 的事务管不到外面，你仍然必须自己在那一侧用 idempotency key 去重。没有银弹:跨系统的「恰好一次」，最终都要落到「幂等」这块基石上。

说法真实含义对 QuoteFlow 怎么用
"只投一次"网络层做不到，是误解别指望它，按「会重复」来设计
at-least-once可靠投递的现实默认:宁重勿丢消息/重试的底座，搭配幂等
effectively-onceat-least-once + 幂等去重的效果扣款、签发只发生一次的真正实现
Kafka EOS仅在「Kafka→处理→Kafka」闭环内成立跨出去调支付仍需自己幂等

▲ 对一个受监管的扣款/签发系统，「只收一次钱、只签一次保单」不是靠某个神奇开关，而是靠你在每个有副作用的边界上亲手放一个 idempotency key。

Q1客户端调支付服务扣款，超时了。为什么它无法判断到底扣没扣成?这叫什么问题?
两将军困境(Two Generals' Problem)。「请求没送到」和「下游成功了但应答丢在回程」从发送方看完全一样。会丢包的网络里，发送方无法 100% 确认接收方是否收到——这是被证明无解的，所以系统不追求确认，而是用幂等绕过它。
Q2「给账户余额 +100」和「把保单状态设为 ACTIVE」，哪个天然幂等?对不幂等的那个，重试前你会怎么改造?
「设为 ACTIVE」幂等(设几次都一样);「+100」不幂等(做两次多记一次)。改造:给这次扣款/记账分配一个 idempotency key，服务端用去重表保证同一 key 只真正执行一次，重试只取回旧结果。
Q3有人说「我们用了 Kafka 的 exactly-once，所以调外部支付网关绝不会重复扣款」。哪里错了?
边界错了。Kafka 的 EOS 只在「Kafka 读→处理→写回 Kafka」的闭环内成立。一旦副作用跨出去(调外部支付网关)，Kafka 事务就管不到了——那一侧仍可能重复，必须自己在支付调用上放 idempotency key去重。跨系统的恰好一次，终归要靠幂等。

A→Z术语表

今日术语

Idempotency
一个操作执行一次与执行多次，对系统最终状态的效果相同。消化重复的核心性质。
Idempotency Key
客户端为每次业务意图生成的唯一标识，服务端据此去重，保证同一意图的副作用只真正发生一次。
Two Generals' Problem
会丢包的网络里，发送方无法 100% 确认接收方是否收到消息——被证明无解，是重复不可避免的根源。
At-least-once
投递语义:超时就重试，保证不丢，但可能重复。可靠消息系统的现实默认。
At-most-once
投递语义:发一次不重试,不会重复,但可能丢失。
Exponential Backoff
重试间隔逐次翻倍(1s→2s→4s…)，给下游恢复时间，避免火上浇油。
Jitter
在退避时间上加随机扰动，打散同时重试的「惊群」，让下游负载平滑。
Retry Storm
大量调用方同时超时同时重试，把小抖动放大成雪崩(cascading failure)。
Poison Message
无论重试多少次都会失败的消息(损坏/永久错误)，会堵塞队列。
Dead Letter Queue (DLQ)
毒丸消息的隔离队列:重试耗尽后移入，不丢、不堵主队列，待人工排查或修复后重放。
Effectively-once
at-least-once 投递 + 幂等去重得到的效果:底层可能多次，最终状态如同一次。即可落地的「exactly-once」。
Exactly-once Semantics (EOS)
如 Kafka 提供:仅在「读→处理→写回同一系统」的闭环内成立;跨出边界仍需自行幂等。
