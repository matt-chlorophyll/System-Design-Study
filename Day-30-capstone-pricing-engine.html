1第一步 · 需求与范围

先把题目读懂，再动手

面试里最高的失分点，是听到「设计一个寿险报价平台」就开始画框图。正确的开场是圈定范围 + 列两类需求（Day 1）。QuoteFlow 的范围我们一路用到现在：公开网站 / App / broker API 三个渠道；新业务侧的实时报价 → 投保申请 → 自动核保 → 保单签发；以及 in-force 侧的夜间批量重定价、billing、再保上报。

关键是把 functional 和 non-functional 分清，因为难点全在后者。而且要立刻看出：这个系统其实是两个性质相反的子系统缝在一起——一条要低延迟（实时报价），一条要高吞吐（夜间批量），它们的设计取向几乎相反，这决定了后面的架构必须把读写、在线离线分开。

需求面QuoteFlow 的具体条目第几天的工具
Functional报价、校验、自动核保、签发、in-force 管理、夜间重定价、billing、再保上报Day 1 · 5 · 10
Latency实时报价 p99 < 300ms；核保「即时」决策秒级Day 2 · 3 · 7
Throughput夜间重算百万级 in-force 保单，跑进维护窗口Day 2 · 17

▲ 一张表就把「设计要满足什么」钉死了。注意 auditability 在普通系统里是加分项，在受监管寿险定价里是上线前提——后面每个组件都要为它让路。

2第二步 · 估算

用数字给设计定调

估算（Day 3）的作用不是精确，而是判断这是个什么量级的系统、瓶颈大概在哪。做几个 back-of-envelope：

假设报价 峰值 2,000 QPS。一次报价要读费率表 + 核保规则 + 跑评分模型——如果每次都打数据库，单库扛不住，且费率表是读多写少的典型，缓存命中率能到 95%+（Day 7），于是真正落到 DB 的只剩百来 QPS。这一步估算直接告诉你：报价路径必须有缓存层，不是可选项。

in-force 侧：假设 500 万份在内保单，夜间窗口 4 小时。要全部重算，需要 5,000,000 ÷ (4×3600) ≈ ~350 笔/秒的持续吞吐——这不是延迟问题，是把活儿切碎、并行、可重试的批/流处理问题（Day 17）。数字一摆，「为什么实时和批量要拆开」就不再是教条，而是算出来的。

估算的用法
  • 面试里把这两三个数说出来，比画十个框更能证明你「懂系统」——因为架构的每一个分叉，都是被某个数字逼出来的。2000 QPS 逼出缓存，350 笔/秒逼出批处理，百万级数据逼出分片。
3第三步 · 高层架构

一张端到端蓝图

现在把零件摆上桌。读路径（报价）和写路径（核保签发）、在线和离线（夜间批量），在图里就是分开的几条泳道。每个框，都是前 29 天的某一天：

读这张图的正确方式不是「记住框」，而是顺着一笔请求走：报价从渠道进来 → 网关限流鉴权 → 报价服务命中 Redis 拿到费率表/规则 → 调评分模型 → 返回，并把这条报价（含版本号）写进 audit log。投保这种写动作则不走同步阻塞，而是丢进队列异步处理。夜间批量完全是另一条泳道，跟在线互不抢资源。

4第四步 · 关键取舍

每个分叉，背后是哪一天的取舍

架构图只是「摆零件」，真正的功力在于能说清为什么这样选、代价是什么（Day 28 的 ADR 思维）。挑四处最关键的：

设计决定选了什么 + 为什么代价 / 来自
读写分离报价走缓存 + follower 读；签发走队列异步写。一条优化延迟，一条优化吞吐与解耦读到的可能是 follower 的稍旧数据（Day 12 复制延迟）
费率表版本钉死请求里带 rate_table_version，缓存按版本 key。换版本=换 key，天然一致、可复现要管版本生命周期、灰度与回滚（Day 7 · 28）
核保异步化投保 → 事件入队 → 核保 worker 消费。削峰、可重试、可补偿从同步「秒回」变最终一致；需幂等 + 死信队列（Day 15 · 18）
audit log 独立且不可变append-only，与业务库分离。任何决定都先留痕再生效多一份写、多一份存储；但合规不可妥协（Day 1 · 24）

▲ 面试官真正想听的就是右边这一列。能主动说出「我选 A，代价是 B，因为在这个场景 B 可接受」，比任何漂亮架构图都值钱。

下面把这套设计的灵魂——把版本与可审计焊进每一笔写入——落成伪代码。这是寿险定价区别于普通 CRUD 系统的地方：

quote_and_log.py · 报价路径核心（示意）
def handle_quote(req):
    # 1) 钉死版本 —— consistency + reproducibility 的起点
    ver = req.rate_table_version or registry.current_version()

    # 2) 读多写少 → 缓存优先（命中率 95%+，Day 7）
    rates = cache.get(f"rates:{ver}") or db.load_rates(ver)
    rules = cache.get(f"rules:{ver}") or db.load_rules(ver)

    # 3) 纯函数式定价：同输入 + 同版本 → 同输出（可复现）
    premium, applied = price(req.applicant, rates, rules)
    risk = scoring_model.score(req.applicant)      # 模型也带版本

    # 4) 先留痕，再返回 —— audit 是一等公民，不是事后补
    audit.append({
        "quote_id": new_id(), "premium": premium,
        "rate_table_version": ver,
        "model_version": scoring_model.version,
        "rules_applied": applied,
        "computed_at": now(),
    })
    return { "premium": premium, "risk": risk, "version": ver }

注意这段代码里，每一个 non-functional 需求都对应一两行：版本钉死（一致性 + 可复现）、缓存优先（延迟）、纯函数定价（可复现）、先 append 再返回（可审计）。这就是 Day 1 说的「从契约层就为质量属性留位置」走到了实现层。

5第五步 · 抗住故障

找瓶颈、加冗余、想清楚怎么挂

设计的最后一步（Day 1 第六步）是主动找系统会怎么坏，并让它坏得优雅。把前面学的韧性零件套上去：

报价服务无状态，所以可以横向多副本 + 跨可用区部署（Day 6 · 12），挂几台不影响。评分模型或费率服务变慢时，报价路径要有熔断 + 降级（Day 20）——比如退回到上一版安全费率或返回「稍后重试」，而不是把线程全卡死引发雪崩。网关层做限流，挡住 broker 端突发洪峰，保护后端。

数据层用 leader-follower 复制保可用与读扩展，接受复制延迟这个代价；真要强一致的地方（比如保单签发、扣费）走主库 + 事务（Day 14）。跨服务的多步流程（投保 → 核保 → 签发 → 扣费）用 saga 做最终一致 + 补偿，而不是一个分布式大事务。所有这些，最后都靠可观测性兜底：SLI/SLO + 告警（Day 24）让你在用户投诉前就发现 p99 在涨。

受监管定价的收尾提醒
  • 韧性设计里有个寿险特有的约束：降级也要可审计。如果报价时模型挂了、用了 fallback 费率，这件事必须照样写进 audit log——否则事后无法解释「为什么这条报价跟正常情况不一样」。在受监管系统里，连「出过故障」本身都要留痕。

?毕业自测 + 收官思考

检验一下这 30 天

Q1为什么 QuoteFlow 的实时报价和夜间批量重定价要拆成两条独立路径？
因为它们优化的 NFR 相反。报价要低延迟（p99<300ms、读多、要缓存），批量要高吞吐（百万级、可切碎并行重试、可延迟）。塞进同一套设计会两头不讨好，还会互相抢资源。这是 Day 2 + Day 17 的核心判断。
Q2请求里带 rate_table_version 同时解决了哪两个 non-functional 需求？
consistency 和 auditability/reproducibility。钉死版本意味着费率表更新不会让进行中的请求新旧混用（一致性），也意味着任何一条历史报价都能用同一版本+同输入精确复现（可审计/可复现）。顺带还让缓存可以安全地按版本做 key。
Q3把核保从同步改成「事件入队 + worker 消费」，得到什么、又必须额外做什么？
得到：削峰、解耦、可重试、对突发流量更稳。代价/必须做：从同步秒回变成最终一致（要管理用户体验）；消费端必须幂等（同一事件重投不能重复签发），并配死信队列兜住反复失败的消息。Day 15 + Day 18。

A→Z术语表

今日术语

End-to-end Design
把需求、接口、存储、扩展、韧性等各层零件拼成一个完整可运行系统的设计过程。
Read/Write Split
把读路径（缓存+follower）与写路径（主库/队列）分开优化，各自满足不同 NFR。
Hot Path
延迟最敏感、流量最大的关键路径（这里是实时报价），优先为它做缓存与降级。
Version Pinning
把费率表/规则/模型版本钉死在请求里，保证一致性与可复现。
Saga
用一串本地事务 + 补偿动作替代分布式大事务，实现跨服务流程的最终一致。
Graceful Degradation
依赖故障时退回到受限但可用的行为（如 fallback 费率），而非整体崩溃。
Append-only Audit Log
只追加、不可改的决策留痕，支撑 traceability 与 compliance。
Capstone
综合作业：把所学整合进一道完整的 interview-style 系统设计题。
