系统一定会坏
—— 把「坏」设计成可承受的

硬盘会坏、网线会断、整个机房会停电、人会手滑误删表。可靠性工程不假设这些不发生，而是承认它们必然发生，再用冗余、隔离、灾备、演练把每一次故障的代价压到可承受的范围内。今天我们学怎么和故障共处。

1心态：假设一切都会坏

可靠不是「不出错」，是「出错也没事」

新手对「可靠」的直觉，往往是「让每个组件都别坏」。这条路走不通。任何一块硬盘都有年化故障率，任何一台机器都会重启，任何一个机房都可能因为施工挖断光纤或电力故障而整片失联。规模一大，「极小概率的事」每天都在发生——一万块盘，哪怕年故障率 1%，平均每天也有几块在坏。

所以可靠性工程换了个问法：不是「怎么让它不坏」，而是「当它坏了——而它一定会坏——系统整体还能不能继续服务、最多损失多少、多久能恢复」。这套思路有个经典名字叫 design for failure(为失败而设计)。它贯穿今天所有内容：你不是在消灭故障，你是在把单点的、不可控的故障，转化成局部的、可承受、可恢复的故障。

先把两个常被混用的词钉死。Reliability(可靠性) 是「系统在一段时间里持续正确工作的能力」，常用 MTBF(平均无故障时间)衡量；Availability(可用性) 是「在某一刻系统可用的概率」，就是我们 Day 2 量化过的那串 9。两者相关但不同：一个系统可以频繁出小故障但每次秒恢复(可靠性低、可用性高),也可以很少坏但一坏就停很久(可靠性高、可用性低)。今天的工具，本质都是在缩短「坏了到恢复」的时间，从而把可用性撑住。

承接前面几周的工具

2故障模式

认识敌人：故障怎么发生、怎么被放大

要为失败而设计，先得知道失败长什么样。故障不是只有「挂了」一种，下面几类各有各的应对：

故障模式它是什么对 QuoteFlow 的样子
崩溃 / 宕机
crash-stop		组件干脆地停了，不再响应报价服务一个实例 OOM 被杀掉
慢故障
gray failure		没死，但又慢又卡——比死更难处理费率库一个副本磁盘老化，查询从 5ms 变 800ms，拖垮上游
网络分区
partition		机器都活着，但彼此连不上(Day 12 的 P)主备机房之间链路中断，两边都以为对方挂了
级联失效
cascading		一处故障把负载推给别处，连环压垮一个副本挂 → 流量涌向其余副本 → 它们也过载 → 雪崩
数据 / 人为故障
data & human		坏数据、配置错误、误删——冗余救不了错误的费率表被推到所有副本，每个副本都「忠实地」算错

▲ 注意最后两行：级联失效会把一个小故障放大成全局故障；而数据/人为故障对「复制冗余」免疫——你把错误数据可靠地复制到了每一处。这正是「为什么光有冗余不够」。

头号敌人：单点故障(SPOF)与级联

可靠性设计里最先要猎杀的，是 single point of failure(单点故障，SPOF)——任何「它一坏，整个系统就停」的组件。一台没有备份的数据库主节点、一个只有一份的 API 网关、一条独苗的网络链路，都是 SPOF。找 SPOF 的方法很机械：对架构图上每个框问一句「如果这个框现在消失，会发生什么？」——只要答案是「全站挂」，它就是必须消灭的单点。

而 级联失效 是让局部故障升级为全局灾难的放大器。机制几乎总是同一个：某个节点失效 → 它的负载被转移到健康节点 → 健康节点因此过载、也变慢或挂掉 → 更多负载再转移……正反馈一旦启动，整个系统在几十秒内连环倒下。这就是 Day 20 那些护栏(熔断、限流、bulkhead、超时)真正的用武之地——它们的核心作用就是在级联的链条上打断正反馈，宁可拒绝一部分请求，也不让故障蔓延到全局。

3冗余

消灭单点的唯一办法：留备份

对付 SPOF 的根本手段就一个字——冗余(redundancy)：任何关键组件都不止一份，一份倒下，另一份顶上。但「留备份」有好几种姿势，代价和切换速度差别很大，要会挑：

模式怎么工作切换 / 成本
Active-Active
双活		多份同时对外服务、分担流量一份挂，其余无缝接住(只需扛住多出来的负载)；成本高，但资源不闲置
Active-Passive
主备 / 热备		主在服务，备待命(可能预热)主挂 → failover 切到备，有秒级到分钟级中断；备机平时闲着，成本是「保险费」
N + 1 / N + M满足负载要 N 份，多配 1(或 M)份余量容忍 1(或 M)份同时坏而不降容量；冗余度可量化裁剪
跨可用区 / 跨区域
multi-AZ / region		副本分散到不同机房、不同地理区域扛住整个机房/区域级故障；跨区域要付出延迟与数据同步的代价

一个关键纪律：别让冗余「假冗余」

冗余最容易翻车的地方，是看似两份、其实共享同一个隐藏单点。两台数据库副本，如果插在同一个机柜、同一个电源、同一台交换机下——电源一跳，两份一起死，你的「冗余」是假的。这就是为什么真正的冗余要讲故障域(failure domain)隔离：副本之间不能共享会一起坏的东西(同一台宿主机、同一个机架、同一个机房、同一片供电)。云上的 availability zone(可用区) 就是把这件事产品化——不同 AZ 在物理上电力、网络、制冷都隔离，把副本摊到多个 AZ，才算真冗余。

还有一条经济学纪律：冗余不是越多越好，它直接换钱。从「单份」到「多 AZ 双活」，可用性的每多一个 9，成本往往不是线性而是陡增。所以冗余度要由业务需求(SLO)反推，而不是一味堆。QuoteFlow 里，对外实时报价这条路径值得多 AZ 双活(挂了就丢生意、伤口碑)；而一个内部的、跑批用的分析报表服务，active-passive 甚至「坏了明天再修」可能就够——把钱花在最该花的可用性上。

4灾备：RTO 与 RPO

大灾难来了：能多快恢复、会丢多少数据

冗余对付的是「一个组件坏」。但还有更大的灾难：整个区域断电断网、机房失火、勒索软件加密了你的主库。这时需要 disaster recovery(灾备，DR)——一套「主站整体没了，怎么在别处重新站起来」的预案。衡量灾备方案，业界就用两把尺子，务必记牢：

RTORPO
全称Recovery Time ObjectiveRecovery Point Objective
回答恢复服务最多花多久?(停机时长)最多能容忍丢多少数据?(时间窗口)
指向沿时间轴向前看：多久能重新上线沿时间轴向后看：丢回到哪个时间点的数据
由什么决定切换/重建的速度:热备 vs 冷备份恢复备份/复制的频率:连续复制 vs 每天一次
越严越贵RTO→0 需要随时待命的热备站点RPO→0 需要同步复制(牺牲写延迟)

▲ 记忆法：RTO 是「Time，多久能回来」，RPO 是「Point，丢到哪个点」。一个管停机时长，一个管数据丢失量——是两件独立的事，要分别定指标。

有了这两把尺子，灾备方案就能按预算分档，从便宜到贵大致是：冷备份(Backup & Restore)——只存快照，灾后现搭机器恢复，RTO 几小时、RPO 几小时，最便宜；温备(Pilot Light / Warm Standby)——核心组件常驻、按需放大，RTO 分钟到小时；热备双活(Multi-site Active-Active)——两地同时在线，RTO 近乎 0、RPO 近乎 0，最贵。选哪档，不是技术问题，是「这套系统停一小时、丢一小时数据，业务损失多少」算出来的。

5混沌工程

与其等它半夜崩，不如白天主动弄崩它

前面的冗余和灾备都设计好了——但你怎么知道它们真的管用?故障转移配置可能写错、备份可能根本没法恢复、那条「自动切换」的脚本可能三年没人测过。绝大多数线上大故障，败在「我们以为有冗余，真出事时它没生效」。混沌工程(chaos engineering) 就是答案：在可控的条件下，主动往生产(或类生产)系统里注入故障，验证系统是否如预期那样优雅降级。理念由 Netflix 的 Chaos Monkey 推广——它会在工作时间随机杀掉生产实例，逼工程师把「任何一台随时会死」当成设计前提。

关键是它不是「乱搞」，而是一套科学方法：① 先定义系统正常时的稳态(steady state)，用指标描述(比如报价 p99 延迟、成功率)；② 提出假设——「杀掉一个 AZ，稳态应该不变」；③ 在受控、小范围(blast radius)内注入故障；④ 观测稳态有没有被打破。如果系统扛住了，你赢得了信心；如果没扛住，你在白天、有人盯着、可以随时叫停的条件下发现了弱点——这远好过它在某个周日凌晨三点自己爆发。控制爆炸半径和有快速止损的开关是做这件事的前提纪律。

受监管系统怎么做混沌
  • QuoteFlow 不会去生产环境随机杀报价实例——监管和客户体验都不允许。务实的做法是在类生产(staging)的影子环境里、用影子流量(回放真实请求)跑混沌实验：注入「费率库变慢」「主 AZ 失联」「再保上报接口超时」，验证熔断、降级、failover 是否如预期触发，并把每次演练完整留痕——这本身就是向监管证明「我们具备恢复能力(operational resilience)」的证据。
6贯穿案例

给 QuoteFlow 设计「打不死」的报价路径

把今天五块拼图按在 QuoteFlow 最关键的资产——对外实时报价——上。它一旦不可用或算错，直接丢生意、甚至触发监管问题，所以值得最高规格的可靠性投入。

Case · QuoteFlow

① 消灭单点 + 冗余

报价 API 做成 active-active 多副本，摊到至少两个 AZ，前面挂负载均衡 + 健康检查(Day 6)，坏实例自动摘除。费率/规则库用 leader-follower 复制(Day 12)，follower 跨 AZ；主挂了自动 failover 选新主。每个框都过一遍「它消失会怎样」，确保没有 SPOF。

② 打断级联

报价服务调用风险评分、再保参数等下游时，统统加 超时 + 熔断 + bulkhead(Day 20)：某个下游慢了，快速失败并降级(比如用缓存的费率版本给一个保守报价)，而不是把线程全耗死、拖垮整条链路。

③ RTO / RPO 与灾备

给报价路径定档：RTO < 5 分钟、RPO 近乎 0(费率/保单数据一条都不能丢、要可复现)。这逼出「跨区域、对关键数据用同步或近实时复制」的方案。而内部夜间分析库可以宽松到 RTO 数小时、RPO 一天——钱花在刀刃上。

④ 混沌 + 审计

在影子环境定期演练「杀一个 AZ」「费率库变慢」「failover」，每次都验证报价稳态(p99、成功率、复现性)不破，并把演练与每次真实故障的检测→恢复全程留痕——既是改进输入，也是向监管证明 operational resilience 的合规证据。

下面用伪代码把「级联打断 + 优雅降级」这一环具体化——感受可靠性是怎么写进调用逻辑的，而不是事后补的运维补丁：

pricing/quote_handler.py · QuoteFlow 报价的弹性骨架(示意)
# 目标：任一下游故障 → 局部降级，绝不整条挂死
def handle_quote(req):
    rates = get_rate_table(req.version)        # 主路径：钉版本，保证可复现

    try:
        # 下游风险评分：超时 + 熔断，防级联(Day 20)
        score = risk_svc.score(req, timeout=120ms)
    except (Timeout, CircuitOpen):
        score = fallback_score(req)             # 优雅降级：用保守规则兜底
        audit.log("degraded", reason="risk_svc_unavailable")  # 降级也留痕

    quote = price(req, rates, score)

    # 关键数据同步落到跨 AZ 副本后才算成功 → 守住 RPO≈0
    persist_sync(quote, replicas=2, zones=["az-a", "az-b"])

    audit.log("quote", id=quote.id, image=DEPLOY_SHA,   # 哪个版本算的
              rate_version=req.version, degraded=quote.degraded)
    return quote

留意三处：风险评分挂了不是抛错而是降级兜底(打断级联);persist_sync 同步写到两个 AZ 才返回(守住 RPO);而每一步都写 audit——连「这次报价是降级算的」都记下来。在受监管定价里，故障期间发生了什么、系统怎么应对的，本身就是必须可追溯的一等数据。

★关键要点

今天带走这四句

1

故障是常态不是异常。可靠性不是「让组件不坏」，而是「坏了也能继续服务、损失可控、快速恢复」——design for failure。

2

先猎杀 SPOF(用冗余),再用 护栏打断级联(熔断/限流/超时)。真冗余要跨故障域,否则是假冗余。

3

灾备用两把尺子：RTO(多久恢复)+RPO(丢多少数据)。它们由业务损失反推,越严越贵,要分档花钱。

4

冗余设计了不等于有效。混沌工程在可控条件下主动注入故障,白天把弱点逼出来——对 QuoteFlow,演练留痕本身就是合规证据。

?今日小测 + 思考题

读完自测一下

Q1「报价数据库只有一台主、没有副本」——这是什么?为什么危险?
这是 单点故障(SPOF)。它一坏，整个报价路径就停——不管上游有多少副本都救不了。对它问「如果这个框消失会怎样」，答案是「全停」，所以必须用复制/failover 做冗余来消灭。
Q2「灾后最多容忍丢 5 分钟的数据」——这定的是 RTO 还是 RPO?要怎么实现?
这是 RPO(Recovery Point Objective),管「丢多少数据」。RPO=5 分钟意味着备份/复制频率至少要 5 分钟一次;若要 RPO≈0,得用同步复制(代价是写延迟上升)。注意它和 RTO(多久恢复服务)是两件独立的事。
Q3两份数据库副本插在同一个机柜、同一路供电下,算真冗余吗?
不算——这是「假冗余」。它们共享一个隐藏单点(供电/机柜),电源一跳两份一起死。真冗余要做故障域(failure domain)隔离,把副本摊到不同 AZ,确保它们不会因为同一个原因一起坏。
Q4既然要稳,为什么 Netflix 反而主动去杀生产实例?
这是 混沌工程。冗余/故障转移「配了」不等于「真的有效」——很多大故障就败在「以为有冗余、真出事没生效」。主动在可控、小爆炸半径、能随时止损的条件下注入故障,能在白天有人盯着时把弱点逼出来,远好过它在凌晨自己爆发。

今日术语

Reliability
系统在一段时间内持续正确工作的能力(常用 MTBF 衡量),区别于某一刻可用的 availability。
Design for Failure
把「组件必然失效」当设计前提,目标是让故障局部化、可承受、可快速恢复。

Single Point of Failure,单点故障:一坏整个系统就停的组件,必须用冗余消灭。

Redundancy
关键组件留多份(active-active / active-passive / N+1),一份倒下另一份顶上。
Failure Domain
故障域:会「一起坏」的范围(同机柜/同供电/同机房)。真冗余要跨故障域隔离。
Failover
故障转移:主组件失效时自动(或手动)把服务切到备用组件。
RTO
Recovery Time Objective:灾后恢复服务可容忍的最长停机时长。
RPO
Recovery Point Objective:灾后可容忍丢失的最大数据时间窗口,由备份/复制频率决定。
Availability Zone
可用区:云上电力/网络/制冷物理隔离的机房单元,把副本摊到多 AZ 才算真冗余。
Chaos Engineering
混沌工程:在受控、小爆炸半径内主动注入故障,验证系统是否如预期优雅降级。
Blast Radius
爆炸半径:一次实验/故障可能波及的范围,混沌实验要刻意把它控制到最小。
