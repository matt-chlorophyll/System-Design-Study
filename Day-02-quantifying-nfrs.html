把“做得多好”变成
能算的数字

昨天我们列出了 non-functional 需求;今天把它们逐个量化——并看清这些数字之间真实的、躲不掉的取舍。

1Latency:别信平均值

用百分位说话,盯住那条尾巴

“平均延迟 80ms”听起来不错,但它会骗人。延迟分布几乎总是右偏的:大多数请求很快,少数请求拖得很长。平均值被这条长尾轻轻一拉就失真,而用户真正记住的,恰恰是那几次卡顿。

所以工程上用百分位(percentile)来描述延迟。p99 = 300ms 的意思是:把所有请求按耗时排序,99% 的请求都不超过 300ms,只有最慢的 1% 比它更久。常用的几个:

  • p50(中位数):典型体感,一半请求比它快。
  • p99:几乎所有人的“最坏体验”;SLA 通常写在这里。
  • p99.9:极端尾部,大流量下每天都有成千上万次请求落在这。

为什么尾延迟在系统里会被放大?因为一个请求常常要扇出(fan-out)成多个下游调用。QuoteFlow 的一次报价,可能同时去取费率表、跑核保规则、查再保参数——只要任意一个慢,整次报价就慢。当一个请求依赖 N 个下游、要等它们全部返回时,“至少一个落在尾部”的概率随 N 迅速上升,于是下游的 p99 会变成上游的常态。这就是为什么大系统里压尾延迟,往往比压平均值难得多。

2Throughput 与 Little's Law

“多快”和“多少”是两个轴

Latency 衡量单次请求多快返回;throughput 衡量单位时间能处理多少(常写成 QPS / RPS,每秒查询/请求数)。两者是不同的维度:一辆 F1 很快(低延迟)但只坐两个人;一列地铁单程慢(高延迟)却一趟运几千人(高吞吐)。设计时必须分开说清你要的是哪一个。

把这两个轴连起来的,是一条朴素却极有用的公式 —— Little's Law:

公式

L  =  λ  ×  W

系统中同时在处理的请求数(并发 L)= 到达速率(throughput λ)× 每个请求停留时间(latency W)

它的威力在于:三个量知道两个就能推第三个。给 QuoteFlow 估个数——若实时报价 λ = 500 QPS,平均处理 W = 0.2s,那么任意时刻系统里大约有 L = 500 × 0.2 = 100 个请求在飞。这个 100 直接告诉你:线程池/连接数/内存要按“同时 100 个在途”来备,而不是按 500。

还有一个反直觉但关键的结论:当系统接近吞吐上限时,延迟会急剧恶化。队列开始堆积,W 暴涨,p99 先崩。所以“提高吞吐”和“压低延迟”常常彼此拉扯——把利用率推到 95% 省了机器,却可能让 p99 翻好几倍。容量规划要留余量(headroom),正是为此。(Day 3 会专门做这类 back-of-envelope 估算。)

3Availability:数清那几个 9

“高可用”要换算成停机时间

Availability 就是系统正常服务的时间比例。但“99.9%”听着抽象,翻译成“一年能坏多久”立刻就有体感。记住这张表,面试和评审里随口能报:

可用性俗称每年停机每月停机
99%两个 9≈ 3.65 天≈ 7.2 小时
99.9%三个 9≈ 8.77 小时≈ 43.8 分钟
99.99%四个 9≈ 52.6 分钟≈ 4.4 分钟
99.999%五个 9≈ 5.26 分钟≈ 26 秒

▲ 每多一个 9,容许的停机就少一个数量级——成本也往往跳一个台阶。多数业务系统的合理目标是 3~4 个 9;盲目追五个 9 通常不划算。

真正的陷阱在于:可用性会随依赖“串联”而变差。如果报价要顺序依赖 A、B、C 三个服务,任一挂掉就报价失败,那么整体可用性是它们的乘积:0.999 × 0.999 × 0.999 ≈ 0.997——只剩三个 9 不到,比单个还差。依赖越多,串得越长,越脆。

反过来,冗余(并联)能把可用性拉上去。同一个服务放两个独立副本,只要不同时都挂就还能服务,不可用概率相乘:1 − (1−0.99) × (1−0.99) = 0.9999——两个“两个 9”的副本并起来,居然到了四个 9。这就是为什么高可用设计离不开冗余与多副本。这部分数学,下面用代码直观看一眼。

availability.py · 串联 vs 并联,以及延迟预算
# ── 可用性:依赖是“串联”还是“并联” ──
chain    = 0.999 * 0.999 * 0.999          # 三个串联依赖 → 0.9970，更差
parallel = 1 - (1-0.99) * (1-0.99)        # 两副本并联 → 0.9999，更好

# ── 延迟预算:300ms 的 p99 SLA 怎么分下去 ──
budget_ms = 300
spend = {
  "auth_check":        15,
  "rate_table_fetch":  40,   # 命中缓存;未命中会飙到 ~250ms → 砸 p99
  "underwriting_rules":60,
  "premium_calc":      25,
  "reinsurance_param": 35,
  "network_overhead":  20,
}
spent     = sum(spend.values())            # = 195ms
headroom  = budget_ms - spent             # = 105ms 留给尾部抖动 / 重试

assert headroom > 0, "延迟预算超支:得砍依赖或加缓存"

这段“延迟预算”很值得养成习惯:把 SLA 的 p99 当成一笔钱,分给路径上的每一段,你会立刻看清哪里是瓶颈、还剩多少余量。注意 rate_table_fetch 那行——缓存未命中会从 40ms 跳到 250ms,这正是尾延迟和缓存策略(Day 7)交汇的地方。

4Scalability 与 Consistency

“量涨了扛得住”与“到处读到的一样”

Scalability — 加资源,产能要跟着涨

可扩展性问的是:当负载翻倍,你能不能靠加资源把吞吐也接近翻倍?两条路:纵向扩展(scale up)——换更强的单机,简单但有天花板、且单点风险高;横向扩展(scale out)——加更多机器分摊,理论上无上限,是分布式系统的主线(Day 6 详谈)。

理想是线性扩展:2 倍机器 = 2 倍吞吐。现实几乎从不线性——总有无法并行的部分(共享数据库、锁、协调开销),机器越多,这部分占比越拖后腿,加到一定程度甚至负增长。所以“能扩展”不是一句口号,而要问清:扩到哪一步开始失效、瓶颈在哪个共享资源。对 QuoteFlow,无状态的报价计算容易横向扩;而它们都要读的那张费率表/数据库,往往才是真正的扩展瓶颈。

Consistency — 多副本下,大家读到的一样吗

一旦数据有多个副本(为了可用与扩展,几乎必然),就要回答:写入之后,别处立刻能读到最新值吗?两个极端:

  • Strong consistency(强一致):任何读都拿到最新写入。语义干净,但要跨副本协调,更慢、可用性更脆。
  • Eventual consistency(最终一致):副本最终会收敛,但短时间内可能读到旧值。更快、更可用、更能扩,代价是要容忍“暂时不一致”。

这不是“哪个更好”,而是看数据的角色选挡位。QuoteFlow 里,当前生效的费率表版本要强一致——绝不能两个用户在同一刻拿到来自不同费率表的报价,这在受监管定价里是合规红线;而喂给分析/报表的下游数据,晚几秒收敛完全可以接受,选最终一致换吞吐与可用性。(CAP / PACELC 的完整故事在 Day 12。)

5把维度连起来

这些数字会互相拉扯

关键认知:这五个维度不是各自独立的旋钮,拧高一个常常压低另一个。把昨天“没有最优、只有取舍”这句话,落到具体的张力上:

想要更…常见代价QuoteFlow 里的体现
高吞吐(榨利用率)排队 → 延迟与 p99 恶化把机器用到 95%,实时报价 p99 先崩
强一致更高延迟、可用性更脆费率表跨区强一致 → 写入变慢
高可用(多冗余)成本上升、可能牺牲强一致多区多副本贵,且要接受最终一致
低延迟靠缓存/冗余/就近 → 更复杂、可能读旧值缓存费率表提速,但要处理失效一致性
强可扩展引入分布式复杂度与协调开销分片后,跨片事务与运维都变难

▲ 每一行都是一笔买卖。成熟的设计不是“全都要满分”,而是按业务把预算有意识地投到最该高的那一两个维度,其余够用即可。

所以量化的真正意义,不只是写个好看的 SLA,而是逼出取舍:当你写下“实时报价 p99 < 300ms、99.9% 可用、费率表强一致、夜间百万保单批量重算”,你已经在替自己排优先级——也已经暗示了实时与批量该是两条不同的路径(这正是 Day 17 批处理 vs 流处理要展开的)。把数字写清楚,后面所有架构决策才有了可以对照的标尺。

?今日小测 + 思考题

读完自测一下

Q1某接口平均延迟 80ms,但 p99 是 1.2s。能说“它很快”吗?为什么?
不能。平均被大量快请求拉低,掩盖了长尾:每 100 次就有 1 次要等 1.2s。在大流量或扇出场景下,这条尾巴会被放大成许多用户的真实体感。要看 p99/p99.9,不是 mean。
Q2承诺 99.9% 可用,一年大约允许停机多久?99.99% 呢?
99.9% ≈ 8.77 小时/年(三个 9);99.99% ≈ 52.6 分钟/年(四个 9)。每多一个 9,容许停机减少约一个数量级。
Q3报价顺序依赖三个各 99.9% 的服务,任一挂掉就失败。整体可用性约是多少?如何改善?
串联相乘:0.999³ ≈ 99.7%,比单个还差(掉到三个 9 以下)。改善靠冗余/并联(关键依赖多副本)、减少串联深度、以及降级与缓存兜底,让单点故障不必然拖垮整条链。
带着这两个问题回来讨论

① QuoteFlow 实时报价 p99 要 < 300ms,但费率表偶发缓存未命中会让某些请求飙到 800ms。你会从哪几个角度去压这条尾巴?(提示:缓存、预热、超时与降级、扇出并行……)
② 强一致 vs 最终一致:在 QuoteFlow 的不同部件(实时报价用的当前费率表版本 / 喂给分析下游的数据)分别更适合哪种?各自的理由是什么?

A→Z术语表

今日术语

Percentile (p99)
按耗时排序后,99% 的请求都不超过的那个延迟值;比平均值更能反映体感。
Tail Latency
分布尾部(最慢的少数请求)的延迟;扇出与高负载会将其放大。
Throughput (QPS)
单位时间内系统能处理的请求/数据量,如每秒查询数。
Little's Law
L = λ × W:系统内并发请求数 = 到达速率 × 单请求停留时间。
The Nines
用“几个 9”表达可用性(99.9%=三个 9),可换算成每年允许停机时长。
Error / Latency Budget
把允许的失败或延迟当成一笔预算,分配给路径上各段,用来定位瓶颈与余量。
Horizontal Scaling
scale out:靠增加机器分摊负载来提升吞吐,与纵向加强单机(scale up)相对。
Eventual Consistency
副本最终会收敛,但短时间内可能读到旧值;以一致性换取更低延迟与更高可用。
